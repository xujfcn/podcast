Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we designed overload coordination: multidimensional reservations, deadline-aware queues, fair scheduling, retry budgets, fallback headroom, workload-specific degradation, and distributed admission leases. Today we take the next logical step. If capacity is scarce, who gets to use it? We are designing tenant-aware budgets and fairness for an AI API gateway: service tiers, burst allowances, organizational quotas, and policies that remain predictable when normal traffic turns into an incident.

This is not a billing dashboard with a throttle attached. A tenant budget is a reliability control. It decides how much one customer, team, application, or internal workload may consume before it affects everyone else. Fairness is not necessarily giving every caller the same number of requests. It is protecting a defensible share of scarce capacity while honoring explicit commitments and keeping the system useful when demand exceeds supply.

Start by naming the principal. “Tenant” can mean a paying customer, an organization, a project, an API key, a user, or a workload owned by the platform itself. These identities form a hierarchy, and the hierarchy matters. If a customer has ten API keys, key-level limits alone do not prevent the customer from exceeding its organizational commitment. If a company has several products, product-level fairness may be useful while an organization-wide budget remains the final boundary. Define the hierarchy explicitly instead of letting authentication fields accidentally become the quota model.

A practical hierarchy might be organization, project, application, credential, and end user. Each level can have a limit, a weight, and a policy scope. A project can receive a reservation from its organization, while an application can receive a smaller envelope from the project. The effective budget is the intersection of those ancestors, not the largest allowance found anywhere on the path. This prevents a generous child setting from bypassing a deliberately conservative parent.

Separate identity from entitlement. An API key tells you who is calling. An entitlement policy tells you what that caller is allowed to consume. Keeping the two separate makes plan changes, key rotation, delegated access, and internal service accounts easier to reason about. It also prevents a dangerous shortcut: granting a new credential a fresh quota simply because the quota key changed. Consumption should follow the protected principal, not the easiest string to rotate.

A budget needs more dimensions than requests per minute. Count or estimate input tokens, output tokens, model invocations, concurrent streams, images, audio seconds, tool calls, and spend. Some dimensions are instantaneous, such as active streams. Others accumulate over a time window, such as tokens per minute. Still others are commitments over a billing period. A tenant may have plenty of monthly spend remaining but no safe concurrency headroom right now. Treat each dimension as a separate constraint and make the blocking dimension visible.

Use budgets for both rate and capacity. Rate budgets limit how quickly work arrives. Capacity budgets limit how much work may be active or reserved at once. A token bucket is useful for smoothing bursts, but it does not by itself protect a provider from a hundred long-running streams. A concurrency semaphore protects active work, but it does not stop a tenant from consuming its entire daily token commitment in one short burst. The two controls should cooperate, not substitute for each other.

The basic token bucket remains a useful mental model. Tokens accumulate at a configured refill rate up to a maximum burst size. A request spends tokens according to its estimated cost and waits or fails when the balance is insufficient. For AI traffic, the token in that bucket may represent model tokens rather than HTTP requests. Keep the words distinct: an API request bucket and an inference-token budget have different behavior and different operational meaning.

Estimate cost before admission. Prompt length, requested output cap, model class, image size, audio duration, tool definitions, and expected workflow steps all contribute. A simple request-count quota can be easy to operate, but it systematically favors expensive workloads if every request costs one unit. Use weighted units when the resource is meaningfully different, and reconcile the reservation with actual usage afterward. If a request uses less than reserved, return the remainder according to policy; if it uses more, charge the excess and update the estimation model.

Do not make every cost prediction exact. Exact prediction is impossible for generative output and agentic workflows. The goal is a conservative, explainable reservation. Track an estimate, a maximum allowed amount, and an uncertainty margin. A request can be admitted when its estimated cost fits the budget and its hard maximum does not violate a safety limit. If the maximum is too large, require the caller to lower the cap or use an asynchronous workflow with a separate budget.

Reservation and charging are different events. At admission, reserve capacity so several concurrent requests cannot all spend the same balance. At completion, reconcile actual usage. For a stream, reserve an output allowance and active connection, then settle when usage is known or a bounded hold expires. For a multi-step agent, reserve each next step only when it is about to run. Charging the entire possible workflow at the beginning wastes capacity; charging only after completion allows unlimited speculative concurrency.

Unknown usage deserves a clear policy. A client can disconnect, a provider can omit usage metadata, or a network failure can leave dispatch ambiguous. Keep a pending charge rather than releasing everything immediately. Apply a conservative bounded hold, and reconcile through provider reporting or an operation ledger. If unknown outcomes repeatedly occur for one workload, tighten its budget or require idempotency and asynchronous reconciliation. Otherwise the tenant can appear to have infinite capacity precisely when accounting is least reliable.

Fairness begins with isolation. Reserve a minimum share for each eligible tenant or class, then allow unused share to be borrowed. This is better than a fixed equal partition when tenants have different commitments and traffic patterns. A quiet tenant should not permanently strand its capacity, but a busy tenant should not turn every temporary vacancy into a permanent takeover. Borrowing should be reclaimable, with a defined order for returning capacity when the original owner needs it.

Weighted fair queuing is a strong default for shared capacity. Give each tenant or service tier a weight, track virtual finish time, and choose the next eligible request from the tenant with the smallest finish value. Deficit round robin can be simpler when requests have variable estimated costs: each tenant receives a deficit counter, and expensive work waits until its accumulated credit covers the cost. The important property is not the algorithm's name. It is that service is proportional, bounded, and resistant to one tenant's request volume.

Variable cost creates a subtle fairness problem. If fairness is measured only by request count, a tenant sending tiny prompts may receive the same service as one sending enormous contexts. If fairness is measured only by tokens, a stream-heavy tenant may occupy every connection while appearing within its token share. Choose a primary scarce-resource fairness measure and add caps for other dimensions. A tenant should receive a fair token share without being able to monopolize concurrency, tool execution, or gateway memory.

Service tiers should express commitments, not magical priority. A premium plan might receive a larger guaranteed share, a higher burst ceiling, faster queue treatment, and protected fallback headroom. A standard plan might receive a smaller guarantee and more elastic borrowing. A free or evaluation plan may be best-effort with strict incident shedding. Document exactly what each tier means: minimum share, maximum burst, deadline target, fallback behavior, and degradation options. A label such as “priority” is too vague to be a reliable contract.

Guarantees need a time basis. A tenant might have a guaranteed token rate over a rolling minute and a monthly allowance over a billing period. These are not interchangeable. A tenant that was quiet for six hours should not necessarily bank six hours of unused inference capacity and release it as a massive burst. Define whether credits accumulate, expire, or are capped. Burst policy is a product decision with infrastructure consequences, so make it explicit and test it under correlated demand.

Bursts are useful when bounded. They let a deployment absorb a release, a news event, or a user spike without making the normal rate artificially high. But an unbounded burst is merely a queue hidden inside a quota. Set a maximum burst size by resource dimension and workload class. Long-context requests may receive fewer burst credits than short interactive calls because their reservations are larger and less predictable. If the burst is exhausted, return a stable quota response or queue only when the remaining deadline makes waiting useful.

Organizational budgets should account for shared responsibility. If a company has multiple projects, a project-level quota prevents one product from dominating, while the organization-level quota prevents the portfolio from exceeding its commitment. Add an internal platform reserve for incident response, security workflows, and operational automation. That reserve must be visible and bounded. “Internal” should not mean unlimited, because an internal batch job can harm customer traffic just as effectively as an external tenant.

Use separate budgets for interactive and batch work. Interactive calls have deadlines and user-visible latency. Batch jobs are often more tolerant of queueing and can consume off-peak headroom. If both share one unclassified budget, an overnight evaluation can spend the tokens needed for daytime chat, or interactive retries can starve a useful background queue. Let tenants allocate a portion of their entitlement between classes, with safe defaults and limits on how quickly allocations can change during an incident.

Do not let priority become a quota bypass. A premium request can be scheduled ahead of best-effort work, but it still needs an available provider route, an authorized model, a valid safety decision, and a reservation that fits the tenant's hard budget. A high service tier should not permit infinite retries or unlimited tool side effects. When a tenant is over its hard commitment, the correct response is to queue, degrade, or reject according to policy—not to rename the request “urgent.”

Fairness also applies during fallback. When the primary provider is constrained, a naive controller can send the largest or most aggressive tenant to every fallback route. Reserve fallback capacity by service tier and, where appropriate, by organization. A tenant that is entitled to premium continuity may receive protected fallback share, but that share should be sized against the actual contract and incident scenarios. Do not promise failover that the gateway has not reserved or tested.

Fallback compatibility can change fairness calculations. A tenant's request may require a particular region, context length, model family, or data-handling policy. Another tenant may have many more eligible routes. If both are judged against one global queue, the constrained tenant appears unfairly expensive. Track fairness within eligibility domains, and expose when a request's effective capacity is limited by policy. Fairness cannot mean equal access to a route a tenant is forbidden to use.

Shared quotas need atomic accounting. If multiple gateway instances decrement a tenant balance independently, a burst can overspend before the replicas converge. Use a strongly consistent quota service, partitioned counters with bounded oversubscription, or leases for capacity slices. The chosen design should state its failure behavior. When the coordinator is unavailable, it is usually safer to admit only within a conservative local reserve than to let every instance continue spending the same global balance.

A quota lease should identify the principal, budget dimension, amount, scope, expiration, policy version, and fencing token. The worker must verify that the lease is current before dispatch and renew it only under defined conditions. When an entitlement changes, a new generation invalidates old leases. This avoids stale workers continuing to send requests after an administrator has reduced a tenant's emergency ceiling. It also gives the decision ledger a precise answer to “which policy authorized this work?”

Concurrency budgets require ownership cleanup. A client can cancel, a process can crash, or a stream can end without a clean close. Every active slot needs a lease and expiry, with heartbeats for long-lived streams. Reclaiming a stale slot too quickly can create duplicate work; reclaiming it too slowly can freeze the tenant. Use provider operation IDs and idempotency keys where possible, and distinguish a confirmed cancellation from an unknown downstream state.

Retries should spend the tenant's budget. If the first attempt consumes an output reservation, a second attempt needs a new reservation, even when the gateway suspects a transient provider failure. Otherwise an overloaded tenant can multiply its effective share during exactly the incident when capacity is scarce. Maintain retry budgets per tenant, workload class, route, and incident. Carry the original deadline and cap the total attempt cost. A retry is new work from the capacity controller's perspective, even if it is the same business operation.

Side effects make retries harder. A tool call may have completed even if the model response was lost. For an unknown tool outcome, do not automatically replay just because the tenant has remaining quota. Reconcile the operation, require an idempotency key, or route the workflow into a recovery state. Quota enforcement and side-effect safety are linked: a budget should not reward unsafe replay, and an idempotency ledger should not be bypassed by a fresh credential.

For streaming APIs, make admission decisions before opening the stream. A rejected stream should be a normal typed error, not a connection that hangs until the client times out. Once accepted, enforce the concurrency lease and output budget during the stream. If the budget is approaching its hard ceiling, finish at a contractually valid boundary or send a defined limit event. Never silently cut a structured response in the middle of a tool argument and call it success.

Graceful degradation can preserve fairness by reducing cost. Offer a lower output cap, a smaller model, a cached answer, fewer optional enrichments, or a delayed batch job. These modes must be authorized by the tenant or by a documented service-tier policy. Record the selected mode in response metadata and the decision ledger. A request that was “served” only because the gateway silently changed its semantics should not count as a successful reliability outcome.

Budget policy should be versioned. When a customer moves plans, a project changes allocation, or an incident activates emergency shedding, attach a policy version to every reservation. Keep the prior version available long enough to explain decisions made during the transition. Avoid changing refill rates, weights, and burst ceilings independently without a transaction or effective timestamp. Partial policy rollout is a common source of apparent unfairness: two gateway instances can evaluate the same request differently.

Policy changes also need hysteresis. If a tenant repeatedly crosses a threshold by a small amount, rapidly opening and closing access creates oscillation and a poor client experience. Use separate engage and release thresholds, minimum hold times, and a bounded grace period. Grace is not free capacity; reserve it explicitly. A short overage window may be a useful product feature, but it should be charged, capped, and visible rather than emerging accidentally from race conditions.

Measure fairness over meaningful windows. A five-second slice can make a fair controller look unfair during a burst, while a monthly average can hide a tenant being starved during every business hour. Track short-term service, rolling-hour usage, and longer commitment fulfillment. Compare delivered useful work with entitlement, not just admitted request count. Include deadline success, queue age, fallback use, degradation, rejected work, and cost by tenant and class.

Manual overrides must be narrow and expiring. An operator may grant a temporary burst, pause one project, reserve capacity for a security response, or move a tenant to a tested degradation mode. Each override needs an owner, reason, scope, policy version, and automatic expiration. Avoid editing a global quota table under pressure without recording why. Emergency controls should make the system more predictable, not create a second invisible policy layer.

Test fairness with adversarial workloads. Simulate one tenant creating many keys, another sending huge prompts, a third opening long streams, and a fourth retrying every timeout. Add correlated provider failure, coordinator partitions, clock skew, cancellations, and policy changes during active reservations. Ask whether any tenant can multiply its share through identity rotation, retries, queue placement, or an unknown-outcome loophole. The test passes when excess demand is contained and the reason is explainable.

Replay historical traffic with privacy-safe shapes. Compare equal-share, weighted, reservation-based, and tiered policies against useful work completed, deadline success, queue age, provider utilization, fallback reserve, cost, and rejected volume. Include counterfactuals: what would happen if one large tenant doubled its traffic, if a provider lost half its quota, or if a premium tenant's eligible fallback set shrank to one route? A policy that looks efficient in average traffic may fail badly under one realistic incident.

The most important design choice is the order of protection. During overload, a typical policy might protect safety and security operations, then contractually guaranteed interactive service, then ordinary interactive traffic, then batch and speculative work. Within each class, share capacity according to entitlement and fair scheduling. The exact order belongs to the product, but it must be written down before an incident. If the order exists only in an operator's intuition, it will change with every stressful decision.

There is a useful symmetry with the previous two episodes. Controlled reinstatement asks whether a provider has earned exposure. Overload coordination asks whether the system can safely grant that exposure. Tenant-aware fairness asks which principal may consume the exposure that remains. Health, capacity, entitlement, fairness, deadline, and side-effect risk meet in one admission decision. Ignoring any one of them turns a clean policy into a loophole.

A mature AI API gateway therefore resolves tenants through an explicit hierarchy, measures budgets across rate and capacity dimensions, reserves before dispatch, reconciles actual usage, schedules by weighted fair share, bounds bursts, protects fallback headroom, charges retries, isolates interactive and batch work, versions policy, and records every decision. It allows unused capacity to be borrowed without making borrowing permanent. It honors service commitments without treating priority as a safety bypass. And when demand exceeds supply, it fails in a way clients can understand.

The goal is not perfect equality. Perfect equality can be wasteful, and it can ignore promises customers intentionally purchased. The goal is predictable fairness: every principal knows its entitlement, every exception has a boundary, every burst has a cost, and every scarce resource has an owner. That is what lets a gateway remain useful during a spike without turning one tenant's success into everyone else's outage.
