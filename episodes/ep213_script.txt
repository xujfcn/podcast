EP213: AI API Gateway State Machines - Make Request Lifecycles Explicit

Welcome back to AI Dev Tools, the Crazyrouter podcast. Today we are talking about state machines for AI API gateway requests. A request is not simply pending and then done. It can be admitted, queued, routed, retried, streamed, cancelled, accepted, rejected, or left indeterminate. When those transitions exist only in scattered conditionals, operators cannot explain what happened and clients cannot make reliable decisions.

The first step is to define a small lifecycle vocabulary. A logical operation might move from received to admitted, from admitted to dispatched, and from dispatched to producing. It can then reach accepted, rejected, cancelled, failed, or indeterminate. Provider attempts need their own states because one logical operation may contain several attempts. Keep the logical operation and provider attempt identifiers distinct so a retry does not look like a new user request.

Every state should have an owner, an entry condition, an exit condition, and a bounded set of legal next states. Received means the gateway has parsed an identifiable request. Admitted means policy and capacity checks passed. Dispatched means an attempt was sent to a provider. Accepted means the response satisfied the request contract, not merely that the socket closed. These definitions turn vague log messages into testable behavior.

State transitions should be monotonic where possible. A request that has reached accepted must never later become retryable because a delayed provider record arrived. A cancelled operation should not return to producing merely because a buffered token was received. If reconciliation changes billing or evidence, record a new fact without rewriting the already committed user-visible outcome.

Use explicit transition guards for deadlines and cancellation. A queued request may be cancelled before dispatch. An in-flight stream may enter cancelling and then cancelled after resources are released. A deadline can produce a timeout outcome even when the provider eventually sends data. The gateway must decide which event wins according to a documented ordering rule, otherwise race conditions will produce contradictory client behavior.

Provider attempts deserve careful isolation. An attempt can be connecting, active, draining, succeeded, failed, or abandoned. When a provider times out, mark the attempt as failed or indeterminate according to the evidence available, then decide whether the logical operation may try another route. Do not let a late callback from an old attempt mutate the state of a newer attempt. Compare attempt identifiers at every asynchronous boundary.

Streaming makes state design visible. Before the commit point, content is provisional and the operation is producing. The gateway should move to accepted only after the terminal event arrives and final validation passes. If the connection closes early, choose rejected or indeterminate based on the contract and evidence. A client may display provisional text, but it should still receive a clear terminal outcome event.

Queues also need lifecycle states. Waiting, reserved, dispatched, and expired are not interchangeable. Reserve capacity only when the request is actually ready to run, and release that reservation on every terminal path. A queue timeout should not be counted as a provider error, while a provider rejection should not be hidden as ordinary queue churn. These distinctions make capacity metrics and customer explanations much more useful.

Retries should operate on transition policy, not on exceptions alone. A rejected structured response may permit one new attempt. A completed content filter result may be terminal. A cancellation from the client should normally stop further work. For each transition, define whether retry is allowed, what budget it consumes, and whether the logical request identifier stays stable. This prevents accidental retry storms and duplicate side effects.

Tool calls add another lifecycle boundary. The gateway may accept a tool proposal while execution remains pending approval or delegated to a separate executor. Proposal accepted does not mean side effect completed. Model the execution identifier separately, enforce idempotency for side effects, and make a tool execution failure visible without pretending that the original model response was invalid.

Persistence matters whenever a process can restart. You do not need to store every token to recover a useful state machine, but you do need durable operation identity, the latest committed state, attempt summaries, and enough evidence to distinguish accepted from indeterminate. Write terminal state with an idempotency key so a worker retry cannot create two completion records or two charges.

An event log is often more valuable than a mutable status column alone. Record state changes with timestamp, actor, operation identifier, attempt identifier, reason code, and a redacted evidence summary. Materialize the current state for fast reads, but preserve the event history for incident analysis. This lets an operator answer whether a request was queued, which provider was tried, why fallback occurred, and when acceptance was committed.

Do not expose internal complexity as an unstable client API. The client needs a predictable outcome model: accepted, rejected, cancelled, failed, or indeterminate, plus a stable operation identifier and actionable reason. Internal states such as draining or reconciling can remain in diagnostics. For streaming, define the terminal event and make SDKs surface it directly instead of equating end-of-stream with success.

Observability should follow transitions. Measure time spent in admission, queueing, connecting, producing, validation, and reconciliation. Count illegal transitions, stale callbacks, abandoned attempts, terminal-state rewrites, and operations stuck beyond their expected maximum age. A latency histogram without lifecycle context cannot tell you whether time was spent waiting for capacity or waiting for a slow provider.

Alerts should target stuck and contradictory states. An increasing number of producing operations beyond their deadline indicates cancellation or provider cleanup trouble. A growing indeterminate population indicates missing terminal evidence. Any accepted operation that later receives a rejection event is a correctness incident even if the customer did not notice. These alerts are more precise than watching HTTP five hundred rates alone.

Testing should exercise races, not only the happy path. Deliver a provider response after a deadline. Cancel immediately before dispatch. Duplicate a terminal event. Retry while a previous attempt sends a late callback. Restart after writing an attempt result but before committing the logical outcome. Verify that the state machine chooses one legal result, releases resources exactly once, and preserves the evidence needed to explain it.

Property-based tests are useful for transition logic. Generate sequences of provider events, client cancellations, timer events, and worker restarts, then assert invariants: no transition leaves a terminal state, no attempt can commit another attempt's result, reservations are eventually released, and accepted results satisfy their contract. This finds combinations that hand-written examples often miss.

The practical checklist is straightforward. Define logical and attempt lifecycles separately. Give every state legal transitions and explicit guards. Make deadlines and cancellation deterministic. Treat streaming commit as a real transition. Keep queue, provider, validation, and tool execution outcomes distinct. Persist terminal evidence with idempotency. Expose a stable client outcome model. Measure time and errors by state, and test event races aggressively.

The larger lesson is that an AI API gateway is a distributed system with a request lifecycle, not a single function call. Explicit state machines make retries, cancellation, streaming, fallback, billing, and recovery easier to reason about. They also give developers a trustworthy answer to the most important question: what happened to my request, and is the result safe to use?
