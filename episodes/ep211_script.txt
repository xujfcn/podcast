EP211: AI API Gateway Cancellation Contracts - Stop Work When the User Leaves

Welcome back to AI Dev Tools, the Crazyrouter podcast. Today we are talking about cancellation contracts for AI API gateways. A user closes a browser tab, an application abandons a request after its deadline, or an agent decides that a tool result is no longer needed. The visible request is over, but the expensive work behind it may still be running. A reliable gateway needs a precise answer to a basic question: when the caller stops waiting, what exactly stops next?

Cancellation is not just a client convenience. It is a resource control mechanism. An abandoned generation can continue consuming provider concurrency, tokens, network buffers, and application memory. At low traffic, that waste is easy to ignore. During a burst or an incident, orphaned work can occupy the capacity needed by requests whose users are still present. The gateway should treat cancellation as part of the request lifecycle, not as an incidental socket error.

Begin by separating three signals that applications often collapse. A deadline says the result is no longer useful after a known time. Explicit cancellation says the caller no longer wants the operation, even if time remains. A transport disconnect says the connection disappeared, but it may not prove that the logical operation should stop. Mobile clients reconnect, proxies reset streams, and asynchronous jobs intentionally outlive the request that created them. The public contract must state which signal controls which kind of operation.

For synchronous completion APIs, the usual default is simple: when the client cancels or its deadline expires, the gateway should stop waiting, cancel queued work, and attempt to cancel any active provider request. The important word is attempt. Some providers expose a real cancellation operation, some stop when the HTTP connection closes, and some continue generation internally. The gateway must not promise that remote computation ended unless it has evidence. It can promise that it stopped forwarding output and released its own resources.

Propagation has to begin before provider execution. If a request is still in an admission queue, cancellation should remove it without consuming a provider slot. If routing is evaluating several candidates, those checks should share the same cancellation context. If a request has already opened a provider stream, closing the downstream response should trigger upstream cleanup immediately. Every asynchronous boundary needs a listener, and every listener needs an owner that removes it when the operation completes.

Deadlines should travel as absolute timestamps or remaining budgets, not as a fresh timeout at every hop. If the client has twelve seconds remaining, the gateway must not give an adapter thirty more seconds, and the adapter must not reset the clock when it opens a stream. Reserve a small cleanup margin so the gateway can close connections and record the outcome before the caller's deadline. A chain of locally reasonable timeouts can otherwise create globally abandoned work.

Streaming makes cancellation visible and measurable. The gateway may have delivered hundreds of tokens before the user presses stop. That is a successful partial delivery followed by cancellation, not a generic server failure. Record time to first token, delivered tokens, generated tokens when known, and the point where cancellation was observed. Do not convert a deliberate stop into an error banner if the product experience treats partial output as useful.

Tool calls require a stricter contract because cancellation cannot reverse the world. Once a tool has sent an email, placed an order, or changed a record, closing the model stream does not undo that side effect. Separate cancel from compensate. The gateway can stop future model and tool steps, but completed or ambiguous actions need durable state and a reconciliation path. Return an operation identifier so the application can inspect what happened after the interactive request ended.

Asynchronous jobs need the opposite default from synchronous calls. The submission connection may close while the job should continue. Give those jobs an explicit cancel endpoint, a stable operation state, and clear transitions such as queued, running, cancel requested, cancelled, completed, and cancellation failed. Make cancel idempotent. Repeating the same cancel command should return the current state rather than create a second control operation or hide a result that already completed.

Provider adapters should expose capability, not pretend uniformity. One adapter may support hard cancellation with confirmation. Another may support connection close with an unknown remote outcome. A third may not support cancellation at all. Normalize these into honest states such as cancelled locally, cancellation requested upstream, confirmed upstream, or outcome unknown. Routing policy can prefer cancellable providers for interactive workloads without claiming that every provider behaves identically.

Billing needs the same honesty. A caller may owe for tokens generated before cancellation, tokens delivered before cancellation, or the provider's entire completed request, depending on the upstream contract. The gateway should record estimated usage immediately and reconcile it when final provider usage arrives. Do not label a cancelled request as free merely because no final response reached the client. Expose a stable usage status so developers can distinguish final, estimated, and pending charges.

Cancellation races are normal, so define them deliberately. Completion and cancellation can arrive within the same millisecond. Use one authoritative operation state machine and make terminal transitions atomic. If completion wins, return the completed result when the contract allows it. If cancellation wins, suppress later output but retain provider evidence for billing and diagnosis. Never let two workers publish conflicting terminal states for the same logical operation.

Test cancellation at every boundary. Cancel while queued, during provider connection setup, before the first token, after partial output, during a tool call, and as the final provider event arrives. Test a provider that ignores connection close and one that confirms cancellation. Verify that concurrency permits return, buffers drain, listeners disappear, and operation state remains consistent. A test that only checks the client received a cancelled exception misses most of the reliability risk.

Observability should reveal how much abandoned work the system prevents. Measure cancel requests, time from client signal to gateway observation, time to local resource release, upstream cancellation confirmation, tokens generated after cancellation, and cost awaiting reconciliation. Track orphaned work by provider and adapter version. A rising gap between client cancellation and provider termination can explain capacity loss long before ordinary error rates change.

The developer interface should remain small. Support standard cancellation primitives in each SDK, accept explicit deadlines, document whether disconnect implies cancel, and provide operation identifiers for work that may outlive the connection. Return a stable cancellation reason and an outcome field that says whether upstream termination was confirmed. Developers need enough information to design their workflow without learning the gateway's internal topology.

The practical checklist is direct. Distinguish deadlines, explicit cancellation, and disconnects. Propagate one remaining time budget through queues and adapters. Release local resources promptly. Model provider cancellation capability honestly. Treat partial streams as partial outcomes. Never imply that cancellation reversed a tool side effect. Keep asynchronous cancellation explicit and idempotent. Reconcile usage after uncertain remote completion. Test races, and measure work that continues after users leave.

The larger lesson is that request termination is a distributed protocol. A cancelled user interface does not automatically cancel a queue entry, a provider generation, a tool action, or a charge. A gateway becomes more reliable when it connects those layers with an explicit lifecycle and reports uncertainty instead of hiding it. That saves capacity, reduces surprise cost, and gives developers behavior they can build around.
