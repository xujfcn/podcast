EP207: AI API Gateway SDK Design - Make Reliability the Default

Welcome back to AI Dev Tools - The Crazyrouter Podcast. Today we are talking about a part of an AI API gateway that developers touch every day but teams often treat as packaging: the SDK. A gateway can have excellent infrastructure and still create unreliable applications if its client library makes the happy path easy and the safe path optional. The goal of a good SDK is to make sound behavior the default while keeping important decisions visible and controllable.

This episode is about developer reliability. It is different from testing provider compatibility. Compatibility asks whether a route behaves according to a defined interface. SDK design asks whether a developer can use that interface safely under deadlines, disconnects, retries, and changing traffic.

Start with the request lifecycle. A typical call has a caller deadline, a gateway queue, an upstream provider request, a response stream, and sometimes a tool action after the model responds. If the SDK exposes only a single request function, these stages become invisible. Developers then set a giant timeout, retry every exception, or leave streams running after a browser tab closes. Give the lifecycle names in the API: connect timeout, total deadline, stream read timeout, cancellation, and completion.

Deadlines should be explicit and finite. A client should not wait forever because a provider connection is half-open or a response stream has stopped producing events. Set a sensible default total timeout, allow a per-request override, and make the override part of the request context so it appears in logs. Distinguish a deadline exceeded before the provider accepted work from one after generation started. Those outcomes have different retry and billing implications.

Avoid saying timeout equals failure. A streaming client may receive useful partial text before the deadline. The SDK should tell the application whether the stream ended normally, was cancelled locally, or stopped because the deadline expired. Return accumulated usage and the provider request identifier when available. Do not pretend partial output is complete, but do not throw away useful evidence either. A typed result can make completion state impossible to ignore.

Retries need to be narrow, bounded, and tied to error category. Connection failures before request acceptance may be retryable. A rate limit may be retryable after the server-provided delay. A malformed request, authentication failure, policy refusal, or unsupported capability is not fixed by sending it again. Stable exception types or result codes are far better than asking developers to parse provider-specific strings.

Never retry an active stream as if it were a fresh unary request. If a client disconnects after several tokens, a second request can duplicate work, cost, and possibly a tool action. For non-streaming calls, an idempotency key can make a bounded retry safe when the gateway stores the outcome. For streaming, offer resume only when the protocol and provider support a real continuation. Otherwise report the incomplete stream clearly and let the application decide.

Backoff should be bounded by the caller deadline. A policy that sleeps for ten seconds when one second remains is wasteful. Calculate each delay from remaining time, apply jitter, and stop when the retry budget or deadline is exhausted. Expose retry count and final reason in error context. Developers should be able to tell whether a request was slow because the model was slow, because the SDK waited between attempts, or because the gateway queued it.

The SDK should carry request identity from application code to the final provider event. Generate a request ID when the caller does not supply one, preserve a caller correlation ID, and return both in response metadata. A retry should have an attempt ID while retaining the parent request ID. This makes logs searchable without confusing one logical operation with several upstream attempts, and it lets support teams match a report to traces without requesting sensitive prompts.

Error messages should work at two levels. The human-readable message should say what happened and what action is reasonable. Machine-readable fields should include category, retryability, request ID, attempt count, safe route information, and whether the provider may have accepted work. Keep raw provider details in diagnostic metadata, but do not force application code to depend on a provider error format.

Design the error taxonomy around ownership and action. Client errors belong to the caller: invalid messages, unknown model, oversized payload, or unsupported option. Gateway errors may require configuration or operator action: no eligible route, queue rejection, or normalization failure. Provider errors may be transient or permanent. Policy errors require a change in input or authorization. A generic APIError class encourages unsafe catch-and-retry code; a precise hierarchy enables deliberate behavior.

Streaming deserves a first-class SDK surface. Offer an async iterator or equivalent that handles event parsing, keep-alives, terminal markers, and connection closure. Make cancellation composable with the host runtime: an AbortSignal in JavaScript, a cancellation token elsewhere, or the native context mechanism in a server framework. When cancellation happens, send it upstream promptly and close the local connection deterministically. The application should not need to know which HTTP client method releases a socket.

Be careful with convenience helpers. A method named complete should not silently buffer an unbounded stream into memory. A method named create should not automatically retry after the model may have called a tool. A helper that converts a response to text should preserve whether the response was truncated, refused, or interrupted. Convenience is valuable when it removes plumbing, but dangerous when it removes information needed for a correct decision.

Request builders are another reliability boundary. Validate required fields locally, enforce maximum sizes before uploading large payloads, and reject contradictory options early. A builder can warn when a streaming request uses a timeout intended only for connection setup. It can require an explicit policy for tool-enabled workflows. These checks do not replace server validation; they prevent obvious mistakes from becoming billable upstream work.

Safe defaults should be workload-aware. Interactive chat needs a short time to first token and responsive cancellation. Batch summarization needs a longer deadline, durable retries, and progress tracking. A tool-using agent needs strict idempotency and approval boundaries. One universal default cannot optimize all three. Let the SDK expose named profiles as starting points, then show resolved values in request metadata. Profiles should be ordinary configuration, not magic hidden in separate products.

Observability must be easy without logging private content. The SDK can emit metrics for request count, retry count, time to first token, completion time, cancellation latency, and response state. It can attach trace context and safe dimensions such as model alias, route class, status category, and SDK version. It should never require full prompts or generated text just to understand reliability. Provide hooks for redacted events and let the application choose additional evidence.

A good SDK also protects budgets. Token limits and output limits should be explicit. Retries should count against a request retry budget and, where configured, a tenant budget. Expose estimated and actual usage separately because estimates can be wrong, especially when a provider reports usage only at the end of a stream. When a request is cancelled, make usage state clear: unknown, partial, or finalized. This prevents cost dashboards from being built on false precision.

Versioning needs to include behavior, not only package numbers. When a release changes default timeouts, retryable statuses, stream parsing, or error classes, document it as a behavioral change. Include SDK version in user-agent and telemetry. Keep compatibility shims for a reasonable migration window, and let teams opt into new defaults before they become the next major release. A package upgrade should be reviewable as an operational change.

Test the SDK at its boundaries. Use a local fake gateway to simulate slow headers, partial streams, disconnects, duplicate events, rate limits, malformed JSON, and cancellation races. Verify that resources are closed and retries stop at the deadline. Test every supported runtime's cancellation mechanism. These tests do not prove provider quality, but they prove that the library preserves the lifecycle guarantees developers rely on.

Documentation should show failure paths beside the first successful request. Give developers short examples for setting a deadline, handling a typed rate-limit error, consuming a stream, and cancelling work. Explain what may have happened when a timeout arrives. Include the request ID in support examples. A quickstart that omits these details optimizes only for the first five minutes; a dependable SDK helps during the first production incident too.

The practical checklist is straightforward. Make deadlines finite and visible. Keep retries bounded, jittered, and error-aware. Never replay active streams blindly. Propagate request identity and safe telemetry. Use typed errors that explain ownership and retryability. Make cancellation native. Validate requests locally without hiding server rules. Offer workload-aware profiles, explicit budget controls, and behavioral release notes. Test slow and interrupted paths as seriously as successful paths.

The larger lesson is that an SDK is part of the reliability architecture. Developers express intent through a few lines of code, and the library decides how that intent meets networks, queues, providers, and disconnects. When safe behavior requires custom middleware in every application, reliability becomes optional and uneven. When the SDK makes the right boundary visible and the safe choice easy, teams spend less time rediscovering failure modes and more time building useful products.
