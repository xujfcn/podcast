Welcome to AI Dev Tools, the Crazyrouter Podcast. This is episode five hundred eighty-four. Today: backpressure for AI gateways. Admit only work you can finish. Yesterday we discussed cancellation: what happens after a user stops waiting. Today we move one step earlier. Why did we accept more work than we could serve in the first place? A gateway can have healthy servers, working providers, and no obvious errors, yet still deliver an awful experience because every request is waiting behind too much other work. The solution is not an infinite queue. It is a clear admission contract, bounded waiting, and feedback that reaches the caller before resources run out.

Imagine a fictional coding assistant gateway. It has capacity for forty simultaneous generations on one route. Under ordinary traffic, each generation occupies a slot for about five seconds. As a rough steady-state illustration, forty divided by five is eight completions per second. Now the provider slows down and requests take twenty seconds. With the same forty slots, the rough completion rate falls to two per second. Your incoming traffic is still six per second. A queue absorbs the difference for a while, but it grows by roughly four requests every second. Autoscaling the gateway does not automatically create more provider capacity. And if callers retry while waiting, the queue grows even faster. These are illustrative averages, not a sizing guarantee; production workloads have variable lengths, bursts, and long tails.

Start by separating three controls that are often mixed together. A rate limit controls how quickly work may arrive, such as requests or tokens per minute. A concurrency limit controls how much work may be active at once. A queue limit controls how much accepted work may wait. You need all three, because none substitutes for the others. A tenant can remain inside its request rate limit while opening many long-lived streams. A concurrency limit can protect the provider but leave an unbounded pile of waiting tasks in gateway memory. A small queue can prevent memory exhaustion while still allowing a single tenant to consume every active slot. Write down the resource each control protects before choosing its number.

Admission should happen before expensive work begins. Authenticate the caller, apply a small bounded parsing budget, validate the request shape, and classify the workload. Then ask whether the gateway has the resources and time to make a credible attempt. Do not download a huge document, run retrieval, and construct a giant prompt before discovering that the generation queue is full. Bound request bodies and preprocessing concurrency independently. For model work, use more than request count when the workload calls for it. Input size, requested output cap, model route, and stream lifetime can all affect capacity. Predictions will be imperfect, so use conservative reservations and reconcile actual usage rather than treating an estimate as a promise.

Make waiting deadline-aware. Suppose a request has four seconds left before its end-to-end deadline. The queue currently estimates three seconds of waiting, and a useful response usually needs another three. Accepting that request may just manufacture a timeout. Reject it or offer a different, explicitly supported service class. Do not silently switch to a less capable model or convert synchronous work into an asynchronous job. Queue-time estimates are uncertain, so expose them as estimates and apply safety margins appropriate to the service objective. Recheck the deadline when dequeuing. A request that was feasible at admission can become stale while waiting. Removing expired work before provider dispatch saves money and protects useful traffic.

A practical queue needs at least three bounds: item count, retained bytes, and maximum age. Ten waiting requests might be tiny chat prompts or ten enormous document contexts. Counting only items misses that difference. Keep queue metadata compact and put large payloads in controlled storage when the architecture requires it, with authorization and retention limits. Do not move the unbounded queue into a database and declare the problem solved. Storage, scanning, polling, and eventual execution still cost resources. For interactive traffic, a short queue often gives a better outcome than a long one: a quick, explicit overload response lets the application respond honestly instead of showing a spinner until the deadline expires.

Now separate admission permits from execution permits. A queue reservation says you may wait; it does not say a provider slot is already occupied. At dispatch, acquire the execution resources you need and release the queue reservation exactly once. If acquisition fails, follow an explicit bounded policy rather than spinning in a tight retry loop. Avoid holding one scarce permit indefinitely while waiting for another. That can produce deadlock or a convoy where otherwise usable capacity sits idle. A central scheduler can allocate a compatible set of resources together. Simpler designs can use a fixed acquisition order with short bounded waits and rollback. In either case, cancellation and timeout paths must release ownership safely.

There is an important connection to yesterday's cancellation episode. Releasing a local socket does not prove that remote generation stopped. Track local connection capacity separately from estimated provider work still in flight. If an upstream request has an uncertain terminal state, retain a bounded accounting reservation or quarantine allowance until completion evidence, cancellation confirmation, or a documented conservative expiry rule resolves it. Do not hold a local worker forever, and do not pretend the upstream work disappeared. Otherwise the gateway can admit replacement calls into apparently free slots while abandoned generations continue consuming the provider's real capacity. Good backpressure requires truthful accounting, not just fast cleanup.

Streaming adds another boundary: the client may read more slowly than the model generates. Picture a mobile browser on a poor connection. If your gateway keeps reading upstream and appending every chunk to an unlimited application buffer, one slow client can hold megabytes of memory, and thousands can exhaust the process. Put explicit byte limits and stall timers on each stream, plus a global buffer budget. Await downstream writes where the framework provides flow control. But remember that transport-level flow control does not guarantee that the model itself pauses computation or billing. Some providers may continue generating behind their own buffers. Treat pausing a socket and pausing inference as different capabilities.

When a stream reaches its high-water mark, stop reading upstream where supported and start a bounded stall policy. Resume only after the buffer drains below a lower threshold, so the system does not rapidly oscillate between pause and resume. If the client stays stalled, cancel upstream where possible, terminate the stream using the protocol's documented failure semantics, and reconcile any uncertain usage. Once response headers have been sent, you cannot replace the response with a new HTTP status code. You also must not emit a normal completion marker for truncated output. A connection closing unexpectedly is not a successful answer. Never discard arbitrary token chunks just to make room: that can corrupt text, structured output, or tool-call arguments.

Fairness is the next layer. A global limit protects infrastructure; it does not protect tenants from each other. Use per-tenant queue bounds and a scheduler that makes service classes explicit. Separate interactive requests from large background jobs when their latency goals differ. Weighted scheduling can reserve more service for a contracted class while still providing a minimum share to others. Bound priority and authorize it server-side; a client-supplied urgent flag is not a capacity entitlement. If you estimate job cost, also watch estimation errors. A tenant that continually requests a small output cap and then launches many follow-up calls can still dominate capacity at the logical-operation level. Monitor fairness across both requests and complete workflows.

Return overload signals that describe what the caller can do. A tenant quota exhaustion commonly maps to HTTP four twenty-nine. Temporary service-wide overload may map to five oh three. Choose and document a consistent API contract instead of exposing whichever upstream status happened last. Include a stable machine-readable reason and a request identifier without leaking other tenants' activity. Send Retry-After when you have meaningful guidance, but do not promise an exact recovery time you cannot know. Clients should respect that guidance, use jittered backoff, and stay inside the original deadline and retry budget. Internal retries and fallback attempts must pass admission too. A fallback is not free capacity, especially when every gateway sends its overflow to the same backup.

Measure the entire funnel: offered, admitted, queued, dispatched, completed, rejected, expired, and cancelled. Report queue age and wait-time percentiles, active execution permits, buffered bytes, slow-consumer terminations, and work that continues after local cancellation. Measure useful completions within deadline, not merely accepted requests. If you only graph latency for successful calls, aggressive rejection can make the service look magically faster while users experience an outage. Conversely, a controlled increase in early rejections can be the right tradeoff if it preserves critical work and reduces wasted provider spend. Evaluate that tradeoff by tenant and service class, with the denominator visible.

Before shipping, run an overload exercise with an open-loop load generator: keep the offered arrival rate independent of response speed. A closed-loop test that waits for each response before sending another can hide queue collapse by slowing itself down. Mix short and long generations, pause selected downstream readers, reduce provider throughput, and trigger retries. Assert that queue bytes and age stay bounded, expired requests never dispatch, permits do not leak, and one noisy tenant cannot starve the rest. Then remove the overload and measure recovery. The queue should drain without a retry storm, and the controller should not instantly jump back to an unsafe concurrency limit. If you use adaptive limits, bound their range and change rate; start with simple static limits until your measurements are trustworthy.

Here is the implementation checklist. Name each constrained resource. Bound its active work and waiting work separately. Admit with the remaining deadline in mind. Make permit transitions cancellation-safe. Apply streaming backpressure with byte limits and explicit failure semantics. Enforce tenant fairness. Give callers honest overload guidance. Finally, test recovery as carefully as rejection. Cancellation tells the system when to stop work that is no longer useful. Backpressure prevents the system from promising work it cannot reasonably finish. Together with deadlines and retry budgets, they turn an AI gateway from a request forwarding pipe into a controlled execution boundary. This has been AI Dev Tools, the Crazyrouter Podcast.
