Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we examined evidence availability reconciliation. We learned how to correct customer-facing records after retention expiry, provider migration, deletion, and late corrections without inventing proof. Today we move one level earlier in the control chain. A policy can be perfectly designed and still fail if one region, worker, cache, or provider adapter runs a different version. A policy change can be reviewed in one control-plane service, approved in another, and enforced by executors that never received the intended artifact. Our topic is policy distribution and regional consistency: keep every gateway on the same rules, prove which rules are active, and prevent a partial rollout from becoming a protection gap.

Imagine a gateway policy that says sensitive documents may be sent only to providers in Singapore. The policy is updated to add a second approved region after a contract review. The control plane publishes version 42. Region A receives it immediately. Region B is offline and continues enforcing version 41. A routing cache in Region C holds version 40, while one worker has a locally bundled fallback policy from version 39. The system now has four answers to the same authorization question. All services are healthy, all requests are authenticated, and every decision may look locally reasonable. Yet the platform no longer has one policy. It has a distributed disagreement about what authority means.

Start with policy identity. Every policy artifact needs a stable policy ID, semantic version, content digest, schema version, author, reviewer, approval record, effective time, expiration or supersession information, dependencies, and target scope. The digest must cover the exact normalized artifact that evaluators consume, not merely a source file or deployment package. Record tenant, region, operation class, data classification, provider scope, and enforcement stage. A human-friendly name is not enough. When an incident happens, the gateway must prove which exact rules a worker evaluated.

Separate source, compiled artifact, and runtime snapshot. The source policy is authored and reviewed. A compiler validates it and produces an executable artifact. A runtime snapshot activates that artifact in a region or worker. These objects need linked identities and independent integrity checks. A successful source review does not prove that compilation preserved meaning. A valid compiled artifact does not prove that every worker activated it. The policy chain should show source digest, compiler version, artifact digest, activation receipt, and runtime observation.

Treat policy publication as a transaction with visible stages. Typical states include drafted, validated, reviewed, approved, scheduled, distributing, partially active, active, superseded, rolled back, and retired. A policy should not be called active merely because the control plane stored it. Define activation criteria across all required regions, workers, caches, and adapters. If partial activation is allowed, expose the exact scope and block operations that require global consistency. A status label such as “deployed” is dangerous when it means “accepted by one service.”

Build a signed distribution manifest. The manifest should list the intended policy artifact, target regions, target worker classes, required dependencies, effective time, minimum evaluator version, rollout mode, and rollback reference. Sign or otherwise authenticate the manifest so executors can verify that the artifact came from the approved control plane. Include a sequence number or epoch to prevent an old manifest from arriving after a newer one and being accepted. Workers should reject artifacts that are validly signed but outside their target scope, expired, incompatible, or superseded.

Use pull and push together. Push distribution gives low latency and can announce a new policy to every region. Pull reconciliation lets workers recover after disconnects and detect missed updates. Neither is sufficient alone. A push can be lost, and a pull can accept a stale endpoint if it lacks version checks. Workers should periodically report the active digest and fetch the intended artifact when their state lags. The control plane should compare desired state with observed state and make drift visible. Distribution is complete only when observation converges, not when a message was sent.

Policy epochs prevent mixed decisions. Assign a monotonically increasing epoch to each activation set. A request evaluated under epoch 42 should carry that epoch through routing, provider selection, tool authorization, retention assignment, and billing obligations. If a downstream executor sees an older epoch, it can reject the handoff, request refresh, or apply a documented compatibility rule. Without an epoch, different hops may claim to have used “version 42” while actually using different dependencies or compiled semantics.

Decide where consistency is required. Strong global consistency for every policy can harm availability and latency. Eventual consistency for a data-residency or tool-safety rule can create unacceptable risk. Classify policies by consequence. Low-risk ranking preferences may tolerate a short propagation window. Authorization, residency, credential scope, deletion holds, and irreversible tool controls may require a quorum, a regional barrier, or fail-closed behavior until the intended version is active. Consistency is not a universal setting; it is an obligation attached to the risk of disagreement.

Use policy bundles for related changes. A routing rule may depend on provider capability facts, pricing maps, region definitions, tenant entitlements, and evaluator code. Publishing the rule without its compatible dependencies can produce a policy that is syntactically valid but semantically incomplete. A bundle should identify every dependency, version range, digest, and compatibility condition. Activation should verify the bundle as a unit. If one dependency is missing, keep the prior safe bundle or enter a bounded degraded state. Never silently substitute the newest available dependency.

Schema compatibility must be explicit. A new policy schema may add a field, change default behavior, or alter the meaning of an empty list. Older workers may parse the artifact while interpreting it incorrectly. Define schema versions, required evaluator versions, backward-compatibility rules, and migration behavior. Test unknown fields, missing fields, null values, enum changes, and default values. A parser accepting an artifact is not proof that the evaluator preserves policy meaning. Reject incompatible combinations before activation.

Compilation correctness needs semantic tests. Compile representative policies and compare the executable evaluator against a reference implementation or decision corpus. Test allow, deny, obligation, exception, conflict, missing-data, and timeout paths. Include policy invariants such as “riskier inputs never gain authority,” “unverified residency never authorizes sensitive routing,” and “a revoked credential cannot become valid through cache refresh.” Store compiler version, test corpus version, and result digest with the artifact. Optimization is safe only when it preserves the decisions and obligations that matter.

Regional consistency requires more than matching digests. Two workers may run the same artifact but use different clocks, capability facts, provider catalogs, keys, or tenant configuration. Record relevant inputs and their freshness. A region should attest to policy digest, evaluator version, dependency digests, clock status, key set, and capability snapshot. If a dependency is stale, the region may need to block only affected operations. A green policy digest with an expired provider fact is not full consistency.

Control-plane and data-plane roles should be distinct. The control plane authors, validates, approves, and distributes policy. The data plane evaluates and enforces it. A worker should not invent a missing rule because the control plane is unavailable. It may continue using a previously approved snapshot within a defined continuity window, provided the snapshot is not expired or revoked. For high-risk policies, absence of fresh control-plane confirmation may require fail-closed behavior. Continuity is a bounded safety mode, not permission to run indefinitely on whatever was last cached.

Policy freshness should be checked at decision time. Cache entries need policy epoch, creation time, expiry, invalidation reason, and dependency watermark. A cached allow decision may be valid for one operation but unsafe for another. Authorization caches should bind decisions to tenant, actor, operation, data class, provider, region, and relevant purpose. If any bound context changes, reevaluate. A cache should never turn a historical allow into permanent authority. Policy distribution and decision caching are separate systems that must share invalidation semantics.

Revocation needs priority propagation. A new permissive policy can wait for ordinary convergence, but a revocation or emergency deny may need an expedited path. Define emergency epochs, push fan-out, local deny lists, cache invalidation, credential revocation, and acknowledgment deadlines. Workers that miss the emergency update should prove isolation or stop affected operations. Do not assume that a later normal publication will eventually correct a dangerous stale allow. Safety-critical negative authority should have an independent, short path.

A rollback is another policy publication. Restoring an earlier artifact can reopen a vulnerability or re-enable a provider that was quarantined. Require a rollback reason, scope, approver, compatibility check, and expiration. The rollback must receive a new publication ID and epoch even if it reuses an old artifact digest. Downstream services need to distinguish “old artifact deployed again” from “the earlier decision continues unchanged.” Preserve the incident context that caused the rollback and define which obligations are inherited or changed.

Partial rollout must be visible to callers. If Region A runs epoch 42 and Region B runs epoch 41, the gateway should not present a single global status that hides the split. Routing may direct a tenant to a region with the required epoch, or the gateway may reject a request whose policy requires convergence. Include policy epoch and region in operation receipts. Customer support and auditors need to know whether an operation was evaluated during a transition window. A hidden rollout boundary is an accountability defect.

Migration windows need compatibility rules. During a controlled transition, old and new evaluators may coexist. Define which decisions can be made under either version, which require the new version, and which must stop until all dependencies align. If an operation begins under epoch 41 and crosses into a worker on epoch 42, carry the original decision and recheck obligations that changed. Do not blindly reauthorize the operation under the new rules, and do not blindly trust the old decision after its context has changed. Use explicit handoff semantics.

Provider adapters are policy executors too. An adapter can translate a gateway decision into provider parameters, region selection, logging flags, safety settings, or tool restrictions. If the adapter is stale, the worker may claim to enforce a current policy while sending an incompatible request. Include adapter version and configuration digest in the policy bundle. Test that the adapter actually applies each obligation. A policy saying “do not retain content” is incomplete if the adapter still enables provider logging by default.

Key and trust-root rotation can create false consistency. A worker may have the current policy digest but an old signing key, or it may accept an artifact signed by a retired authority. Bind policy activation to trust-root version and key status. Publish key changes with overlap, expiry, and revocation behavior. Test clock skew and certificate rotation. A policy artifact is not trustworthy merely because its bytes match; the authority that approved it and the key that authenticated it must also be valid for the activation time.

Tenant overrides require isolation. A global policy may allow a provider, while a tenant policy forbids it due to residency or contract terms. Store the inheritance chain, override digest, precedence rules, and effective result. Distribute tenant-specific snapshots only to authorized workers and avoid leaking one tenant’s rules through shared caches. When the global policy changes, identify which tenant projections are affected. A worker that updates its global snapshot but misses a tenant override can create a subtle policy gap.

Policy obligations must travel with decisions. An allow result may carry obligations such as redact fields, use region X, disable retention, limit output, validate schema Y, or require human review before tool execution. Distribution consistency includes these obligations, not only the allow or deny bit. A downstream service that receives “allowed” without the obligation set may enforce an incomplete decision. Use signed decision receipts with policy epoch, obligation digest, context binding, and expiry. Executors should reject a handoff when required obligations are missing.

Monitor convergence and drift. Useful signals include desired-versus-observed digest mismatch, worker acknowledgment latency, stale snapshot age, partial-region duration, evaluator version skew, dependency freshness, rejected artifact count, emergency revocation propagation time, cache invalidation lag, policy decision disagreement, and rollback frequency. Break these down by region, worker class, tenant, operation, and policy risk class. Averages can hide one stale worker handling a sensitive tenant. Alert on the worst relevant boundary, not only the platform median.

Run consistency probes continuously. Submit synthetic decisions that should produce the same result in every region, using the same policy epoch and controlled inputs. Probe allow, deny, obligation, missing dependency, expired snapshot, stale capability, and revoked credential cases. Compare decision receipts, not just HTTP status. If a region produces a different result, quarantine the affected policy class and investigate artifact, evaluator, dependency, clock, or configuration drift. Synthetic probes should exercise the real distribution and enforcement path.

Test failure and race conditions. Publish a new policy while a region is offline. Deliver updates out of order. Restart a worker between activation and acknowledgment. Expire a dependency after the policy digest converges. Revoke authority while a cached allow is being consumed. Rotate keys during rollout. Roll back after some regions activate the new policy. Let a provider adapter reject one obligation. Restore an old snapshot from backup. Verify that unsafe work is blocked, safe continuity is bounded, receipts remain explainable, and the system never reports global activation when only a subset converged.

Incident response needs a policy timeline. When a decision is disputed, reconstruct source approval, compilation, distribution, activation, cache use, dependency facts, and enforcement at each hop. Preserve observed acknowledgments and missing acknowledgments. If a region was stale, identify the operations evaluated there. If a rollback occurred, link it to the incident and affected epochs. The policy timeline should support both impact analysis and customer explanation. “The policy was deployed” is not enough; the question is which artifact actually enforced the decision.

Retirement is part of distribution governance. When a policy is superseded, revoke old manifests, invalidate caches, stop accepting old epochs, and remove artifacts from workers and staging stores according to retention rules. Keep a minimal retirement receipt with artifact digest, scope, time, verification, and unresolved exceptions. An old policy sitting on disk is not automatically dangerous if it cannot be activated, but the system should prove that it is unreachable. Retirement must close both the control-plane record and the data-plane execution path.

The deeper lesson is that policy is a distributed dependency, not a document. Its meaning depends on source, compiler, evaluator, runtime inputs, caches, keys, adapters, tenant overrides, and regional activation. A safe gateway makes every link visible and versioned. It knows the difference between desired state and observed state, between a valid artifact and an active artifact, and between a matching digest and a matching decision. It treats disagreement as a control condition, not as an inconvenient deployment detail.
