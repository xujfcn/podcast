Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. Today we’re continuing our series on trustworthy AI API gateways with a problem that appears after you have good provenance and replay: how do you know that a change is safe before it reaches production? The answer is not a larger test suite by itself. It is semantic contract testing: defining what a gateway must preserve, guarantee, reject, and explain across providers, adapters, policies, and versions.

A gateway sits between an application and a rapidly changing model ecosystem. Clients speak one API shape, while providers expose different capabilities, error formats, token accounting, streaming conventions, safety controls, and tool semantics. The gateway promises to translate between those worlds without changing the meaning of an allowed request. That promise is a contract.

Many teams treat an API contract as a list of endpoints and JSON fields. That is necessary, but incomplete. A client does not care only that a field exists. It cares whether a denied request remains denied, whether a tool call is authorized before execution, whether a stream terminates correctly, whether usage accounting is honest, and whether a retry can duplicate an external action. Semantic contract testing checks those behavioral promises.

This matters because a gateway can be syntactically correct and semantically wrong. It can return valid JSON while silently dropping a system instruction. It can map a provider’s refusal into a generic server error. It can retry a request that was not safe to retry. It can report a successful completion while truncating the final stream event. None of these failures are caught by validating that the response parses.

Start by separating three layers of contract. The first is the wire contract: methods, paths, headers, schemas, status codes, streaming frames, and content types. The second is the semantic contract: what the request means, which policy decisions must hold, and how provider differences are normalized. The third is the operational contract: latency expectations, budget limits, rate behavior, observability, and recovery guarantees.

Do not let the wire schema become a substitute for the semantic contract. A schema can say that a message has a role and content, but it cannot say that the gateway must preserve the ordering of messages, reject an unauthorized tool, or avoid exposing a provider-specific internal field. Those rules belong in explicit invariants that can be tested and reviewed.

An invariant is a statement that should remain true across an entire class of executions. For example: a request classified as restricted data is never routed to a provider outside its approved region. A tool call is never executed without a successful authorization decision. A response marked complete is not emitted before the gateway has observed the provider’s terminal signal. A retry does not occur after a non-idempotent side effect has started.

Write invariants in a form that an automated harness can evaluate. “Preserve safety” is an aspiration. “If the request contains a restricted data label, every provider invocation carries an approved-region attribute and the selected provider is in that region” is testable. Include the trigger, the required condition, and the evidence needed to prove the condition.

Connect every contract assertion to the provenance model from the previous episode. A failed semantic test should identify the contract version, policy generation, adapter build, provider fixture, and normalization rules involved. This turns a red test from a vague regression into a precise claim about which promise changed and under which artifacts.

Contract tests need a stable vocabulary for outcomes. Define categories such as accepted, rejected, transformed, retried, partially completed, provider-failed, and gateway-failed. Include whether a response is authoritative, provisional, or simulated. If one adapter calls a provider refusal a successful HTTP response while another calls it an error, the semantic layer should still expose a consistent meaning to clients.

Avoid asserting that every provider must behave identically. Providers differ, and pretending otherwise creates brittle tests or misleading compatibility. Instead, define the gateway’s compatibility boundary. Some capabilities are required and portable. Some are optional and must be advertised. Some are provider-specific extensions that may pass through only when the client explicitly opts in.

Build a capability matrix, but test behavior rather than labels alone. A catalog may say that a model supports structured output, vision, parallel tools, or a long context. The contract test should send representative requests and verify the actual behavior: accepted constraints, preserved structure, correct refusal, or a clear unsupported-capability response.

A capability claim has at least four states: supported, unsupported, unknown, and temporarily unavailable. Do not collapse unknown into supported. If the catalog is stale or the provider has not been probed, route conservatively or expose uncertainty. A false positive can produce invalid output or an unsafe action; a false negative usually produces a visible limitation that can be investigated.

Use consumer-driven contracts for client expectations. A client team should be able to say, “I require streamed deltas, a stable finish reason, usage when available, and no silent fallback across data regions.” The gateway team then runs those expectations against every adapter and deployment candidate. This prevents the central contract from being designed only around the implementation’s current convenience.

Also use provider-facing contracts for adapters. An adapter should declare how it maps messages, tools, response formats, usage, errors, and streaming events. Test the mapping in both directions where possible. If the gateway sends a canonical tool schema and the provider returns a tool call, verify that names, argument encoding, and ordering survive the round trip.

Round-trip testing is powerful but easy to misuse. If you serialize a request into provider format and deserialize it back, equality does not always mean correctness. Some transformations are intentionally lossy, such as removing unsupported optional fields. Define semantic equivalence explicitly. The round trip should preserve the fields that affect authorization, meaning, and client behavior, while making permitted loss visible.

Canonicalization is part of the contract. JSON object ordering may not matter semantically, but message order does. Unicode normalization, whitespace, null values, numeric precision, and timestamp formats can matter unexpectedly. Document which representations are normalized and which are preserved. Fingerprint the canonical form for comparison, while retaining an original reference when exact recovery is allowed.

Test negative space aggressively. A robust contract is defined not only by what the gateway accepts, but by what it must refuse. Include malformed tool arguments, unknown model names, unsupported modalities, over-budget requests, expired credentials, invalid tenant bindings, region conflicts, prompt-size overflow, and provider responses that violate the adapter contract.

Negative tests should verify the boundary, not just the status code. Check that no provider call was made when admission failed. Check that sensitive data did not enter an unauthorized trace. Check that the error does not disclose an internal policy or secret. Check that retries, fallbacks, and side effects are absent unless the contract explicitly permits them.

Treat failure semantics as first-class. A provider timeout, a provider rate limit, an invalid provider response, and a gateway policy denial are not interchangeable. Clients may decide whether to retry, degrade, notify a user, or ask for approval based on the category. Define stable error classes, machine-readable reason codes, and safe human messages.

Do not promise that an error code will never evolve. Promise compatibility rules instead. For example, reason-code families may remain stable while additional detail fields are added. Deprecated codes can map to a canonical class. Contract tests should cover backward compatibility for clients that understand the stable subset.

Streaming requires its own contract suite. A non-streaming test cannot prove that a stream is correct. Verify event ordering, identifiers, incremental content, tool-call fragments, usage timing, cancellation, keep-alives, terminal events, and connection closure. Test a provider that emits an error after partial content and confirm that the client receives an unambiguous terminal state.

Be precise about partial output. If a model emits text and then fails, the gateway should not silently label the result complete. It may return a partial response, an interrupted stream, or a structured error, but the client must be able to distinguish those states. Preserve the distinction in usage accounting and provenance as well.

Test cancellation and deadlines as semantic behavior. When a client cancels, the gateway may need to cancel the provider request, stop reading the stream, and prevent post-completion transformations. When a deadline expires, a late provider response must not be delivered as if it were on time. Race tests should cover cancellation arriving before admission, during provider invocation, during a retry decision, and immediately before a side effect.

Retries deserve special attention. The contract must define idempotency, not merely configure a retry count. A request can be technically identical yet unsafe to repeat because a provider started a tool action or charged an external resource. Carry an idempotency key through the gateway and adapter where the provider supports it. If safe deduplication cannot be proven, do not retry automatically.

Test fallback as a policy decision, not as a networking trick. A fallback may violate region, cost, capability, privacy, or model-quality constraints. The contract should specify which dimensions are invariant during fallback and which may change. If a fallback changes model family or output guarantees, make that visible to the client and record it in the decision envelope.

Provider mocks are useful, but happy-path mocks can hide the hardest failures. Build adversarial fixtures that reorder stream frames, duplicate terminal events, omit usage, return malformed JSON, change an error schema, exceed declared latency, or close the connection mid-tool-call. An adapter is trustworthy only if it responds predictably to provider behavior outside the ideal path.

Use recorded provider fixtures for deterministic regression tests, but do not confuse fixtures with reality. A fixture captures one behavior at one time. Pair it with live compatibility probes in a controlled environment and with schema or capability monitoring. When a live probe differs, preserve the old fixture and create a new version rather than overwriting history.

Property-based testing can explore combinations that humans rarely enumerate. Generate message sequences, optional fields, tool definitions, policy labels, provider outcomes, and cancellation points within defined constraints. Then assert properties such as no unauthorized invocation, stable canonicalization, bounded output, and valid terminal state. Shrink failing cases to the smallest reproducible example.

Metamorphic testing is especially useful when exact outputs are nondeterministic. Change an irrelevant JSON field order and expect the same decision. Add an allowed metadata field and expect the same routing. Duplicate an idempotency-safe read request and expect equivalent side-effect behavior. Change the tenant region and expect the route or denial to change according to policy. These relations test meaning rather than a single answer.

For AI systems, avoid exact-text assertions unless text itself is the contract. Models can phrase equivalent answers differently. Test structural and policy properties: valid JSON, required keys, citation references, tool authorization, refusal categories, maximum length, data classification, and absence of forbidden content. Where quality matters, use calibrated evaluators with thresholds, review samples, and an escalation path for ambiguous cases.

An evaluator is another component that needs a contract. Record evaluator version, rubric, model, temperature or sampling settings, and confidence. A quality score without its evaluator lineage is not reproducible evidence. Do not let an automatic judge silently become the production authority for safety or billing decisions without explicit governance.

Differential testing compares two implementations on the same normalized corpus. Compare an adapter build against its predecessor, a provider against a reference provider, or a new policy engine against a shadow implementation. Differences are signals, not automatically failures. Classify them as expected improvement, expected incompatibility, regression, or unresolved divergence.

Use a semantic diff report. Instead of saying that two JSON responses differ, explain that the finish reason changed from complete to length, the tool argument key disappeared, the usage count increased, or the route crossed a region boundary. Link each difference to the invariant that accepted or rejected it. This makes review faster and less dependent on staring at raw payloads.

Test configuration and policy transitions, not just steady states. During rollout, replicas may use different generations. A contract test should exercise mixed-version conditions and verify the allowed compatibility window. If a new policy requires a field that old replicas cannot interpret, the rollout must be blocked or staged through a compatible intermediate version.

This is where activation provenance and semantic testing meet. A candidate artifact can pass tests in isolation yet fail when combined with the policy, model catalog, or adapter version actually active in a region. Test the deployment bundle: gateway build, policy generation, capability snapshot, feature flags, secrets interface, and observability schema. The unit of safety is often the combination, not the container image.

Give tests realistic observability assertions. A contract is not fully satisfied if the behavior is correct but impossible to investigate. Verify that every consequential decision has a correlation identifier, stable reason code, artifact references, latency measurements, and a redacted evidence trail. Make sure denied requests do not vanish from metrics and successful requests do not hide fallback or retry behavior.

At the same time, do not assert that logs contain raw sensitive content. Test for the presence of references, classifications, and digests rather than prompts or credentials. A good observability contract proves that an operator can investigate without turning the telemetry system into a second data lake of secrets.

Establish gates with different strengths. Fast unit and property tests run on every change. Adapter contract tests run for each provider integration. Deployment-bundle tests run before activation. Shadow traffic and canary probes validate behavior in production-like conditions. Post-activation monitors watch invariants continuously. No single gate should carry the entire burden.

A canary should measure semantic health, not only HTTP success. Track policy-denial consistency, fallback rates, stream termination correctness, tool authorization outcomes, usage-accounting discrepancies, and provider-specific error translation. A release that lowers latency while increasing silent partial streams is not healthy.

Define automatic rollback carefully. Roll back when an invariant breach is clear, such as unauthorized routing, malformed terminal events, or duplicated side effects. For quality drift or evaluator disagreement, quarantine, reduce traffic, or require review rather than oscillating between versions. Rollback itself is a change and should produce provenance with the trigger, evidence, and resulting activation.

Keep contract tests readable by humans. The best test name tells an operational story: “restricted requests never fall back outside the approved region after provider timeout.” Include a short rationale and links to the policy or incident that motivated it. Tests are executable documentation, but only if someone can understand what failure would mean.

Do not allow the test corpus to become a graveyard of historical quirks. Review contracts for relevance, ownership, and expiry. When a behavior is intentionally changed, update the contract through an approved compatibility process and preserve the old test fixture as historical evidence if it helps explain past incidents.

A practical implementation can start small. Choose one high-consequence path, such as chat completion with tools. Define ten invariants: authorization before invocation, region preservation, canonical message ordering, safe retry behavior, valid stream termination, stable error classes, usage accounting, redacted provenance, idempotency enforcement, and no real side effects in replay. Build fixtures for success, denial, timeout, malformed response, partial stream, and tool approval.

Then run the same corpus through three modes. In conformance mode, verify the current adapter against the gateway contract. In differential mode, compare a candidate build with the active build. In replay mode, use historical decision envelopes and provider fixtures to ensure that the explanation remains faithful. Report missing evidence and intentional differences instead of hiding them behind a green checkmark.

Measure the tests themselves. Track coverage by invariant, provider, capability, error class, rollout state, and data classification. Line coverage can be useful, but it does not tell you whether every critical boundary was exercised. A gateway may have ninety percent code coverage and zero tests for cancellation during a non-idempotent tool call.

The deeper principle is that compatibility is a managed promise. A gateway is not successful because it accepts many requests. It is successful when clients can rely on stable meanings while providers, policies, models, and implementations evolve. Semantic contract testing makes that promise explicit, executable, and connected to evidence.

When a contract test fails, resist the urge to patch the assertion until the build turns green. Ask what changed: the client expectation, the provider behavior, the adapter mapping, the policy, the capability claim, or the test fixture. Decide whether the difference is a bug, a documented incompatibility, or a new behavior that needs a new contract. Preserve the decision and its evidence.

And remember the boundary between explanation and guarantee. A passing test is evidence that a defined scenario satisfied a defined invariant. It is not proof that every possible prompt, provider response, race, or deployment combination is safe. State the coverage, the assumptions, the unknowns, and the conditions under which the result remains valid.

The architecture we want is straightforward to describe. Clients depend on a stable semantic contract. Adapters translate provider-specific behavior under explicit mappings. Policies constrain routing, data, tools, and retries. Contract tests exercise positive, negative, adversarial, streaming, transition, and side-effect boundaries. Provenance records which versions and evidence produced each result. Monitoring checks the same invariants after activation.

That combination changes the operational question. Instead of asking, “Did the deployment return 200?” we can ask, “Did it preserve the meaning we promised, under the artifacts we approved, with evidence we can replay?” That is the level of confidence an AI API gateway needs.
