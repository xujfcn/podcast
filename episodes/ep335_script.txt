Today we’re talking about response delivery confirmation at the AI API gateway: how to distinguish model completion, gateway persistence, client receipt, and application acknowledgment so a lost response does not become duplicate work or unexplained billing.

An HTTP success is not always a user-visible success. The provider may finish generation while the gateway connection fails. The gateway may persist the result while the client times out. A streaming client may receive most tokens but miss the final event. Each state matters for recovery and accounting.

Start with an explicit response state machine. Track accepted, executing, provider completed, gateway received, persisted, delivery started, delivery completed, client acknowledged, expired, and failed states. Do not collapse provider completion and client delivery into one boolean called success.

Give every operation and result a stable identity. Include tenant, request, attempt, response version, and delivery channel. A reconnect or polling request should retrieve the same result rather than start a second inference. Idempotency applies to result retrieval as well as creation.

Persist before claiming durable success. If a provider result is important, write it to durable storage before acknowledging completion to the client. Verify checksum, content length, schema, and artifact references. A memory buffer or open socket is not a durable record.

Separate result persistence from delivery. The gateway can store a result even when delivery fails. Clients should be able to query operation status and retrieve an authorized persisted result without forcing another provider call. Retrieval authorization must be checked again at read time.

Define acknowledgment semantics. A transport acknowledgment may mean bytes reached a TCP stack. An application acknowledgment may mean the client parsed and stored the result. A business acknowledgment may mean downstream work accepted it. Choose which level the API promises and name it precisely.

Make non-streaming responses retryable. If the client times out after the model completed, a status endpoint or idempotent GET should reveal whether a result exists. Do not ask the client to guess whether it is safe to resend the original generation request.

Design streaming termination carefully. Emit a clear final event containing operation ID, response ID, usage when available, finish reason, and integrity information. Distinguish normal completion, provider error, gateway cancellation, client disconnect, and truncated stream. A missing final event should trigger reconciliation, not automatic duplicate generation.

Support resumable delivery where useful. A client can request a response from a known sequence or byte offset when the result format supports it. Validate response version, checksum, sequence continuity, and authorization. Never replay a partial stream as though it were a fresh response without marking the boundary.

Handle backpressure and slow clients. Persist or buffer within bounded limits, then choose whether to pause provider work, spill to storage, or terminate delivery. A slow consumer must not hold unlimited memory or keep expensive model generation running forever.

Connect cancellation to state. A client cancel request may stop delivery, provider generation, both, or neither depending on the operation phase. Record who canceled, when, and which side effects had already occurred. Cancellation after provider completion does not erase a result that was already generated or billed.

Keep delivery channels consistent. Polling, webhook, SSE, WebSocket, and batch download should expose compatible operation and result identities. A webhook retry and a polling request must converge on one result. Channel-specific formatting can differ, but lifecycle semantics should not.

Secure webhooks and callbacks. Sign event identity, timestamp, payload digest, and delivery attempt. Use short replay windows, endpoint authorization, and a unique event ID. Record delivery response codes without logging secrets or full sensitive results. A callback URL is not permission to disclose every artifact in the operation.

Make webhook delivery retry-safe. Retry transient failures with bounded exponential backoff, preserve event ordering where required, and stop after a defined policy. The receiver must deduplicate by event ID. Do not retry permanent authorization or schema failures indefinitely.

Preserve ordering selectively. Tokens, tool-call fragments, and state transitions may require sequence numbers. Independent notifications can be parallel. Document whether ordering is per operation, session, tenant, or channel. A global delivery queue creates unnecessary blocking and still does not guarantee client processing order.

Verify before release. Check response schema, tool-call structure, artifact access, usage metadata, and policy state before delivering. If validation fails after provider completion, retain the evidence and return a typed delivery or acceptance error. Do not claim the model failed when the gateway rejected its response.

Protect result access. Bind status and download permissions to tenant, operation, response version, and expiration. Use short-lived URLs for artifacts and re-check policy when refreshing them. A client that once had access may lose it before retrieving a delayed result.

Define retention and expiry. Keep pending results long enough for the documented recovery window, then expire them with an observable state. Distinguish result expiry from deletion, legal hold, and billing retention. Tell clients whether a missing result can be recovered, regenerated, or is permanently unavailable.

Reconcile unknown outcomes. When the connection to a provider or client breaks, query provider status, inspect durable gateway records, and compare usage evidence before retrying. An unknown provider outcome is not proof of failure. A duplicate attempt may create duplicate model usage and conflicting responses.

Make billing stateful. Record provider completion, actual usage, response persistence, delivery attempts, and any refund or adjustment separately. A client timeout should not automatically mean no charge, and a successful client receipt should not hide a provider-side usage discrepancy.

Expose safe status information. Clients need operation ID, lifecycle state, retry guidance, result availability, expiry, and possibly a trace reference. Avoid exposing provider credentials, internal topology, sensitive policy text, or another tenant’s metadata. Status should help recovery without becoming an information leak.

Test delivery races. Cover provider completion during client timeout, persistence failure after provider success, disconnect before final stream event, webhook duplication, out-of-order events, polling during persistence, cancellation during delivery, expired result retrieval, revoked access, partial artifact download, schema rejection, provider usage uncertainty, retry after unknown outcome, and concurrent acknowledgments.

Measure delivery reliability. Track provider-to-gateway completion, persistence latency, delivery latency, final-event loss, reconnect success, webhook retry and deduplication, acknowledgment rate, expired retrievals, unknown outcomes, duplicate generations, result validation failures, storage backlog, and billing reconciliation gaps. The meaningful success rate is the percentage of authorized operations whose result reached the promised confirmation point.

The practical pattern is this: model explicit states, assign stable identities, persist before durable acknowledgment, separate storage from delivery, define confirmation levels, make retrieval idempotent, terminate streams clearly, support bounded resume, control slow clients, connect cancellation to state, unify channels, secure callbacks, retry safely, preserve only necessary ordering, validate before release, scope access, define expiry, reconcile unknown outcomes, separate billing events, expose useful status, test races, and measure the promised confirmation point. Reliable delivery means every party can tell what completed, what was stored, what was received, and what still needs action.
