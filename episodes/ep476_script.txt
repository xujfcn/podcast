Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we designed policy distribution and regional consistency: publish signed immutable bundles, activate complete artifacts, gate decisions on freshness, fence stale writers, and preserve a receipt for every consequential decision. Today we move to the next layer of trust. We are designing provider contracts and capability negotiation: how an AI gateway can determine whether a model endpoint is actually compatible with a request, instead of trusting an optimistic model name, a marketing label, or an undocumented assumption.

An AI gateway is often described as a router that chooses between providers. That description is too shallow for production. The gateway is a compatibility broker. It receives a request with requirements, inspects the capabilities and constraints of candidate endpoints, selects a route whose contract fits, and then preserves evidence that the route behaved as promised. A provider may advertise a model that supports tools, structured output, long context, streaming, or vision. The difficult question is not whether a feature exists in a brochure. It is whether this exact endpoint, account, region, API version, and request mode support the feature with defined semantics.

Start by separating identity from capability. A model identifier tells us what a provider calls an endpoint. It does not tell us its context limit, tokenizer behavior, supported input modalities, tool semantics, output guarantees, retention policy, rate limits, or failure modes. The same model family may appear behind several provider adapters with different limits and different interpretations of the request schema. A capability record should therefore include provider identity, endpoint identity, model identity, API version, region, account or tenancy boundary, and the observation time. Names are useful for humans; identities and versions are what enforcement can trust.

Define a canonical capability vocabulary inside the gateway. Use explicit fields for input modalities such as text, image, audio, and video. Describe output modalities separately. Represent context capacity in tokens or another declared unit, with a tokenizer identifier and a maximum that includes system messages, tools, and generated output where applicable. Record whether streaming is supported, whether usage arrives in stream events, whether structured output is schema-constrained or merely prompted, and whether tool calls are native, emulated, or unsupported. An absent field must not silently mean supported. Unknown capability is different from a negative capability.

Capabilities have levels, not just booleans. A provider may accept JSON but not enforce a JSON Schema. It may accept tool declarations but return arguments without validation. It may stream text but not stream tool-call deltas. It may support images only through URLs, while another endpoint accepts base64 data. Model these distinctions as enumerated modes with definitions. For example, structured output could be unsupported, best-effort JSON, grammar-constrained JSON, or schema-constrained with a documented refusal behavior. Route requirements should name the minimum level they need.

The contract should describe semantics as well as syntax. A successful HTTP response does not prove that the provider honored the requested temperature, stop sequence, seed, tool choice, or response format. A streaming endpoint might send a final usage event, omit it, or report estimated usage. A tool-capable endpoint might return a tool call in one message shape and a provider error in another. Capture these behaviors in a contract that the adapter can normalize and that tests can verify. If semantics are unknown, expose that uncertainty to the router rather than laundering it into a clean-looking internal object.

Provider contracts must be versioned and signed like policy bundles. Include a contract identifier, sequence number, content digest, issuer, schema version, source evidence, and effective interval. Record whether a value came from provider documentation, an authenticated capability API, a controlled probe, an observed production response, or an operator override. Evidence sources have different confidence levels. A documentation statement may describe a family, while a probe demonstrates behavior for one account and region. The router should be able to require a minimum confidence for high-risk features.

Do not confuse a contract with a permanent truth. Capabilities change. Providers add or remove models, alter context limits, introduce new tool semantics, move endpoints, change retention terms, or impose temporary rate limits. A contract needs freshness metadata and an expiration or revalidation policy. The gateway should know which fields may be stale within a bounded window and which require current confirmation. A stale display label is harmless; a stale claim that prompts are not retained can be a privacy incident.

Capability negotiation begins by extracting requirements from the request. The request may explicitly ask for vision, a 128K context window, schema-constrained output, a named tool, parallel tool calls, streaming, low latency, or a particular model family. Requirements also come from tenant policy, endpoint defaults, application metadata, and the operation lifecycle. A privacy policy may prohibit a provider without a contractual retention guarantee. A residency policy may require a region-specific endpoint. A quota policy may disallow a route whose concurrency lease is exhausted. The candidate set is the intersection of all these requirements.

Normalize requirements before routing. Convert aliases into canonical feature names, normalize units, expand implicit needs, and attach hardness. A hard requirement means that a candidate failing it cannot be selected. A preference affects ranking but may be sacrificed under a documented fallback. “Supports tools” is usually too vague; the requirement might be native tool calls, a specific tool schema version, serial execution only, or parallel calls with stable identifiers. Make the normalized requirement visible in the decision receipt so a later investigation can explain why an apparently capable provider was excluded.

Compatibility is directional. The client request has a required contract, and the provider advertises an offered contract. The question is whether the offered contract satisfies the required one, not whether the two labels match. A request for JSON Schema level three may be compatible with a provider offering level four, but not with level one. A request for 100,000 input tokens and 4,000 output tokens may not fit an endpoint with a 128,000 total context window once tools and system instructions are included. Compatibility evaluation must calculate the actual envelope, not compare an advertised headline number.

Make the envelope calculation explicit. Let the request budget include system content, conversation content, tool definitions, tool results that will be sent back, requested output, and provider-specific framing overhead. Use the declared tokenizer where possible, and apply a conservative margin where tokenization is uncertain. If the gateway cannot compute the envelope reliably, it should lower confidence or reject a route that requires a hard limit. A provider response error after admission is too late: the gateway has already spent latency, quota, and perhaps a retry budget.

Tool contracts deserve their own negotiation. A tool declaration has a name, description, argument schema, execution policy, and lifecycle. The provider may support strict schema validation, loose argument generation, tool choice control, parallel calls, partial streaming, and explicit cancellation at different levels. The gateway should translate a canonical tool contract into the provider adapter’s request shape, then validate the response before any tool executes. If arguments fail the schema, treat that as a compatibility or model-output failure, not as permission to execute a best guess.

Never let an adapter silently downgrade a hard requirement. It is reasonable to emulate a feature when the caller has opted into emulation and the risk is understood. For example, a gateway might implement structured-output validation after generation, or simulate a tool loop around a text-only endpoint. But an emulated feature has different latency, failure, and security properties. Mark it as emulated in the capability result, include the adapter version, and require a policy-approved fallback mode. A caller that requires provider-enforced schema output must not receive a prompt-only approximation because a field was ignored.

The same rule applies to streaming. Streaming is not just an HTTP transfer mode. It defines when the operation is admitted, how partial output is represented, how cancellations are propagated, when usage is known, and whether a tool call can begin before the final message. A provider that supports text streaming but not reliable cancellation should not satisfy a requirement for bounded-cost interactive streaming. The contract should identify event ordering, terminal events, retry safety, and whether partial content can be replayed or resumed.

Error behavior is part of compatibility. A provider may return authentication errors, quota errors, invalid-request errors, overload signals, content refusals, transient transport failures, or ambiguous timeouts. Normalize these into a gateway taxonomy without losing the original provider code. The contract should state which errors are retryable, whether retrying can duplicate a tool call, whether a timeout means the provider may still be processing, and whether an idempotency key is honored. Route selection must consider this behavior because a nominally capable endpoint with unsafe retry semantics may be unsuitable for an operation that permits only one execution.

Idempotency is especially important for generation with side effects. A text completion can often be retried, although duplicate billing and different sampling results still matter. A tool call that creates an invoice, sends a message, or changes a record cannot be retried merely because the connection closed. Negotiate an idempotency contract that covers the provider request, the gateway operation ID, and the tool execution boundary. If the provider lacks idempotency support, the gateway should either avoid the route for side-effecting work or place execution behind a durable deduplication layer.

Usage reporting also needs a contract. Define which counters are available, their units, whether cached tokens are separated, whether reasoning or hidden tokens are reported, and when final usage becomes authoritative. A provider may send estimates during a stream and a corrected total afterward. The gateway should record provisional and final usage separately, reconcile them against the operation ledger, and avoid using an unmarked estimate for quota enforcement. If usage is missing, the policy should specify whether to apply a conservative charge, suspend the operation, or mark the amount unknown for later reconciliation.

Latency and capacity claims need evidence. A provider’s advertised context length says nothing about p95 latency at the requested size, and a healthy endpoint can still be unable to honor a concurrency promise. Separate static compatibility from live eligibility. Static compatibility checks the contract. Live eligibility checks health, capacity, rate-limit leases, recent error classes, and regional facts. A route may pass the contract and still be temporarily ineligible. The receipt should record both results so operators can distinguish “cannot do this request” from “can do it, but not now.”

Capability discovery can combine three mechanisms. First, ingest provider declarations and authenticated metadata. Second, run controlled probes that test request and response semantics on a safe fixture. Third, observe production behavior through privacy-minimized telemetry. Declarations provide breadth, probes provide confidence, and observations reveal drift. None should automatically overwrite the others. Store evidence with timestamps and scope, then let a reconciliation process produce a contract version. A production observation from one model revision should not silently redefine every endpoint in the family.

Probe carefully. A capability probe must not send real tenant prompts, invoke real tools, or create billable side effects. Use synthetic content, a sandbox account, deterministic seeds where supported, and explicit budgets. Test the boundaries that affect routing: maximum accepted context, schema enforcement, image formats, stream terminal events, cancellation, usage finalization, and error mapping. A failed probe may mean unsupported capability, a transient outage, a probe bug, or an account restriction. Classify the result instead of collapsing every failure into “false.”

Contract negotiation should happen before expensive work. Validate the request envelope, select a compatible route, and only then allocate provider reservations or begin a stream. For multi-turn interactions, repeat the compatibility check when the conversation grows or tools return large results. For long-running jobs, pin the contract version and route eligibility snapshot at admission, while allowing only explicitly safe revalidation events during execution. Otherwise, a model upgrade halfway through an operation can change semantics and make the final receipt impossible to interpret.

Route pinning and failover need a clear contract. Pinning a provider for all attempts gives consistent behavior but may reduce availability. Failing over to another provider can preserve service but may change tokenization, tool semantics, safety behavior, or output quality. Define which requirements must remain invariant across failover and which preferences may change. If a request requires schema-constrained output, failover is allowed only to a route that satisfies the same level. If it requires a specific model family, a generic fallback is not equivalent unless the caller or policy permits it.

When failover changes a capability dimension, make the change explicit. The operation receipt should include the initial contract, each attempted contract, the reason for transition, and any changed assumptions. The client-facing response should not claim that the same model handled the request if the gateway selected a different endpoint. For streaming, failover after bytes have been sent may be impossible without duplicate or incoherent output. The contract should define whether the gateway fails the stream, resumes from a provider checkpoint, or completes only the already-admitted route.

Provider adapters are enforcement boundaries, not thin translation utilities. Each adapter should declare which canonical fields it can faithfully map, which fields it emulates, and which it rejects. Centralize normalization of provider errors, usage, finish reasons, tool calls, and stream events, but retain raw evidence under the operation’s privacy policy. Add contract tests at the adapter boundary. A new adapter is not ready because a basic text prompt works; it is ready when its declared capability levels match observed behavior for the request modes it exposes.

Use contract tests as executable documentation. Keep a fixture for each supported feature level and provider behavior. Assert that a strict schema request is rejected when enforcement is unavailable, that an oversized envelope is rejected before dispatch, that a tool argument is validated before execution, and that a missing usage event is marked unknown. Test both positive and negative cases. Negative tests are essential because the dangerous bug is usually a route that is selected when it should have been excluded.

Detect drift continuously. Compare current observations with the active contract and alert on meaningful changes: a tool-call field disappears, a context limit shrinks, a retention attestation expires, usage totals diverge, or a provider starts returning a new error class. Use thresholds and confidence so one malformed response does not revoke a healthy endpoint. But when evidence crosses a hard safety boundary, publish a capability downgrade or revocation quickly. The route planner should react to the new contract without waiting for a code deployment.

Capability downgrades must be monotonic where possible. If strict schema support is revoked, an older contract must not be allowed to restore it merely because a delayed event arrives. Use sequence numbers, epochs, and fencing for contract updates, just as with policy and quota coordination. A provider’s capability record can be newer than the policy that references it, so the evaluator should record both versions and reject combinations that violate compatibility rules. Out-of-order control-plane events are normal distributed-system conditions, not edge cases.

Privacy and residency belong in provider contracts. A route’s geographic label does not prove where prompts, logs, abuse-review samples, backups, or support data travel. Record the data-handling scope that the provider contract actually covers, including retention, training use, subprocessors, and telemetry destinations where known. Make claims scoped to a product, account, endpoint, and contract date. “Provider is private” is not a machine-checkable property. “This endpoint, under this account agreement, has zero-day retention for this data class, verified at this time” is closer to one.

Keep negotiation explainable without exposing sensitive prompts. The decision explanation can say that a route failed because it lacked image input, exceeded the effective context envelope, had only best-effort JSON, lacked a current residency attestation, or could not guarantee idempotent tool execution. Store hashes or classified attributes rather than raw content in the receipt. Support teams need enough information to answer why a route was chosen and why another was rejected, while the evidence store still obeys retention and regional boundaries.

Failure handling should degrade conservatively. If capability metadata is stale, the gateway may continue with low-risk text requests when the contract’s grace period permits it. It should restrict or reject requests requiring uncertain tools, residency, retention, or strict output guarantees. If the provider contract service is unavailable, use the last signed contract within its allowed age and no more. Do not infer support from a successful request that happened to work once, and do not route around an unknown by deleting the requirement.

A practical decision pipeline now looks like this. Normalize the request and derive hard requirements. Load a fresh, signed policy and capability snapshot. Compute the effective context and data-handling envelope. Filter candidates by hard compatibility and local eligibility. Rank the remaining routes using latency, cost, capacity, and preference. Reserve the required quota or lease. Dispatch through an adapter that enforces the negotiated contract. Validate streaming, tool, and structured-output behavior. Reconcile usage and emit a decision receipt. Each step has a defined failure mode and a versioned input.

Observe the whole chain. Track rejection counts by capability reason, contract age, adapter version, provider error class, failover dimension, and unverified evidence. Track false positives and false negatives from contract tests and post-request validation. A high rate of “schema supported” routes followed by invalid outputs means the capability level is overstated. A high rate of pre-dispatch rejections after a provider change may indicate that the contract is correctly conservative, or that discovery is stale. Metrics should make that distinction investigable.

The key design choice is to treat compatibility as a guarded claim. A route is not good because it has the requested model name or a test prompt returned text. It is eligible only when identity, capabilities, limits, behavior, evidence, freshness, policy, and live state satisfy the operation’s requirements. The gateway is making a promise on behalf of the system, and vague promises become outages, silent downgrades, privacy violations, or duplicated side effects.

The series now has another layer. Budgets and fairness govern scarce capacity. The operation lifecycle gives one identity across attempts, streams, tools, usage, and reconciliation. Privacy-aware observability limits what evidence is collected. Residency-aware routing adds place to that evidence. Policy distribution keeps rules consistent across regions and time. Provider contracts and capability negotiation make the selected route’s technical behavior explicit. Together, these mechanisms let an AI gateway answer not only where a request went and which policy authorized it, but whether the endpoint could actually satisfy the requested semantics and what evidence supported that conclusion.
