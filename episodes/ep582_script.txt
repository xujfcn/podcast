Today we are talking about deadline propagation and timeout budgets: how to stop an AI request from living longer than the user can use its answer. Yesterday we bounded retries. Today we focus on the clock that every stage must share. This is a practical architecture discussion, not a claim about features implemented by any particular gateway.

Imagine a customer support application with a fifteen-second response target. Retrieval gets a ten-second timeout. The model client gets thirty seconds. The gateway allows another thirty seconds for a fallback. Each setting sounds defensible, but the user does not experience three independent requests. They experience one operation. If the browser gives up after fifteen seconds while the backend keeps generating for a minute, your system is spending money and holding capacity for an answer that may never be delivered.

A timeout limits how long one activity may wait. A deadline says when the whole operation stops being useful. You need both. A connection timeout protects against a slow connection establishment. A response timeout limits a particular exchange. An idle timeout detects a stream that has stopped making progress. None of these automatically enforces the total lifetime of the user operation. A stream can emit one tiny event just before every idle timeout and remain alive far beyond the intended deadline.

Start at the product boundary. Define whether success means the first visible token, a complete answer, or an accepted background job. Those are different contracts. For an interactive extraction endpoint, success might require a fully validated object within fifteen seconds. For a chat interface, you might measure first meaningful output separately from completion. A long-running document analysis may belong behind a job identifier and a status endpoint instead. Do not silently convert an interactive timeout into a background task without an explicit product contract.

At admission, establish an operation identifier and an effective deadline. Treat a caller-provided deadline as an input to validate, not unlimited authority. Reject malformed values and clamp excessively long budgets to a server-side maximum. If the caller allows less time than your default, preserve that tighter limit. A request that is already expired should not enter the expensive inference queue. Keep deadlines separate from authorization: having time remaining never grants permission to execute a tool or use a restricted model.

Within one process, use a monotonic clock to measure elapsed time. Wall clocks can move when the system synchronizes time. Across machines, a monotonic timestamp from one host has no portable meaning on another. Choose a documented propagation contract. An absolute deadline needs bounded clock-skew handling. A relative remaining-time field needs explicit accounting for transit and queue delay; otherwise each hop can accidentally add time back. Do not assume a custom header reaches a provider or that the provider enforces it. Your gateway still needs a local timer and cancellation handling.

The key rule is that a child operation cannot outlive its parent budget. Before a downstream call, calculate remaining time, subtract the reserve needed to finish locally, and apply the smaller of that value and the stage's own maximum. Recompute after waiting for a connection or a concurrency permit. If the result is not positive, do not dispatch. SDK settings differ, so confirm whether a timeout covers connection setup, reads, pool acquisition, the entire call, or only inactivity. A promising configuration name is not a substitute for a timing test.

Here is a hypothetical fifteen-second extraction request. Admission and authentication consume half a second. Queueing consumes two seconds. Retrieval consumes another two and a half. Ten seconds remain. Reserve one second for validation and delivery, leaving at most nine for model work. If the first attempt spends six seconds and fails, the second attempt does not get a new nine seconds. Only three seconds remain before the reserved finishing window. If your eligible fallback cannot plausibly produce a useful result in that window, stop rather than starting doomed work. These numbers illustrate accounting, not recommended production defaults.

Reservations are not guarantees. A validation stage can run longer than expected, and network delivery can stall. Enforce the parent timer through finalization too, and choose reserves using observed latency distributions. Be careful with percentile arithmetic: adding the ninety-ninth percentile of every component does not produce a mathematically exact ninety-ninth percentile for the whole system. Measure end-to-end outcomes as well as component timings. Use the stage budgets to constrain behavior, then validate the product target under realistic load.

Queues deserve special attention because they can consume the budget before a model sees the request. Carry expiration information with queued work. Check it when enqueueing and again when a worker dequeues it. Bound queue length and admission concurrency, rather than allowing a growing pile of expired requests. With parallel retrieval branches, each branch inherits the same outer deadline. Parallelism changes the critical path, but it does not create more wall-clock time. Cancel unnecessary branches once the answer no longer depends on them, and bound fan-out so speed does not become uncontrolled cost.

Streaming adds a second clock. Track time to meaningful first output and time since useful progress, while retaining an absolute completion bound where the product requires one. Transport heartbeats may prove a connection is alive without proving the model is progressing. Define which events reset which timer. Once headers and partial output have reached a client, you usually cannot replace the response with a normal JSON error and a different HTTP status. Use the stream protocol's documented terminal error or completion behavior, and make interrupted output visible instead of presenting it as a complete answer.

Cancellation must travel in the other direction. When the user disconnects or the parent deadline expires, signal outstanding child tasks, stop scheduling new attempts, close streams where appropriate, and release local resources. That is best-effort cancellation, not proof that a remote provider stopped computation or billing. A tool action might already have committed its side effect. If a payment or message send has an unknown outcome, reconcile its action identifier rather than assuming cancellation rolled it back. Time limits and idempotency solve different problems.

For observability, capture the initial budget, queue time, remaining budget at each dispatch, stage duration, and the reason work stopped. Distinguish a caller disconnect from a local deadline, an upstream timeout, and an idle-stream timeout. Record whether work completed after the client stopped waiting, where that is observable. Avoid using unique operation identifiers as metric labels; put them in appropriately protected traces or logs. Useful aggregate signals include expired-before-dispatch counts, deadline success rate, wasted downstream work, and time spent waiting for capacity.

Test the invariants with a fake clock and controlled dependencies. Make a request expire in the queue and verify no provider call occurs. Delay retrieval and verify the model receives a smaller budget. Trigger a retry and verify the deadline does not reset. Send stream heartbeats without useful content. Disconnect the client during generation. Simulate clock skew between services and a tool that succeeds just before cancellation. Assert both the user-visible outcome and the absence of extra downstream work. A fast error alone does not prove the backend stopped.

For a first rollout, choose one endpoint and document its completion contract. Establish one parent deadline, inspect all library timeout semantics, and add queue-expiration checks. Instrument before tightening limits, then canary the change with a rollback path. Watch completed, valid user outcomes rather than celebrating lower average latency caused by more failures. Deadline propagation makes an important promise: every component spends the time that remains, not the time it wishes it had. Thanks for listening to AI Dev Tools, the Crazyrouter Podcast.
