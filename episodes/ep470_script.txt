Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we designed controlled provider reinstatement: a route does not jump from open to trusted, but earns traffic through representative probes, canary cohorts, shared permits, staged ramps, rollback triggers, and probation. Today we take the next step. A healthy provider can still be unable to accept every request at once. We are designing overload coordination: how an AI API gateway decides what work may enter the system when provider capacity, fallback headroom, token budgets, or tenant priorities are constrained.

This is not simply rate limiting. Rate limiting usually asks whether one caller has exceeded a fixed allowance. Overload coordination asks a broader question: given the capacity available across several routes, which work should proceed now, which work should wait, which work can move to a fallback, and which work should be rejected clearly before it consumes scarce resources? The decision must account for estimated tokens, queue time, streaming connections, tool side effects, deadline remaining, provider health, and the cost of displacing higher-value work.

The objective is graceful degradation. During a capacity shortage, the gateway should preserve the most important operations, protect every provider from a retry-driven collapse, and make less critical work fail or defer in a predictable way. It should not allow whoever happens to arrive first to consume all capacity. It should not send every request to a fallback until that fallback fails too. And it should not hide overload behind long queues that guarantee timeouts.

Start with a capacity model that describes what can actually become scarce. Requests per minute are only one dimension. A provider may have separate limits for concurrent requests, input tokens per minute, output tokens per minute, image pixels, audio seconds, tool-call executions, context length, or account-level spend. A gateway may also be constrained by connection pools, worker memory, CPU for streaming transforms, or a tenant-specific quota. Capacity is a vector, not a single number.

For every route and capability scope, maintain a capacity budget with a current estimate, a confidence level, and an expiration time. The estimate can come from provider quotas, observed throughput, explicit reservations, and recent saturation signals. Confidence matters because a quota document may be stale, while a measured limit may reflect temporary regional pressure. A low-confidence estimate should produce conservative admission rather than a false sense of available capacity.

Separate hard capacity from soft capacity. Hard capacity is a limit beyond which requests are rejected, such as a provider-enforced quota or a connection-pool ceiling. Soft capacity is the operating range in which latency and error rates remain acceptable. A route might technically process another thousand requests while already violating its latency contract. Admission control should protect the soft boundary and leave a reserve for bursts, retries that are already in flight, and high-priority work.

Reservation is more useful than observation alone. When a request is admitted, reserve the resources it is expected to consume before dispatch. For a text generation request, that may include one concurrency slot, an estimated input-token cost, a maximum output-token allowance, and a stream connection. For a tool workflow, reserve the model call separately from the possible tool execution, because the tool may have its own concurrency and side-effect limits. Release or reconcile the reservation as actual usage becomes known.

Estimates must be conservative without being wasteful. Use request metadata, historical usage by model and operation class, prompt length, max tokens, image dimensions, and tool definitions to form an initial estimate. If the provider bills or limits on hidden transformations, add a safety margin. Track estimation error by workload stratum. A single global multiplier is usually wrong: short chat requests may be predictable while long agent runs have a wide tail.

Unknown consumption needs a policy. A stream can end without a final usage record. A provider can return a response whose accounting event arrives later. A disconnected client may leave the gateway unsure whether the provider generated ten tokens or ten thousand. Do not immediately return the full reservation in these cases. Mark it as pending, apply a bounded hold period, and reconcile through usage metadata, provider reporting, or a conservative timeout. Otherwise an overload event can be amplified by phantom capacity.

The admission decision should happen early, but it must be revisited at key boundaries. At ingress, check authentication, request validity, tenant policy, and a preliminary capacity estimate. Before dispatch, recheck route health, live permits, and the remaining deadline. Before a tool call, perform a fresh admission check for the tool and any new model request. A workflow that was safe to start may become unsafe after a long reasoning step or a provider recovery event.

Use a request state machine rather than a boolean admitted flag. A request can be classified, queued, reserved, dispatched, streaming, paused, completed, cancelled, expired, or rejected. Each transition should have an owner and a timestamp. This makes capacity accounting auditable and prevents a common leak: a cancelled request remains counted forever, while a retried request receives a second reservation without releasing the first.

Queueing is not free capacity. A queue consumes memory, occupies coordination state, and reduces the time available for useful work. Every queued request needs a deadline-aware expiry. Estimate queue wait from the service rate and current reservations, then compare it with the request's remaining deadline. If the predicted wait leaves no time for provider execution and response delivery, reject early or offer an asynchronous path. A fast, honest rejection is often better than a timeout after several futile retries.

Queues should be scoped by capability and workload, not just by provider. A long-context generation can block short interactive requests if they share one unbounded queue. Separate classes may include interactive chat, batch generation, embeddings, image operations, tool orchestration, and background evaluation. The exact taxonomy depends on the gateway, but each class should have a capacity envelope and a policy for borrowing unused headroom.

Fairness needs a deliberate design. A simple global FIFO queue is easy to explain but can let one high-volume tenant dominate. Strict per-tenant quotas protect fairness but may leave capacity idle when a tenant is quiet. Weighted fair queuing, deficit round robin, or hierarchical token buckets can combine isolation with utilization. Assign weights based on service tier or explicit policy, then enforce maximum shares so even the highest-priority tenant cannot consume every route during an incident.

Priority is not just a number on the request. Define what the priority permits. A premium interactive request might bypass a batch queue, receive a larger fallback budget, or retain a connection reservation. It should not bypass authorization, provider compatibility, safety checks, or a hard quota. Priority should also be bounded in time. An old request waiting in a priority queue must not become immortal simply because new high-priority work keeps arriving.

Protect deadlines explicitly. Calculate an admission deadline, a dispatch deadline, and a completion deadline from the client contract. A request with only two seconds remaining should not enter a queue designed for thirty-second jobs. Prefer work that can finish within its deadline, but do not use deadline urgency as a loophole for unlimited priority inversion. When a request becomes impossible to complete safely, expire it and return a typed overload or deadline error with retry guidance.

Backpressure must reach the client and the caller that can actually slow down. Return a stable error code, retry-after guidance when meaningful, and a distinction between temporary capacity shortage, tenant quota exhaustion, and unsupported fallback. For streaming APIs, send a clear pre-stream response before dispatch if admission fails. Once a stream has begun, do not pretend that a midstream cancellation is a normal successful completion. Preserve the internal reason and expose the contractually correct result.

Retries deserve special protection. When a provider is overloaded, clients and SDKs often retry simultaneously. A gateway retry can turn one failed operation into several reservations and several provider attempts. Use a retry budget per request, tenant, route, and incident scope. Require a fresh admission decision for every attempt. Prefer switching to a compatible route only when the fallback has confirmed capacity, and carry the original deadline so a retry cannot outlive the operation.

Retry budgets should distinguish transport ambiguity from confirmed rejection. A connection reset after dispatch may leave an operation unknown, especially when tools can have side effects. A clear quota rejection may be safe to route elsewhere, while an unknown tool outcome may require reconciliation rather than automatic replay. The gateway's overload controller must cooperate with the operation ledger and idempotency policy, not treat every failure as a free retry.

Fallback headroom should be reserved, not assumed. If the primary route becomes overloaded, the fallback must absorb a surge without exceeding its own soft capacity. Maintain an explicit reserve for failover and high-priority traffic. Do not allocate every available fallback slot to ordinary traffic simply because the primary looks healthy. Reserve sizing can use historical incident volume, correlated failure scenarios, and a target recovery time. The reserve should be visible to admission decisions and released gradually as primary confidence improves.

Fallback compatibility is part of capacity. A route that has spare requests per minute may still be unable to serve the request's context length, modality, tool contract, region, or data residency requirement. Filter candidates by capability and policy before comparing remaining headroom. A fallback that cannot preserve the API contract is not capacity for that request. If only an inferior mode is available, require an explicit degradation policy rather than silently changing behavior.

Provider health should modulate admission, not merely remove failed routes. A route in probation after controlled reinstatement may accept low-risk work but keep a lower concurrency ceiling. A route with elevated unknown outcomes may accept read-only calls while excluding effectful tools. A route with latency degradation may remain available for batch work with long deadlines but be removed from interactive selection. Health vectors should map to workload-specific capacity envelopes.

Correlated failures require a failure-domain view. Two provider brands may share an upstream cloud region, model family, network path, or account quota. Sending overload traffic to both is not diversification. Tag capacity by provider, region, account, model family, network path, and other relevant domains. During an incident, reduce correlated capacity estimates together when evidence supports it. Conversely, avoid collapsing independent routes merely because they share a brand name.

Admission controllers must be distributed, but independent local guesses are dangerous. If ten gateway instances each believe they can admit one hundred requests, the shared provider may receive one thousand. Use a central coordinator, distributed counter with leases, or partitioned quotas with bounded oversubscription. Every method has tradeoffs. A coordinator can become a bottleneck, while local partitions can strand capacity. Choose a design that fails conservatively when coordination is unavailable.

A capacity lease should include scope, resource dimensions, amount, owner, expiration, controller generation, and fencing token. Dispatch is valid only while the lease is current. When a policy changes or an incident controller takes over, the new generation invalidates old leases. This is the overload counterpart to the recovery lease from the previous episode. It prevents a stale worker from dispatching work after the system has declared the route saturated.

Use bounded oversubscription only where it is measurable and reversible. A small allowance can improve utilization when estimates are noisy, but it must be tied to a confidence score and a hard ceiling. If actual usage repeatedly exceeds estimates, reduce the allowance by workload class. Never use optimistic oversubscription to paper over missing provider quota data. Uncertainty is a reason to collect better evidence, not to invent capacity.

Admission control should be transactional around the reservation decision. Validate the request, compute candidate routes, reserve capacity on one route or a declared fallback plan, and commit the decision with an idempotency key. If the downstream dispatch fails before ownership is clear, reconcile the reservation rather than blindly releasing or duplicating it. Partial failures in the controller are normal distributed-systems events; the state machine must make them safe.

When resources are scarce, shed work in an intentional order. A reasonable policy may first stop speculative retries, then delay background batch jobs, then reduce optional output budgets, then reject low-priority interactive work, while preserving safety-critical or contractually protected operations. The order is product-specific and should be documented. Work shedding must never bypass access control or safety review simply because a request is urgent.

Graceful degradation can reduce demand before rejection. Offer a smaller output cap, disable optional enrichments, switch from a high-cost model to a compatible lower-cost model, or return a cached answer when the API contract allows it. Each degradation must be explicit in policy and observable in the response metadata. Do not silently truncate a tool argument or remove a required field. If the client did not authorize a degraded mode, reject with a useful explanation.

Caching can help, but cache hits are not a substitute for admission policy. A cache lookup should happen before expensive reservation where safe, and cached results can preserve capacity during an incident. Yet cache refreshes, personalization, and stale data policies still consume resources. Treat refresh work as a separate class with its own budget. Never let a stampede of simultaneous misses bypass the same overload controls applied to ordinary requests.

Autoscaling is complementary, not magical. More gateway workers do not create provider quota, and more provider replicas may not reduce a regional limit. Scale the layer whose bottleneck is actually measured. If the queue grows because token capacity is exhausted, adding CPU only increases the number of requests waiting. If connection pools are the bottleneck but provider quota is available, scaling workers may help. Capacity telemetry must identify the limiting dimension before an automated scaler acts.

Monitor saturation with leading indicators. Queue age, reservation utilization, remaining deadline, token estimate error, concurrency occupancy, stream counts, retry amplification, fallback reserve, and rejection mix often reveal overload before error rates peak. Track high-percentile values and by-class breakdowns. A healthy global average can conceal a small interactive workload whose deadlines are already failing.

The metrics must be tied to decisions. Record why a request was admitted, queued, routed to fallback, degraded, expired, or rejected. Include the capacity dimension that blocked it, the policy version, the controller generation, and whether the decision used an estimate or reconciled actual usage. Keep tenant identifiers out of high-cardinality metric labels, but retain protected detail in an access-controlled decision ledger.

Audit fairness and usefulness, not just utilization. A controller can achieve ninety-five percent provider utilization while starving one workload class or producing unacceptable tail latency. Review accepted work by tenant, class, priority, deadline outcome, fallback use, and degradation mode. Look for priority inversion, quota leakage, and repeated rejection of the same cohort. Capacity policy should be evaluated as a service contract, not merely as a resource optimizer.

Simulation is essential before changing thresholds. Build a provider and workload simulator that generates bursty arrivals, token-size distributions, long-lived streams, retries, cancellations, quota changes, correlated route failures, and recovery ramps. Replay historical traffic with privacy-safe shapes. Compare policies for accepted useful work, deadline success, fallback reserve consumption, cost, rejected requests, and oscillation. Do not judge a policy only by how quickly it clears a queue.

Test pathological cases deliberately. What happens when estimated output is half the actual output? When a request is cancelled after dispatch but before usage arrives? When the coordinator loses connectivity during a burst? When a high-priority tenant submits an unbounded batch? When the primary recovers while fallback reserve is nearly empty? When two workers commit the same reservation? The desired answer is not that nothing fails. It is that the failure is bounded, visible, and recoverable.

Run overload game days in layers. Begin with shadow admission decisions that cannot change routing. Then enforce admission for synthetic traffic, then for background work, and finally for a small production cohort. Keep an operator pause and an automatic path to stricter shedding. Test provider recovery and overload together: a route should not receive a full ramp merely because it passed health checks if its available capacity is already scarce.

Manual controls should be narrow and expiring. Operators may cap a route, reserve capacity for a tenant class, pause a queue, disable a degradation mode, or force all new work into a safe fallback. Every override needs a reason, owner, scope, maximum duration, and audit record. Avoid a global bypass that turns off admission during the exact incident when admission is most needed. Emergency exceptions should reduce ambiguity, not remove all guardrails.

There is also a product lesson. A gateway that exposes only provider errors makes overload feel random. A gateway that exposes stable capacity and degradation semantics gives clients a chance to respond intelligently. SDKs can honor retry-after, use asynchronous jobs for long work, lower optional budgets, and avoid retrying unknown side effects. The infrastructure contract is stronger when the client can distinguish overload from invalid input and from a provider contract failure.

Overload coordination is ultimately an exercise in preserving optionality. Capacity is scarce, and every admission consumes some future choice. A request admitted now may prevent a safety-critical operation from entering later. A retry may consume the last fallback slot. A long stream may hold a connection through the next incident. Good admission control makes those tradeoffs explicit, bounded, and reversible.

The deeper connection to provider reinstatement is symmetry with a deliberate difference. Recovery asks whether a route has earned more exposure. Overload coordination asks whether the system can afford to grant that exposure now. A route may be healthy but capacity-constrained. A fallback may be compatible but reserved. A request may be valuable but impossible within its deadline. Health, capacity, priority, and contract must meet in one admission decision.

A mature AI API gateway therefore combines scoped health vectors with multidimensional reservations, deadline-aware queues, fair scheduling, retry budgets, fallback reserves, workload-specific degradation, distributed leases, and a durable decision ledger. It sheds work before queues become graveyards, preserves uncertainty instead of recycling it into phantom capacity, and makes every route prove both that it is healthy and that it has room.
