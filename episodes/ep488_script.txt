Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we examined provider recovery and safe work resumption. We separated technical health from resumability, classified uncertain attempts, preserved idempotency, rechecked authority and residency, released queues progressively, and kept ambiguous side effects quarantined. Today we turn to the records created by that work. A multi-provider AI gateway can produce operation ledgers, policy decisions, provider events, usage facts, billing records, traces, tool receipts, and evidence packages across regions and tenants. Keeping everything forever creates a privacy and security problem. Deleting everything quickly makes incidents impossible to explain. Our topic is operation ledger retention and purpose-limited deletion: preserve what is needed for accountability, remove what no longer has a legitimate purpose, and prove that both actions happened.

Start with a simple scenario. A customer asks an agent to process a document. The gateway records an admission decision, a model attempt, a fallback, a tool call, a provider receipt, a usage event, and a billing adjustment. Six months later, an auditor asks why the customer was charged twice. The response depends on the ledger. But the original document and full prompt are no longer needed for that question, and retaining them indefinitely increases exposure. A sound system can reconstruct the decision from metadata, hashes, references, and provider identifiers without keeping every content payload. Retention is not a choice between total memory and total forgetting. It is a design for evidence by purpose.

Define the purposes before defining retention periods. Possible purposes include live operations, reliability analysis, customer support, billing, abuse investigation, regulatory accountability, security incident response, model quality evaluation, and legal preservation. Each purpose has different evidence requirements and different access boundaries. A billing dispute may require operation IDs, attempts, usage, pricing versions, and adjustment rules. It rarely requires the customer’s full prompt. A security investigation may temporarily require controlled content access, but that does not justify keeping all content forever. Purpose is the reason data may remain; when the reason ends, deletion should begin.

Build a data inventory for the entire operation graph. Include gateway logs, authorization decisions, queue envelopes, workflow checkpoints, provider request IDs, model outputs, tool arguments, tool results, traces, usage records, invoices, cache entries, object-store artifacts, backups, exports, notifications, and human review notes. Record the owner, tenant, region, classification, purpose, source, retention rule, deletion mechanism, legal hold behavior, and evidence needed to prove deletion. The inventory must include derived copies. A prompt deleted from the primary database is not gone if it survives in a debug dump, failed-job archive, analytics warehouse, or provider upload bucket.

Separate payloads from evidence. Payloads include prompts, documents, images, audio, model outputs, tool arguments, and tool results. Evidence includes identifiers, hashes, timestamps, policy versions, route decisions, provider IDs, status transitions, usage measurements, and integrity proofs. Many operational and accounting questions can be answered with evidence rather than content. Store the minimum content needed at each stage, and prefer references to controlled artifacts. A hash can prove that a payload was the same object seen at two boundaries without revealing the payload to every operator.

Use an evidence envelope with explicit fields. It might contain operation ID, attempt ID, tenant, actor, purpose, policy version, authority digest, route, provider account, region, native request ID, canonical status, usage state, charge state, side-effect state, event times, retention class, and integrity metadata. Include links to content only when the purpose requires them. The envelope should make clear whether a fact is observed, derived, estimated, disputed, or unknown. It should also identify the rule that permits retention. A record without a purpose is a candidate for deletion, even if it is technically useful.

Retention should be attached to data classes and purposes, not only tables. A single database table may contain customer-support traces, security events, and billing facts that need different lifetimes. Tag records at creation with tenant, classification, purpose, retention class, creation time, expiration time, and hold status. Derived records should inherit the strictest applicable constraint unless a policy explicitly permits a different purpose. Do not rely on a nightly query that guesses retention from a table name. Data can be copied, transformed, and exported long before that query runs.

Use event time and retention time deliberately. A provider usage event may arrive weeks after the original operation. A dispute may start after the normal billing period. A security incident may require preserving a bounded window before and after detection. Define whether retention starts at creation, last access, operation completion, invoice finalization, incident closure, or another justified event. Avoid resetting the clock on every read; otherwise routine investigation can create indefinite retention. If access extends retention for a legitimate reason, create an explicit extension with an owner, purpose, deadline, and audit record.

Legal and security holds need precise boundaries. A hold should identify the tenant, operation range, data classes, purpose, requesting authority, start time, scope, and review date. It should pause eligible deletion without freezing unrelated data across the entire platform. A security hold may preserve metadata and selected artifacts while excluding raw content that is not relevant. When the incident or dispute ends, the hold must be released or renewed explicitly. “Keep everything because there may be an audit” is not a bounded hold; it is a permanent exception disguised as caution.

Deletion must be purpose-aware and verifiable. For a content artifact, deletion may require removing the object, thumbnails, derived embeddings, OCR text, cache entries, temporary files, search indexes, exports, and scheduled jobs. For a ledger event, deletion may mean removing sensitive payload fields while retaining a redacted accountability record. For a backup, deletion may occur through expiry and cryptographic erasure rather than immediate block editing. Document what “deleted” means for each storage system and what evidence can prove it. Never claim that data is gone merely because the primary API returns not found.

Use a deletion state machine. States can include eligible, scheduled, in-progress, deleted, verification-pending, blocked-by-hold, failed, and deletion-unknown. Record the deletion request, actor, purpose, scope, system acknowledgments, verification method, and remaining uncertainty. If a provider or backup system cannot confirm deletion, keep the record in verification-pending or unknown rather than marking it complete. A deletion controller should be safe to retry and should not create competing deletion jobs. Repeated requests should converge on one deletion outcome and preserve the history of attempts.

Cryptographic erasure is useful, but it has conditions. Encrypt sensitive artifacts with keys scoped by tenant, region, purpose, or retention class. When the purpose ends, destroying the relevant key can render copies unreadable. But key destruction is not automatically proof that every plaintext copy is gone. Check caches, temporary processing areas, provider-side artifacts, logs, and exported reports. Retain a minimal deletion receipt that identifies the key scope, destruction event, affected artifact set, and verification limitations. If a backup still contains encrypted bytes but the key is destroyed, label the state accurately as cryptographically inaccessible, not physically absent.

Provider retention must be part of route governance. A gateway may delete its copy while a provider retains prompts, files, generated images, or logs under a separate contract. Before routing sensitive data, record the provider’s retention terms, deletion API, default logging behavior, region, and evidence available after deletion. If the provider cannot delete or prove deletion within the required period, restrict the route to data classes that permit that limitation or apply a gateway-controlled transformation. “The provider says it usually deletes” is not an operational guarantee.

Do not confuse cache expiry with deletion. A cache entry may disappear from the hot cache while surviving in a snapshot, replica, disk layer, or analytics export. Define cache retention separately from source retention and verify invalidation at every cache that can serve the artifact or decision. Authorization caches may retain metadata longer than content caches, but they can still reveal sensitive relationships. On revocation or purpose completion, invalidate derived authority and content access independently. A deleted document should not remain discoverable through a stale search result or a cached tool response.

Observability systems require special care. Traces are often copied to vendors, sampled into long-term stores, attached to tickets, and enriched with request bodies. Redact at source rather than hoping downstream filters catch everything. Use structured fields for operation identity, status, timing, and error class. Store payload previews only under an explicit diagnostic mode with a short deadline. When a trace is useful for an incident, preserve the minimum span set and replace sensitive values with references or stable hashes. Debug convenience is not a sufficient retention purpose for customer content.

Sampling should preserve explanations, not secrets. A small, representative set of metadata-rich traces may explain latency, retries, routing, and provider behavior without retaining every prompt. For failures that require payload inspection, create a controlled evidence artifact with a specific incident purpose, access list, expiration, and redaction process. Never let an emergency capture switch silently become permanent logging. When the incident closes, expire the diagnostic artifacts and retain only the redacted facts needed for the postmortem.

Billing and audit records often need longer retention than operational payloads. Keep immutable operation and charge identifiers, usage facts, pricing versions, invoice references, adjustment reasons, and transaction links for the justified accounting period. Remove or tokenize customer content that is not needed to prove the charge. If a customer disputes a bill, preserve the relevant evidence package, not the entire tenant history. A financial record should explain how an amount was calculated and which attempts produced it without becoming a backdoor archive of user data.

Retention across tenants and regions must be enforceable by construction. Include tenant and residency in storage placement, encryption context, access checks, and deletion jobs. A global analytics warehouse may need aggregated metrics rather than row-level events. If cross-region replication is required for availability, document the replication purpose and deletion propagation target. A deletion request should identify all approved replicas and downstream processors. When a region is unavailable, mark deletion propagation as pending and enforce an access block until the data can be verified or the risk policy supplies a bounded fallback.

Backups create an unavoidable time dimension. Some backup systems cannot delete one record without rebuilding an entire snapshot. Define maximum backup residence, encryption-key scope, restore controls, and deletion behavior before putting sensitive data into backups. A restore must not silently resurrect expired records into production. On restore, apply retention and deletion manifests before making data accessible. Keep a restore audit trail and quarantine records whose deletion or hold state cannot be resolved. Backup recovery is a data lifecycle event, not merely an infrastructure procedure.

Exports and human copies are part of the data graph. CSV files, incident bundles, screenshots, support tickets, email attachments, local downloads, and notebook outputs can outlive the system that created them. Restrict export formats, watermark sensitive reports, set expiration, and log recipients. Prefer signed links to uncontrolled attachments. When an evidence package is shared, record the recipient, purpose, fields included, and expiration. Deleting the source record does not delete a spreadsheet already downloaded by an operator. Governance must cover the places humans actually work.

Access controls should follow purpose and retention. A billing analyst may see usage and charges but not prompts. An incident responder may request a redacted payload view for a bounded case. A provider operator may see native request IDs and errors but not customer documents. Every exceptional content access should require a purpose, case ID, scope, and expiration. Log both successful and denied access. Access logs themselves are sensitive operational evidence and need their own retention class. Do not retain detailed access records forever merely because they prove that someone looked.

Deletion can conflict with reproducibility. A team may want to replay a historical request to reproduce a provider regression, but replaying customer content may violate purpose limitation or create a new external side effect. Prefer replayable metadata, synthetic fixtures, redacted payloads, and provider contract snapshots. If the original payload is essential, create a separately authorized research artifact with minimization, access controls, and a short deadline. Reproducibility should explain the behavior without turning old customer data into a permanent test corpus.

Model quality work needs strict separation from customer operations. If prompts or outputs are retained for evaluation, record the evaluation purpose, consent or contractual basis, transformation, sampling method, and deletion schedule. Remove identifiers and sensitive fields where possible. Do not assume that replacing a user name is enough; document content may remain identifying. Store evaluation labels and aggregate metrics separately from raw examples. When a model or provider changes, preserve the contract and metric definitions longer than the individual examples needed to calculate them.

Incident response needs a controlled preservation workflow. When suspicious activity is detected, freeze relevant events before normal retention jobs delete them. Capture policy versions, operation lineage, provider identifiers, access events, queue state, and integrity proofs. Preserve raw content only when it changes the investigation, and place it behind a stricter evidence store. Mark the scope and deadline of the hold. At closure, produce a redacted incident record and release or narrow the hold. An incident should not become an excuse to retain an entire customer’s history indefinitely.

Deletion verification should use independent evidence. The system performing deletion should not be the only system declaring success. Compare source indexes, object-store listings, cache inventories, provider acknowledgments, key events, and access attempts. Use canary artifacts to test the deletion path regularly. For large datasets, verify sampled partitions plus complete metadata manifests, and state the confidence and limitations. A deletion report should answer what was targeted, which systems acknowledged it, what remains inaccessible or unknown, and who owns follow-up work.

Make retention and deletion observable. Useful metrics include records past expiration, deletion latency, deletion failures, unknown deletion outcomes, hold duration, provider deletion acknowledgment rate, content-to-metadata ratio, sensitive access exceptions, backup residence age, stale cache discoveries, and records restored after deletion. Break them down by tenant, region, provider, data class, and purpose. A low deletion failure rate can still hide a serious gap if one provider never honors deletion. Measure both minimization and explainability.

Test lifecycle races. Let retention expire while an incident hold is being created. Delete an artifact while a provider webhook arrives. Restore a backup containing records whose retention ended. Replicate data to a region that becomes unavailable during deletion. Export an evidence package just before source deletion. Retry deletion after a partial provider failure. Make a cache return a stale result after the source is gone. Verify that holds are not bypassed, deleted content is not resurrected, unknown states remain visible, and the system never claims stronger deletion than its evidence supports.

The deeper lesson is that an operation ledger is not a permanent memory palace. It is a purpose-bound accountability system. Keep enough structure to explain authority, execution, delivery, side effects, usage, and cost. Remove content when the purpose ends. Preserve integrity proofs without preserving unnecessary payloads. Treat providers, caches, backups, exports, and human copies as part of the same lifecycle. Make deletion idempotent, observable, and honest about uncertainty. Privacy is not achieved by having no records; accountability is not achieved by keeping everything.
