Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we designed multi-tenant isolation for AI gateways: authenticated tenant context, scoped storage and retrieval, protected caches, durable workflows, regional controls, operator boundaries, and adversarial tests. Today we stay at that boundary and examine a related problem. An AI system rarely acts as one identity. A human asks an application to start a workflow. The gateway calls a model. The model proposes a tool action. A worker dispatches it through another service. Each hop may need authority, but none should inherit unlimited power. We are designing delegated agent identity and authorization chains: how to pass narrow, verifiable authority from a human to an application, gateway, sub-agent, and tool without turning delegation into impersonation.

The motivating failure is easy to imagine. A finance manager asks an assistant to prepare a vendor payment. The assistant creates a plan, a sub-agent checks invoices, a worker calls the accounting system, and a notification service tells the manager what happened. If every component simply uses the manager's token, the system has created a reusable impersonation credential. A prompt injection can spend money. A compromised worker can read unrelated records. A stale approval can authorize a changed destination. The safer design is a chain of constrained authority in which every component proves who it is, for whom it acts, what it may do, on which resources, until when, and under which policy.

Start by separating identity, delegation, and permission. Identity answers which principal is making this call. Delegation answers whether that principal is acting on behalf of another principal. Permission answers which operation is allowed on which resource. These are related claims, not interchangeable fields. A service account can be authentic without being allowed to delete a customer record. A gateway can act for a user without becoming that user. A model can recommend a refund without acquiring refund authority. Keeping these concepts distinct prevents the common shortcut of treating a valid bearer token as proof of every fact needed for an action.

Define a principal vocabulary before designing tokens. Include human users, tenant service accounts, applications, gateway instances, model sessions, workflow runs, workers, tools, and external providers. Give each principal a stable identifier and lifecycle. A workflow run is not the same identity as the user who created it, and a worker process is not the same identity as the workflow it executes. Record relationships such as created-by, acts-for, dispatched-by, and approved-by. Those relationships should be represented in an auditable authorization context rather than inferred from names or a shared database row.

The chain should be explicit. A useful request context may say: user U authorized application A to create workflow W in tenant T; gateway G accepted W under policy version P; workflow W authorized worker K to execute step S; tool adapter X may call provider Y for resource R with operation O. Each link has an issuer, subject, audience, scope, expiration, and evidence of the prior link. The downstream service does not need to trust every upstream detail equally. It verifies the claims relevant to its decision and rejects a missing, malformed, or unexpected link. A chain is valuable only when each hop can enforce its own boundary.

Keep the original user identity and the acting service identity visible. In a downstream audit record, do not write only “gateway called delete.” Record the authenticated gateway, the delegated user or application, the tenant, the workflow, the step, the authorization policy, and the tool or provider target. Preserve the chain of custody without copying unnecessary personal data. A support engineer investigating an incident should be able to answer both “which service made this request?” and “which human or business process caused it?” Blurring those answers makes accountability impossible and encourages operators to grant broad service privileges as a substitute for traceability.

The first authorization decision should happen at the gateway, but it must not be the last. The gateway can verify that a user may create a workflow and request a capability. The workflow service can verify that a particular step is part of the approved graph. The tool adapter can verify that the normalized arguments target an allowed resource. The provider can apply its own credential and resource checks. This is defense in depth, not duplicated bureaucracy. Each service sees a smaller, more concrete decision than the gateway saw. A confused deputy is prevented when downstream services refuse to accept a broad “the gateway said so” assertion in place of their own checks.

Design scopes around actions and resources, not vague roles. “Finance manager” is a useful policy input but a weak runtime authorization claim. A delegation should say something like “create payment drafts for vendors in tenant T,” or “read invoice metadata for project P,” with limits on amount, currency, destination, and time. Separate read, propose, approve, execute, cancel, and export. A model session might receive propose-payment, while only a human or a constrained payment worker can execute-payment. Avoid a single write scope that silently includes destructive, irreversible, and financial operations.

Resource scopes must be resistant to substitution. A token scoped to project P should not be accepted for an arbitrary project ID supplied in tool arguments. Bind the scope to canonical resource identifiers, tenant, region, and resource version where appropriate. The tool adapter normalizes arguments before authorization and rejects ambiguous aliases. If a payment draft is approved for a specific amount and destination, changing either value creates a new authorization decision. Do not let a model preserve the word “approved” while quietly changing the object underneath it.

Delegation should be attenuating. A child principal may receive equal or less authority than its parent, never more. If a user delegates “read invoices” to an application, the application may delegate a narrower “read invoice headers for project P” to a sub-agent, but not “delete invoices for the entire tenant.” Enforce attenuation mechanically by intersecting parent and requested child scopes. Do not ask the model to behave within the intersection; calculate it in code. If the requested child scope is not a subset, deny the delegation and record a policy event. Attenuation is one of the clearest proofs that delegation is not impersonation.

Limit delegation depth and lifetime. A long chain is difficult to explain, verify, and revoke. Set a maximum depth for sub-agents and service hops, and include the parent delegation identifier in each child credential. Use short-lived credentials for interactive actions and bounded workflow credentials for durable work. A workflow that lasts three days may need renewable step credentials, but renewal must reauthorize the current state and policy rather than extending the original token forever. Expiry should be based on both wall-clock time and business deadlines. A credential that outlives its workflow or approval is a security defect even if the signature remains valid.

Revocation is harder for distributed systems because a token may already be in flight. Build for it explicitly. Maintain revocation or epoch state for users, service accounts, tenant memberships, workflows, and approvals. Include a policy or authorization version in delegated claims. At sensitive boundaries, check the current version or a short-lived cache of it. When a user leaves a tenant, invalidate the relevant epoch and stop renewal. When a workflow is cancelled, reject new step credentials and mark existing ones unusable for dispatch. Revocation cannot undo a provider action that already committed, so pair it with reconciliation and incident response rather than presenting it as a time machine.

Separate capability issuance from capability use. A token service may issue a narrow credential after evaluating identity, tenant, policy, resource, and workflow state. The tool adapter then uses that credential for one defined operation. The adapter should not be able to mint a broader token simply because a model requested one. Keep signing keys and issuer privileges away from workers that process untrusted model output. If a worker needs another capability, it should ask the authorization service with its current chain and receive a new, independently evaluated grant. This makes escalation visible and gives the policy engine a chance to deny it.

Do not place secrets or complete authority chains inside prompts. Models need a description of available capabilities, constraints, and expected result types. They do not need raw access tokens, signing keys, internal service credentials, or hidden policy assertions. The gateway holds credentials in a protected registry and passes a reference to the authorized adapter. Tool results should be filtered before returning to the model, especially when they contain tokens, cookies, internal URLs, or data from a broader service account. Prompt text is not a secure transport for identity, and a model's recollection of a token is not a revocation mechanism.

Treat the model as a policy subject, not a trusted principal by default. A model session can have an identity for accounting, tracing, and rate control, but that identity should not imply human authority. The model produces proposals or requests within a capability set compiled by the gateway. A policy engine evaluates the proposed operation, normalized arguments, data classification, risk, budget, and current workflow state. The resulting authorization decision belongs to infrastructure. If the model claims “the user approved this,” the gateway must find a verifiable approval object; the statement alone carries no authority.

Sub-agents deserve separate identities and budgets. A research sub-agent, coding sub-agent, and execution sub-agent may all be driven by the same parent workflow, but their permissions and data needs differ. Create a child identity with a purpose, parent ID, allowed tools, token budget, time budget, and output contract. Give research read-only retrieval and no external write access. Give an execution worker only the exact step and resource it must change. When a child returns a recommendation, the parent should treat it as untrusted input and run its own validation. Child identity is useful only when it creates a real boundary rather than a decorative label.

Approval is a delegation event with a precise subject. The approval record should include who approved, which tenant, which workflow and step, the exact action, canonical arguments, resource versions, risk summary, policy version, and expiry. The approver should see the same normalized facts that the executor will use. When the action reaches the tool, verify that the approval is still valid, unused or intentionally reusable, and bound to the current chain. A generic approval flag in a workflow row is dangerous because it can be copied to another step. Approval should grant a bounded capability, not bless a whole future conversation.

Human delegation and application delegation have different trust properties. A user may authorize an application to act for a narrow purpose, but an application cannot necessarily consent to all actions the user could perform manually. Model user-granted permissions separately from service policy and tenant policy. Require explicit product semantics for unattended operation, especially for financial, legal, communication, and destructive actions. Make it clear whether the user approved one action, a class of actions, or a recurring automation. Recurring automation needs its own expiry, spending limits, notification rules, and revocation surface. “The user connected their account” should never mean “the agent may do anything.”

Service-to-service authentication must include audience restriction. A token issued for the workflow service should not be accepted by the billing service unless the billing service is the intended audience and the scope covers the requested operation. Verify issuer, audience, signature algorithm, key status, not-before, expiry, tenant, and chain depth. Reject algorithm confusion, unsigned claims, unexpected key types, and tokens issued by a test environment. Internal network placement is not identity. A request from a private subnet can still be forged by a compromised workload, and a trusted service can still become a confused deputy.

Provider credentials are the final translation layer, not a shortcut around the chain. The gateway maps an authorized internal capability to a tenant-approved provider credential, model, region, and quota. The provider request should carry a stable operation and idempotency identity, but should not expose unnecessary internal claims. If a shared provider account is used, the gateway remains responsible for tenant attribution, spend limits, and data policy. If a provider supports delegated tokens or project-level roles, use them to narrow the external blast radius. Failover must preserve the same tenant, region, and capability constraints; it must not silently switch to a credential with broader authority.

Authorization decisions need a durable explanation. Store the decision ID, subject, issuer chain hash, requested action, canonical resource, policy version, result, reason code, and expiry. Minimize sensitive arguments and protect the record with tenant-scoped encryption. The explanation should be stable enough for an auditor to understand why the decision was made without requiring the original model to run again. Do not store only “allowed: true.” A useful reason says which policy rule matched, which limits were applied, and whether approval, ownership, or a delegated grant supplied the authority. Explainability here is an operational control, not a marketing feature.

Caching authorization decisions requires special care. Include tenant, principal, delegation ID, resource version, policy version, action, and relevant risk inputs in the cache key. Use short expiries for memberships, approvals, quotas, and sensitive writes. Invalidate on revocation, policy update, resource ownership change, and workflow cancellation. A cache hit must still verify token expiry and proof-of-possession requirements. Never cache a broad allow result and reuse it for a narrower-looking request without comparing canonical scope. A stale decision can be more dangerous than a slow decision because it gives a false sense that the boundary was checked.

Watch for confused-deputy patterns in indirect actions. A user may ask an agent to send a report to a URL, call a webhook, invite an address, or search a connected system. The gateway might possess network or provider privileges that the user lacks. Validate destination ownership, tenant policy, data classification, and allowed egress before dispatch. Do not let the downstream service infer user consent from the gateway's credential. For webhooks, bind the destination to a verified tenant configuration. For email, authorize recipient, content class, and sending identity separately. For network tools, apply allowlists and block internal address ranges unless explicitly governed.

Concurrency can invalidate an authorization chain. A manager approves adding a user to a group, but another administrator removes that user before the worker runs. A resource version, membership epoch, or conditional write protects against applying an old decision to a changed object. The executor should present the approval and expected version to the target service, which atomically checks both. If the check fails, classify the result as stale and request a new decision. Do not automatically retry with the latest object and assume the approval still applies. Authorization is about a specific state, not only a verb and a name.

Durable workflows should renew authority at meaningful boundaries. At creation, authorize the requested purpose and compile the graph. Before each side effect, verify tenant membership, workflow status, policy version, resource version, budget, approval, and credential health. During a long wait, do not keep a powerful token alive simply because the workflow is alive. Renew the next step's narrow capability after checking that the reason for waiting has not changed. This makes a restart safe: the workflow can recover its state without recovering stale authority. A durable workflow must preserve intent and evidence, but it must revalidate permission before acting.

Testing delegated authorization requires adversarial chains, not only happy-path tokens. Create synthetic users, tenants, applications, gateways, workers, tools, and providers with deliberately different scopes. Attempt to remove a parent link, swap a tenant, change an audience, replay a child token, increase delegation depth, replace a resource ID, reuse an approval, and renew after revocation. Deliver a valid token to the wrong service. Give a worker a broad infrastructure credential and confirm that internal claims still restrict it. Try to persuade the model that a human approved an action when no approval object exists. Every case should fail closed with a useful, tenant-scoped event.

Inject failures at the authorization boundaries. Revoke membership after a workflow is queued. Rotate a signing key while a step is waiting. Expire proof-of-possession keys during a retry. Change a policy between planning and dispatch. Return a stale resource version after approval. Duplicate a request with the same operation ID but a different scope. Partition the authorization service and observe whether the system safely pauses or incorrectly falls back to an old global allow. A temporary inability to prove authority should produce a controlled wait or denial, never an assumption that the caller is still trusted.

A practical pipeline now comes together. Authenticate the human, application, or service and resolve the authorized tenant. Create a workflow with an explicit purpose and policy version. Compile the model's proposal into typed capabilities and attenuated child scopes. Issue a short-lived, audience-bound delegation for the next step. Before dispatch, verify the chain, proof of possession, tenant, workflow state, resource version, budget, approval, and region. The adapter maps that effective capability to a tenant-approved provider credential and records the operation. The downstream service repeats its own checks. On completion, persist the effective authority and evidence. On mismatch, stop, classify the failure, and request a fresh decision rather than guessing.

The key lesson is that delegation should move authority, not identity. A gateway can act for a user without pretending to be the user. A sub-agent can receive a narrow capability without inheriting the parent's entire role. A worker can execute a step without becoming an unrestricted administrator. The chain should be explicit, attenuating, audience-bound, short-lived, revocable, and checked again at the point of side effect. Models may select among capabilities, but infrastructure must issue, constrain, and verify them. The result is a system that can explain not only what happened, but why each component was allowed to make that particular change.

Delegated identity connects the human, application, gateway, model, worker, tool, and provider without collapsing their responsibilities into one credential.
