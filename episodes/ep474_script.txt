Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we designed privacy-aware observability for an AI API gateway: measure latency, quality, cost, fairness, and policy outcomes without turning telemetry into a shadow copy of every prompt, response, and tool argument. Today we take the next logical step. We are designing multi-region and data-residency-aware routing: how to place inference requests, quotas, telemetry, failover, and reconciliation across regions while respecting sovereignty constraints, latency goals, provider boundaries, and the uncomfortable fact that a fallback route can change the compliance story.

A multi-region gateway is often introduced as a performance feature. Put servers close to users, reduce round-trip time, and keep serving traffic when one location fails. Those benefits are real, but they are not the whole design. For AI workloads, a region is not just a network location. It can determine where a prompt is processed, where a model provider stores request data, where tool calls execute, where logs and traces are exported, where usage evidence is reconciled, and which legal or contractual obligations apply.

The first principle is simple: location is part of the operation contract. A client may require that data stay inside the European Union, inside a specific country, or within a tenant-approved set of jurisdictions. Another workload may allow global processing for lower cost or better availability. The gateway must not treat the region as an implementation detail selected after the request has already been admitted. It must capture the allowed geography, the prohibited destinations, the required processing guarantees, and the evidence needed to prove that the decision was honored.

Start with an explicit residency policy. Do not infer it only from the user’s IP address. An IP can identify a network exit point, not the data owner, contractual entity, or legal basis for processing. Use authenticated tenant configuration, endpoint policy, workload classification, and explicit request attributes where appropriate. If a client claims a residency class that conflicts with its account policy, fail closed or route to a well-defined review path. A gateway should never turn an ambiguous location signal into an unreviewed cross-border transfer.

Represent geography as constraints, not a single label. A request might say: processing must occur in Germany; provider storage may occur in the European Economic Area; telemetry may leave the region only as an aggregate; tool execution must remain in the customer’s country; disaster recovery may use an approved second region after an incident. These are different constraints over different data classes and lifecycle stages. A single field called region cannot express them safely.

Create a residency envelope for each operation. The envelope can include an allowed processing set, an allowed storage set, an allowed telemetry set, an allowed tool-execution set, and a failover policy. It should also include the policy version, the source of each constraint, and whether the constraint is hard or negotiable. Hard constraints exclude a route. Negotiable preferences influence ranking but do not override stronger rules. This distinction prevents an optimizer from interpreting “prefer local” as permission to leave the approved boundary when local capacity is exhausted.

Do not confuse the gateway’s region with the provider’s region. A request can enter through a gateway in Frankfurt, traverse a global control plane, and be processed by a provider endpoint in another jurisdiction. Conversely, a provider may offer a regional endpoint while routing support traffic or backups elsewhere. The eligibility check must evaluate the full data path, not just the first server that receives the request. Document the path from client to gateway, gateway to provider, provider to storage, and gateway to telemetry destination.

Control-plane and data-plane placement deserve separate treatment. The data plane handles prompts, outputs, images, audio, and tool arguments. The control plane may handle route configuration, quota state, policy bundles, health signals, and deployment metadata. Some control-plane facts can be centralized safely; some are themselves sensitive. Tenant pseudonyms, usage totals, and policy decisions may reveal commercial activity even without raw content. Define which control-plane facts may cross regions, at what granularity, and under which encryption and access controls.

The gateway should make a placement decision before content transformation and provider dispatch. The sequence matters. Authenticate the principal, load the applicable residency policy, classify the operation, construct the residency envelope, filter ineligible routes, reserve capacity within the permitted set, and only then normalize or forward content. If a transformation service outside the boundary is called before the route decision, the request has already crossed the boundary even if the final model call stays local.

Regional admission is a capacity problem as well as a compliance problem. A tenant may have a global quota but separate regional commitments. A region may have healthy infrastructure but no eligible provider for a large context window, image input, tool use, or structured output contract. Reserve against the capacity that is actually eligible for this operation. Do not admit a request using global capacity and discover later that the only available provider violates its residency envelope.

This is where the budget and fairness work becomes geographic. Track quotas by tenant, workload class, route family, and region when the contract requires it. Maintain headroom for failover, but do not silently borrow capacity from a prohibited destination. If a regional quota is exhausted, the gateway should return a clear capacity response or use an explicitly approved alternative. “We were under the global limit” is not a valid explanation for breaking a local limit.

Routing should optimize only inside the eligible set. Rank candidates by latency, cost, capability, health, and quality evidence after hard policy filters have been applied. A fast global route is not a candidate for a country-bound request. A cheap route is not a candidate if its provider stores data in an unapproved location. An attractive fallback that changes the processing jurisdiction must be evaluated as a distinct route with a distinct policy outcome, not hidden inside a generic retry loop.

Latency objectives need honest definitions. Measure client-to-gateway latency, regional queue wait, gateway-to-provider connect time, provider time to first byte, and total completion time. A local gateway may reduce the first network hop while a distant provider increases generation time. A regional route may also have higher queueing during a local incident. The placement policy can express a latency target, but the gateway should expose which part of the path caused a miss rather than claiming that “the region was slow.”

Failover is the difficult case. Suppose a request is approved for a single country and the local provider times out. The gateway may have three options: wait and reconcile, return a clear failure, or use a pre-approved alternative. It must not fall back globally simply because another provider is healthy. The fallback decision is constrained by the residency envelope, the operation state, and the side-effect risk. If the request has streamed output or invoked a tool, another attempt may also be unsafe even when its region is approved.

Define failover modes explicitly. In strict mode, a hard residency boundary permits no cross-border fallback. In approved-set mode, the request may move among a named set of regions and providers. In emergency mode, a policy may allow a broader route only after an explicit customer or administrator authorization, with clear user-visible notice and extra audit evidence. Emergency mode should have an owner, expiration, scope, and review. It should never be a permanent hidden exception created during an outage.

Streaming adds another placement concern. Once the gateway sends the first byte to a client, it has created a user-visible commitment. If the provider stream stalls, switching providers may produce duplicate or incompatible content. The gateway should prefer a regional retry only when the operation remains retry-safe and no meaningful partial response has been delivered. After an uncertain provider outcome, preserve the operation state and reconcile before launching a new attempt. Geographic eligibility does not erase idempotency requirements.

Tools make residency multidimensional. A model may be processed in one approved region while a tool call touches a customer database in another. The tool may send an email, create a ticket, retrieve a document, or execute a payment. Define a residency envelope for each child operation, not just for the parent model call. The parent can be eligible while a particular tool is not. Tool authorization must check destination, data class, execution region, and external effect policy before dispatch.

Caching can quietly defeat residency. A response cache keyed by a prompt fingerprint may be replicated globally. A semantic cache may preserve sensitive fragments or embeddings whose location is easy to overlook. Define cache residency separately from model residency. Use regional cache partitions, tenant-aware encryption, short retention, and a policy that prevents an object created under one residency class from being served to a different class. If the cache cannot prove eligibility, bypass it rather than treating a hit as harmless.

Telemetry must follow the same rules as inference. In the previous episode, we separated low-risk aggregates from protected content references. Now add destination policy. A regional request may emit a global metric containing only bounded counts, but its detailed trace, policy evidence, usage record, or error body may need to remain local. Do not export raw provider request references, exact token counts, or operation-linked metadata across borders without checking the telemetry envelope.

Use region-scoped collectors where necessary. A local collector can receive detailed traces and retain them inside the approved boundary. A central service can receive minimized aggregates: route family, coarse latency bucket, error class, and count. If operators need global incident visibility, design a federated query or privacy-preserving summary rather than replicating every event into a global lake. The operational convenience of one dashboard is not automatically a sufficient purpose for cross-border data movement.

The operation ledger should record placement facts without becoming a copy of content. Store the requested residency class, resolved envelope, selected processing region, provider region, telemetry policy, and failover decision. Preserve policy and route versions so the choice can be reconstructed later. Store safe references to protected evidence rather than prompt text. An authorized reviewer should be able to answer where the operation went, why that route was eligible, and whether a fallback changed the boundary.

Unknown outcomes require geographic reconciliation. A provider may accept a request in an approved region while the gateway times out. The gateway may not know whether a tool side effect completed. A late usage callback may arrive from a provider system that is not in the same region. Reconciliation must preserve the original route and evidence, validate the callback’s provenance, and apply regional retention and access policy. Never “move” the ledger fact to a central system by copying the raw payload without checking its data class.

Provider adapters should expose residency-aware capabilities. The adapter contract should say which endpoint was used, which provider region was selected, whether the request was stored, what retention option was applied, and which policy acknowledgment was returned. If the provider cannot make these facts available, classify the route as unverifiable. It may still be usable for workloads with weaker requirements, but it should not qualify for a strict residency envelope merely because a marketing page lists a regional product.

Synthetic replay is especially valuable here. Preserve structural facts such as context-length bucket, tool schema, route constraints, deadline, output contract, and failure timing. Replace customer content with fixtures that stay in the test region. A replay can show that a regional adapter mishandled a streaming close event or that a fallback policy ignored a hard constraint without exporting the original prompt. The objective is to reproduce the decision boundary, not the customer’s data.

Test the negative paths deliberately. Create a request whose approved region has no eligible provider and verify that it is rejected or queued, not sent globally. Disable a regional collector and verify that traffic handling follows the defined telemetry degradation policy. Expire a provider residency attestation and confirm that routing changes. Make a local provider return a timeout after accepting a tool call and verify that the gateway reconciles before retrying. Inject a configuration that allows model processing locally but telemetry globally, and ensure the policy checker catches the mismatch.

Test race conditions across regions. Two regional gateways may observe the same client retry and both attempt admission. A quota lease may be issued in one location while a cancellation arrives in another. A provider callback may reach a different regional reconciler after the original operation has expired. Use globally unique operation and attempt identifiers, deterministic idempotency rules, and an authority model for reservations and finalization. Local autonomy is useful, but it must not create two conflicting business histories.

Clock and ordering problems become harder across regions. Use monotonic clocks for local duration and synchronized wall clocks for cross-region event comparison. Do not decide that a cancellation preceded a provider acceptance merely because timestamps disagree by a few milliseconds. Preserve event sequence, source region, clock quality, and causal identifiers. The ledger should distinguish observed ordering from inferred ordering and should surface uncertainty when a cross-region race cannot be resolved immediately.

Security boundaries should be regional too. Keys used to encrypt protected telemetry, caches, and content references may need to remain within a jurisdiction. Separate key scopes by region and data class. A global operator should not automatically possess every regional decryption key. Rotate keys without making historical evidence unreadable before its retention period ends, and define how deletion works when a key is destroyed. Cryptographic erasure can support retention enforcement, but only if backups and replicas use the same key discipline.

Access control needs location-aware views. An operations role may see route health globally but detailed operation metadata only in approved regions. Billing support may inspect usage evidence in the region where it was generated while seeing a minimized global summary elsewhere. A privacy administrator may reidentify a tenant pseudonym only under a regional authorization. Every query should carry purpose, scope, and data-class checks. Operation IDs are useful correlation keys, but they must not become universal permission tokens.

Watch for region-based fairness failures. A tenant in a smaller region may face worse availability because its approved provider set is narrower. A global tenant may enjoy more fallback options and lower queue delay. Measure admission success, time to first byte, degradation frequency, unknown outcomes, and cost by residency class and region. The answer is not to ignore residency constraints. It is to make the tradeoff visible, invest in local capacity, offer explicit service tiers, and avoid promising identical behavior where the eligible route sets are fundamentally different.

Configuration changes need the same provenance as request decisions. A change to an allowed region, provider endpoint, telemetry exporter, cache partition, or emergency failover mode can alter compliance for thousands of operations. Version policy bundles, require review for boundary changes, run semantic contract tests, and stage rollout by region. Record who approved the change, when it became active, and which operations saw each version. When an incident occurs, the gateway should be able to distinguish a provider outage from a route-policy deployment that accidentally widened the destination set.

Build a placement decision record that is small but complete. It should include the principal and workload class in protected form, the residency envelope, candidate rejection reasons, selected route, processing and tool regions, telemetry destination class, policy and capability versions, and the decision outcome. Keep rejection reasons typed: outside allowed set, missing attestation, insufficient local capacity, unsupported contract, or stale capability metadata. A typed record gives operators an explanation without copying the original content.

The operational rule is to filter first, optimize second, and explain always. First remove every route that violates hard geography, privacy, capability, or side-effect constraints. Then rank the remaining routes by latency, cost, health, and quality. Finally, preserve enough evidence to explain why the winner was chosen and why the alternatives were rejected. If a system ranks every global provider before checking policy, it has already made optimization the authority over compliance.

Multi-region architecture is therefore not just active-active deployment. It is a distributed policy system with regional execution, regional evidence, controlled federation, and explicit uncertainty. Availability improves when regions can operate independently, but trust improves only when their decisions are consistent with the same contracts. Central coordination can help with policy and quotas, while local components protect data boundaries and continue serving during control-plane interruptions. The design must specify what happens when the policy service is unavailable: use a cached signed policy, allow only safe known routes, or reject new work. Never improvise a destination.

A mature AI API gateway can make this practical. It can accept a request, construct a residency envelope, filter providers and tools, reserve eligible capacity, route locally when possible, fail over only within an approved set, keep detailed telemetry inside the right boundary, aggregate safely across regions, reconcile uncertain outcomes, and expose the placement evidence needed for support and audit. It can degrade capability without silently changing the compliance promise. It can measure regional fairness without pretending every region has the same route set.

This also changes how we think about user experience. A clear response such as “no compliant route is currently available” is better than a fast answer that quietly violates the customer’s policy. A response that says “queued in your approved region” is better than a mysterious timeout. If an emergency policy allows a broader destination, the customer should know what changed, what consent or administrative rule authorized it, and what data handling consequences follow. Compliance is not only a backend property; it is part of the product contract.

The sequence from the recent episodes now forms a coherent foundation. Budgets and fairness protect scarce capacity. The operation lifecycle gives one identity across attempts, streams, tools, usage, and reconciliation. Privacy-aware observability limits what evidence is collected and who can see it. Multi-region routing adds place to that evidence: where the request was processed, where its effects occurred, where its telemetry went, and which fallback boundaries were respected. Together, these disciplines make an AI gateway explainable across both time and geography.
