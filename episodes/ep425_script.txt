Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. Today we’re talking about tool outcome finality: how an AI API gateway knows when an external effect is really done, instead of confusing acceptance, processing, visibility, and completion.

An agent may call a provider and receive an immediate response. That response can mean many different things. The provider may have accepted the request, queued it, started processing, created a provisional record, or completed the business operation. These states are not interchangeable.

If a gateway reports every successful HTTP response as completed, agents and users will make decisions on evidence that is too weak. They may send a duplicate message, release a resource too early, treat an unfinished deployment as live, or assume a financial transaction has settled when it has only been accepted.

Finality is the point at which the system can safely treat an outcome as settled for a defined purpose. Different tools need different finality boundaries.

Start by defining the business outcome. For a message, finality may mean the provider accepted the message for delivery, or it may mean the recipient device confirmed delivery. For a payment, finality may mean authorization, capture, settlement, or ledger posting. For a deployment, it may mean rollout started, all instances updated, or health checks passed.

Do not define finality using only provider vocabulary. A provider’s “success” status may describe its internal workflow, while the customer needs a stronger business postcondition.

Create an outcome state machine. Useful states include received, authorized, dispatched, accepted, queued, processing, partially complete, completed, settled, failed before effect, canceled, disputed, and unknown.

Give every state a precise meaning and evidence requirement. “Accepted” should require proof of provider acceptance. “Completed” should require proof that the expected operation finished. “Settled” should require the business-level condition that makes the result durable for the relevant purpose.

Do not let clients infer state from missing errors. Tool adapters should return explicit status and finality fields rather than forcing a model or SDK to interpret a vague response.

Separate transport success from action success. A 200 response can contain a rejection, a queued job, a partial result, or a provider-side error represented inside JSON. Validate the response schema and semantic status before deciding what happened.

Separate provider completion from target-state verification. A provider can say that an update completed while a read from the target still shows an old version, a stale replica, or a different object.

Use postconditions for important writes. Define what must be observable before the gateway can call the action complete: a version transition, a ledger entry, a message ID, a deployment health state, a created resource, or a verified artifact.

Do not require immediate postcondition checks when the system is eventually consistent. Instead, define an observation window, consistency level, and acceptable evidence delay. A result can be complete but not yet visible through a particular read path.

Represent provisional outcomes honestly. “Accepted, awaiting processing” is more useful than “success,” and “completed according to provider; target verification pending” is more precise than “done.”

Make finality purpose-specific. A customer may need to know whether a request was accepted, while billing needs to know whether usage is chargeable, and a workflow engine may need to know whether a resource is ready for the next step.

One action can therefore have multiple finality dimensions. Record provider finality, gateway finality, target finality, business finality, and billing finality when they differ.

Do not force one global completed flag to represent all of these dimensions. It creates false certainty for at least one consumer.

Define which consumers may act on each state. A user interface may show progress at accepted. A workflow may wait for completed. A financial release may wait for settled. A compensation workflow may need a disputed or unknown state.

Make state transitions monotonic where possible. A late timeout should not move a settled action back to failed. If new evidence conflicts with a prior state, record a dispute or correction event with provenance.

Preserve uncertainty. If the gateway lost the connection after dispatch, the action may remain unknown until status lookup or target verification resolves it. Unknown is safer than inventing a final result.

Use stable action identities and execution receipts. Every state transition should point to the same logical action, its attempts, provider references, authorization decision, and evidence sources.

Record the evidence level for each transition. A provider acknowledgment, signed webhook, target read, downstream event, and human review may each provide different confidence and authority.

Do not treat the latest event as automatically authoritative. Resolve conflicts using source identity, operation identity, target scope, account, sequence, consistency, and documented precedence rules.

Verify that the evidence belongs to the right provider account and environment. A status from a test project must not finalize a production action, and a fallback account must not be assumed to observe the original operation.

Bind finality to target version when possible. If an update was authorized for version 12 and the target advances to version 14, the gateway must determine whether the intended postcondition was achieved or whether another actor changed the object.

For create operations, verify stable resource identity, tenant, owner, provider account, and creation context. Existence alone does not prove that this action created the resource.

For delete operations, distinguish deletion requested, deletion accepted, hidden, archived, and irreversibly removed. These states have different operational and compliance meanings.

For deployments, distinguish request accepted, rollout started, rollout progressing, rollout paused, rollout completed, health verified, and rollback completed. “Deployed” is not a single universal state.

For financial operations, distinguish authorization, capture, settlement, posting, reversal, and reconciliation. Do not release goods or close an invoice based on a weaker state than the business requires.

For messages, distinguish queued, accepted, sent, delivered, displayed, and bounced. The gateway should not claim recipient delivery when it only has a provider acceptance receipt.

For asynchronous model jobs, distinguish job submitted, processing, output available, output verified, and artifact retained. A completed generation job with a missing or corrupt artifact is not fully complete for the client.

For file operations, distinguish upload accepted, bytes stored, checksum verified, replicated, published, and deletion confirmed. A successful upload response may not prove durable availability.

For read operations, finality may be about observation rather than mutation. Record source, read timestamp, consistency level, cache age, and whether the data is known to be current enough for the intended decision.

Make caches finality-aware. A cached “completed” result may be safe for display but unsafe for triggering another side effect if the underlying state can be reversed or disputed.

Attach expiration to provisional states. An accepted action that remains processing beyond its expected window should trigger escalation, not remain indefinitely optimistic.

Use risk-based deadlines. A low-impact background task may remain pending for minutes. A production deployment, credential change, destructive operation, or payment may need a shorter deadline before human review or a safety stop.

Do not automatically retry when finality is absent. First reconcile the existing action. A missing final response is not evidence that no effect occurred.

When a provider offers idempotency and status lookup, use both. Idempotency prevents duplicate effect, while status lookup resolves whether the original effect reached finality.

If a provider offers only acceptance, document the limitation. Use target verification, delayed callbacks, ledger checks, or human review where appropriate, and expose the weaker finality to clients.

If no reliable finality evidence exists, restrict the tool’s use. High-impact actions should not depend on a provider contract that cannot distinguish accepted, failed, and completed.

Make fallback routing finality-aware. A fallback provider may have different asynchronous behavior, status semantics, or business guarantees. The original action’s finality contract may not transfer automatically.

If routing changes during processing, preserve the original provider reference and account. Do not merge a fallback attempt into the original final state without proving whether both providers acted.

Use parent and child receipts for workflows. A parent action may be accepted while one child is complete, another is processing, and a third is disputed. The parent should expose aggregate state without hiding child uncertainty.

Define aggregate rules explicitly. A batch may be complete only when all children are complete, or it may be partially complete with a safe continuation. Do not let an arbitrary “mostly done” threshold become an undocumented business rule.

Keep compensation separate. If a partially completed workflow requires rollback, the rollback is a new action with its own authorization, idempotency, receipt, and finality state.

Do not report compensation as if the original action never happened. Preserve the original effect and the subsequent repair.

Make human approvals finality-aware. An approver should see whether the proposed action is new, a retry, a compensation, or a continuation of an accepted but unresolved operation.

Do not ask for approval to repeat an action when the gateway can safely query its status. Reauthorization for observation and authorization for a new effect are different decisions.

Record finality expectations at authorization time. The policy may require settlement, health verification, or target-state confirmation before the action can unlock a downstream operation.

Carry those expectations through every adapter. A protocol translation layer must not drop the required postcondition merely because the provider API uses a simpler status model.

Validate the provider response before promoting it. Check operation identity, target, account, schema, status, timestamps, sequence, and completeness.

Treat malformed or truncated responses as insufficient evidence. A response that cannot prove finality should produce an explicit incomplete or unknown state.

Use signed callbacks and trusted event channels when available. Verify signature, source, audience, event identity, operation identity, and freshness before accepting a callback.

Make event consumers idempotent and order-aware. Repeated or out-of-order events should not create duplicate transitions or make a final action appear provisional again.

Use an append-only evidence log. Keep request, authorization, dispatch, acceptance, polling, callback, target read, and manual review as separate facts from the materialized current state.

Preserve historical truth. If the gateway believed an action was accepted at 10:00 and learned it was completed at 10:04, retain both observations and their times.

Do not rewrite a provisional result into a falsely clean history. Later certainty resolves uncertainty; it does not erase it.

Make receipt fields explicit. Include action identity, attempt IDs, provider reference, provider account, target, status, finality class, evidence level, observed timestamp, expiration, and next safe action.

Give clients safe next steps. For processing, poll or wait. For unknown, reconcile or contact support. For disputed, stop automated follow-up. For completed, continue only if the required finality class has been reached.

Do not let the model choose a stronger interpretation than the receipt. A model may summarize “the request was accepted,” but it must not say “the transfer settled” when the receipt only proves acceptance.

Use typed tool results. A schema with status, finality, evidence, retry policy, and next action is safer than free-form text.

Make finality semantics discoverable in documentation and SDKs. Developers should know what a returned status means, how long it may remain provisional, and which endpoint resolves it.

Do not hide provider-specific limitations. If delivery confirmation is unavailable, say so. Transparent weaker guarantees are safer than a universal success label.

Connect finality to billing. Provider-billed, gateway-billable, and customer-visible completed units may differ. Record the evidence and pricing rule used for each decision.

Do not charge twice because an action moved from accepted to completed. Status transitions describe one action, not new usage.

Use finality to drive workflow scheduling. Downstream steps should wait for the state they actually require instead of waking on every transport response.

Use timeouts as state transitions, not just exceptions. A deadline can move processing to overdue, unknown, or manual review depending on the action class.

Do not turn an overdue state directly into failed unless policy proves that no effect could have occurred. A slow provider may still complete after the client deadline.

Support cancellation semantics. Cancellation requested, cancellation accepted, canceled before effect, and effect completed before cancellation are distinct outcomes.

A cancellation response is not proof of cancellation. Verify the external state or preserve the action as unresolved.

Define what happens when finality is permanently unavailable. Options include human review, a customer-visible unknown state, bounded compensation, or a documented operational exception. Silent optimism is not an option.

Use manual review for high-impact disputes. Show the original intent, authorization, attempts, provider references, evidence, target state, and conflicting observations without exposing secrets.

Record manual decisions as evidence events. Include reviewer authority, scope, time, and rationale, while preserving all prior facts.

Test every boundary. Simulate provider acceptance without completion, completion without response, stale callbacks, delayed visibility, partial batches, duplicate attempts, regional failover, and conflicting target reads.

Test finality confusion in clients. Return accepted and verify that the SDK does not display completed. Return processing and verify that the workflow does not start the next destructive step.

Test cache staleness. Serve an old completed state, change the target, and verify that risk-sensitive actions require fresh evidence.

Test provider account substitution. Make a status lookup succeed only in another account and verify that the gateway refuses to merge unrelated evidence.

Test target-version races. Authorize an update against one version, change the object, and delay the provider response. The final state should be resolved only according to the documented version contract.

Test partial completion and compensation. Complete some child operations, leave others unknown, and verify that the parent remains partial or unresolved rather than falsely complete.

Test expiration. Let a provisional state exceed its expected window and verify escalation, safe client guidance, and no blind retry.

Test contradiction handling. Make provider status say complete while target verification says unchanged. The system should preserve both facts and mark the action disputed or unresolved.

Measure time to finality. Track duration from dispatch to acceptance, acceptance to completion, completion to target verification, and provider completion to gateway confirmation.

Measure false-finality incidents. Count cases where the gateway or client acted on completed status before the required evidence existed.

Track provisional outcomes by tool and provider. A high rate may be normal for asynchronous work, but it should be visible and tied to user experience and operational cost.

Track overdue and unknown actions by risk class. An unknown payment and an unknown metadata read should not share the same alert threshold.

Track evidence quality. Measure the percentage of actions with provider references, signed callbacks, target verification, and business-level confirmation.

Track duplicate attempts after provisional results. This reveals whether SDKs and agents understand the finality contract.

Track downstream actions triggered too early. These incidents often indicate that workflow rules are listening to transport success instead of business finality.

Keep state and evidence schemas versioned. Finality definitions evolve, but historical records must remain interpretable.

Never silently strengthen or weaken the meaning of “completed.” Introduce explicit finality classes and compatibility rules when semantics change.

The central design principle is simple: an external action is final only when the evidence meets the requirement of the decision that depends on it.

An AI API gateway should therefore distinguish accepted, processing, completed, settled, and verified outcomes; preserve uncertainty; bind evidence to the right action and target; and make every downstream step wait for the finality it truly needs.
