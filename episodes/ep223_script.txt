EP223: AI API Gateway Health Probes - Test Readiness Before You Route Production Traffic

Welcome back to AI Dev Tools, the Crazyrouter podcast. Today we are talking about health probes for AI API gateways. A process can be alive while its provider connections are broken, its policy service is unavailable, its queues are saturated, or its billing path is failing. If a load balancer sees only a successful HTTP response from a health endpoint, it may route production traffic into a system that is technically running but not ready to serve.

Start by separating health concepts. Liveness asks whether the process can continue running. Readiness asks whether it can accept new work. Routability asks whether a specific route, model, region, and workload class can be served. Dependency health asks whether required policy, capacity, provider, storage, and accounting components are available. One green signal cannot honestly represent all of these conditions.

A liveness probe should be cheap and local. It confirms that the process event loop, scheduler, and essential memory are functioning. It should not call every provider or perform a full model completion. If liveness depends on a slow external service, a temporary dependency outage can cause a restart storm and erase useful evidence. Keep liveness focused on whether the process should remain alive.

Readiness should reflect admission capability. Check whether the gateway can authenticate requests, evaluate required policy, reserve capacity, dispatch to at least an approved route, and finalize outcomes. Use bounded timeouts and cached dependency state where the contract permits it. If readiness is false, stop new traffic while allowing in-flight work to drain according to policy. Do not confuse a readiness failure with a process failure.

Routability is contextual. One model may be healthy while another is throttled. One region may have capacity while a second has a residency or network problem. A basic readiness endpoint should be complemented by route-level status with model, provider, region, capability, and workload-class dimensions. The router should consume the status relevant to the request instead of excluding or selecting an entire cluster based on one aggregate result.

Synthetic checks should test the real contract at a safe scale. A probe can send a tiny approved request through admission, policy, adapter, provider, response validation, usage accounting, and cleanup. Use a dedicated tenant, minimal content, strict cost limits, and an idempotent operation. Do not make a probe indistinguishable from customer traffic in billing or analytics. Its purpose is to test the path, not to generate realistic load.

Probe failures need classification. A connection failure, policy denial, capacity rejection, invalid provider response, billing mismatch, and deadline miss imply different actions. Record the phase, dependency, route, error class, latency, and observed state. A single failed probe may be noise; repeated failures in the same phase should reduce route confidence or remove it from admission. Avoid treating every failure as a reason to restart the whole gateway.

Use hysteresis and consecutive thresholds. Marking a route unhealthy after one packet loss creates flapping. Waiting for a long average can send too much traffic into a failing provider. Define failure counts, recovery counts, time windows, and minimum hold times. When a route is degraded, require stronger evidence to restore it than to keep it out of service. Publish the state transitions so operators can understand why routing changed.

Health status should include freshness. A green result from ten minutes ago is not equivalent to a recent successful check. Attach timestamp, expiry, probe version, configuration revision, and route identity. If the status is stale, treat it as unknown and follow a documented fail-safe policy. Unknown is valuable information; silently presenting stale green status is dangerous.

Dependency checks should respect criticality. Authentication, policy, capacity reservation, and accounting may be mandatory for a route. Analytics or optional enrichment may be noncritical. Define whether each dependency is required before admission, required before finalization, or reconciled asynchronously. A gateway can remain routable when an optional dashboard is delayed, but it should not claim success if the usage record required for billing was never captured.

Provider health must be more than HTTP reachability. A provider can accept a TCP connection and return an HTTP response while producing malformed streams, incorrect usage, excessive tail latency, or unsupported capabilities. Route probes should validate the specific contract that matters: completion shape, terminal event, schema, tool boundary, cancellation, or usage. Keep probes small and targeted so they do not become a second production workload.

Streaming routes need streaming probes. Verify first-byte latency, event order, heartbeat behavior, terminal semantics, and cancellation. A route that answers short non-streaming requests may still be unable to sustain long connections. Include idle and maximum-duration limits, and confirm that probe cancellation releases capacity. Otherwise the health system can mark a route healthy while its real streaming resource pool leaks.

Tool-capable routes require a safe tool test. Prefer a read-only fixture or a mock executor with no external side effect. Verify authorization, argument schema, refusal behavior, and executor connectivity separately. Never use a real mutating action as a health check. If a tool path is unavailable, mark that capability unhealthy without necessarily removing ordinary text generation from the route.

Health probes need their own budgets. Limit frequency, concurrency, tokens, provider cost, and retention. During an incident, do not increase probe volume until it competes with customer traffic. Use a small number of well-designed checks and sample deeper diagnostics only when a route is already degraded. A health check that causes overload is a self-inflicted outage.

Routing should react gradually. Remove a failing route from new admissions, drain or cancel work according to contract, and shift traffic only within policy, capability, residency, and budget constraints. Keep a small probe path to test recovery, but do not immediately send full traffic when one check succeeds. Recovery can be canaried by tenant class or a limited percentage, with rollback if the failure returns.

Health status is evidence for operators and automation. Record which probe ran, against which route and revision, with which effective policy, what it observed, and what action followed. Include correlation IDs and provider request IDs when available. Do not put secrets or raw customer data in probe records. Make it possible to compare a route's probe results with customer failure capsules without exposing protected content.

False positives and false negatives have different costs. A false positive keeps traffic on a bad route and can amplify an incident. A false negative removes useful capacity and increases load elsewhere. Tune thresholds using real customer outcomes, not probe success alone. Correlate health state with deadline misses, malformed responses, policy gaps, reservation leaks, and billing reconciliation failures.

Tests should exercise the health system itself. Make policy unavailable, slow the provider, return malformed stream events, exhaust capacity, expire cached status, break cancellation, and interrupt the accounting path. Verify that liveness, readiness, and routability respond independently. Confirm that traffic drains safely, probes stay within budget, unknown state is visible, and recovery does not create a thundering herd.

The practical checklist is clear. Separate liveness, readiness, routability, and dependency health. Keep liveness local. Make readiness reflect admission and finalization capability. Probe real route contracts with tiny safe traffic. Classify failures, track freshness, use hysteresis, and respect dependency criticality. Give streams and tools dedicated checks, bound probe budgets, drain unhealthy routes gradually, and canary recovery.

The larger lesson is that health is a routing decision, not a green badge. An AI gateway is ready only when it can uphold the contract for the work it is about to accept. Well-designed probes test that claim at the right scope, produce evidence, and help automation protect users without turning every dependency blip into a restart or a traffic stampede.
