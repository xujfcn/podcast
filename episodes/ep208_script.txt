EP208: AI API Gateway Overload Control - Stay Useful When Demand Exceeds Capacity

Welcome back to AI Dev Tools - The Crazyrouter Podcast. Today we are looking at a reliability problem that appears only when an AI product starts succeeding: more work arrives than the system can safely complete. Providers slow down, tenant traffic spikes, agents create bursts of parallel calls, and queues grow faster than workers can drain them. The gateway must decide what enters, what waits, what degrades, and what is rejected. That is overload control.

Overload is not the same as an outage. During an outage, a dependency may be unavailable. During overload, useful capacity still exists, but demand exceeds it. A gateway that accepts everything can turn a temporary traffic spike into a broad failure. Latency rises, callers time out, abandoned work keeps consuming provider capacity, retries add more demand, and eventually even high-priority requests fail. Reliability means preserving useful service, not maximizing the number of requests admitted.

The first principle is simple: bound every queue. An unbounded queue does not create capacity; it hides excess demand in memory and latency. Set limits for request count, estimated tokens, and waiting time. Token-aware limits matter because one large context can consume more provider time and memory than hundreds of small classifications. A queue should answer a concrete question: how much work can still finish before its callers no longer care?

Measure queue age, not only queue depth. A depth of one hundred requests may be healthy for a fast embedding route and disastrous for a slow reasoning model. Track the oldest item, predicted start time, and predicted completion time by route class. If a request cannot plausibly begin before its deadline, reject it immediately. Fast rejection gives the caller time to choose a cheaper model, reduce the prompt, or postpone the task.

Admission control belongs before expensive work. Validate authentication and basic syntax first, but do not upload large files, tokenize huge prompts, reserve tool sessions, or open provider streams before checking capacity. Use a lightweight estimate of request cost: input size, requested output limit, model class, tool usage, and recent route throughput. The estimate will be imperfect. It only needs to separate obviously cheap work from obviously expensive work well enough to protect the system.

Capacity is multi-dimensional. A gateway can have available HTTP connections but no remaining token throughput. It can have provider quota but no local memory for stream buffers. It can have global capacity while one region or model pool is saturated. Build admission decisions from the limiting resource for each route. A single requests-per-second limit is easy to operate, but it treats a ten-token lookup and a fifty-thousand-token generation as equivalent.

Use concurrency limits where work duration varies. A token bucket controls arrival rate, while a concurrency limiter controls how much work is active. AI requests often need both. The rate limit absorbs short bursts. The concurrency limit prevents long generations from occupying every provider slot. Adapt the limit slowly from observed latency and error rates, with hard minimum and maximum bounds. A controller that reacts too quickly can oscillate between flooding and starving a provider.

Queues need scheduling policy, not just first in, first out. Pure FIFO lets a few large jobs block many interactive requests. Separate workload classes such as interactive, background, batch, and agent tool calls. Give each class a bounded share and a clear maximum wait. Within a class, consider cost-aware scheduling so small requests can make progress without starving large ones. Fairness is an operational contract, not an accidental property of arrival order.

Tenant isolation is essential. One customer launching a batch should not consume every route slot. Set per-tenant concurrency and token budgets, then keep a reserved portion of capacity for other tenants and control traffic. Weighted fair sharing can let larger plans use more capacity without granting them the ability to cause a global outage. Publish the effective limits and return machine-readable reasons when a tenant reaches them.

Not every request deserves the same protection. Health checks, authentication refreshes, cancellation signals, and operator probes should remain responsive during overload. Reserve a small control-plane lane for them. If cancellation is queued behind generation work, abandoned requests continue burning scarce capacity. If health checks fail only because the normal worker pool is full, an orchestrator may restart healthy instances and make the overload worse.

When rejecting work, be precise. Use an overload status that distinguishes tenant quota, route saturation, queue timeout, and provider capacity. Return a retry-after value only when the gateway has a defensible estimate. Include a request identifier and safe alternatives, such as an available model class or asynchronous submission route. Do not tell every caller to retry in one second. Coordinated retries create another spike.

Retry advice should include randomness and a horizon. A client needs a minimum delay, a maximum delay, and an indication of whether conditions are likely to improve. The gateway can expose a retry token or admission ticket for workloads that must preserve order, but it should not promise a place in line unless it can enforce that promise. For background jobs, durable queues are usually better than keeping an HTTP request open.

Load shedding should happen in layers. First stop optional work: shadow traffic, duplicate evaluations, speculative routes, and nonessential logging enrichment. Next reduce expensive features, such as multiple candidate generations or oversized output limits, when the application has explicitly allowed degradation. Then reject lower-priority new work. Never silently change the model or quality level when that would violate the caller's accuracy, policy, or data residency requirements.

Streaming changes the capacity model. A stream may hold a connection for minutes while producing tokens slowly. Count active streams separately, monitor time to first token and inter-token gaps, and close streams promptly after caller disconnects. Backpressure must propagate from the client through the gateway to the provider. Buffering unlimited events for a slow consumer shifts overload into gateway memory and delays detection of abandoned work.

Agents amplify overload because one user action can create a tree of model and tool calls. Carry a workload identity and parent operation ID through every branch. Enforce a total concurrency budget for the operation, not only per HTTP request. A loop that launches twenty tools and then retries the model can otherwise appear as many unrelated, individually valid calls. Operation-level budgets keep fan-out proportional to the original intent.

Fallback is useful only when spare capacity is real. Moving traffic from a saturated provider to a second provider can save requests, but it can also overload the fallback and remove your last healthy route. Reserve fallback headroom and account for capability differences before shifting traffic. Ramp traffic gradually, observe queue age and completion quality, and stop the transfer when the destination approaches its protection threshold.

Overload signals should be visible to both operators and developers. Track admitted, queued, shed, cancelled, and completed work by tenant class and route. Measure queue delay separately from provider latency. Record estimated versus actual token cost to improve admission models. Alert on sustained rejection and growing queue age, but also alert when cancellation latency rises, because that indicates capacity is being spent on work nobody wants.

Test overload behavior deliberately. Replay bursts with a mix of small and large prompts, slow streams, disconnected clients, and agent fan-out. Verify that queues remain bounded, high-priority traffic continues, tenant shares hold, and recovery does not release a retry storm. Failure tests should include a provider that becomes slow rather than fully unavailable. Slow dependencies are where uncontrolled queues do the most damage.

Recovery needs discipline. When capacity returns, do not open every gate at once. Drain queues with a controlled ramp, expire work whose deadlines passed, and keep admission limits conservative until latency stabilizes. Watch for retry traffic that was scheduled while the system was overloaded. A stable recovery may complete fewer requests in its first minute, but it avoids a second collapse.

The practical checklist is compact. Bound queues by count, cost, and age. Admit work against the actual limiting resources. Isolate tenants and workload classes. Reserve capacity for cancellation and control traffic. Reject early with precise, jitter-friendly guidance. Shed optional work before essential work. Propagate streaming backpressure. Budget agent fan-out as one operation. Protect fallback headroom, and reopen capacity gradually.

The larger lesson is that overload control is product behavior. It determines whose work completes, how long developers wait, and whether a busy service remains predictable. A gateway earns trust when it says no before accepting work it cannot finish, preserves capacity for valuable requests, and gives callers enough information to respond intelligently. That is how an AI API platform stays useful when demand exceeds capacity.
