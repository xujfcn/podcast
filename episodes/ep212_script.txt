EP212: AI API Gateway Response Acceptance - Do Not Confuse HTTP 200 with Success

Welcome back to AI Dev Tools, the Crazyrouter podcast. Today we are talking about response acceptance at an AI API gateway. A provider returns HTTP two hundred, tokens arrive, and the request looks successful. But the answer may be truncated, the JSON may not match its schema, a tool call may be incomplete, or the stream may end without a final usage event. Transport success only says that bytes moved. Developer reliability depends on knowing whether the result is actually safe to use.

This distinction matters because AI responses are not ordinary static payloads. A completion can be syntactically valid while failing the application's purpose. A streaming connection can close cleanly after delivering only part of a logical message. A model can produce a tool name with malformed arguments. A gateway that reports all of these as success pushes uncertainty into every client and makes failures appear far away from their cause.

Start by defining an acceptance contract for each request type. For plain text, acceptance may require at least one content event and a recognized terminal reason. For structured output, it may require valid JSON that conforms to a declared schema. For tool calling, it may require a known tool, complete arguments, and a stable call identifier. For multimodal work, it may include valid media references, content type, dimensions, or checksums. The contract should be explicit before routing begins.

Keep transport state separate from outcome state. Transport state answers whether the provider connection opened, transferred data, and closed. Outcome state answers whether the gateway accepted the response for the requested contract. A useful response envelope can report both: provider transport completed, outcome rejected because the schema failed. That is more actionable than converting every problem into a generic five hundred error or quietly passing bad data through.

Finish reasons deserve first-class treatment. Providers use values such as stop, length, content filter, tool call, and error, but their meanings are not perfectly uniform. Normalize them into a small gateway taxonomy while preserving the original value for diagnosis. A length limit is usually a complete transport exchange but an incomplete application result. A content filter may be an intentional policy outcome, not a provider outage. Routing and retry decisions should use those distinctions.

Streaming needs an explicit commit point. Tokens before that point are provisional. The gateway should not claim a fully accepted response until it observes the expected terminal event, completes any final validation, and records the operation outcome. Clients can still render provisional tokens for responsiveness, but the protocol should expose whether the stream ended as accepted, rejected, or indeterminate. A closed socket is not a commit record.

For server-sent events, validate the event sequence as well as individual chunks. Check that identifiers remain consistent, tool argument fragments assemble in order, terminal markers do not appear twice, and no content arrives after a terminal state. Bound the size of assembly buffers. If a provider violates the sequence, stop presenting the stream as normal and return a stable protocol error with the provider request identifier attached.

Structured outputs require two layers of validation. First, parse the payload according to the declared encoding. Second, validate it against the exact schema version associated with the request. Do not repair arbitrary JSON silently and call it accepted. If the gateway offers repair, expose that as a separate transformation with its own status, model cost, and evidence. Developers need to know whether they received the model's valid output or a gateway-generated correction.

Tool calls add an authorization boundary. Schema-valid arguments do not prove that a call is allowed. Acceptance should verify the tool exists in the request's capability set, the call identifier is unique, required arguments are present, and limits such as maximum calls are respected. The gateway can accept the tool proposal without executing it. Keeping proposal acceptance separate from side-effect execution makes agent workflows easier to reason about.

Usage data also needs consistency checks. Token counts may arrive only in the final stream event or in a later provider record. Compare reported totals with known request and output bounds, reject impossible negative or decreasing counters, and mark usage as estimated when final evidence is missing. Do not reject an otherwise useful answer only because billing evidence is delayed, but do not label the charge final either.

Retries after rejection must be deliberate. A malformed schema result might justify one constrained retry with the same logical request identifier and a fresh provider attempt identifier. A content policy result usually should not. A truncated answer may be continued, regenerated, or returned as partial depending on the contract. Put these decisions in policy, cap their cost, and expose the attempts so a developer can see how the accepted result was produced.

Fallback routing must preserve acceptance requirements. Switching providers is not useful if the fallback ignores the requested schema, lacks the required tool mode, or represents finish reasons differently. Filter routes by capability before sending traffic, then apply the same gateway-level acceptance contract after every attempt. Provider diversity should increase availability without weakening the result developers receive.

Return evidence without leaking sensitive content. Include a gateway operation identifier, provider attempt identifier, normalized finish reason, acceptance status, schema version, validation error code, usage status, and timing. Avoid logging full prompts, generated text, or tool arguments by default. Hashes, sizes, field paths, and bounded error summaries often provide enough evidence to debug the contract safely.

Metrics should measure accepted results, not just successful HTTP calls. Track transport success, acceptance success, rejection reason, truncated output, invalid schema, malformed stream sequence, unknown finish reason, and delayed usage reconciliation. Break these down by provider, model, adapter version, and request contract. A provider can have excellent uptime while producing a rising rate of unusable outcomes.

Test the boundary with adversarial fixtures. Return HTTP two hundred with an empty body. Close a stream before the terminal event. Split a tool argument across unusual chunk boundaries. Send valid JSON for the wrong schema version. Duplicate the final event. Report impossible usage. Then verify that the gateway classifies each case consistently, releases resources, records evidence, and never upgrades an indeterminate result into accepted success.

The developer interface should stay predictable. Let the request declare an acceptance mode such as text, JSON schema, or tool proposal. Return a stable outcome object for non-streaming calls and a terminal outcome event for streams. Document which failures are retryable and whether partial content may be displayed. SDKs should make the final acceptance state easy to check instead of treating stream completion as implicit success.

The practical checklist is straightforward. Define acceptance before routing. Separate transport completion from usable outcome. Normalize finish reasons. Require a terminal commit event for streams. Validate schemas and tool proposals at the gateway boundary. Preserve capability requirements during fallback. Mark uncertain usage honestly. Retry rejected outcomes only under bounded policy. Measure accepted results, and test malformed provider behavior as carefully as connection failures.

The larger lesson is that an AI gateway is not only a traffic router. It is a trust boundary between variable provider behavior and stable developer contracts. HTTP two hundred is useful evidence, but it is not the final verdict. Reliability improves when the gateway accepts a result only after it can explain why that result satisfies the request.
