Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we designed safe tool execution at the AI gateway: capabilities, schemas, authorization, approvals, idempotency, isolated workers, bounded budgets, and honest outcome states. Today we move one level up. A single tool call is manageable when its boundary is clear. Real agent work is a sequence of calls that may run for minutes, hours, or days, across services that fail independently. We are designing durable agent workflows and saga-style orchestration: how to persist intent, resume after crashes, fence stale workers, coordinate long-running steps, compensate safely, and stop an agent from forgetting what it already did.

The motivating problem is simple to describe. A customer asks an agent to onboard a new employee. The workflow might create an identity, provision a mailbox, add team memberships, issue equipment, open a payroll record, and notify a manager. Each step touches a different system. The model may help decide what is needed, but it must not be the database of record for progress. If the process crashes after the mailbox is created, restarting the prompt and asking what happened can produce a second mailbox or skip a required audit step. Durable orchestration begins by treating workflow state as infrastructure, not conversational context.

Start with a durable workflow identity. Give every run a workflow ID, tenant, requester, purpose, policy context, creation time, deadline, and version of the workflow definition. Every step receives a stable step ID, not just a position such as “step three.” A stable identity lets the system distinguish a retry of the same logical action from a new action that happens to look similar. Store the model attempt that proposed the plan, but do not confuse that proposal with the authoritative workflow. The workflow definition, policy decisions, and recorded facts determine what may happen next.

Separate the plan from the execution graph. A plan is a proposed sequence or set of actions. The execution graph is a validated, policy-approved representation with dependencies, conditions, timeouts, compensation rules, and concurrency limits. A model can suggest “provision standard access,” but the gateway should compile that suggestion into explicit steps such as resolve the employee, verify the department, create the account, and attach approved groups. If compilation finds ambiguity, pause for clarification or approval. Do not let a free-form plan mutate into hidden branches while workers are already changing state.

The workflow definition needs a version. If a policy or business rule changes while a workflow is running, silently replacing its semantics creates a difficult audit problem. Pin a run to a definition version, then define which changes can be adopted safely. A patch that only improves diagnostics may be harmless. A change from “manager approval required” to “no approval required” is not a harmless patch. New runs should use the newest definition; existing runs should either finish under their pinned version or pass through an explicit migration that records the old and new semantics and rechecks authorization.

Persistence must survive the failures you actually expect. Keep workflow state in durable storage with transactional updates, not only in a process memory object or a chat transcript. A useful state record includes current status, completed step outcomes, pending timers, compensation status, lease information, version, last event position, and a hash of the relevant definition. Store immutable events such as WorkflowStarted, StepScheduled, StepDispatched, ProviderAcknowledged, StepCompleted, StepUnknown, CompensationRequested, and WorkflowClosed. A materialized state view makes reads fast; the event history makes recovery and audit possible.

Use an event history carefully. Event sourcing does not mean logging every internal variable forever. Events should represent meaningful external or state transitions, with sensitive values minimized and references or hashes used when raw data is unnecessary. Make event names precise. “StepFinished” is weaker than “PaymentAuthorizationAccepted” or “ShipmentBookingOutcomeUnknown.” Include causation and correlation identifiers so a compensation can be traced back to the step that required it. When an event is appended, enforce an expected version. That optimistic concurrency check prevents two workers from both advancing the same workflow from the same prior state.

A durable workflow needs a clear state machine. Distinguish draft, validated, awaiting approval, ready, running, waiting, succeeded, failed, compensating, partially completed, cancelled, expired, and outcome unknown. Do not use one generic “in progress” state for all of them. Each state should define legal transitions and who may cause them. A cancelled workflow must not be allowed to start a step that was queued before cancellation. A compensation failure should not be represented as an ordinary workflow failure if a real-world side effect remains. State names are operational commitments: they tell clients, operators, and recovery code what is safe to do next.

The most important recovery rule is this: never infer execution from intention. A model message saying “I created the account” is not evidence. A worker log saying “dispatch started” is not proof that the provider committed. The workflow should advance based on durable gateway and provider evidence. If the process dies after sending a request but before recording the response, the step is outcome-unknown. Recovery must reconcile by querying a provider request ID, an idempotency key, or a domain-specific status endpoint. If no reconciliation path exists, the system should preserve uncertainty and route the case to a controlled review path.

This is where the saga pattern helps. A saga is a sequence or graph of local transactions, each committed independently, with compensating actions for steps that need to be undone when a later step fails. It is not a distributed transaction and it does not restore the past perfectly. If the workflow creates a user, sends an email, and then fails to provision a laptop, deleting the user may not unsend the email. Compensation is a new operation with its own authorization, idempotency key, evidence, and failure modes. The workflow must tell the truth about what was reversed, what cannot be reversed, and what still needs attention.

Declare compensation at design time. For each side-effecting step, record whether it is reversible, compensatable, manually recoverable, or irreversible. Define the compensation input from durable facts, not from a model improvisation after the incident. Specify whether compensation runs automatically, requires approval, or is prohibited after a certain point. A refund may compensate a charge, but it may have a different financial policy and settlement delay. Removing a group membership may compensate an access grant, but it may not address data already downloaded. The compensation contract should describe limits rather than promising magical rollback.

Use forward recovery when it is safer than rollback. Suppose a shipping label was purchased and the warehouse reservation failed. Cancelling the label might create fees and still leave the order blocked. A better recovery could be to select an approved alternate carrier and continue, subject to policy and a budget. Saga orchestration should support both compensation and continuation paths. The decision must come from a workflow policy or approved operator action, not from the language model optimizing for a tidy narrative. A workflow that has reached a real-world side effect needs an operationally useful path, not merely a grammatically complete answer.

Long-running steps require asynchronous handles. A worker should not hold a gateway request open while waiting for an external approval, batch job, shipment, or cloud deployment. Dispatch the operation, persist the provider operation ID, and transition to waiting. A timer or event can wake the workflow to poll or process a callback. Every poll must recheck that the workflow is still authorized and not superseded by cancellation. Use bounded polling with backoff, provider rate limits, and a reconciliation deadline. If a callback arrives twice, deduplicate it. If it arrives after the workflow is cancelled, record it and apply the state machine’s late-event rules.

Timers are part of the durable contract. Approval expiry, retry delays, maintenance windows, leases, and overall workflow deadlines should be represented as durable timers, not sleep calls in a worker. A process restart should not erase a scheduled retry. Timer handlers must be idempotent because delivery may be duplicated. At execution time, verify that the timer still applies to the current workflow version and state. A stale timeout must not cancel a workflow that was already extended under a recorded approval. Include the timer ID and expected state version in its wake-up command so a late message is safely ignored.

Workers need leases and fencing. When a worker claims a step, it receives a lease with an expiry and a fencing token. If the worker pauses due to a network partition and its lease expires, another worker may take over. The old worker must not be able to dispatch a late side effect after recovery. Pass the fencing token to the workflow store and, where possible, to the downstream adapter. The store rejects state transitions from an old token. The adapter rejects dispatch if the workflow step is no longer current. A timeout alone is not enough; without fencing, “at least once” delivery can become duplicate production work.

Idempotency belongs at every side-effect boundary. The workflow-level identity prevents duplicate runs of the same business request. The step identity prevents duplicate logical steps inside that run. The provider idempotency key protects the external API from retried dispatch. Keep these identities distinct and related. If a user intentionally asks to run the same onboarding process again, it should have a new workflow ID even if the employee and target are identical. If the same worker retries a timed-out step, it should reuse the same step and provider key. Never generate a fresh key merely because a process restarted.

Concurrency must be explicit in a workflow graph. Independent read steps can often run in parallel. Two writes to the same account, quota, or membership set may need serialization. Define resource locks, optimistic versions, or conditional writes. A workflow can reserve a budget before fan-out and limit the number of children it creates. When a parent is cancelled, specify whether children stop, finish, or compensate. Do not let a model infer safe parallelism from the visual order of a prompt. A graph with explicit dependencies is both more efficient and more honest about which operations can race.

Nested agent calls need a hard boundary. A durable workflow may ask a model to draft a plan or choose among approved alternatives, but every model turn must be tied to a workflow state, a budget, and a maximum duration. Persist the model request, available capability set, response classification, and resulting decision. If the model asks for a step that is not in the compiled graph, reject it and record a policy event. If it repeats an equivalent decision, use the existing result rather than opening another branch. The model is a planner inside the workflow, not the workflow engine itself.

Workflow pause and resume should preserve context without preserving unsafe assumptions. When a run waits for a human answer, store the exact question, the options shown, the facts used, and the expiry. When the answer arrives, bind it to the workflow ID, tenant, user, and expected state version. Reauthorize actions that may have become stale. For example, “approve the transfer” should not remain valid after the amount, destination, or account version changes. Resumption is a fresh control point, not permission to replay a plan from last week unchanged.

Cancellation also has a linearization point. Before a step is dispatched, cancellation can prevent it. After dispatch, cancellation becomes a request to stop, a provider cancellation attempt, or a reconciliation task. Record which event won the race. If the provider supports cancellation, capture its acknowledgment and final outcome. If cancellation is not supported, let the workflow show in-flight or unknown status rather than claiming success. A parent workflow can be cancelled while a child operation continues in the external world; the cancellation handler must create the right observation and compensation work instead of deleting the child record.

Failure classification drives recovery. A validation failure means the graph or inputs need correction. A policy denial means changing credentials or casing is not a recovery. A provider rate limit can wait. A connection failure before dispatch may retry. A timeout after dispatch requires reconciliation. A permanent business rejection may allow a defined alternate path. An executor crash requires checking the ledger and lease before deciding. Put this matrix in the workflow definition and adapters. Generic retry libraries are dangerous when they cannot distinguish “never sent” from “sent, but response lost.”

Backpressure applies across the whole workflow system. Limit active runs per tenant, queued steps per provider, concurrent compensations, fan-out width, and total side-effect budget. A single request to “audit all repositories” should not create unlimited child workflows. Use admission control before expanding a graph, then reserve capacity for critical compensation and reconciliation work. When a limit is reached, pause with a structured reason and a retry time. Do not drop events or let a model keep proposing equivalent work. A durable system is allowed to be slower; it is not allowed to forget obligations because the queue is full.

Observability must make a workflow explainable without making private payloads public. Expose workflow ID, status, current step, next wake time, deadline, attempt counts, and uncertainty state. Link traces from model planning to policy evaluation, worker dispatch, provider operation, and compensation. Redact credentials and minimize sensitive arguments. Operators need enough evidence to decide what to do, but not unrestricted access to customer data. Metrics should include time spent waiting for approval, unknown-outcome rate, compensation success rate, stale-worker rejection count, workflow age, and the number of runs requiring manual recovery. These measure reliability better than model latency alone.

Build a recovery console around evidence. An operator should be able to inspect the event timeline, provider request IDs, normalized inputs, policy versions, and available reconciliation actions. The console should not offer a dangerous “rerun everything” button. It should present safe choices: reconcile this step, retry a pre-dispatch failure, approve a defined compensation, resume from a specific state, or close as manually resolved with a reason. Require elevated approval for irreversible actions and record the operator identity. Recovery tooling is part of the safety boundary, not an internal shortcut around it.

Testing durable workflows means killing them at every seam. Crash after event append but before scheduling. Crash after dispatch but before acknowledgment. Deliver a callback twice, out of order, and after cancellation. Let a lease expire while a worker is paused. Change authorization during a long wait. Replay a timer after the workflow has advanced. Return a provider success with a delayed side effect, then return an error after the side effect committed. Create a partial fan-out and exhaust the budget. Verify that replay produces the same decisions, no duplicate side effects, and a visible unknown state when evidence is insufficient.

Use deterministic replay for logic and real reconciliation for effects. The event history should let you reconstruct why a workflow selected a branch without calling the model again or relying on a changed prompt. For model-assisted decisions, store the bounded input, model identifier, tool set, output, and decision classification; then decide whether replay uses the original decision or requires a new approved evaluation. External systems cannot be replayed safely, so adapters need fake providers and reconciliation tests. Separate “we can replay the orchestration logic” from “we can repeat the external action.” The first is useful; the second may be dangerous.

The public API should expose durable control surfaces. Create a workflow and return its ID, status URL, definition version, and cancellation endpoint. Let clients retrieve a typed timeline or a privacy-filtered summary. Provide step-level status with retryability, side-effect classification, and reconciliation guidance. Webhooks and streams should be resumable using an event cursor. If a client disconnects, it can reconnect without assuming that silence means failure. If the workflow is complete, return the final business outcome and any unresolved obligations. If it is partially completed or unknown, say exactly that.

A practical implementation pipeline now comes together. Authenticate the requester and create a workflow identity. Compile the model’s proposal into a versioned, policy-filtered execution graph. Validate dependencies, resources, budgets, approvals, and compensation metadata. Persist the initial event and state transactionally. Schedule ready steps with stable identities. Acquire fenced leases and recheck authorization immediately before dispatch. Execute through the isolated tool boundary using provider idempotency. Record evidence, reconcile unknowns, advance the graph, and schedule the next work. On failure, select a declared alternate or compensation path. Close only when all side effects and unresolved obligations have a truthful terminal classification.

The key lesson is that agent reliability is mostly memory with rules. A model can reason about the next step, but it should not be trusted to remember which step committed after a crash, whether an approval is still valid, or whether a timeout hides a charge. Durable state, immutable evidence, leases, fencing, idempotency, and explicit compensation turn a fragile conversation into an accountable process. Saga orchestration does not make distributed systems magically atomic. It makes partial completion visible and gives the organization a controlled way to recover.

This episode extends the series from safe tool execution to safe multi-step work. Provider contracts define what each external system can guarantee. Policy distribution controls the capabilities and data boundaries available to a run. Admission control limits workflow fan-out, worker capacity, and compensation load. Streaming exposes progress and resumable events. The operation ledger records evidence for individual calls. Durable orchestration connects those calls into a state machine that can survive time, failure, cancellation, and human intervention.
