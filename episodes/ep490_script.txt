Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we built a canonical operation history that separates facts, interpretations, and decisions. We preserved late provider corrections without rewriting the past, versioned reconciliation rules, and kept historical uncertainty distinct from the current best-supported view. Today we look at a related change that can affect both the future and the work already in flight: a provider contract migration. A provider changes its model behavior, API semantics, data-retention terms, pricing, region, safety guarantees, or tool protocol. The endpoint still answers, but the promise attached to the answer has changed. Our topic is provider contract migration safety: move traffic without creating a compatibility gap between old decisions, new behavior, and customer expectations.

Consider a gateway using a provider that guarantees structured JSON output, one-hour request retention, and processing in a specific region. The provider announces a model upgrade. The new version is faster and cheaper, but its schema handling differs, its default retention is longer, and its region selection is less specific. New traffic can be routed to the replacement after a feature flag changes. But what about queued jobs authorized under the old contract? What about long-running workflows, retries, provider tokens, billing estimates, and customer promises made before the migration? A route change is not just an endpoint update. It is a change to the set of guarantees under which work was admitted.

Start by defining the contract explicitly. A provider contract should include endpoint identity, model or service version, capabilities, input and output semantics, error behavior, latency expectations, usage fields, pricing rules, cancellation guarantees, idempotency support, data-retention terms, processing regions, security controls, and support obligations. Record which parts are contractual, which are observed behavior, and which are only operational assumptions. A model name alone is not a contract. Two endpoints with the same friendly name can differ in tool calling, context limits, logging, billing, or data residency.

Bind every route decision to a contract version. When the gateway admits an operation, record the provider contract, policy version, capability requirements, data class, region, pricing class, and customer-facing guarantees. An attempt should carry the contract digest it was evaluated against. This does not mean that every in-flight request must finish under an obsolete contract. It means the system can determine what was promised, what changed, and whether continuation, replay, or migration requires a fresh decision.

Separate contract migration from provider replacement. A replacement may be another account, region, model version, API protocol, or entirely different vendor. Each has a different compatibility risk. A patch release may preserve semantics but change latency or usage reporting. A model upgrade may preserve the API while changing output quality, refusals, or tool arguments. A vendor migration may change all of these at once. Classify the change by affected dimensions and choose controls proportional to the risk. Do not use one generic “provider updated” workflow for a pricing-only change and a data-processing change.

Build a compatibility matrix before changing traffic. Compare old and new contracts across input limits, output schema, tokenization, modalities, tool calling, streaming events, error codes, safety behavior, context retention, region, logging, cancellation, idempotency, usage reporting, and price. Mark each dimension compatible, incompatible, unknown, or conditionally compatible. For conditional compatibility, state the adapter, validator, or policy obligation required. Unknown should not become compatible merely because a basic request succeeded. The matrix is a decision artifact, not a documentation exercise.

Use contract tests with representative but safe fixtures. Test normal responses, malformed input, long context, structured output, tool calls, streaming, refusals, rate limits, timeouts, cancellation, usage reporting, and provider status lookup. Include edge cases that caused historical incidents. Use synthetic or redacted data and stable expected properties rather than brittle exact text comparisons. A contract test should verify the guarantee the client relies on: schema validity, event ordering, no unexpected data retention, correct region, or idempotent retry behavior.

Shadow traffic can reveal semantic drift, but it must be controlled. Do not send sensitive customer data to a new provider merely to compare outputs unless the route is authorized for that data and the provider contract permits it. Prefer synthetic traffic, redacted inputs, or a private evaluation corpus. If live shadowing is justified, separate shadow requests from customer-visible attempts, mark them for billing, and prevent tool side effects. A shadow result should not silently create a second charge, send a duplicate message, or write to a customer system.

Canary traffic should test more than availability. Route a small, bounded percentage of eligible work to the new contract. Measure response validity, semantic quality, latency, token usage, cost, refusal rate, tool-call correctness, region evidence, cancellation, and downstream effects. Break results down by operation type and data class. A canary that passes short text prompts may still fail long-context workflows or structured tool calls. Define promotion gates before the canary begins, and define automatic rollback conditions that reflect customer harm rather than only HTTP errors.

Protect admitted work with contract compatibility policies. A job admitted under contract version 12 may continue on version 12 if the provider remains available and the work is low risk. It may migrate to version 13 if the compatibility matrix proves the required guarantees are preserved. If a guarantee changed, require reauthorization, an adapter, a narrower scope, or quarantine. Do not assume that queued work can follow the current default route. The route selected today may not satisfy the contract under which the job was admitted.

Long-running workflows need checkpoint migration. Store the contract digest and capability assumptions at each checkpoint. When resuming, compare them with the target contract. A workflow paused after generating a plan may resume on a new model only if the plan and next action are revalidated. A structured output created under an old schema may need migration before a new tool adapter accepts it. A provider token issued under the old account or region may not be reused on the new route. Resume from verified state, not from a label that says in progress.

Protocol adapters should preserve meaning, not hide differences. An adapter can translate field names, streaming events, error codes, or tool schemas. It should also record what could not be preserved. If the old provider guaranteed cancellation but the new one does not, the adapter must not expose a false cancellation success. If the old endpoint returned final usage and the new endpoint reports estimates, the billing layer must see that difference. Every translation should carry source protocol, target protocol, mapping version, lossy fields, and validation result.

Structured output migrations are especially dangerous. A new provider may return valid JSON that does not satisfy the old schema, or satisfy the schema while changing the meaning of a field. Validate syntax, schema, required invariants, enumerations, units, null behavior, and semantic constraints. Version schemas explicitly. If a downstream tool expects schema version 4, do not pass a provider response that merely resembles version 4. Use a migration function with tests and preserve the original provider output reference for audit. When semantic migration is impossible, fail safely or route to a compatible provider.

Tool protocols require a hard boundary. A model migration may alter tool names, argument shapes, optional fields, or the tendency to call tools. Revalidate tool definitions, canonicalize arguments, and apply fresh authorization immediately before dispatch. Never let a new model’s apparently compatible plan bypass the existing tool policy. During canaries, disable irreversible tools or use a synthetic adapter. Compare proposed actions, not just final text. A provider contract migration that changes tool-call frequency can change the system’s real-world behavior even if ordinary answers look similar.

Streaming contracts need event-level comparison. Providers may change event names, sequence numbering, heartbeats, finish reasons, usage trailers, or reconnection semantics. A client that expects a final usage event may undercount or fail to close the operation. A gateway that treats an early finish signal as terminal may truncate output. Record protocol version, event sequence, last delivered event, and finality evidence. Translate only when the mapping preserves ordering and termination semantics. Otherwise negotiate a new client contract or buffer and normalize the stream before delivery.

Data-retention changes deserve their own migration gate. If the replacement provider stores prompts longer, uses them for training, or cannot honor deletion requests, the route may be incompatible for sensitive tenants even when model quality improves. Re-evaluate consent, data classification, residency, provider terms, deletion guarantees, and encryption context. A route should be eligible only when the new contract satisfies the tenant and policy requirements. If not, keep the old route, transform the data, or reject the operation. Cost and latency never override a binding privacy obligation.

Region and account migrations can alter authority. A provider may move traffic from one region to another, or a new account may have different permissions, quota, logging, and legal terms. Record the provider account and region selected before dispatch and verify the actual values when the provider exposes them. If the new route cannot attest to the required region, classify that uncertainty explicitly. Do not let a fallback silently cross a residency boundary merely because the model identifier is unchanged.

Pricing migrations need versioned accounting. A new contract may change input-token definitions, cached-token discounts, image units, tool fees, minimum charges, or currency. Record the pricing version at admission and attempt time. When a migration occurs, reconcile estimates and final charges separately. Do not retroactively apply new pricing to old work unless the customer contract permits it. If the provider sends usage in a new format, validate the mapping before posting charges. A cheaper route that cannot explain its bill is not operationally cheaper.

Capability negotiation should be dynamic but bounded. Before dispatch, the gateway can ask whether the target contract supports the required modality, context length, tools, schema, region, and cancellation behavior. Cache capability facts with version, expiry, source, and verification time. Do not treat a stale capability cache as a permanent guarantee. When a contract changes, invalidate affected capability decisions and require new evidence for high-risk routes. Capability negotiation tells the gateway what the endpoint claims to support; contract tests and runtime validation show what it actually does.

Migration must account for provider-side in-flight work. If the old endpoint accepted requests before the cutover, those requests may still be running, billable, or capable of producing side effects. Record a cutover watermark and classify pre-cutover attempts separately from post-cutover attempts. Decide whether to drain, cancel, query, or quarantine old work. Do not close the old route until provider status, usage, credentials, and side effects are reconciled. A route can stop accepting new work while remaining operationally active for status lookup and compensation.

Credential rotation should follow the contract graph. New routes may require new accounts, keys, scopes, or token exchanges. Issue credentials with the narrowest scope and lifetime needed for the new contract. Prevent old credentials from silently refreshing into the new account unless explicitly authorized. Revoke or expire old credentials after in-flight work is resolved. If both routes coexist during a migration, bind each credential to route, account, region, contract version, and tenant constraints. A successful authentication proves only that a credential works, not that it is allowed for this operation.

Fallback rules must be migrated deliberately. If the old provider becomes unavailable during rollout, the fallback may send work to a route that was never tested against the new contract. Rebuild the fallback graph with compatibility edges, residency constraints, capability requirements, pricing limits, and risk classes. A provider can be a healthy fallback for text completion and an unsafe fallback for tool execution. Test failover during the migration, not only after the new route is fully live. Recovery paths are part of the contract surface.

Use reversible rollout stages. Start with contract validation, then synthetic probes, shadow evaluation where allowed, canary traffic, bounded expansion, and full promotion. Keep rollback artifacts: old route configuration, policy snapshot, provider credentials, adapter version, pricing mapping, and capability facts. Rollback should stop new admission to the new contract, preserve the evidence of work already sent, and decide what happens to its in-flight attempts. It should not blindly replay customer operations on the old route. Reversal of configuration is not reversal of external effects.

Define migration stop conditions. Stop when schema failures exceed the threshold, provider region evidence is missing, cancellation behavior is incompatible, usage reconciliation diverges, duplicate side effects appear, sensitive data reaches an unauthorized location, or customer-visible quality falls below the contract. Some stop conditions should block only one operation class or tenant segment. Others require immediate isolation. Make conditions machine-readable and attach them to the rollout. “We will watch it closely” is not a control.

Customer guarantees must be mapped explicitly. Customers may rely on response format, latency, availability, model family, retention, region, price, or tool behavior. A migration can preserve one guarantee while changing another. Document which guarantees are invariant, which may change with notice, and which require opt-in. If the new provider cannot preserve the contract, use a compatible route, offer a degraded but honest mode, or fail with an actionable explanation. Do not silently deliver a different guarantee because the endpoint still returns a response.

Human review belongs at the boundary of material change. Automation can run tests, compare metrics, rotate traffic, and roll back when a defined threshold is crossed. A human should approve migrations that alter data residency, retention, irreversible tool behavior, billing semantics, or customer-visible guarantees. Present the old and new contract, compatibility gaps, mitigations, canary evidence, rollback plan, and affected workloads. Record the decision, conditions, approver, and expiration. Review should accelerate safe migration by making the important differences visible.

Observe semantic drift after promotion. Some provider changes are gradual or unannounced. Monitor output validators, tool arguments, refusal patterns, latency, tokenization, usage, cost, region, cancellation, and customer corrections. Compare against contract baselines by provider version and route. A migration is not finished when traffic reaches one hundred percent; it is finished when the new contract remains within its obligations over the observation window. If behavior drifts, create a new contract fact and evaluate whether traffic should be reduced or isolated.

Test migration races and partial failure. Change the contract while a queue is draining. Roll back after new-provider attempts have begun. Deliver old-provider webhooks after cutover. Rotate credentials while a session reconnects. Make the adapter lose a field. Return valid JSON with changed semantics. Drop usage trailers. Move traffic to an unexpected region. Trigger a tool call during a canary. Verify that old decisions remain explainable, new attempts are correctly authorized, billing remains traceable, side effects are not duplicated, and rollback does not pretend that external work never happened.

Keep a migration ledger. Record the old and new contract digests, affected routes, tenant and data-class scope, rollout stages, test results, traffic percentages, stop conditions, operator actions, provider observations, corrections, and final decision. Link every attempt to the contract active at dispatch. If a migration is abandoned, record why and what state remains. If it succeeds, record the evidence that promotion gates passed. This ledger supports incident response, customer support, compliance review, and the next migration.

The deeper lesson is that provider contracts are part of authority. A policy decision to send data, invoke a model, call a tool, or charge a customer is meaningful only relative to the guarantees of the selected endpoint. When those guarantees change, the gateway must treat migration as a controlled change to semantics, not as a configuration refresh. Preserve old facts, test new behavior, isolate incompatible work, and make every route decision explain which contract it relied upon.
