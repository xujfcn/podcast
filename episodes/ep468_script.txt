Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we connected the canonical operation ledger to distributed tracing and replayable incident analysis. We learned how to preserve timing, causality, uncertainty, and the difference between historical facts and replay-derived hypotheses. Today we move from understanding failures to containing them. We are designing adaptive circuit breakers and provider health models for AI workloads.

The familiar circuit breaker has three states: closed, where requests flow; open, where requests are rejected or diverted; and half-open, where a small number of probes test recovery. That model is still useful, but an AI API gateway cannot treat every failure as the same. A slow streaming response, a malformed structured output, a rejected tool call, a rate limit, an authentication error, and a provider outage have different meanings. If one undifferentiated error counter opens the circuit, the gateway can make a bad situation worse. It may abandon a provider that is healthy for embeddings while its chat endpoint is degraded, or it may keep sending requests to a provider that returns fast but semantically unusable answers.

The goal is not simply to send traffic away from a failing provider. The goal is to protect client intent, preserve reliable contracts, and make a safe routing decision under incomplete information. That requires a health model with multiple dimensions, a breaker scope that matches the failure domain, and feedback that distinguishes transport symptoms from semantic outcomes.

Start by defining what health means. Provider health is not one boolean. It is a set of observations about a capability in a region, under a protocol, for a workload class, at a point in time. A provider may be healthy for text generation but unhealthy for vision. Its chat endpoint may be healthy in North America but timing out in Europe. Its streaming path may be broken while non-streaming responses work. A model may produce valid JSON under one schema and repeatedly violate another. Health should therefore be represented as a vector or a set of scoped records, not a single provider status.

A practical health key might include provider, product capability, model family, region, protocol mode, and contract profile. The contract profile matters because an operation requiring tool calls, strict JSON, low latency, or a residency guarantee is not interchangeable with a plain text completion. If the gateway opens a breaker at the provider level after a structured-output failure, it may unnecessarily remove capabilities that are still reliable. If it scopes too narrowly, it may miss a broad network outage. The design must make scope explicit and allow evidence to roll up cautiously.

Separate four layers of observation. Transport health asks whether connections can be established, requests are accepted, bytes arrive, and responses complete. Service health asks whether the provider returns expected protocol statuses, such as successful responses, rate limits, overload signals, and authentication results. Contract health asks whether the response conforms to the gateway’s declared schema and safety requirements. Outcome health asks whether the result is useful enough for the client intent, including tool-call validity, citation requirements, or task-level success when that can be measured.

These layers must not be collapsed. A provider can be transport-healthy and contract-unhealthy. It can return HTTP 200 quickly while producing invalid tool arguments. It can be contract-healthy but outcome-poor for a particular workload. It can be service-healthy but temporarily rate-limited for one tenant. The gateway should record each observation with its classification and confidence, then let routing policy decide which dimensions matter for the next operation.

The canonical operation ledger from the previous episodes gives us the place to preserve these observations. For every provider attempt, record dispatch time, connection phases, first-byte time, stream progress, completion status, protocol status, validation result, usage estimate, and provider request reference. Attach a reason code to failures rather than relying on free-form text. Examples include CONNECTION_REFUSED, TIMEOUT_BEFORE_ACCEPT, TIMEOUT_AFTER_ACCEPT, RATE_LIMITED, AUTH_REJECTED, OVERLOADED, SCHEMA_INVALID, TOOL_ARGUMENT_INVALID, CONTENT_POLICY_BLOCK, and UNKNOWN_AFTER_DISPATCH. These codes drive safer aggregation and make incident analysis reproducible.

The first important rule is that uncertainty is not failure. If the gateway loses its connection after dispatch, it may not know whether the provider generated nothing, generated a complete answer, or accepted a tool call. Classifying that as a hard failure can trigger an unsafe immediate retry, possibly duplicating an external effect. Classifying it as success is worse. Record an unknown outcome, begin reconciliation if supported, and let the breaker treat the event according to the specific risk. An unknown after dispatch may be a strong signal about network reliability, but it is not proof that the provider service is incapable of completing the request.

The second rule is that latency needs shape, not just an average. AI workloads have long and variable tails. Track time to connection, time to acceptance if observable, time to first byte, inter-token gaps, total generation time, and completion rate. Streaming health must include stall behavior: a stream that sends one token and then pauses for forty seconds can be worse for an interactive client than a short, explicit timeout. Use rolling histograms or quantile sketches rather than only averages. A provider with a healthy median and a catastrophic ninety-ninth percentile may need a latency-aware route penalty before it needs a full open circuit.

The third rule is to distinguish overload from permanent incompatibility. A 429 with a retry-after value usually says something about current capacity, tenant quota, or admission policy. A 401 or 403 may indicate a credential or permission problem that retries cannot fix. A schema violation may indicate an adapter bug, a model capability mismatch, or a prompt contract problem. A circuit breaker should not respond to all of them with the same state transition. Transport and overload errors often call for backoff and diversion. Authentication and configuration errors call for operator attention and longer suppression. Semantic failures may call for a capability-specific penalty or model change.

Now consider breaker state. A simple closed, open, and half-open state is a good foundation, but each transition needs scope, reason, and expiry. Closed means eligible, not guaranteed. Open means the scoped capability is temporarily excluded from normal selection, not that the entire provider is condemned. Half-open means controlled probes are permitted under a budget. Store the state transition in the ledger or health store with the observation window, policy version, actor or automated controller, and next review time. This turns an opaque in-memory decision into something an operator can explain.

Use time-based decay rather than permanent punishment. A provider that had a burst of overload errors should recover as evidence ages, especially if later probes succeed. But decay must be asymmetric. Bad evidence should affect routing quickly when it represents a credible safety or contract failure. Recovery should require enough successful observations to establish confidence. This is the difference between a breaker that flaps and one that learns. A useful model may increase a failure score rapidly, reduce it slowly, and separately track confidence so that a small sample cannot make a strong claim.

Confidence is essential. Ten consecutive failures from one overloaded tenant do not establish global provider failure. One malformed response does not establish a broken model. Conversely, a failure observed across independent tenants, regions, and request types is stronger evidence. Weight observations by independence, recency, severity, and observability quality. A provider-supplied overload response is a more direct signal than a client disconnect, but a client-visible stream stall may still matter for user experience. Do not let a high-volume tenant dominate the global health score without a tenant-aware aggregation layer.

A robust design maintains several views at once: global health, tenant health, route health, and operation-specific risk. Global health can suppress a provider when a broad outage is evident. Tenant health can prevent one quota issue from affecting everyone else. Route health can distinguish a model, region, or protocol path. Operation risk can say that a request with an external side effect must not be sent to a route with a high unknown-outcome rate, even if its ordinary completion rate looks good.

This is where health models meet routing. A route selector should not ask only, “Which provider has the highest score?” It should evaluate eligibility first. Exclude candidates that violate residency, data-classification, model capability, tool, or contract requirements. Then calculate a route utility that includes quality, latency, cost, remaining budget, current breaker state, health confidence, and risk of an unknown result. A provider with the lowest nominal price is not economical if it frequently causes expensive reconciliation or duplicate-prevention work.

Keep circuit decisions separate from load balancing. The breaker answers whether a scoped route is safe enough to consider. The router answers which eligible route best satisfies the operation’s requirements. If these responsibilities are mixed, a load spike can accidentally open a breaker, or a breaker can become an unreviewable scoring penalty. Record both decisions: the health controller’s state and the route selector’s choice. This separation also makes replay easier. An incident investigator can reconstruct whether a provider was excluded or merely ranked below another candidate.

Fallback policy needs its own guardrails. A fallback is not automatically safe because it is available. Verify model capability, prompt compatibility, context-window limits, output schema, safety policy, region, cost ceiling, and tool semantics. For streaming requests, determine whether the client can tolerate a restart, a status transition, or a switch to buffered output. If tokens have already been delivered, a fallback may produce a discontinuous answer. The gateway should either continue under a clearly defined degraded contract or stop and report the partial result according to policy.

The most dangerous fallback is an automatic retry after an unknown side effect. Suppose a model response requested a purchase tool, the gateway dispatched it, and the connection died before confirmation. A generic breaker may mark the provider unhealthy and route the same operation to another model. The second model may request the purchase again. To prevent this, bind effect authorization to the operation and effect identity, not merely to the current provider attempt. Before retrying, query the effect ledger or reconciliation service. If the outcome is unknown, the safe default is to pause, reconcile, or require explicit confirmation.

Health for tool-capable models therefore needs semantic signals. Track malformed tool arguments, unsupported tool names, policy-denied tools, duplicate proposals, and successful effect completion separately from ordinary text quality. A provider that generates excellent prose but repeatedly emits invalid arguments is not healthy for an agent workflow. Conversely, a tool refusal may be correct behavior under a safety policy and should not count as provider failure. The validator must classify the response in the context of the contract that was requested.

Budget pressure is another health dimension. When a provider’s prices, token usage, or retry costs threaten a tenant budget, the gateway may need to shed optional work or select a cheaper route. That is not a provider outage, and it should not pollute the provider’s global health score. Model it as resource pressure in the operation and tenant policy layers. Health signals can still inform the choice: a cheap route that frequently exceeds output limits may create a higher total cost. The ledger should preserve reserved, estimated, and settled usage so the controller does not learn from stale assumptions.

Adaptive breakers should be careful under correlated failure. If every provider depends on the same regional network, opening one provider and sending traffic to another may simply move the load into the same outage. Maintain dependency awareness for DNS, egress, identity, region, and shared queues. A provider-health model can include a dependency label and an aggregate incident signal. During a shared dependency failure, the gateway may need to reduce concurrency, serve cached or precomputed responses, switch regions, or return a transparent degraded status rather than cycling through providers.

Concurrency limits are often more effective than binary blocking. When a provider is slow but not completely unavailable, a bounded queue and a small in-flight limit can protect tail latency. Use adaptive concurrency based on completion rate, latency, and overload signals. If active requests increase while useful completions fall, reduce the sending window. If successful probes recover and queue time remains acceptable, increase it gradually. Do not treat every timeout as a reason to open the circuit; sometimes the safer action is to stop adding work while allowing existing requests to finish.

Probe design matters in half-open state. A probe should represent the capability being tested, but it must be safe, cheap, and non-effectful. Use a minimal prompt or provider health endpoint where available. For structured output, validate the same schema family without exposing customer content. For streaming, test the streaming path rather than assuming a non-streaming success proves anything. For tool routes, use a dry-run tool contract or a synthetic adapter. Record probe results separately from customer traffic, because a provider may optimize or prioritize health checks differently.

Avoid probe storms. When many gateway instances observe the same outage, they can all enter half-open state and send a flood of tests at the moment a provider is recovering. Coordinate breaker state through a shared store or use leases that limit probes per scope and time window. A local fast path can make an immediate suppression decision, while a distributed controller establishes the durable state. Include jitter in probe schedules, but retain enough metadata to explain why a probe was sent and which state transition allowed it.

Health data itself needs consistency rules. A regional worker may receive events out of order. A late success should not erase a newer failure, and a clock-skewed timestamp should not create an impossible recovery timeline. Use event ingestion time, source time, sequence numbers where available, and monotonic versioning per health key. If two observations conflict, preserve both and apply a deterministic reducer. The reducer should expose uncertainty rather than hiding it behind the latest-write-wins shortcut.

The tracing and replay design from EP467 gives us a verification path. A route decision span can link to the health observations that influenced it. A replay can use the recorded health vector, breaker state, and policy snapshot to ask whether the route should have been eligible. It can test alternative thresholds without changing historical truth. For example, an analyst can compare a five-minute latency window with a one-minute window and see how many operations would have diverted, how much fallback capacity was consumed, and whether unknown outcomes increased. These are experiments, not retroactive corrections.

A health model should produce explanations that humans can use. Instead of saying, “Provider score: 0.31,” say, “Excluded for structured-output route because schema-invalid responses reached 8.4 percent over 20 independent attempts, above the 2 percent threshold; transport remained healthy; next probe in 90 seconds.” For a tenant-specific condition, say, “Deferred because this tenant received a provider rate limit with retry-after 30 seconds; global provider health is unchanged.” Explanations should include evidence windows, scope, confidence, and the policy version.

Monitor the controller, not just the providers. Useful metrics include breaker opens by reason and scope, half-open probe success, flap rate, time spent open, false-positive diversion rate, fallback saturation, unknown-outcome rate, stream-stall rate, contract-validation failure rate, health-event lag, and route decision latency. Track how often operators override a breaker and whether those overrides later prove correct. A controller that suppresses outages quickly but sends all traffic to an overloaded fallback is not healthy. Measure the whole system outcome.

Test with fault injection. Introduce connection refusal, delayed first byte, token stalls, malformed JSON, wrong tool arguments, provider 429s, invalid credentials, partial streams, duplicate callbacks, and delayed reconciliation. Vary the failure by tenant, region, model, and protocol. Verify that only the intended breaker scope changes. Confirm that a global outage does not create a retry avalanche, that a tenant quota issue does not remove a provider for everyone, and that an unknown side effect pauses rather than duplicates work.

Test recovery too. Restore the provider gradually. Send successful probes, then mixed results, then normal traffic. Confirm that the breaker does not close after one lucky response, that concurrency ramps up safely, and that stale open state expires or is superseded according to policy. Review whether the recovery path respects budget, residency, and contract constraints. A circuit that opens correctly but closes recklessly is still a production risk.

Security boundaries must remain explicit. Health keys can expose tenant behavior if they are too detailed. Aggregate sensitive signals carefully, restrict access to raw attempts, and avoid placing prompts or outputs in health labels. Provider request IDs are useful correlation references, not credentials. Breaker overrides need an authenticated actor, a reason, an expiry, and an audit trail. Never make it possible for a support user to bypass a safety or residency exclusion by clicking an operational override that was intended only for capacity management.

Roll out in stages. First, classify provider attempt outcomes with stable reason codes and separate unknown from failure. Second, add scoped health records for transport, service, contract, and outcome dimensions. Third, introduce passive scoring without changing routing, and compare predictions with actual client outcomes. Fourth, enable capability-scoped breakers and bounded concurrency for a small set of routes. Fifth, add half-open probes, distributed coordination, and replay-based threshold analysis. Only after the model is explainable should it drive broad automated diversion.

The deeper lesson is that a circuit breaker is not an angry switch. It is a safety boundary around a specific capability, informed by evidence and constrained by policy. Provider health is not a reputation score. It is a time-bounded, scoped statement about what the gateway can currently trust a route to do. Adaptive behavior should protect the client contract without inventing certainty, shifting risk blindly, or hiding why a route was excluded.

The operation ledger tells us what happened. Tracing tells us where time and causality flowed. Replay lets us test the controller’s decisions. The health model turns those facts into cautious, reversible routing behavior. Together they let an AI gateway respond to failure without losing the semantic identity of the work it is trying to complete.
