Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we built the canonical operation ledger: one durable identity for a client intent, linked to routing decisions, provider attempts, tool effects, usage, uncertainty, reconciliation, and public status. Today we take the next logical step. We will connect that semantic history to end-to-end request tracing and replayable incident analysis.

The distinction matters. A trace can tell us where time was spent across gateway services. A ledger can tell us what the operation meant and why the system chose a particular action. A replay can help us reconstruct the decision path under controlled conditions. None of these is sufficient alone. A trace without semantics becomes a waterfall of spans. A ledger without timing becomes a sequence that cannot explain latency. A replay without evidence can become a fictional retelling. Together, they can turn a confusing AI gateway incident into a bounded, testable explanation.

Imagine a customer sends one request asking an assistant to summarize a document and then create a ticket if the summary indicates a security issue. The gateway authenticates the tenant, checks residency, selects a model, opens a stream, validates the model output, authorizes a tool call, and sends a request to a ticketing system. The model provider times out after accepting the request. A fallback model is selected. Meanwhile, the ticketing system completes the original tool call, but its response is delayed. The client sees a pending status and later receives a result.

If all we have is an application log, we may see a timeout, a retry, and a ticket creation. If we have only a distributed trace, we may see spans with a missing child and a long tail. If we have only the ledger, we can explain the semantic sequence but not the exact queue delay or connection stall. The incident becomes understandable only when the operation ID, trace context, attempt IDs, effect IDs, timestamps, and evidence references agree.

Start with a context model. The canonical operation ID identifies the client intent. The trace ID identifies a distributed causal investigation context, usually spanning one execution path. A span ID identifies a timed unit of work. An attempt ID identifies an interaction with a provider. An effect ID identifies an external side effect. These identifiers must be linked, not substituted for one another. A retry may create a new trace or a new span, but it remains part of the same operation. A tool execution may happen after the model span has ended, but it remains linked to the same semantic intent.

Propagate trace context through internal services, but propagate it carefully through provider boundaries. The gateway can send a traceparent header to its own services. It should not assume that an external provider will honor the header, preserve it, or keep it private. Store the gateway trace context and provider request identifiers as separate references. If a provider returns its own trace or request ID, record it as external correlation evidence. Never allow an untrusted provider-supplied identifier to become the gateway’s security identity.

A useful root span represents the operation execution window, not necessarily the entire retention life of the ledger record. Under it, create spans for admission, policy evaluation, route selection, provider dispatch, response validation, stream delivery, tool authorization, effect execution, reconciliation, and finalization. Use spans to measure work and causality. Use ledger events to record facts and decisions. A route-selection span can contain attributes such as candidate count and decision latency, while the ledger stores the policy version, selected route, exclusion reason codes, and budget reservation.

Do not put raw prompts, full completions, authorization tokens, tool arguments, or document contents into span attributes. Tracing systems are often broadly accessible, heavily indexed, and retained differently from protected evidence stores. Use classifications, hashes, byte counts, schema IDs, and references to encrypted artifacts. A content hash can establish that two pieces of evidence are the same without making either piece visible in the trace. If an operator needs the content, an access-controlled workflow can retrieve it and create an audit event.

Sampling requires special care in AI gateways. Ordinary request sampling may discard exactly the rare failure that matters. Start a trace with a provisional sampling decision, then upgrade or retain it when the operation enters an important state: a provider failure, an unknown outcome, a policy denial, a tool effect, a budget breach, or a client-visible degradation. Tail-based sampling can help, but it should never be the only source of truth. The ledger remains authoritative for semantic events even when the detailed trace is not retained.

Use trace links for asynchronous work. A reconciliation worker may run minutes after the original request and on another host. Creating a child span with a stale parent can distort the timing tree. Instead, create a new trace or span with a link to the original span and operation. Record the reconciliation deadline and external reference in the ledger. The trace shows the worker’s actual execution window; the link shows why it ran. This avoids pretending that a delayed job was a synchronous child of a request that had already ended.

Time is where tracing and ledgers complement each other. Record event time, ingestion time, and span start and end times. Wall clocks can be skewed, so use monotonic duration inside each process and synchronize clocks well enough for investigation. A provider timestamp is evidence, not absolute truth. When an event arrives late, preserve its source timestamp and ingestion timestamp. If two events cannot be ordered confidently, say so. A replay that invents an exact order may be neat, but it is less trustworthy than a replay that exposes the uncertainty.

The first incident-analysis question is usually, “What did the client experience?” Build a client-visible timeline from delivery checkpoints: request accepted, first byte, stream segments or response body committed, interruption, status update, and final result. Link each checkpoint to the operation ledger and, where available, to the span that performed the delivery. This lets an operator distinguish provider generation time from gateway buffering time, and gateway work from client network delay. It also prevents an internal success from being mistaken for a client-visible success.

The second question is, “Where did the time go?” The trace should answer this through service and network spans. Break down queue wait, policy evaluation, route selection, connection setup, provider time to first byte, token generation, validation, tool execution, and response delivery. Include retries and backoff as explicit spans or events. Do not hide a five-second retry delay inside a generic request span. If the operation deadline was spent waiting for a circuit-breaker lease or a reconciliation query, that should be visible as its own phase.

The third question is, “Why did the gateway make that decision?” The trace alone cannot answer this. Join the span to the ledger’s decision event. Show the policy version, contract requirements, excluded candidates, compatibility checks, circuit state, budget reservation, and reason codes. A timeline without a decision record can show that provider B was selected but not whether provider A was forbidden by residency, unavailable because of a circuit, or rejected because it could not preserve structured output.

Now consider replay. Replay is not a magic button that runs the original prompt again. It is a controlled reconstruction of selected decision points using recorded inputs, configuration snapshots, and explicit safety boundaries. The aim is to answer questions such as: Would the current reducer rebuild the same status? Would this policy have permitted the fallback? Would the validator have rejected the provider response? Could two workers have claimed the same effect? Replay should produce evidence about a hypothesis, not overwrite the original history.

Separate three replay modes. The first is projection replay: read the append-only ledger events and rebuild the current operation projection without contacting providers or tools. This should be deterministic and safe. It tests the reducer, migrations, and event completeness. The second is decision replay: feed recorded, redacted inputs and configuration snapshots into routing, policy, budgeting, or validation logic, while disabling external side effects. This tests whether a decision can be reproduced. The third is system replay: rerun a request through a sandbox or provider mock, with synthetic clocks and explicit effect suppression. This tests behavior under a controlled scenario, not historical reality.

Never call an external tool during replay merely because the original record says a tool was called. A replay must default to dry-run. Tool adapters should receive a replay context and refuse real execution unless a separately approved test environment, tenant, and allowlist are active. For effectful operations, return the recorded outcome or a deterministic fixture. If the test is specifically about reconciliation, use a fake external service that models the known states: accepted, completed, unknown, duplicate, and not found. A replay that sends a real email or creates a real ticket is not an analysis tool; it is an operational hazard.

Redaction must preserve meaning. Removing a prompt entirely may make a validation failure impossible to reproduce. Instead, define field-level redaction and typed surrogates. Replace a secret token with a stable placeholder, a document with a synthetic document carrying the same size and schema shape, and a tool argument with a digest plus approved representative values. Preserve the contract version, content classification, language, token-count range, and structural features needed by the decision under test. Label every surrogate so no analyst mistakes it for original evidence.

Configuration snapshots are as important as input snapshots. Record the model allowlist, residency rules, budget policy, timeout values, circuit state, prompt-template version, schema version, adapter version, and feature flags that influenced the operation. A replay using today’s configuration may be useful for regression analysis, but it cannot claim to explain yesterday’s decision. Store immutable references to the exact bundles used at the time. If a dependency was not captured, mark the replay as partial rather than silently substituting a current value.

Randomness and nondeterminism require explicit handling. Model outputs can vary. Load balancing can change. A policy may depend on a changing health score. Capture random seeds where the component supports them, but do not promise bit-for-bit provider reproduction unless the provider contract actually provides it. For decision replay, replace nondeterministic signals with recorded observations: the provider’s health state at the time, the measured latency bucket, the budget remaining, and the candidate response. Then distinguish “decision reproduced from recorded observations” from “full system behavior reproduced.” Those are different confidence levels.

A replay report should include the original operation reference, replay mode, evidence bundle version, configuration bundle, redaction profile, safety mode, outputs, divergences, and confidence. For each divergence, classify the cause: changed policy, changed input, missing evidence, nondeterministic component, schema migration, timing difference, or suspected bug. Do not summarize the result as simply reproduced or not reproduced. A route difference caused by a deliberate policy change is not a regression. A route difference caused by an unrecorded feature flag may be an observability failure.

Treat replay outputs as new evidence, never as amendments to the original operation. Give each replay its own replay ID, actor, purpose, and expiration policy. Keep a clear visual and programmatic distinction between historical facts, recorded observations, analyst assumptions, and replay-derived hypotheses. If an analyst changes one input and obtains a different route, the report should say exactly which input changed and which conclusions no longer transfer. This discipline prevents a useful experiment from quietly becoming a rewritten incident narrative.

The ledger and trace should support a causal graph, not merely a list. A provider timeout may cause fallback selection. Fallback selection may cause a second model response. The second response may cause tool authorization. The delayed original provider response may later reveal an unknown duplicate risk. Represent causal links using event references, span links, and explicit reason codes. A later event can explain an earlier choice without pretending it caused that choice. This is why event time, decision time, and knowledge time should remain distinguishable.

Knowledge time is especially useful. At the moment a provider timed out, the gateway knew only that the outcome was unknown. Minutes later, reconciliation may establish that the provider completed successfully. The later fact must not be projected backward into the earlier decision. Record when the system learned the fact. During a postmortem, ask whether the gateway acted correctly given its knowledge at each point, not whether the final outcome makes the earlier decision look unnecessary.

Fault injection can validate the complete investigation path. Crash after the provider accepts a request but before the attempt event is committed. Delay the trace export while allowing ledger events to commit. Deliver events out of order. Drop a provider callback. Duplicate a reconciliation message. Skew one service clock. Then verify that the operation remains queryable, the public status remains conservative, the projection can be rebuilt, and the incident report identifies what is known, unknown, and inferred. Observability is part of the failure mode, so test it like a production feature.

A practical implementation can use OpenTelemetry for traces, a relational or streaming ledger for semantic events, and encrypted object storage for protected evidence. Add a correlation service or query layer that joins operation IDs, trace IDs, attempt IDs, and effect IDs without copying sensitive payloads into every system. Use schema registries for event and span attribute conventions. Establish naming rules early: stable operation names, bounded-cardinality attributes, reason-code vocabularies, and explicit status enums. High-cardinality values belong in indexed references or carefully governed stores, not unrestricted metric labels.

Metrics complete the picture. Track trace retention coverage for incident-worthy operations, the percentage of ledger events carrying valid trace links, projection rebuild agreement, replay divergence rates, evidence access latency, unknown-outcome age, and the fraction of incidents answered without raw-content access. Measure cardinality and storage cost as well. A trace system that becomes too expensive will be sampled aggressively; a ledger that is too noisy will be ignored. The best design captures the facts needed for decisions and lets detailed evidence be retrieved deliberately.

Access to investigation data must be layered. An SRE may need timing and statuses. A support agent may need the public operation view and a safe explanation. A security investigator may need policy evaluations and access history. A model-quality engineer may need redacted response structure. Grant the minimum useful view, and make break-glass access reasoned, time-bounded, and audited. Every retrieval of protected evidence should create an access event connected to the incident or support case. The audit trail must cover not only the request, but also the investigation of the request.

Incident tooling should guide operators toward safe actions. A timeline view can show the semantic ledger on one side and linked spans on the other. Highlight uncertainty, late-arriving facts, and client-visible transitions. Offer buttons or commands for read-only projection rebuild, redacted decision replay, and sandbox validation. Do not place a “retry now” control next to an unknown side effect unless the tool has first checked idempotency and reconciliation state. The user interface should encode the same caution that the gateway’s state machine encodes.

When writing an incident report, use a fixed structure: client intent, contract, timeline, decisions, attempts, effects, client-visible outcome, evidence confidence, divergences, and next safe action. State what happened, what was known at each decision point, what remains uncertain, and what evidence supports each claim. Avoid phrases like “the provider failed” when the evidence only shows a timeout after dispatch. Say “the gateway lost confirmation after dispatch; reconciliation later reported completion,” if that is what the record proves.

Roll out in stages. First, link every operation to a trace root and add bounded semantic span names. Second, add ledger-to-trace references for route decisions, attempts, validations, and delivery checkpoints. Third, implement projection replay and a read-only investigation view. Fourth, implement decision replay with redacted fixtures and configuration snapshots. Fifth, add sandbox system replay and fault-injection scenarios. Delay any automated remediation until the investigation path is trustworthy. Automation built on ambiguous evidence can repeat an incident faster.

The deeper lesson is that observability is not just visibility. It is a contract about what the system can later prove. The canonical ledger preserves intent and decisions. Tracing preserves timing and execution structure. Evidence stores preserve the minimum protected material needed for verification. Replay preserves the ability to test a hypothesis without rewriting history or causing a new side effect. Each layer has a distinct job, and their references must line up.
