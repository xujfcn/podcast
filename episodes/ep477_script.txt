Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we designed provider contracts and capability negotiation: identify endpoints precisely, calculate the real request envelope, negotiate tool and streaming semantics, detect drift, reject silent downgrades, and preserve the contract snapshot used for every attempt. Today we turn to the moment when a compatible request meets an incompatible reality: too much demand, too little capacity, and not enough time. We are designing deadline-aware admission control for an AI API gateway: how to decide what enters the system, what waits, what degrades, and what gets rejected before overload turns into a cascade.

This is related to rate limiting, but it is not the same thing. A rate limiter usually counts requests or tokens over a window. Admission control asks whether this particular operation can be accepted now, given its estimated work, deadline, provider contract, tenant budget, fallback headroom, and side-effect risk. A short text completion and a long streaming agent run are both requests, but they consume very different resources. A gateway that treats them as interchangeable may look fair while it quietly exhausts context capacity, connection slots, retry budgets, or human patience.

The objective is not to make every request succeed. The objective is to keep the system useful and honest when demand exceeds supply. That means protecting already-admitted work, preserving capacity for high-value operations, avoiding queues that can only end in timeout, and telling callers early when their requirements cannot be met. A graceful rejection at the edge is often better than a thirty-second wait followed by a provider error, a partial stream, and an ambiguous bill.

Start by defining admission as a durable decision. When the gateway accepts an operation, it makes more than a networking promise. It promises to allocate a bounded amount of capacity, apply a particular policy and provider contract, and either produce a result or report a defined failure. Create the operation identity before reserving scarce resources. Record the request class, tenant, deadline, required capabilities, estimated input and output tokens, streaming expectation, tool-side-effect level, and fallback rules. The admission record becomes the basis for later queueing, cancellation, reconciliation, and explanation.

Do not confuse arrival with admission. A request can be authenticated, syntactically valid, and placed in a queue without being admitted to provider execution. Define explicit states such as received, classified, waiting, admitted, dispatched, completed, cancelled, rejected, and expired. Each transition needs an owner and a reason. If a client disconnects while work is waiting, the gateway should be able to cancel it without accidentally consuming a provider lease. If a deadline passes in the queue, the operation should expire rather than enter execution simply because a worker became free.

The first hard input is the deadline. “Fast” is not a deadline. Capture an absolute deadline or a remaining budget supplied by the caller or derived from a service-level policy. Then subtract known costs: authentication, normalization, capability evaluation, queueing, provider connection setup, expected time to first token, generation time, tool execution, and reconciliation. Add a safety margin for uncertainty. Admission should ask whether the selected route can plausibly finish the required work before the deadline, not whether it is healthy in the abstract.

Deadline handling must distinguish time to first byte from time to completion. An interactive user may care about a quick first token but tolerate a longer stream. A batch job may have no visible stream and care only about completion before a scheduled cutoff. A tool-using operation may need enough remaining time to validate arguments and execute a side effect after the model responds. Define milestones and deadlines for each stage. A route that can start quickly but cannot finish before the tool deadline is not a successful admission for that operation.

Now classify the work. Useful dimensions include latency sensitivity, estimated token cost, streaming connection duration, computational intensity, side-effect risk, retryability, tenant priority, and whether the request is interactive, batch, background, or recovery work. Avoid creating dozens of classes that nobody can explain. A small taxonomy is enough if it maps to concrete behavior. For example: interactive text, interactive multimodal, agentic tool use, asynchronous batch, and control-plane or reconciliation work. Each class can carry default deadlines, queue limits, degradation options, and reservation rules.

Estimation is imperfect, but imperfect estimates are still better than pretending all work costs the same. Estimate input tokens with the correct tokenizer when possible. Include system instructions, tool definitions, conversation history, retrieved documents, and provider framing overhead. Estimate output tokens from the requested maximum and workload class. For multimodal inputs, use provider-specific cost units or a conservative mapping. For agentic work, estimate not just one model call but a bounded number of turns, tool calls, and result expansions. Store the estimate and its confidence; admission can reserve conservatively when uncertainty is high.

The key resource is usually multidimensional. A provider may have a token-per-minute ceiling, request-per-minute ceiling, concurrent-request limit, stream connection limit, context limit, or separate quota for images and audio. The gateway may have worker capacity, queue memory, network bandwidth, and fallback reservations. A request fits only if it fits every relevant dimension. Reserving ten request slots does not help if those ten operations require more tokens than the provider can deliver before their deadlines. Admission should calculate a resource vector, not one generic cost number.

Reservations should be explicit and reclaimable. Before dispatch, reserve the expected input and maximum output budget, concurrency, and any fallback or tool-execution capacity required by policy. When the operation completes, reconcile the reservation against actual usage and release the remainder. If generation stops early, capacity should return to the pool. If a stream stays open, the active connection reservation remains visible. If the estimate was wrong, record the variance and feed it back into future estimation, rather than hiding it in a generic “provider latency” metric.

There is a subtle trap in token reservations. Reserving the maximum output for every request can make the gateway reject useful work even when most responses finish early. Reserving too little can create a mid-operation shortage and force unsafe truncation or failover. Use a two-stage reservation where the provider and policy allow it: reserve a conservative initial budget, then extend it only when capacity and deadline checks still pass. For streaming, define whether extension is automatic, caller-approved, or forbidden. Never allow an operation to grow without a bounded cost and termination rule.

Queueing is a policy decision, not a storage implementation. A single first-in, first-out queue is easy to build and easy to starve. A huge queue can hide overload while increasing latency and wasting work that will eventually miss its deadlines. Set queue bounds in time, count, and estimated resource cost. When a queue is full, reject or shed according to workload policy. The gateway should not accept unlimited promises merely because it can store unlimited request metadata.

Choose a scheduling discipline that matches your commitments. Strict priority protects urgent work but can starve background tenants. Weighted fair queuing protects shares but may delay a genuinely critical operation. Earliest-deadline-first can be effective when deadlines are meaningful, but it can also let a flood of near-term work displace longer jobs that would have completed successfully. A practical design combines classes: reserve protected capacity for high-priority work, use weighted fairness within each class, and apply an aging rule so waiting work does not disappear forever.

Fairness must operate at the right identity level. If one organization can create a hundred API keys, key-level queues do not create organizational fairness. Charge admission against the tenant hierarchy established by policy: account, project, application, user, and perhaps operation class. Keep a separate platform reserve for control-plane tasks, health probes, contract refresh, and reconciliation. Without that reserve, customer traffic can prevent the system from learning that a provider is unhealthy or from accounting for the work already performed.

Protect capacity for already-admitted operations. A common failure pattern is to admit new traffic optimistically until a provider reaches its connection limit, then let new requests compete with streams and tool loops that are already in flight. Define a protected active-work pool and a separate admission pool. The protected pool covers completion, cancellation, usage finalization, and required retries. A request may enter only if the gateway can preserve enough capacity to finish it under expected conditions. This is one reason admission can be stricter than a simple utilization threshold.

Use hysteresis to prevent oscillation. If the gateway opens admission at eighty percent utilization and closes it at eighty-one percent, tiny fluctuations can create rapid accept-reject cycles. Set distinct open and close thresholds, and consider a minimum hold time. More importantly, make the thresholds resource-aware. Token throughput, active streams, queue delay, and error rate may signal pressure at different times. A provider can have free request slots but no remaining token budget, or free token budget but a saturated network. The admission state should explain which constraint is binding.

Load shedding is the honest alternative to infinite waiting. Shed work before provider dispatch whenever possible. Drop expired operations, reject requests whose hard capabilities cannot be met, refuse new background work when its queue budget is exhausted, and apply explicit degradation to workloads that have opted in. Degradation might reduce maximum output, disable optional retrieval, choose a smaller approved model, switch from streaming to non-streaming, or defer batch work. It must never silently remove a hard requirement such as residency, strict schema enforcement, or a required tool guarantee.

Degradation needs an ordered ladder. Start with the least surprising change: remove optional preferences, reduce a soft output budget, or choose an equivalent route within the same provider contract. Next, defer work if the caller accepts asynchronous completion. Only then consider a broader model or provider fallback, and only when policy permits it. Each step should be represented in the operation receipt. A caller should be able to tell whether the response came from the preferred model, a lower-cost equivalent, or an explicitly approved degraded mode.

Provider contracts matter directly during overload. A route may be technically compatible but operationally ineligible because its current contract reports a low concurrency limit, an expiring quota lease, or a lack of safe cancellation. Static capability and live capacity are separate checks. Admission loads the signed contract snapshot, then consults current health and resource state. If live metadata is stale, apply the contract’s grace policy and lower the maximum work admitted. Never infer available capacity from a success that happened several minutes ago.

The gateway also needs a fallback budget. Sending every rejected request to a secondary provider is not resilience; it is a synchronized overload transfer. Reserve fallback capacity for work that actually meets the fallback’s contract and has enough deadline remaining. Make failover count against the operation’s retry and budget policy. If the primary has already streamed content, the fallback may not be able to continue coherently. For such operations, admission should either require a route with sufficient protected headroom or choose a failure mode that tells the client the stream cannot be resumed.

Retries are new demand unless capacity has been reserved for them. A timeout can mean the provider is still processing, so retrying immediately may double the load and duplicate a side effect. Associate retry eligibility with the operation lifecycle and the provider’s idempotency contract. Reserve a bounded retry budget for retryable, side-effect-free work. For tool calls that create or change records, require an idempotency key and a durable deduplication boundary. If those guarantees are absent, admission should reject the side-effecting mode or route it through a safe execution service.

Cancellation is part of admission, not an afterthought. If a caller cancels a queued operation, release its reservation. If a stream is active, propagate cancellation to the provider and mark whether the provider acknowledged it. If a tool has already started, cancellation may not undo the side effect; the receipt must preserve that distinction. A gateway that counts cancelled requests as free immediately, while the provider continues generating, will over-admit and create a second overload wave. Resource release should follow observed termination or a conservative timeout.

Backpressure must cross the client boundary. For synchronous APIs, return a structured overload response with a retry hint only when retrying is likely to help. “Try again immediately” during a provider incident is an invitation to a thundering herd. Include a stable reason, a bounded retry-after, and whether the operation was never dispatched. For streaming protocols, send a clear admission failure before opening a stream. For batch APIs, offer a durable accepted-for-later state only if the system can actually preserve that queue across restarts and policy changes.

An overload response should be safe to retry. Give the operation a client-supplied idempotency key or create a gateway operation token before admission. If the client receives a network error after sending the request, the status endpoint should distinguish never received, received but rejected, waiting, admitted, and outcome unknown. This prevents clients from blindly replaying an operation whose provider attempt may still be running. Admission control and idempotency together turn uncertainty into a queryable state instead of duplicated work.

Observability should expose why admission changed. Track accepted, queued, rejected, expired, cancelled, and shed operations by tenant, class, provider, capability, and binding resource. Measure queue wait, deadline slack at admission, reservation error, utilization, active streams, retry pressure, and fallback headroom. Record the decision reason in a privacy-minimized form: token capacity exhausted, protected pool reserved, deadline infeasible, tenant budget unavailable, contract stale, or fallback not eligible. Do not log prompts merely to explain a queue decision.

Watch for feedback loops. If queue time grows, callers may increase deadlines, retry more aggressively, or ask for larger fallback budgets. If provider errors rise, the gateway may fail over, saturating the fallback and causing even more errors. If a model returns longer answers than estimated, reservations become inaccurate and admission appears healthier than it is. Use control-loop thinking: measure with bounded intervals, change one policy lever at a time, and keep emergency caps that do not depend on a single noisy metric.

Test admission with adversarial scenarios. Fill every provider’s token budget while request slots remain free. Hold many long-lived streams open and send short interactive requests. Create one tenant with many keys and verify organization-level fairness. Make a provider timeout after doing work, then verify that retry policy does not duplicate a side effect. Advance the clock so queued requests miss their deadlines. Deliver capacity updates out of order. Restart the gateway between reservation and dispatch. The correct result is not always success; it is a bounded, explainable outcome.

Distributed gateways need coordination without pretending the world is perfectly synchronized. A regional admission decision may use a local lease for provider capacity and a policy-approved share of global quota. Leases need expiry, fencing, and an owner identity. If a region loses contact with the coordinator, it must not mint unlimited new capacity from a stale view. Continue only within a fail-safe local budget, or stop admitting work that requires global guarantees. Record the snapshot and lease versions in the operation receipt.

Do not let a control-plane outage turn into a data-plane stampede. Cache signed policy and contract snapshots within explicit freshness windows, but separate cached permission from cached capacity. It may be safe to keep applying a recently signed residency rule; it may not be safe to assume that yesterday’s provider concurrency limit is still available today. When live capacity is unknown, reduce admission to low-risk work with a conservative cap, preserve protected capacity, and make the uncertainty visible to operators and callers.

The decision pipeline can now be stated precisely. Create the operation identity. Authenticate and classify the request. Normalize hard requirements and preferences. Load fresh enough policy and provider contracts. Calculate the complete resource vector and deadline envelope. Check tenant budgets and protected reserves. Evaluate route compatibility and live eligibility. Select a queue or route using the declared fairness and priority rules. Reserve capacity with an expiry and fence. Admit only if the reservation and completion plan are feasible. Dispatch through the contract-enforcing adapter. Reconcile actual usage, release capacity, and emit the final receipt.

There is an important difference between refusing work and failing work. Refusal happens before provider execution because the gateway knows it cannot make a credible promise. Failure happens after admission because transport, provider behavior, or an unexpected condition broke that promise. Keep those categories separate. They drive different client behavior, different alerts, and different reliability work. If most operations are failing after admission, raise the bar or improve capacity estimation. If most are rejected, investigate policy, contract freshness, or an undersized pool. A single “error rate” hides the answer.

Admission control should be explainable to both engineers and customers. Internally, the receipt can include policy version, contract version, resource estimates, queue class, reservation ID, lease epoch, route candidates, rejection reasons, and degradation steps. Externally, expose a stable summary: accepted, queued, rejected for capacity, rejected for deadline, or rejected because the requested capability was unavailable. Avoid revealing another tenant’s usage or provider-sensitive limits. Explain enough to make a retry or product decision possible, while keeping evidence inside the proper privacy boundary.

The design principle is simple: capacity is a promise with a price. An AI gateway should not accept work merely because it can parse the request or place a record in a queue. It should accept only when it can protect the operation’s deadline, budget, provider semantics, fallback rules, and side-effect safety. When it cannot, it should shed load early, degrade only with permission, and return a result that is truthful about what happened.

The series now connects another layer. Provider contracts tell us what an endpoint can actually do. Admission control decides whether the system can safely ask it to do that work now. Budgets and fairness prevent one principal from consuming the whole pool. The operation lifecycle gives one identity across queues, attempts, streams, tools, and reconciliation. Policy distribution keeps the rules consistent. Privacy and residency constrain where evidence and inference may go. Together, these mechanisms turn overload from a mysterious outage into a controlled decision surface.
