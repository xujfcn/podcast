Today we’re talking about execution ownership leases at the AI API gateway: how to keep exactly one effective worker responsible for an asynchronous request, stream, or tool chain when machines restart, networks partition, and regions fail over.

Distributed work rarely fails cleanly. A worker can lose its database connection while the provider request continues. Another worker sees an expired heartbeat and takes over. The first worker then reconnects and tries to publish output or execute a tool. Without an ownership contract, both workers believe they are helping, and the customer receives duplicate effects, conflicting stream events, or two charges.

Start with a stable operation identity. Every logical request, attempt, stream, and tool call needs an immutable ID and parent relationship. Ownership attaches to the operation or a clearly defined child, not to a process ID or network connection. A restarted worker must acquire ownership again rather than assuming yesterday’s memory is authority.

Represent ownership with a lease and a fencing token. The lease says how long an owner may act. The fencing token is a monotonically increasing generation issued on each acquisition. Every state-changing write, stream append, tool dispatch, and billing transition must include the current generation. Storage rejects commands from older generations even if their lease holder wakes up late.

Do not rely on expiration alone. Clock skew, pauses, delayed packets, and partitions can let an old worker believe its lease is valid after another worker has taken over. Expiration permits a new acquisition, but fencing prevents the old owner from changing durable state. Both pieces are required for safe failover.

Choose the ownership boundary carefully. A gateway may own the logical operation while provider attempts and tools use separate child leases. Too broad a lease serializes independent work; too narrow a lease makes the state graph difficult to reason about. Keep one writer for each mutable stream or effect boundary and make cross-boundary transitions atomic.

Acquire ownership atomically. Compare the current owner, generation, lifecycle state, deadline, and policy before issuing a new lease. A completed, cancelled, or expired operation should not become running because a worker requested ownership. Acquisition must fail closed when durable state cannot be read consistently.

Renew with evidence of progress. A worker should renew only while it is healthy, authorized, within deadline, and able to persist state. Include the current generation and expected lifecycle state. Renewal should not extend the customer’s operation deadline or revive work that policy has cancelled.

Set lease duration from failure behavior. A very short lease causes unnecessary takeovers during pauses. A very long lease delays recovery after a crash. Use observed pause, network, storage, and provider latencies, then reserve enough time for safe handoff. Separate the internal ownership lease from the customer deadline and provider timeout.

Make takeover explicit. A new owner must load the latest durable operation state, provider attempt IDs, stream sequence, tool-effect records, remaining budgets, and uncertainty. It should decide whether to observe, resume, cancel, reconcile, or start a new attempt. Takeover is not permission to repeat work whose outcome is unknown.

Fence provider callbacks. Bind callbacks to operation, attempt, and owner generation when the provider supports metadata. When it does not, map provider request IDs to the durable attempt and validate current lifecycle state. A callback from an old generation can update evidence or reconciliation according to policy, but it cannot dispatch new effects.

Protect streams with one append authority. Every event gets a sequence and owner generation. Storage accepts only the current generation and expected next sequence. A late worker cannot append tokens after takeover, and a new worker cannot invent continuity when provider state is unavailable. Mark gaps and uncertainty honestly.

Treat tools as irreversible boundaries. Before dispatch, atomically record tool-call identity, arguments digest, approval, idempotency key, and owner generation. The tool executor should reject stale generations or duplicate keys. If the outcome is unknown, reconcile it before retrying. A new lease never makes an old side effect safe to repeat.

Tie usage and charges to attempts. Provider work may continue after the gateway owner changes. Record which attempt generated usage, which owner observed it, and whether a takeover launched additional work. A stale worker cannot finalize billing, but its delayed provider receipt may still be valid evidence for reconciliation.

Handle graceful handoff. A healthy owner can stop admitting new child work, persist a checkpoint, release or transfer ownership, and wait for acknowledgement. The successor verifies the checkpoint and generation before continuing. A handoff should not require the old owner to remain reachable indefinitely.

Handle abrupt failure conservatively. After lease expiry, the successor must assume the old worker may still run until fencing rejects it. Do not infer that provider work stopped when the gateway process disappeared. Query provider status when available, preserve attempt budgets, and avoid duplicate side-effecting retries.

Coordinate across regions. Ownership storage and generation issuance need consistency strong enough to prevent two accepted writers. During a partition, prefer temporary unavailability over split-brain effects. If regional stores cannot agree on ownership, restrict work to read-only observation or fail according to contract.

Preserve tenant and policy boundaries. A takeover must revalidate authorization, residency, model allowlists, tool grants, and current policy epoch. Ownership metadata is not a substitute for permission. A worker in another region cannot acquire a lease if the request data or effect is not allowed there.

Secure lease credentials. Lease IDs and fencing tokens must be scoped, unguessable where needed, protected in transit, and excluded from customer-visible logs. Sign handoff messages and prevent replay across operations. Old tokens should remain recognizable for rejection without remaining valid authority.

Make observability generation-aware. Record acquisition, renewal, expiry, release, takeover, rejected stale writes, stream conflicts, tool suppression, provider uncertainty, and billing corrections. Operators should see who owned the operation at each transition and why another worker took over.

Test the ugly races. Cover process pause, worker crash, database partition, delayed renewal, clock skew, duplicate acquisition, old owner recovery, stream append after takeover, tool dispatch race, callback from an old attempt, provider completion during failover, graceful handoff, region partition, policy revocation, deadline expiry, and storage restart. Assert that only the current generation can create durable effects.

Measure ownership quality. Track lease churn, takeover latency, renewal failures, stale-write rejection, duplicate provider attempts, duplicate effects prevented, stream gaps, unknown outcomes, split-brain attempts, recovery success, deadline impact, and extra cost. The goal is not zero takeovers. It is recovery without ambiguous authority.

The practical pattern is this: use stable operation IDs, pair leases with fencing generations, define ownership boundaries, acquire atomically, renew only with authority and progress, size leases from real failure behavior, make takeover state-aware, fence callbacks and streams, isolate tool effects, reconcile billing by attempt, support graceful handoff, treat abrupt failure conservatively, require consistent cross-region ownership, revalidate policy, secure tokens, observe generations, test races, and measure recovery. Execution ownership is reliable when a second worker can take over without allowing the first worker to keep writing history.
