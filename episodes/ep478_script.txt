Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we designed deadline-aware admission control: estimate real work, reserve multidimensional capacity, protect operations already in flight, queue fairly, shed load early, and make every overload decision explainable. Today we move from the admission decision into the protocol that users actually experience when bytes begin to arrive. We are designing streaming as a first-class AI gateway protocol: event ordering, framing, usage accounting, cancellation, reconnects, partial results, provider translation, and the hard limits of failover after output has reached the client.

Streaming is often introduced as a user-interface feature. The model starts producing text, the browser renders it, and everyone calls the experience responsive. At gateway scale, streaming is a distributed transaction with an open-ended middle. The gateway has accepted an operation, selected a provider contract, opened a connection, and exposed an evolving result before the final answer exists. Capacity remains reserved while bytes flow. The caller can disappear, the provider can stop, or a tool may be waiting between model turns. If the gateway treats the stream as a pipe, it loses the ability to explain what happened.

The first principle is to define a stream as a sequence of typed events, not as arbitrary text chunks. A useful envelope includes an operation ID, attempt ID, stream ID, monotonic sequence number, event type, timestamp or elapsed time, payload, and a terminal marker. Event types might include accepted, metadata, response-start, delta, tool-call, tool-result, usage, warning, error, and completed. The exact names are less important than the invariant: every event has a stable identity and an unambiguous position in the operation lifecycle.

Do not let provider-specific chunks leak directly into your public API. One provider may emit Server-Sent Events with JSON fragments, another may use WebSockets, another may return a sequence of polling records, and another may combine tool calls with text deltas in a proprietary shape. The gateway needs an internal canonical event model, then adapters translate it to the public protocol. That canonical model is where ordering, accounting, redaction, capability checks, and termination rules live. Without it, every client and downstream consumer must learn every provider’s quirks.

Framing is the first practical boundary. For an HTTP streaming API, Server-Sent Events are convenient because browsers understand them and intermediaries can forward them, but the gateway still needs to define event boundaries, heartbeat behavior, retry hints, and the meaning of an empty data frame. Chunked transfer encoding is a transport mechanism, not an application protocol. A TCP packet can split an event, and multiple events can share one packet. Clients must parse the declared framing rather than assume each read is one logical message.

If you use WebSockets, define message types and close semantics just as carefully. A WebSocket frame is not automatically a complete model event, and a close code does not by itself tell the caller whether the provider completed, the gateway cancelled, or the network disappeared. For either transport, document maximum event size, UTF-8 behavior, compression boundaries, heartbeat intervals, idle timeouts, and whether the server may send a terminal event before closing the connection. Protocol ambiguity becomes expensive when customers build retries and billing logic around it.

Sequence numbers make the stream testable. Assign them at the canonical gateway boundary, not by copying a provider’s counter. The first event may be sequence one, and every subsequent event increments exactly once. Retransmission, if supported, must repeat the same sequence number and event identity rather than create a new event. A client that sees a gap can report it. A client that reconnects can request a replay from a known cursor, if replay is available. If replay is not available, say so clearly; do not pretend a new stream can continue an old one.

Ordering needs an explicit scope. Text deltas from one model turn must preserve order. A usage event may be emitted after the final delta but before completion. A warning about an approaching output limit should not arrive after the terminal event. Tool events create a more complicated sequence: the model may announce a tool call, the gateway may execute it, and a later model turn may produce more deltas. Define whether tool-result events are visible to the caller, whether internal policy events are hidden, and which event proves that a side effect was actually started.

The operation ledger from the previous episodes should remain the source of truth. A stream is a view over operation state, not the state itself. Persist enough metadata to recover the answer to basic questions: Was the request admitted? Which attempt produced sequence 17? Did the gateway send sequence 24 to the client? Did the provider acknowledge cancellation? Was the tool committed? Was usage finalized? You do not necessarily need to persist every token forever, but you do need durable boundaries for identity, authorization, billing, side effects, and terminal status.

Streaming changes admission economics because time is now a resource. A short response that finishes in two seconds and a response that emits one token every five seconds may consume similar tokens but very different connection capacity. Reserve a stream slot before sending the first response event. Track active stream count, expected duration, bytes per second, provider connection state, and the protected capacity required for finalization. If the caller requests streaming but the selected route cannot support it under the contract, negotiate an approved alternative before dispatch, or reject the request. Never silently return a buffered response after promising a live stream.

Backpressure must have a defined direction. The model provider may produce faster than the client can read. If the gateway buffers without limit, one slow client becomes a memory leak and eventually a platform incident. If the gateway drops arbitrary deltas, the client receives an invalid answer. Set a bounded per-stream buffer and choose a policy: pause upstream when the transport supports it, terminate with a structured backpressure error, or switch to a documented sampling or aggregation mode that preserves meaning. For token streams, aggregation may delay interactivity but is safer than losing sequence data.

Provider flow control is not always available. Some HTTP APIs continue generating even when the gateway stops reading. In that case, client backpressure must trigger cancellation or a bounded drain strategy. Mark the provider attempt as still active until termination is observed or a conservative timeout expires. Releasing the connection and token reservation merely because the client socket closed is unsafe. The provider may keep consuming quota, and a new admission decision based on phantom capacity can create a second overload wave.

Heartbeats serve two purposes: keeping intermediaries from deciding that an idle stream is dead, and giving clients evidence that the connection remains managed. A heartbeat must be distinguishable from content. It should not advance application content state, and it should have a documented interval and timeout. Avoid heartbeats that reset every deadline. The operation’s absolute deadline remains authoritative even if a connection is technically alive. A stream that emits heartbeats forever while the model has made no progress is not healthy completion.

Time limits should be split into stages. Set a time to first event, a maximum inter-event gap, a maximum total stream duration, and a deadline for terminal reconciliation. The right values depend on workload class and provider contract. A tool-using agent may need a longer total duration but a strict gap while waiting for each model turn. If a timer fires, emit the appropriate terminal error only once, cancel upstream, and preserve whether the cancellation was acknowledged. Do not use one idle timeout for every workload; batch generation, voice, multimodal reasoning, and interactive text have different progress signals.

Usage accounting is especially difficult when the result is incomplete. The gateway should distinguish estimated usage, provider-reported usage, and usage observed from the event stream. A final usage event may be delayed, omitted, or inconsistent with the number of visible deltas. Define a reconciliation state such as provisional, provider-confirmed, estimated, disputed, or unavailable. Do not invent exact token counts from character length and label them authoritative. If billing requires a conservative estimate, make the estimate explicit and preserve the evidence used to calculate it.

A stream can have multiple notions of completion. The provider may finish generation, the gateway may finish forwarding bytes, and a tool side effect may complete later. The client may receive the terminal event or disconnect before it arrives. Record these milestones separately. “Completed” should mean the public contract’s completion condition was met, while “provider completed” and “client observed completion” remain distinct facts. This prevents support teams from calling a stream successful merely because the model stopped when final bytes were lost in transit.

Cancellation begins at the client boundary but ends only when the whole operation is settled. A client may send an explicit cancel request, close the stream, or time out locally and vanish. Treat all three as cancellation signals, with appropriate evidence strength. Stop sending public events once cancellation wins the race, but continue internal cleanup. Propagate cancellation to the provider using the adapter’s contract. If the provider acknowledges it, record the acknowledgment. If it does not, keep the attempt in an uncertain or draining state until a bounded termination condition is met.

Cancellation is not rollback. If the model emitted a tool call and the gateway started an external action, closing the stream cannot unmake that action. The public protocol should expose a stable operation status endpoint so the caller can learn whether a tool was not started, started, completed, failed, or has an unknown outcome. For side-effecting tools, require idempotency keys and a deduplication boundary before admission. A stream is only as safe as the non-streaming effects hidden inside it.

Partial results need semantics, not just a boolean flag. A text stream may have produced a coherent answer prefix, an incomplete sentence, a tool call without its result, or a result that violated the requested schema. Define which partial outputs are safe for clients to display or store. Include a completion reason such as stop, length limit, cancelled, provider error, policy termination, deadline exceeded, or transport failure. If the response format requires valid JSON, do not imply that a partial prefix is a valid document. Advertise whether partial content is provisional and whether it may be reused.

The gateway should send terminal events that are structurally complete even when the answer is not. A terminal error can include operation ID, attempt ID, last sequence number, completion reason, retryability, and status lookup information without repeating sensitive prompt content. The client needs to know whether any provider attempt occurred and whether replay is possible. It should not have to infer that from a socket close or a half-written JSON object.

Reconnects are a product decision with protocol consequences. The simplest contract is no resume: once the stream breaks, the client queries operation status and decides whether to display the partial result or start a new operation. This is often the safest choice for agentic work. A resumable stream requires a cursor, replay retention, authorization on reconnect, and a clear rule for events that were generated but not delivered. The reconnect request must include the operation identity and a proof that the caller may see it. Never resume solely because someone knows a random stream URL.

If you support replay, define at-least-once delivery. The client may receive sequence 12, lose the acknowledgment, reconnect, and receive sequence 12 again. Idempotent client handling is essential. Exactly-once delivery across an arbitrary network is not a promise a gateway can make cheaply. State the guarantee as ordered, replayable, at-least-once events, or as best-effort live delivery with no replay. Honest weaker semantics are better than a fictional exactly-once stream.

Failover after streaming begins is fundamentally limited. Before the first content byte, the gateway can often fail over if the operation remains within its deadline and the fallback contract is compatible. After bytes have reached the client, a different provider cannot generally continue the same hidden generation state. It may not share the same tokenizer, system prompt interpretation, tool context, or random trajectory. Replaying the original request can duplicate visible text, change the answer, or repeat a side effect. Therefore route selection and admission must consider the point of no return.

Define a commit boundary for public output. Before the gateway emits the first irreversible content event, it may still choose another route. After emission, it should prefer completing or terminating the current attempt rather than pretending a fallback is seamless. If the product permits a visible continuation, label it as a new attempt and provide the prior partial output as context under explicit policy. For strict structured responses, buffer until validation succeeds before emitting the document, even if that sacrifices some time-to-first-byte. Streaming is not automatically more reliable than buffering.

Provider adapters must handle malformed and adversarial event sequences. Test duplicate deltas, missing finish reasons, usage before content, tool results without tool calls, invalid UTF-8, giant event payloads, out-of-order chunks, premature connection close, and a provider that keeps sending after cancellation. The adapter should reject or quarantine impossible sequences rather than pass them downstream. When a provider violates its contract, record the evidence and terminate according to policy. A malformed stream is a provider-contract failure, not a reason to corrupt the public protocol.

Security and privacy apply to every event. Streaming logs can accidentally capture prompts, tool arguments, retrieved documents, or sensitive output in a way that ordinary request logs do not. Separate transport diagnostics from content telemetry. Log sequence numbers, sizes, timing, hashes where appropriate, and contract versions without storing raw payloads by default. Apply redaction before events enter traces or support dashboards. Reconnect tokens, operation IDs, and event cursors must be unguessable and scoped. A stream that is publicly reachable for a few minutes can still expose an entire conversation if authorization is weak.

Moderation and policy enforcement are harder once content leaves the gateway. Decide whether output is inspected before release, sampled, inspected asynchronously, or terminated when a policy signal arrives. Pre-release inspection may require buffering and changes the latency promise. Asynchronous inspection cannot retract bytes already displayed. If a policy requires preventing release of certain content, the gateway must reserve enough buffering and inspection capacity to honor that requirement. A late policy decision is not equivalent to a pre-send guarantee.

Metrics should describe the stream as a lifecycle. Track time to first event, inter-event gap, total duration, bytes and events sent, active stream seconds, buffer high-water mark, cancellation latency, provider drain time, terminal-event delivery, reconnect success, replay volume, partial-result rate, and usage reconciliation lag. Break these down by provider contract, model, tenant, workload class, and termination reason. A good average time to first token can hide streams that hang after token five. A good completion rate can hide clients that disconnect before usage is finalized.

Capacity planning needs stream-specific forecasts. Token-per-minute limits do not tell you how many simultaneous HTTP connections your gateway or provider can sustain. Estimate concurrency from arrival rate multiplied by stream duration, then add uncertainty for long tails. Protect capacity for terminal events, cancellation calls, status queries, and reconciliation. During overload, admission may accept short non-streaming work while rejecting new long-lived streams, or it may require a lower maximum duration. Make those decisions explicit in policy and in the rejection reason.

Distributed deployments add ordering and ownership challenges. A stream should have a clear owner for upstream connection, sequence assignment, and cancellation. If a load balancer moves a reconnect to another region, the new owner needs a durable operation record and either a replay log or an honest no-resume response. Use fencing epochs so an old owner cannot continue publishing after ownership changes. Regional policy and residency constraints still apply to replay data, tool results, and usage records. Moving the stream is moving evidence, not merely moving a socket.

Graceful shutdown must drain streams deliberately. Stop admitting new long-lived work, advertise a retryable maintenance reason where appropriate, and give active streams a bounded drain window. Send a terminal shutdown event only if the public contract defines one and the client can safely act on it. Otherwise close with a status token that can be queried later. Cancel provider attempts that exceed the drain window, but preserve uncertain outcomes and side-effect status. A process manager that kills the gateway without stream-aware shutdown turns routine deployment into data loss.

The implementation pipeline can now be stated. Authenticate the request and create the operation identity. Negotiate streaming capabilities and choose the public protocol. Load policy and provider contracts. Estimate duration, tokens, bytes, tool work, and fallback options. Admit only with an expiring stream reservation and protected finalization capacity. Open the provider attempt through a contract-enforcing adapter. Translate provider frames into canonical typed events. Assign gateway sequence numbers, enforce ordering, redact diagnostics, and apply backpressure. Propagate cancellation. Emit exactly one terminal public outcome, reconcile provider usage and side effects, release reservations, and retain the receipt needed for status, billing, and audit.

Test the entire boundary, not just the happy path. Split every event across arbitrary transport chunks. Slow the client until the buffer fills. Kill the gateway after sequence 9 and before sequence 10. Drop the terminal event. Duplicate a replayed event. Make the provider continue after cancellation. Let a tool commit just as the client disconnects. Exhaust stream capacity while short interactive calls arrive. Change the policy bundle during an active stream. Route a reconnect across regions. Verify that every outcome remains ordered, bounded, authorized, and explainable. The test oracle should include what the client saw, what the provider did, and what the ledger knows.

The central design choice is whether streaming is merely an optimization or a contract. If it is an optimization, the gateway may buffer, downgrade, and retry under simple rules, but it must not claim more interactivity than it delivers. If it is a contract, then event identity, ordering, cancellation, backpressure, usage, partial results, and reconnect behavior must be specified like any other API surface. The extra work is justified because customers will build user interfaces, agents, billing, and safety controls on top of those details.

The series now connects another layer. Provider contracts tell us the stream shapes and cancellation guarantees an endpoint can support. Admission control decides whether enough connection, token, deadline, and finalization capacity exists. The operation lifecycle preserves one identity across attempts and partial output. Policy distribution determines which content may cross boundaries. Privacy-aware observability records timing and evidence without turning the stream into a shadow data store. Streaming is where all those promises become visible one event at a time.
