Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. Today we’re talking about tool result dispute resolution: how an AI API gateway handles conflicting evidence without guessing, silently choosing the convenient answer, or presenting uncertainty as fact.

Tool-using agents often receive more than one signal about an operation. A provider may report success, a callback may say processing, a target read may show no change, and a ledger may contain a pending entry. These signals can disagree without any one of them being malicious or useless.

A reliable gateway must preserve the disagreement, determine which sources are authoritative for the question, and produce a bounded result that says what is known, what conflicts, and what must happen next.

Start by treating a dispute as a first-class state. Do not force every result into success or failure merely because an application schema has only two values.

Useful dispute states include unresolved, partially resolved, source conflict, identity mismatch, stale evidence, scope mismatch, policy conflict, and human review required.

Give every dispute a stable dispute ID. Link it to the logical action, every attempt, every result, every claim, tenant, actor, tool, provider account, route, and delivery attempt.

Preserve each observation independently. A conflict is easier to resolve when the original evidence, timestamps, versions, and source identities remain available.

Do not overwrite one source with another. Replacing a provider response with a later target read destroys the history needed to understand the discrepancy.

Separate event time from observation time. A callback received now may describe an event that happened earlier, while a target read may describe the state at the moment of reading.

Record persistence time and delivery time as well. The order in which the gateway stored or sent observations is not necessarily the order in which the underlying events occurred.

Classify sources by authority. A provider may be authoritative for accepting a request, a target system for current resource state, a ledger for settlement, and a policy engine for authorization.

Authority depends on the question. There is no universal source that wins every dispute.

Define the question before resolving the conflict. “Did the provider accept the request?” is different from “Did the target change?” and “May we tell this user that the operation completed?”

Do not answer a broader question than the evidence supports. A valid acceptance receipt cannot automatically prove final completion.

Bind every observation to identity. Validate tenant, operation, target, resource, environment, provider account, region, model, and action fingerprint.

An apparently conflicting result may actually describe a different operation. Identity mismatch should be classified before semantic conflict.

Use canonical request fingerprints. Compare normalized operation, target, parameters, scope, purpose, and idempotency key across attempts and observations.

Do not merge retries into one provider event. Maintain a logical action identity and separate attempt identities.

A timeout followed by a successful retry is not the same story as one request that transitioned from timeout to success.

Track idempotency explicitly. If duplicate side effects are possible, the dispute should say whether the attempts were deduplicated, independently executed, or unknown.

For asynchronous tools, distinguish accepted, queued, processing, completed-reported, completed-verified, failed, expired, and disputed.

Do not use “success” for every non-error HTTP response. Transport success and business finality are separate facts.

Define freshness windows by operation. A cached status may be acceptable for a dashboard but unacceptable before a refund, deletion, deployment, or access change.

Mark stale evidence instead of treating it as an equal vote. Old evidence can explain history without describing current state.

Do not let a newer but weaker source automatically defeat an older authoritative source. Compare authority, identity, event sequence, and freshness together.

Use provider event sequence numbers or versions where available. They help detect reordering, replay, and missing events.

Do not trust arrival order. Networks delay, duplicate, and reorder callbacks.

Validate signatures and authenticity before semantic comparison. An unauthenticated callback should not enter the same authority class as a verified event.

Check schema versions. A status value can change meaning when a provider changes its API contract.

Do not compare strings without interpreting their versioned semantics. “Done,” “complete,” “settled,” and “active” may represent different lifecycle stages.

Maintain an explicit state machine. Define allowed transitions and which evidence can justify each transition.

Reject impossible transitions. A resource should not move from permanently deleted to active without a documented recreation or restoration event.

Keep impossible events visible as anomalies. Do not silently discard them merely because they break the expected state machine.

Use monotonic facts where possible. An immutable creation event, a ledger sequence, or a verified deletion marker can constrain later interpretations.

Do not assume every state is monotonic. Processing can return to retryable failure, and a provider may correct an earlier report.

Record corrections as new evidence. A provider correction should link to the original observation and explain what changed.

Do not rewrite the original observation. Operators and customers may need to know what was reported at the time.

Distinguish contradiction from evolution. “Processing” followed by “completed” is a normal lifecycle transition; “completed” followed by “never accepted” is a contradiction unless the identifiers differ.

Use causal relationships. A later target state may be caused by this action, another actor, a scheduled job, or an unknown external process.

Do not claim causality from temporal proximity alone. A state change after an action is evidence of sequence, not automatically evidence of responsibility.

Use compare-and-swap or version checks. For updates, prove that the expected prior version led to the observed new version.

A final value without a version transition may not prove that this action caused it.

For creates, verify stable resource identity and ownership. Existence by name is weak evidence when names can be reused.

For deletes, distinguish requested, accepted, hidden, archived, tombstoned, and physically removed. “Not found” is not a complete deletion proof.

For payments, separate authorization, capture, settlement, ledger posting, reversal, and reconciliation. A card provider and an accounting ledger may be correct about different stages.

For messages, distinguish accepted by the API, queued, handed to a provider, delivered, opened, and acted upon. Content matching does not prove delivery.

For deployments, separate release creation, artifact availability, rollout, health, readiness, and traffic exposure. A deployment conflict may be a stage mismatch rather than a true contradiction.

For file operations, compare object versions, checksums, storage regions, replicas, indexes, and deletion markers. Eventual consistency can produce temporary disagreement.

For model jobs, distinguish request acceptance, job scheduling, generation, output persistence, moderation, and client delivery.

For reads, record source, consistency level, query scope, cache age, and observation time. Two reads can disagree because they used different consistency guarantees.

For caches, record the source result identity and policy generation. A cache conflict should identify whether invalidation, revocation, or freshness caused the difference.

Do not let a cache hide a live dispute. If a fresh authoritative observation conflicts with a cached result, mark the cache stale and prevent it from supporting new high-impact claims.

Separate factual disputes from access disputes. A result may be factually clear but unavailable to the current audience, or it may be available but factually unresolved.

Separate policy conflicts from source conflicts. Two policy evaluators disagreeing is a control-plane problem; two providers disagreeing is an evidence problem.

Do not resolve policy disagreement by taking the most permissive result. Fail safe for actions with external consequences.

Preserve policy generation and evaluator identity. A dispute may come from configuration drift rather than conflicting customer data.

Check scope before content. A result for another tenant, region, account, environment, or purpose is not competing evidence for the current operation.

Reject cross-scope evidence rather than downgrading it to a normal conflict.

Use confidence boundaries, not a single confidence score. State which claims are supported, which are uncertain, and which cannot be made.

A disputed result may still support narrow claims. For example, the provider accepted the request, but final target state is unknown.

Return the strongest safe partial answer. Do not withhold every fact merely because one broader claim is unresolved.

Do not compose a confident summary from individually weak observations. Claim aggregation must respect the weakest critical dependency.

For workflows, define whether one unresolved child makes the parent unknown, partially complete, or eligible for compensation.

Do not report “all completed” when one critical child is disputed or the membership set is still changing.

Make dependency graphs explicit. Link parent claims to child observations and record which children are required for the parent conclusion.

Use human review selectively. Send high-impact, unresolved, or policy-sensitive disputes to a reviewer with a safe evidence view.

Do not ask humans to compare unstructured logs manually when the gateway can provide a normalized dispute timeline.

Give reviewers source labels, versions, timestamps, identity checks, authority rules, and recommended next actions.

Require a reason for manual resolution. Record actor, role, purpose, evidence inspected, decision, expiration, and any conditions.

Do not let a human override create permanent truth without scope and time limits. Manual resolution is also a claim with provenance.

Use two-person review for irreversible or high-value outcomes when appropriate. One reviewer should not silently convert uncertainty into settlement, deletion, or access.

Make resolutions reversible. If new evidence arrives, the gateway should reopen or supersede the prior resolution without destroying history.

Do not close a dispute merely because a client stopped waiting. An abandoned client request is not evidence of final state.

Use reconciliation jobs for uncertain effects. Query status, read the target, compare versions, inspect provider events, and attach every observation to the original action.

Do not create a new execution just to resolve an old execution dispute. Status lookup, verification, and compensation are distinct operations.

Use bounded retry and polling budgets. Endless reconciliation can create cost, provider load, and new ambiguity.

Record the reason reconciliation stopped: resolved, expired, inaccessible, contradictory, budget exhausted, or human review required.

Make expiration explicit. When evidence can no longer settle the dispute within the allowed window, return unknown or compensation-required rather than pretending the result is final.

Use compensating actions when the original effect is uncertain. Refund, rollback, cancellation, or manual reconciliation should have their own identity and evidence.

Do not describe compensation as if the original effect never happened. Preserve both the uncertain action and the corrective action.

Bind downstream side effects to dispute state. A disputed payment should not trigger a “payment failed” email, and a disputed deletion should not trigger a compliance certificate.

Require stronger evidence for consequential automation. A display may show “provider accepted, target unverified”; a refund may require reconciled settlement evidence.

Propagate uncertainty through protocols. HTTP responses, webhooks, queues, SDKs, and model tool results must preserve the same finality and dispute labels.

Do not reduce an internal disputed state to HTTP 200 with an ordinary success payload.

Expose machine-readable uncertainty. Include dispute ID, result IDs, evidence classes, freshness, finality, recommended action, and retry safety.

Keep raw evidence access separate and protected. Clients may receive a safe timeline while authorized operators inspect payloads through expiring references.

Do not copy sensitive provider payloads into every dispute record. Store minimal metadata and protected references.

Protect dispute metadata itself. It can reveal outages, customer activity, resource names, provider relationships, and security events.

Bind evidence references to tenant, audience, purpose, result identity, and expiration.

Record every dispute view and raw evidence access. Investigation is part of the audit trail.

Use claim-level resolution. One disputed field should not automatically invalidate unrelated verified claims from the same result.

For structured outputs, attach resolution status to paths and fields. For text, cite the bounded source span and mark interpretation.

Do not allow model-generated prose to erase dispute labels. The model may summarize uncertainty, but it must not turn “unknown” into “probably complete” without a visible basis.

Separate recommendation from evidence. “Wait and reconcile” is a policy decision derived from the dispute, not a provider fact.

Bind the recommendation to policy version and risk class. Different tools need different responses to the same uncertainty.

For low-risk informational work, a stale result may be acceptable with a timestamp. For irreversible work, stale or conflicting evidence should block execution.

Record why a source was selected or rejected. Future investigators should see authority rules, identity checks, freshness checks, and schema validation outcomes.

Do not use an opaque ranking model as the only dispute resolver. Source precedence must be explainable and operation-specific.

Use deterministic resolution rules for safety-critical transitions. Similar evidence should produce the same safe outcome across regions and workers.

When rules cannot decide, preserve unknown. Determinism does not require inventing certainty.

Handle distributed control planes. Policy versions, provider metadata, tool schemas, and authority rules must converge before resolution decisions are trusted.

Detect configuration drift. If two regions resolve the same evidence differently, record evaluator versions and stop unsafe cross-region claims.

Use immutable decision receipts. A resolution should identify input evidence, rules, evaluator version, output state, and expiration.

Do not reuse an old resolution after material context changes. Reauthorize or re-evaluate when tenant, audience, purpose, target, policy, or freshness changes.

Test provider disagreement. Return accepted from one source and failed from another; verify the gateway preserves both and produces a bounded state.

Test identity mismatch. Use a valid response for another target, account, operation, or tenant; verify rejection rather than normal conflict.

Test out-of-order events. Deliver completion before processing, duplicate callbacks, corrections, and delayed failures.

Test stale caches and memory. Replay old evidence after revocation, deletion, policy change, and target updates.

Test retry ambiguity. Lose the first response, execute a retry, and verify that the system distinguishes possible duplicate effects from safe idempotent replay.

Test partial workflow failure. Resolve most children, leave one disputed, and verify parent aggregation follows its declared rule.

Test policy conflict. Make regional evaluators disagree and confirm fail-safe behavior for external side effects.

Test human resolution. Require reason, scope, evidence review, expiration, and audit records; then inject new evidence and verify reopening.

Test recovery. Crash workers during evidence persistence, dispute materialization, reconciliation, and delivery. The dispute must remain recoverable and auditable.

Test cross-tenant isolation. Reuse action IDs, provider IDs, cache keys, and dispute references across tenants.

Test model summarization. Provide conflicting evidence and verify that the answer preserves the conflict, evidence levels, and safe next action.

Measure unresolved disputes by operation, provider, route, tenant, region, and age. Concentrated disputes often reveal integration or consistency problems.

Measure identity mismatches separately. They may indicate retries, provider bugs, routing errors, or abuse.

Measure stale-evidence decisions, correction rates, contradiction duration, and manual resolution volume.

Measure high-impact actions blocked by disputes. This is a safety signal, not merely a conversion problem.

Measure disputes that later become duplicate side effects, billing mismatches, unauthorized disclosures, or incorrect notifications.

Track reconciliation cost, polling volume, provider status calls, and time to finality.

Track unknown outcomes honestly. A decrease in unknowns is good only if false certainty does not increase.

Track false resolution. Count claims later reopened by stronger evidence or policy correction.

Track source authority coverage. Every operation should have documented authority rules for acceptance, state, delivery, billing, and deletion.

Track schema and policy drift. Many disputes begin when status semantics or evaluator versions diverge.

Keep dispute schemas versioned. Historical resolutions must remain interpretable as providers, tools, and policies evolve.

Do not silently change the meaning of resolved, verified, final, or unknown. Use explicit schema versions and migrations.

Make SDKs dispute-aware. Typed responses should expose finality, dispute state, evidence classes, freshness, action safety, and correlation IDs.

Give application developers safe defaults. If they ignore an optional dispute field, the SDK should not silently map an uncertain result to success.

The central principle is simple: conflicting evidence is not a formatting inconvenience; it is a real system state that must be preserved, classified, evaluated, and communicated.

An AI API gateway should define the question, validate identity, compare source authority and freshness, preserve every observation, distinguish evolution from contradiction, return safe partial facts, block risky side effects, and keep every resolution reversible and auditable.

That is how agents can handle ambiguity without guessing—and how a gateway can remain trustworthy when the outside world refuses to tell one perfectly consistent story.
