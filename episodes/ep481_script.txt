Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we designed durable agent workflows: persistent state, stable step identities, fenced workers, reconciliation, compensation, and honest partial outcomes. Today we address the boundary that must surround all of that machinery. When one gateway serves many customers, every workflow, tool call, memory lookup, cache entry, event, and operator action must remain inside the correct tenant. We are designing multi-tenant isolation for AI gateways and agent workflows: how to prevent one customer’s context from becoming another customer’s answer, authority, or bill.

Multi-tenancy is often described as attaching a tenant ID to each database row. That is necessary, but nowhere near sufficient. An AI gateway combines identity, prompts, retrieved documents, provider credentials, tool capabilities, durable workflow state, logs, caches, queues, and billing. A single missing tenant check anywhere in that chain can create a cross-customer leak. Worse, agent workflows amplify the damage because they can act. The failure is no longer only that customer A sees customer B’s text. An agent for A might use B’s credential, resume B’s workflow, approve B’s action, or spend B’s budget.

Begin with a precise tenant model. Define what a tenant is, which organizations can contain subaccounts or projects, and whether users may belong to several tenants. Do not overload tenant, workspace, project, billing account, and deployment region into one ambiguous identifier. A request should carry an authenticated principal, an active tenant, a role or capability set, and any narrower resource scope. The active tenant must be selected through an authorized binding, not accepted because a client supplied an arbitrary header. Tenant context is a security decision, not routing metadata.

Authentication proves who the requester is; tenant authorization proves where that identity may act. Keep those checks separate. A valid user token does not authorize every tenant whose ID the user can guess. Resolve memberships and service-account bindings from a trusted identity store, then mint short-lived internal claims that include tenant, audience, purpose, and policy version. At each trust boundary, verify the claim rather than forwarding an unsigned tenant header. If a user switches workspaces in a web interface, create a new authorized context instead of mutating a global session variable shared by concurrent tabs.

Make tenant context immutable within one operation. Once the gateway admits a request, its tenant identity should travel with the operation ID, trace, workflow ID, queue message, model call, and tool dispatch. Application code should not be able to replace it halfway through execution. Child operations inherit the parent tenant through a controlled constructor, not by copying miscellaneous request fields. If a workflow genuinely needs cross-tenant administration, model it as a distinct privileged operation with explicit source and target scopes. Never let ordinary agent planning invent a tenant transition.

Use tenant-scoped identifiers even when underlying IDs are globally unique. A workflow lookup should require both tenant ID and workflow ID. A tool result lookup should require tenant, operation, and expected resource type. This prevents insecure direct-object references and protects against future migrations that change identifier formats. Repository interfaces should make unscoped access difficult to express. Prefer methods such as load_workflow(tenant, workflow_id) over load_workflow(workflow_id), and reserve global lookup methods for narrowly audited control-plane code.

Database isolation should use defense in depth. Put tenant predicates in application queries, but also enforce row-level security, separate schemas, or separate databases according to risk. Bind the database session to the authenticated tenant where the platform supports it. Test that missing context fails closed rather than returning all rows. Administrative migrations and background jobs deserve special scrutiny because they often bypass row-level policies. A repair script running with elevated database rights should still accept an explicit tenant scope, produce a dry-run count, and reject an accidental request to process everything.

Choose an isolation tier deliberately. Shared tables with row-level security can be efficient for many small tenants. Separate schemas offer stronger operational separation but increase migration complexity. Separate databases or clusters reduce blast radius for regulated or high-value customers, at higher cost. Dedicated gateway workers and provider accounts may be justified when credentials, data residency, or performance guarantees demand them. The important point is that all tiers implement the same logical contract. A premium isolation tier should strengthen boundaries, not introduce a completely different and poorly tested code path.

Durable workflow storage needs tenant binding at creation. Record tenant, requester, policy domain, region, encryption key reference, and definition version in the first immutable event. Every later event must match that binding. A worker cannot claim a step merely because it knows the workflow ID; its lease request must prove that its execution pool is authorized for the workflow’s tenant and region. Compensation, cancellation, and reconciliation must use the same tenant context. Recovery paths are especially dangerous because they run after normal assumptions have already failed.

Queue isolation is frequently overlooked. A shared queue may be acceptable, but every message must carry an authenticated tenant envelope and a nonforgeable operation reference. Consumers should fetch authoritative workflow state and compare tenant, region, step, and expected version before acting. Do not trust the payload alone. Use per-tenant or per-tier concurrency controls so one customer cannot fill every worker slot. Reserve capacity for cancellation, reconciliation, and compensation, because safety work must continue even when ordinary execution is throttled.

The model request itself is a tenant boundary. Construct prompts from tenant-scoped sources only. System instructions, organization policies, retrieved documents, conversation history, user profile, and tool descriptions must all be selected under the same authorized context. Labeling text with a tenant ID after retrieval does not repair a cross-tenant query. Retrieval must apply tenant filtering before ranking and before any candidate content reaches the model. If vector search cannot guarantee that predicate, use separate indexes or namespaces rather than relying on the model to ignore irrelevant documents.

Embedding stores deserve the same controls as transactional databases. Each document chunk should have tenant, source, classification, retention policy, and version metadata. Query APIs should require a tenant namespace that cannot be overridden by free-form filters. Index-building pipelines must preserve ownership when splitting, enriching, and re-embedding documents. Deleted or transferred documents must be removed from both primary storage and derived indexes. Evaluate isolation with adversarial nearest-neighbor tests: distinctive secrets from one synthetic tenant should never appear among another tenant’s candidates, even under unusual queries.

Conversation memory creates another leakage path. Avoid global memory keyed only by user name, email, or model session. The same person may participate in several organizations with different permissions and expectations. Key memory by tenant, principal, purpose, and perhaps application. Separate personal preferences from organization-owned facts. When a user leaves a tenant, revoke access to that tenant’s memory without deleting unrelated personal settings. When data is promoted from a conversation into durable memory, record ownership and provenance so later retrieval can enforce the original boundary.

Caching improves latency, but unsafe cache keys can defeat every authorization check before them. Include tenant, model contract, policy version, data classification, region, and all response-affecting permissions in the key. Do not share semantic response caches across tenants merely because prompts look equivalent; hidden context and contractual data-use terms may differ. Negative caches and authorization caches also need tenant scope. A cached “resource exists” result can leak customer activity, while a cached permission decision can outlive a revoked membership. Use short expiries and event-driven invalidation for security-sensitive entries.

Provider credentials must never be selected from model text. Keep a tenant-scoped credential registry in the gateway, with provider, environment, region, allowed models, quota, and rotation state. The agent may request a capability such as generate_text, but the gateway chooses the credential authorized for the active tenant. Use secret references rather than placing keys in workflow events or queue payloads. If several tenants share a provider account, preserve tenant-level accounting and abuse controls internally. For higher isolation, allocate dedicated provider projects and verify that failover cannot silently switch to a shared credential outside the customer’s contract.

Tool catalogs also need tenant filtering. Two tenants may expose tools with the same friendly name but different endpoints and authority. Compile the model-visible tool set from the active tenant’s policy, then bind each tool token to tenant, operation, schema version, and expiry. At dispatch, reauthorize the specific normalized arguments. A tool called search_tickets for one tenant must not accept another tenant’s project ID simply because the downstream API key can see both. Least privilege is strongest when downstream credentials are tenant-specific, but gateway enforcement remains necessary.

Approvals must be tenant-bound and object-bound. An approval link or chat button should identify the tenant, workflow, exact action, normalized arguments, policy version, approver, and expiry. When activated, verify that the approver still belongs to the tenant and is authorized for that action. Never apply a generic “approved” message to whichever workflow is waiting. If a manager has several tenant tabs open, the displayed organization and target should be unmistakable. A changed amount, destination, resource, or capability invalidates the old approval and requires a new decision.

Encryption can reduce the impact of storage mistakes, but it does not replace authorization. Use envelope encryption with tenant-specific key references for sensitive prompts, tool arguments, workflow evidence, and provider credentials. Bind ciphertext context to tenant and resource identifiers so encrypted blobs cannot be swapped across tenants undetected. Plan key rotation and tenant deletion before launch. A cache or analytics pipeline that receives plaintext after decryption remains part of the boundary. Keep decryption close to the authorized use and avoid passing plaintext through broad event buses.

Regional policy intersects with tenancy. A tenant may require that prompts, embeddings, logs, backups, and operator access remain in a jurisdiction. Record the tenant’s residency policy in authoritative configuration and pin each workflow to a permitted region. Failover should choose only compatible regions and providers. If none are available, fail closed or degrade to a permitted capability; do not move data globally to preserve availability. Background reconciliation and disaster recovery must obey the same placement rules as the original request, including where restored backups and diagnostic exports are processed.

Resource isolation is also a security property. A noisy tenant can cause timeouts, dropped callbacks, and delayed compensations for everyone else. Apply admission control, weighted fairness, rate limits, workflow fan-out limits, token budgets, and queue quotas per tenant and service tier. Track both immediate requests and durable obligations. A tenant that starts thousands of long-running workflows consumes future polling and reconciliation capacity even when little is running now. Charge or reserve capacity when obligations are created, and preserve a protected pool for terminal cleanup.

Billing attribution should come from trusted execution records, not client labels. Every provider call, cached response, tool execution, retry, and compensation should attach to a tenant-scoped operation ledger. Distinguish billable customer work from platform recovery and provider-caused retries. Reconcile shared provider invoices against internal usage without exposing one tenant’s volumes to another. Quota decisions must use committed and reserved usage so concurrent requests cannot overspend the same balance. If attribution is uncertain, quarantine the record for reconciliation rather than assigning cost to the most convenient tenant.

Observability must remain useful without becoming a side channel. Tenant-facing dashboards should query through the same authorization layer as production APIs. Metrics labels should avoid raw customer names, prompts, document titles, and high-cardinality resource identifiers. Logs must carry tenant scope for filtering, but broad log search should be restricted and audited. Traces that cross shared infrastructure should expose only the spans an operator or customer is entitled to see. Even status codes and timing can leak information, so normalize responses for unauthorized and nonexistent resources where appropriate.

Operator access is one of the largest practical risks. Support engineers often need to diagnose a single tenant, but permanent global read access is excessive. Use just-in-time elevation, ticket binding, tenant and resource scope, short expiry, reason capture, and session recording. Redact content by default and reveal sensitive fields only when necessary. Separate the ability to inspect from the ability to act. A support console should not let an operator copy a workflow into another tenant, replay a tool call with different credentials, or export an unrestricted trace through a convenient download button.

Control-plane changes need isolation too. Tenant configuration includes provider allowlists, budgets, model policies, regions, tools, webhooks, and encryption references. Version those settings and require optimistic concurrency so two administrators cannot overwrite one another. Validate webhook ownership and destination before activation. A malicious tenant must not register an internal network endpoint and turn the gateway into a cross-tenant or infrastructure probe. Configuration templates can be shared, but instantiated values and secrets must remain tenant-owned. Audit who changed what, from which prior version, and when it became effective.

Avoid the confused-deputy problem in service-to-service calls. A worker may possess broad infrastructure credentials while acting for a narrow tenant. Downstream services need enough authenticated context to enforce that narrow authority. Use audience-restricted service identities combined with signed tenant and operation claims. A service should reject a claim issued for a different audience, expired workflow, or unauthorized region. Do not let internal network location substitute for authorization. The fact that a request came from the gateway does not mean every action requested by that gateway is legitimate.

Cross-tenant collaboration must be explicit rather than treated as an exception to isolation. If two organizations share a project, create a separately governed collaboration resource with defined owners, participants, data classes, tools, retention, and revocation behavior. Do not duplicate documents into both tenants without provenance. Do not make one tenant’s service account silently act for the other. Each operation should state whether it acts in a tenant, in the collaboration space, or transfers an approved artifact between them. Shared work needs a boundary of its own.

Backups, exports, and analytics are common escape routes from otherwise strong controls. Backups should preserve tenant encryption and deletion semantics. Restore tests must prove that data returns to the right scope. Tenant exports should be generated from authorized snapshots, encrypted, time-limited, and auditable. Analytics pipelines should minimize data and use tenant-scoped intermediate storage. If aggregate models or benchmarks combine customer data, establish an explicit contractual and technical policy. “We removed the tenant ID” is not anonymization when prompts or rare events can identify the source.

Deletion must follow derived data. When a tenant closes an account or requests erasure, identify primary records, workflow histories, embeddings, caches, fine-tuning sets, evaluation corpora, logs, exports, and provider-side retained data. Some audit evidence may need lawful retention, but it should become inaccessible to ordinary product paths and carry a documented expiry. Tombstones can prevent deleted identifiers from being accidentally reused. Produce a deletion manifest that records categories and completion status without retaining the sensitive content being deleted.

Testing isolation requires more than unit tests around tenant predicates. Build two or more synthetic tenants with deliberately distinctive canary data, credentials, tools, budgets, and policies. Run the same user identity in multiple tenants. Attempt direct-object references, cache collisions, workflow resume attacks, forged queue messages, stale approvals, region failover, operator searches, export generation, and deletion followed by retrieval. Randomize tenant switching under concurrency. The strongest invariant is simple: no output, side effect, authority decision, or cost attribution may depend on another tenant’s private state unless an explicit collaboration contract authorizes it.

Use fault injection at tenant boundaries. Drop context fields between gateway and worker. Reuse an operation ID under another tenant. Deliver a callback to the wrong regional endpoint. Restore a database snapshot with stale row-level policy configuration. Exhaust one tenant’s queue while another tenant runs compensation. Rotate credentials during a workflow. Force a cache service to return an entry with a mismatched ownership envelope. Every component should reject ambiguity and emit a safe, tenant-scoped incident signal. Silent fallback to global context is never an acceptable recovery mode.

Incident response must assume a suspected leak is possible. Preserve relevant evidence, disable the affected path, rotate exposed credentials, and identify the precise set of tenants and resources involved. Because every operation carries immutable tenant binding, investigators should be able to trace the blast radius without searching raw customer content indiscriminately. Notify according to legal and contractual obligations, but do not speculate beyond evidence. After containment, add a regression test for the boundary that failed. Isolation incidents demand both technical repair and proof that equivalent paths are covered.

A practical request pipeline now comes together. Authenticate the principal and resolve an authorized active tenant. Load versioned tenant policy, region, budget, credential, and capability context. Create a tenant-bound operation or workflow identity. Retrieve memory and documents through pre-filtered tenant namespaces. Build a model request containing only allowed context and tools. Validate the model’s proposed action, acquire tenant-scoped capacity, and dispatch with bound credentials and idempotency. Persist evidence under tenant encryption, attribute usage to the operation ledger, and expose status through tenant-authorized APIs. At every hop, mismatch means rejection, not repair by guesswork.

The key lesson is that tenant isolation is an end-to-end invariant. It cannot be delegated to one database column, one API gateway header, or one well-behaved model. Identity, storage, retrieval, caches, workflows, queues, credentials, tools, approvals, regions, observability, billing, and operator access must all agree on the same tenant boundary. Durable workflows make this especially important because authority survives longer than a web request. The workflow must remember not only what happened, but for whom it was allowed to happen.

This episode extends the series from durable execution to durable separation. Provider contracts define available capabilities. Admission control protects fair capacity. Safe tool execution constrains side effects. Workflow orchestration preserves state and recovery. Multi-tenant isolation ensures that every one of those mechanisms serves the correct customer and no other.
