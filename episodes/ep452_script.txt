Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. Today we’re talking about tool result contract evidence integrity: how an AI API gateway proves that a result, its evidence, and its restrictions were not altered between production and use.

A tool result can be authentic when it leaves a provider and still become unsafe later. An adapter may rewrite a status, a serializer may drop a field, a cache may serve the wrong version, a callback may be attached to another operation, or a transformation may change the evidence level without declaring it.

Integrity is more than checking whether bytes changed. It means preserving the identity, meaning, authority, and limitations of a result across every boundary.

Start with a complete integrity boundary. Bind the payload to result identity, source identity, operation identity, evidence class, finality, freshness, tenant, resource, purpose, audience, contract version, policy generation, provider context, retention, and allowed uses.

If these fields control what a consumer may do, they belong inside the integrity decision.

Do not hash only the visible answer while leaving scope and expiration outside the protected boundary.

Define the threat model. Consider accidental mutation, buggy adapters, stale caches, replay, cross-tenant substitution, provider callback forgery, serialization loss, compromised internal services, malicious clients, operator error, and inconsistent regional replicas.

Different threats require integrity, authenticity, freshness, authorization, and lineage controls together.

Do not assume a valid checksum proves the sender was authorized or the result is current.

Use stable identities. Result, source, operation, contract, policy, provider event, transformation, and action receipt identities should survive retries and transport changes.

Stable identity makes it possible to detect substitution and duplicate effects.

Do not generate a new logical result ID every time a message is retried.

Define canonical serialization. Specify field names, types, ordering, encoding, null behavior, timestamp precision, enum values, unknown-field rules, and normalization.

Signing and verification must operate on the same meaning, not merely on two strings that happen to parse.

Do not sign one JSON formatting while verifying another undefined representation.

Protect security-relevant metadata. Include tenant, resource, audience, purpose, evidence, finality, expiration, source version, contract version, policy generation, provider account, region, and transformation lineage where relevant.

A payload that is unchanged but moved to another tenant is not the same safe result.

Do not leave authority-bearing headers outside the integrity envelope.

Separate authenticity from integrity. A signature can show who signed an envelope and whether it changed, but it does not prove the signer’s claim was true or that the result remains authorized.

Consumers still need freshness, scope, policy, and evidence checks.

Do not treat cryptographic validity as universal permission.

Bind signatures to audience and purpose. A result signed for an internal verifier should not automatically be valid for a customer export or action executor.

A signature should fail when the result is presented in a different context than the one approved.

Do not create one reusable signed object for every downstream purpose.

Use domain separation. Distinguish provider responses, gateway evidence envelopes, audit records, client views, action receipts, callbacks, and replay artifacts.

A signature valid in one domain must not be accepted as authority in another.

Do not reuse the same token format for display data and external side effects.

Include versioned algorithms and keys. Carry signature version, algorithm, key identity, issuing authority, and verification policy.

Define key rotation, compromise, revocation, and algorithm retirement behavior for stored and in-flight results.

Do not accept old signatures indefinitely just because the content is still readable.

Protect the full envelope. If evidence class, finality, expiration, lineage, retention, or restrictions can be modified without invalidating integrity, downstream consumers may overtrust the result.

The envelope and payload should be verified as one semantic object.

Do not sign the value and serialize the limitations separately.

Preserve source integrity. Record the provider’s response hash, operation identity, account, route, region, callback sequence, and source version where available.

The gateway should distinguish provider-signed facts from gateway-normalized facts.

Do not claim provider attestation for data the gateway created itself.

Preserve transformation integrity. For redaction, summarization, translation, classification, extraction, embedding, merging, and splitting, record input versions, output versions, code or model, parameters that affect meaning, and guarantees preserved or reduced.

A derived result needs its own integrity identity and lineage.

Do not let a transformed result inherit the original signature as if no meaning changed.

Record intentional changes. Normalization, policy filtering, redaction, schema adaptation, and provider translation may be legitimate, but they must be explicit.

Consumers should know what changed and why.

Do not hide an intentional semantic downgrade behind a generic adapter success.

Use append-only provenance. Preserve the original result reference and append transformations, rather than overwriting the history of what was received.

This supports correction, dispute, audit, and forensic reconstruction.

Do not replace a source value in place and lose the evidence of its earlier state.

Protect version binding. Bind a result to source version, contract version, policy generation, route generation, and schema version.

A byte-identical payload under a changed contract may have different allowed uses.

Do not treat payload equality as contract equality.

Protect time binding. Include source event time, observation time, verification time, issue time, expiration, and relevant clock authority.

Integrity should detect attempts to extend freshness by rewriting timestamps.

Do not let a forwarding service reset the issue time.

Protect scope binding. Tenant, subject, resource, operation, provider account, region, purpose, and audience should be checked against the current request.

A valid result used in a different scope is a substitution attack even if its bytes are untouched.

Do not rely on transport channels to provide all scope guarantees.

Protect authorization binding. If a result was read, transformed, exported, approved, or promoted under a decision, bind it to decision identity, policy generation, obligations, and expiration.

The consumer should reject a result whose authorization context no longer matches.

Do not carry an allow decision without the result version it authorized.

Protect finality and uncertainty. Provisional, reported, verified, reconciled, disputed, revoked, expired, corrected, and unknown states must remain distinct and integrity-protected.

Changing unknown to failed or reported to verified changes authority.

Do not collapse state enums for convenience.

Protect correction and revocation links. Include source version, supersession, correction, dispute, deletion, and revocation references needed to update dependent artifacts.

Integrity includes preserving the ability to learn that a result is no longer valid.

Do not make a result tamper-evident but correction-blind.

Handle replay explicitly. A valid old envelope may be copied and presented again in a new context.

Use expiration, nonce, audience, purpose, operation identity, sequence, and single-use receipts where required.

Do not confuse “not modified” with “safe to reuse now.”

Handle substitution. Present a valid result from another tenant, resource, provider, operation, or contract while keeping the request shape identical.

Identity and context binding should detect the mismatch.

Do not validate only the signature and ignore semantic identity.

Handle truncation and omission. Remove fields, shorten arrays, drop stream chunks, omit lineage, and delete restrictions.

The receiver should reject or restrict an incomplete envelope when the missing data matters to its purpose.

Do not make every missing field optional to preserve compatibility.

Handle extension and injection. Add unknown fields that claim stronger evidence, broader scope, longer retention, or new permissions.

Unknown security-relevant fields should be rejected or treated conservatively.

Do not accept arbitrary extensions as authority.

Handle serialization changes. Test numbers, timestamps, Unicode, nulls, empty values, duplicate keys, field ordering, floating-point precision, and integer limits.

Syntactically valid data can still change semantic meaning.

Do not assume all language runtimes interpret values identically.

Handle compression and encryption. Verify integrity after decompression and decryption, while preserving the original content identity and envelope metadata.

Encrypted or compressed data still needs scope, freshness, and authorization checks.

Do not let a protected blob bypass the current policy.

Handle storage. Database rows, object files, cache entries, queue messages, indexes, embeddings, backups, logs, and exports need identifiers and integrity behavior appropriate to their role.

A copy should be detectable as a derivative, not mistaken for the canonical source.

Do not let a cache create an untraceable second source of truth.

Handle cache integrity. Bind cache entries to result identity, source version, contract, policy generation, audience, purpose, expiration, and invalidation state.

A valid cache entry for one request must not satisfy another context.

Do not trust a cache key that omits tenant or purpose.

Handle queue integrity. Sign or authenticate message identity, contract, policy generation, action identity, expiration, and revalidation requirements.

Workers should reject altered, duplicated, expired, and context-mismatched messages.

Do not treat queue transport success as proof of message integrity.

Handle callback integrity. Validate signature, provider account, operation identity, resource, sequence, region, event time, and expected contract.

A correctly formatted callback can still be forged, replayed, or attached to the wrong request.

Do not accept a callback because it parses correctly.

Handle streaming integrity. Protect ordering, sequence, stream identity, content hash or equivalent, completion marker, final state, and interruption status.

A partial stream must not be confused with a complete response.

Do not let a client infer completion from connection closure.

Handle retries. Preserve logical result identity and attempt identity across transport retries.

A retried message should not silently become a new external operation or a different evidence claim.

Do not recalculate authority from an unbound retry payload.

Handle provider fallback. When provider, account, model, route, adapter, or region changes, append the transition and re-evaluate evidence and guarantees.

Do not copy the original provider’s signature, retention, verification, or cancellation claim to a fallback response.

Handle multi-region replication. Carry origin, replication sequence, source version, policy generation, revocation, expiration, and conflict status.

On disagreement, restrict high-impact use or obtain independent verification.

Do not let the most recently received replica overwrite a newer semantic state.

Handle transformations across regions and services. Reverify signatures at trust transitions and ensure output identities link to input identities.

Private transport does not remove the need for semantic binding.

Do not assume an internal hop is incapable of mutation.

Handle human review. Bind approval to result version, evidence, scope, purpose, action, policy generation, freshness, reviewer identity, and expiration.

A signed approval for one result should not authorize a corrected or substituted result.

Do not allow a general approval note to float free of its artifact.

Handle action receipts. Bind the final side-effect receipt to result identity, evidence, finality, freshness, scope, contract, policy, idempotency, expiration, and executor.

Executors should reject altered, replayed, mismatched, and consumed receipts.

Do not use a bearer-like action token without context and single-use semantics.

Handle execution outcomes. Append dispatched, accepted, completed-reported, target-verified, reconciled, failed, canceled, disputed, and unknown outcomes without overwriting earlier facts.

Integrity means preserving uncertainty when the external state cannot be proven.

Do not write a definitive success merely because an HTTP response arrived.

Handle correction and revocation. When the source changes, append a new version and propagate restrictions to derivatives, caches, approvals, queues, references, and executors.

Integrity is incomplete if dependent consumers cannot discover the change.

Do not preserve historical signatures while allowing superseded authority to execute.

Handle deletion. A deleted artifact should not reappear from a backup, cache, export, or replay record without an explicit controlled restoration policy.

Record deletion and restoration identities.

Do not treat a surviving copy as the original result just because it has the same payload.

Handle retention. Preserve enough integrity metadata to enforce retention and prove lifecycle actions without keeping prohibited raw content.

An audit record can prove a result changed or was deleted without storing the entire result everywhere.

Do not create permanent sensitive copies in integrity logs.

Use data minimization. Hashes, classifications, stable references, versions, and outcome codes can often prove continuity without exposing prompts, tool payloads, secrets, or private provider configuration.

Protected drill-down can be used for authorized investigations.

Do not turn observability into a second content repository.

Protect integrity metadata. Keys, signatures, hashes, custody records, and verification logs can reveal operational patterns and must have access, retention, and tamper controls.

The proof itself deserves protection.

Do not let every service that verifies a result modify the verification history.

Define verification policy by purpose. Display, support, analytics, billing, memory, export, and side effects may require different integrity and authenticity levels.

A valid provider signature may support display while a side effect requires gateway binding and target verification.

Do not apply one verification profile to every consumer.

Define behavior on verification failure. Distinguish corrupted, unauthenticated, expired, revoked, incompatible, incomplete, conflicting, and unknown results.

Give consumers actionable instructions: refresh, reconcile, reauthorize, quarantine, or stop.

Do not return one generic error that encourages blind retry.

Use secure failure handling. Do not echo altered payloads into logs or error messages, and do not expose signature details that help attackers probe key or policy behavior.

Return safe identifiers and reason categories.

Do not leak sensitive content while explaining why integrity failed.

Prove verification at ingress. Validate canonical form, signature, identity, scope, contract, policy, timestamps, evidence, lineage, and required fields before placing the result into a trusted store.

Unverified content should remain explicitly untrusted.

Do not let malformed data enter a trusted cache before validation.

Prove verification at every trust boundary. Check provider to gateway, gateway to queue, queue to worker, worker to storage, region to region, service to executor, and internal to external delivery.

Optimize repeated checks carefully, but preserve the boundary and current context.

Do not rely on one early check when later context can change.

Prove transformation integrity. For every adapter and model transformation, compare input and output identity, fields, states, restrictions, lineage, and evidence class.

A transformation that changes meaning must create a new version and an explicit record.

Do not call semantic mutation a formatting operation.

Prove cache and queue integrity. Alter keys, versions, scope, expiration, policy, and action identity; duplicate and reorder messages; restore old data after correction.

The system should detect or safely restrict every dangerous mutation.

Do not test only clean transport conditions.

Prove callback integrity. Send valid-looking callbacks with incorrect signatures, accounts, operations, resources, sequences, regions, event times, and contracts.

Verify no authority or state transition occurs.

Do not accept callbacks from a known provider without binding them to the expected operation.

Prove replay resistance. Reuse a valid result, approval, reference, and action receipt across tenants, resources, purposes, providers, regions, versions, and time windows.

Every inappropriate reuse should fail.

Do not count signature verification as replay prevention.

Prove partial and reordered streams. Drop chunks, duplicate chunks, change sequence, close before final marker, and append data after completion.

The client should receive explicit incomplete or corrupted state.

Do not infer finality from the last received bytes.

Prove correction and revocation. Update or withdraw source evidence after derivatives and actions exist.

Verify all protected paths stop using the superseded or revoked authority and retain safe proof of the transition.

Do not rely on one event consumer to propagate every change.

Prove clock and freshness binding. Alter timestamps, expiration, timezones, precision, and clock source while keeping payload content constant.

The system should detect time mutation and apply purpose-specific freshness rules.

Do not let an attacker extend usability by changing one timestamp.

Prove policy and contract binding. Change policy generation, contract version, route capabilities, retention, verification, or audience after an envelope is issued.

The consumer should reauthorize or restrict when the old context no longer applies.

Do not treat an unchanged signature as proof of current permission.

Prove provider fallback and region behavior. Change provider account, adapter, model, route, region, or callback source after admission.

Verify new facts are recorded and old guarantees are not copied without evidence.

Do not hide provider changes behind a stable client-facing model name.

Prove action receipts. Alter result version, resource, tenant, evidence, freshness, policy, idempotency key, expiration, or executor after receipt creation.

The executor should reject the receipt and append a safe failure reason.

Do not allow a receipt to authorize a similar but different action.

Prove crash recovery. Stop the system during signing, verification, storage, replication, transformation, correction, revocation, receipt issuance, and execution.

After recovery, no result should gain authority, lose a restriction, or create a duplicate effect.

Do not confuse durable storage with durable integrity state.

Prove key rotation and compromise response. Rotate keys, revoke a signing authority, retire an algorithm, and verify behavior for old and new artifacts.

High-impact use should stop or require revalidation when trust roots change.

Do not preserve compromised signatures as live authority for convenience.

Prove privacy. Inspect signatures, hashes, logs, traces, errors, dashboards, support views, dead letters, backups, and exports for raw prompts, tool payloads, secrets, and unnecessary provider details.

Integrity evidence should be useful without being overexposed.

Do not create a sensitive forensic copy at every hop.

Measure verification coverage. Track protected reads, transformations, deliveries, promotions, and executions with successful integrity and context checks.

Actions without a verifiable integrity record are priority investigations.

Do not average away rare high-impact bypasses.

Measure integrity failures by cause: mutation, substitution, replay, omission, signature failure, scope mismatch, version mismatch, stale state, callback mismatch, or missing lineage.

Different failure classes need different fixes.

Do not group every verification failure under network error.

Measure time from mutation or revocation detection to blocking, time from correction to dependent restriction, and time from key compromise to effective denial.

A detection event is not enough if unsafe use continues.

Do not report detection as containment.

Measure transformation drift. Track fields and guarantees lost across adapters, SDKs, regions, providers, storage, and model-mediated processing.

A rising drift rate signals semantic integrity weakness even when hashes still verify.

Do not measure only byte-level corruption.

Measure replay attempts, invalid receipts rejected, mismatched callbacks, conflicting replicas, incomplete envelopes, and unknown outcomes quarantined.

These measures show whether integrity controls influence behavior.

Do not reduce quarantine just to improve operational metrics.

Create integrity assurance reports per contract and operation class. Show protected fields, signing domains, key and algorithm policy, verification boundaries, transformation lineage, executor checks, test results, exceptions, open gaps, and last proof time.

Assurance should expire after relevant code, schema, provider, policy, or key changes.

Do not certify integrity once and assume it survives system evolution.

The central principle is simple: an unchanged payload is not enough. The system must prove that the result is the same authorized meaning, in the same scope, under the same contract, with the same evidence and lifecycle limits.

An AI API gateway should bind payload, provenance, state, time, scope, policy, contract, transformations, corrections, revocations, and action receipts into verifiable integrity boundaries across every hop.
