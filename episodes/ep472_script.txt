Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we designed tenant-aware budgets and fairness: explicit principals, multidimensional quotas, reservations, weighted scheduling, reclaimable borrowing, retry charging, fallback protection, and predictable degradation. Today we take the next logical step. We are designing the end-to-end operation lifecycle for an AI API gateway: one durable identity from client intent through admission, routing, provider attempts, streaming, tools, retries, usage, and reconciliation.

A request can look simple at the edge. A client sends a chat completion, the gateway selects a provider, and a response comes back. But production systems are rarely that linear. The provider may stream tokens, call a tool, time out after doing work, return incomplete usage, or succeed while the gateway loses the response. A retry may reach a second provider. A client may retry the entire operation while the first attempt is still running. If each component records its own local story, the platform eventually has several plausible histories and no reliable answer about what happened.

The operation lifecycle solves this by making the business intent durable before dispatch. The gateway creates one operation record for the client’s intent and links every later event to it. That record is not merely a verbose log line. It is the semantic spine of the request. It answers: what did the client ask for, which policy applied, what capacity was reserved, which attempts were made, what side effects occurred, what usage was observed, and what remains uncertain?

Start with identity. A client request needs an operation ID generated by the gateway or supplied through a validated idempotency key. The external request ID can be safe to expose, while the internal record may include a separate immutable identifier. Do not use a provider request ID as the operation identity. Provider IDs are local to an attempt, may be absent, and change when the gateway fails over. The operation represents intent; provider attempts represent executions of that intent.

Idempotency is about more than avoiding duplicate HTTP responses. It protects the meaning of a client operation when networks fail. A client sends a request and receives no response. It does not know whether the gateway rejected it, the provider never saw it, or the provider completed it while the response was lost. When the client retries with the same idempotency key, the gateway should find the existing operation, return its known result, report that it is still pending, or expose a carefully defined unknown state. It should not blindly create a second side effect.

An idempotency key must be scoped. The same string used by two organizations should not collide, and a key reused for a materially different request must not silently attach to the old result. Store the authenticated principal, endpoint, normalized request fingerprint, policy scope, and expiration alongside the key. If the fingerprint differs, return a conflict rather than guessing. Expiration should be long enough for realistic retries and short enough that the key store does not become permanent application state.

Normalize without erasing meaning. JSON field order may not matter, but model name, tool definitions, output schema, temperature, seed, requested modalities, and safety settings can matter. A request fingerprint should represent the contract-relevant shape, not every incidental header. Keep the original request metadata needed for audit, but protect sensitive prompt and tool content through redaction, encryption, or content references. Reproducibility is not an excuse to create an uncontrolled transcript archive.

The operation state machine should be explicit. A useful sequence is accepted, validating, admitted, queued, dispatched, streaming, awaiting tool, reconciling, succeeded, failed, canceled, or unknown. These are semantic states, not an invitation to add a new label for every code path. Define which transitions are legal and which are terminal. A canceled operation should not later become a normal success merely because a delayed provider event arrived; instead, record the late event and resolve the conflict according to policy.

State alone is not enough. Every transition needs an event with an operation ID, event ID, monotonic sequence or causality marker, timestamp, actor, policy version, and source. The state is a convenient projection. The event history is the evidence. If a database update and an outbound dispatch happen in the wrong order, the record should make the ambiguity visible rather than implying that the desired order definitely occurred.

Use an outbox or equivalent durable handoff between recording and dispatch. First persist the operation and the intent to dispatch. Then a worker reads the outbox and attempts delivery. This prevents a process crash between “we accepted the request” and “we sent it to the provider” from producing a record that cannot be explained. The outbox itself needs delivery state, attempt count, lease expiration, and an idempotency token for the downstream adapter.

But durable handoff does not make dispatch exactly once. In distributed systems, the worker can send a provider request and crash before marking the outbox item complete. On restart, it may send again. The safe design is at-least-once orchestration combined with idempotency where the provider supports it, operation-level deduplication where it does not, and an explicit unknown-outcome path. Do not claim exactly-once execution because a table has a unique constraint.

Represent each provider execution as an attempt. An attempt includes route, model, region, provider request ID, start and end evidence, timeout policy, reservation IDs, retry lineage, and the adapter contract version. It also records classification: not sent, sent with unknown outcome, confirmed success, confirmed rejection, transport failure before dispatch, or provider failure after dispatch. These distinctions matter. A connection error before bytes left the gateway is different from a timeout after the provider may have generated a costly response.

Attempt numbering must be stable. A retry of the same operation is attempt two, even if the second provider is a different route. A worker restart that replays an uncertain send should not quietly overwrite attempt one. Create a new execution record linked to the uncertainty, or attach a clearly marked replay event. This lets operators see that two downstream executions may have occurred and prevents usage reconciliation from counting only the attempt that happened to return a response.

Admission belongs in the lifecycle, not beside it. Before dispatch, record the tenant, project, workload class, budget dimensions, reservation amounts, deadline, and decision reason. A reservation should have its own identity and expiration, and it should link to the policy version that authorized it. If the request is queued, the reservation may be held or refreshed according to a defined rule. If it is rejected before dispatch, the operation should still preserve the decision and the dimension that blocked it.

A reservation is a promise, not usage. At completion, reconcile estimated input tokens, actual input tokens, output tokens, image units, audio seconds, tool calls, concurrency time, and spend. The ledger should keep estimate, maximum, observed value, and final charge separately. If the provider’s usage data is delayed, mark the charge pending. If the result is unknown, do not release every reservation simply because the local process ended. Hold a bounded amount and resolve it through provider reporting, a webhook, a query, or a controlled write-off policy.

The same principle applies to concurrency. A stream may be active for minutes while its token total remains uncertain. Create an expiring lease with heartbeats. On a clean close, release the slot. On a crash, allow reclamation after a safety interval. If the provider operation might still be running, mark the lease as uncertain before reclaiming it. A slot reclaimed too quickly can create duplicate work; one reclaimed too slowly can starve the tenant. The operation ledger should expose that tradeoff.

Deadlines travel with the operation. Capture the client deadline, gateway deadline, queue deadline, provider timeout, and any tool deadline separately. A retry must inherit the remaining end-to-end deadline rather than starting a fresh timer. Otherwise a request that has already consumed most of its useful time can generate a long chain of attempts after the user has stopped caring. At every transition, calculate whether the remaining time justifies queueing, retrying, falling back, or degrading.

Routing decisions should be recorded as decisions, not inferred later from a final provider ID. Store eligible routes, exclusions, health snapshot, capability checks, privacy constraints, budget result, and the selected route. The decision may include scores, but the explanation should be intelligible: this model was selected because it met the data policy, had available capacity, satisfied the context requirement, and remained within the tenant’s budget. If the route was chosen during an incident, record the incident policy and fallback reserve that applied.

Policy versions are part of causality. A model alias can change, a tenant tier can be upgraded, a provider circuit can open, or a safety rule can be revised while an operation is in flight. Attach the effective policy version to admission, routing, each attempt, degradation, and reconciliation. Do not reconstruct yesterday’s decision by reading today’s configuration. The ledger should preserve the rule context that existed when the decision was made.

Streaming deserves its own event model. Record stream opened, first byte, chunks observed, usage updates, client cancellation, provider close, gateway close, and finalization. Avoid storing every token by default. Hashes, byte counts, chunk sequence numbers, timestamps, and selected metadata can prove continuity without copying sensitive content. If the client disconnects after receiving half a response, that is not the same as the provider failing before producing anything. The public result and the internal charge should reflect the distinction.

A stream can end in a difficult middle state. The gateway may have delivered a valid final marker but failed before writing the success record. Or it may have delivered content without knowing whether the provider finished its tool call. Make finalization idempotent. A finalizer should compare the current state and operation version, apply the same result only once, and preserve conflicting late events. Use compare-and-set or an equivalent optimistic concurrency check so two workers cannot both settle the operation as if they were the sole owner.

Tool calls turn generated text into side effects. Treat a tool invocation as a child operation linked to the parent model operation. Record tool name, arguments through an appropriate privacy boundary, authorization decision, idempotency key, start and end status, and effect confirmation. A model response that proposes a tool call is not evidence that the tool executed. The child operation must reach a confirmed, rejected, canceled, or unknown state before the parent workflow decides what comes next.

Unknown tool outcomes require restraint. If the network fails after sending a payment request, calendar mutation, or database write, automatically retrying may duplicate the side effect. First query by idempotency key or provider operation ID. If the tool cannot reconcile, move the workflow to recovery and tell the caller that the outcome is uncertain. Remaining token budget is not permission to replay an unverified side effect. Capacity accounting and effect safety meet at this boundary.

The parent operation should not hide child cost. Tool execution may consume provider calls, compute, network time, and external quotas. Attribute those costs to the tenant and workload, while preserving the relationship to the parent intent. If an agent performs eight model turns and three tool calls, the client may see one conversation response, but the gateway needs a complete internal accounting of the work. This is how budgets, fairness, and incident analysis remain honest.

Retries need lineage and reason codes. Record whether a retry followed a transport failure, provider overload, contract mismatch, safety rejection, or an application-level request. A retry after a connection reset is not equivalent to a retry after malformed provider output. The retry policy should examine the attempt classification, remaining deadline, side-effect risk, tenant retry budget, and alternative route eligibility. “Transient” should be evidence-backed, not a universal escape hatch.

A second client submission complicates matters. If it carries the same idempotency key and matching fingerprint, attach it as a retrieval or wait event. If it carries a new key but the same business correlation ID, it may be an intentional new operation or an accidental duplicate. Do not deduplicate based on similarity alone. Offer a client-visible idempotency contract and let applications choose when a new intent is genuinely new.

Failure responses should be projections of the ledger. A typed quota error should identify the relevant limit and, when safe, a retry horizon. A provider outage response should distinguish “not attempted” from “attempted with unknown outcome.” A degraded response should state what changed: smaller output cap, alternate model, cached result, or deferred batch processing. Stable semantics make client behavior safer than a generic five-hundred error that causes every SDK to retry.

Reconciliation is a workflow, not a nightly cleanup script. When an operation is terminal locally but usage is pending, enqueue a reconciliation task with a deadline and backoff. Query provider usage where supported, consume callbacks, compare gateway counters with billing exports, and record evidence for every adjustment. If the provider never answers, close the uncertainty with an explicit bounded write-off, dispute, or conservative charge. An unexplained gap is not zero usage; it is a data-quality incident.

Reconciliation should be monotonic where possible. Do not let a late report reduce already finalized usage without an adjustment record. Preserve the original observation, the corrected value, the source, and the reason. For token counts, an estimate can become observed usage, then a corrected usage figure, but the history should remain auditable. Financial and quota systems need this discipline because a silent mutation can make both customers and operators lose trust.

Build invariants around the lifecycle. Every attempt belongs to exactly one operation. Every reservation is released, settled, expired, or explicitly written off. No terminal operation silently accepts a new provider attempt. Every tool effect has a known or unknown outcome. A retry cannot exceed the operation’s total deadline. A charged output cannot exceed the provider evidence or the declared conservative cap without an adjustment. Invariants turn the ledger from passive storage into an executable reliability contract.

Watch for impossible combinations. An operation marked “not dispatched” should not have provider tokens. A released concurrency lease should not continue receiving stream heartbeats. A successful tool child should not be missing from the parent’s cost summary. A policy version used for admission should not disappear while the operation is still reconciling. These checks can run online for critical transitions and asynchronously for broader audits.

Privacy must be designed into the evidence model. Store references and cryptographic hashes when the full prompt is unnecessary. Separate operational metadata from content access. Apply retention by data class: short-lived raw traces, longer-lived billing facts, and carefully minimized audit records. Restrict who can view tool arguments and prompts. A trustworthy operation history is not one that remembers everything. It is one that remembers enough to defend a decision without creating a second unauthorized data lake.

Incident replay becomes much more useful once the lifecycle is explicit. An engineer can ask which tenant reservation was active, which routes were eligible, which provider attempts were uncertain, whether the client received a partial stream, and whether a retry multiplied side effects. Replay should distinguish facts from simulations. Historical events are evidence. A counterfactual rerun using a newer router is a hypothesis. Never overwrite the original decision with the replay result.

Test the ledger with fault injection. Crash after writing the operation but before enqueueing dispatch. Crash after provider send but before marking the attempt. Drop the final stream marker. Delay usage for an hour. Duplicate a webhook. Change a tenant policy during queueing. Partition the quota coordinator. Return a tool result after the parent has timed out. Then verify that the system produces one explainable history, not a collection of optimistic guesses.

Test client behavior too. Send the same idempotency key concurrently from multiple gateway replicas. Reuse a key with a different request fingerprint. Retry after a timeout while the original stream is still active. Cancel just as a provider sends its final chunk. Ask whether the response tells the caller what is safe to do next. A technically correct ledger that produces ambiguous client guidance still leaves duplication risk at the edge.

There is a useful symmetry across this series. Health models decide whether a provider deserves traffic. Overload coordination decides whether work can enter. Tenant fairness decides whose work receives scarce capacity. The operation lifecycle records what was promised, attempted, delivered, charged, and left uncertain. These are not separate subsystems joined by log shipping. They are parts of one admission-and-execution contract.

A mature AI API gateway therefore creates a durable operation before dispatch, separates intent from provider attempts, validates scoped idempotency, uses an outbox for handoff, records reservations and policy versions, carries deadlines end to end, models streams and tools explicitly, charges retries, preserves unknown outcomes, reconciles delayed usage, and enforces lifecycle invariants. It makes finalization idempotent and late events visible. It minimizes sensitive content while keeping enough evidence to explain what happened.

The goal is not to pretend that distributed execution can be made perfectly simple. The goal is to make uncertainty explicit and bounded. When a network fails, the gateway should know whether work was not sent, may have been sent, or was confirmed. When a tool outcome is unclear, it should recover safely rather than replay casually. When a customer asks about a charge or a missing response, the platform should answer from durable evidence instead of a best guess assembled from timestamps.
