Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we treated streaming as a first-class gateway protocol: typed events, sequence numbers, bounded buffers, cancellation, usage reconciliation, reconnect rules, partial results, and the point of no return after output reaches a client. Today we cross that boundary into action. We are designing tool execution at the AI gateway: capability declarations, argument validation, authorization, idempotency, sandboxing, retries, durable side effects, and the controls that keep a model’s plan from becoming an unreviewed production operation.

A model can generate text without changing the world. A tool call can send an email, delete a record, provision a server, move money, publish content, or expose data. The moment a gateway executes tools, it is no longer only routing inference. It is coordinating an agentic transaction across a probabilistic planner, a policy system, an external service, and a user who may disconnect halfway through. The hard problem is not making a function callable. It is making every action bounded, attributable, reviewable, and honest about what happened.

Start with a strict separation of roles. The model proposes an action. The gateway decides whether that proposal is admissible. A tool executor performs the action under a constrained identity. The external system returns evidence. The gateway then reports the outcome to the model and caller. Do not collapse these into one “execute tool” step. If a model can directly select a URL, credential, tenant, and arbitrary arguments, the gateway has delegated authorization to generated text. That is not a control plane; it is a prompt-shaped privilege escalation.

The public tool contract should be machine-readable. For every tool, declare a stable name, version, description, input schema, output schema, side-effect class, required scopes, data classification, timeout, retry policy, maximum cost, and whether the action is reversible. Also declare whether it is read-only, idempotent, conditionally idempotent, or non-idempotent. A tool that says “create invoice” is not equivalent to one that says “preview invoice.” The distinction must exist in metadata that policy can evaluate, not only in prose that a model may misunderstand.

Capability declarations need an audience and a lifetime. The model may receive a reduced list of tools relevant to the current task. The gateway’s internal registry may contain more tools than the model is allowed to see. Bind each exposed capability to a tenant, user, operation, policy bundle, and expiry. If a tool is removed or its schema changes, new calls should use the new contract while in-flight calls remain governed by the version under which they were admitted. A name alone is not a sufficient capability identity. Use a versioned tool identifier and preserve it in the operation receipt.

Tool descriptions are part of the attack surface. A description can accidentally encourage unsafe behavior, reveal internal endpoints, or include instructions that conflict with gateway policy. Treat descriptions as controlled configuration. Review them, sign them with the policy bundle, and make clear which fields are informational and which are enforced. Retrieved text, documents, and tool output must never be allowed to redefine the tool’s authority. The model can read a sentence saying “ignore the safety check.” The gateway must still apply the safety check.

Schemas protect structure, but validation has layers. First validate syntax: types, required fields, allowed enum values, maximum lengths, nesting depth, and total payload size. Then validate semantics: account belongs to tenant, date range is permitted, amount is within a limit, resource exists, and the requested operation matches the user’s intent. Finally validate policy: this principal may perform this action on this resource in this environment at this time. JSON Schema can express useful boundaries, but it cannot replace authorization or business invariants.

Reject unknown fields by default, especially when the executor forwards arguments to a downstream API. An extra field can become a hidden mode switch or a future privilege when the provider adds support later. Normalize strings, URLs, identifiers, and time zones before policy evaluation. Be careful with duplicate keys and ambiguous numeric formats. A validator that checks one parsed representation while the executor uses another creates a canonicalization gap. The exact normalized argument set should be stored and signed as the input to execution.

Authorization should be evaluated at execution time, not only when the conversation begins. Permissions can change, credentials can expire, and a plan can sit in a queue. Evaluate the effective principal, tenant, resource, tool version, environment, data classification, and approval state immediately before dispatch. Use least-privilege delegated credentials with an audience restricted to the target service. Do not give a general-purpose model worker a long-lived administrator token and rely on the prompt to keep it careful.

There are at least three identities to preserve. The human or service principal requested the operation. The model generated a proposal. The executor account performed a call. Logs and downstream audit records should connect all three without pretending they are the same actor. Include operation ID, conversation or workflow ID, model attempt ID, tool call ID, policy version, executor identity, and approval evidence. This makes it possible to answer not only “who deleted the record?” but also “which proposal led to it, under which policy, and what did the gateway verify first?”

Consent and approval need precise semantics. A user saying “help me clean up old files” is not automatically consent to delete every file matching a model-generated query. For low-risk reads, standing authorization may be enough. For high-risk writes, require a confirmation that summarizes the normalized action: target, scope, amount, side effect, and expiry. Bind approval to a hash of the exact arguments and tool version. If any material field changes, the approval no longer applies. Never display a friendly summary that hides a dangerous normalized value.

Approval is not a substitute for policy. A user can approve an action they are not authorized to perform, or approve a request that violates data-residency or regulatory rules. The gateway should apply policy first, then determine whether human approval is required. Approval records should state who approved, what they saw, when it expires, and whether the action was executed. For workflows with many small steps, use a bounded approval envelope rather than asking for a click on every token, but make the envelope narrow enough that it cannot silently expand into a different operation.

Before execution, establish an idempotency boundary. Assign a tool call ID and an idempotency key derived from the operation identity, tool version, normalized arguments, and attempt policy. Send that key to the downstream service when supported. If the service has no idempotency support, the gateway must maintain a durable deduplication record or classify retries as unsafe. A timeout does not prove that an action failed. The request may have committed and the response may have been lost. Retrying blindly can create two charges, two tickets, or two deployments.

Idempotency keys have scope and retention rules. A key must be unique enough to prevent accidental collisions but stable across gateway retries for the same logical action. Store the key with states such as reserved, dispatched, outcome-known, outcome-unknown, and expired. If a duplicate call arrives, return the recorded outcome when safe. If the previous outcome is unknown, expose that uncertainty and require status lookup or explicit recovery. Never convert “unknown” into “failed” merely because the HTTP client timed out.

The gateway needs a durable tool execution ledger. A useful record includes proposal received, validation passed or failed, authorization decision, approval requested or granted, dispatch started, provider acknowledgment, downstream request identifier, response received, side effect confirmed, and final classification. Each transition should be monotonic and attributable. Store hashes of sensitive arguments when raw values are not needed, but retain enough evidence to reconcile the external system. The ledger is not just for debugging; it is the source of truth when a caller reconnects after a stream ended.

Execution should happen in an isolated worker boundary. Do not run arbitrary model-generated code in the gateway process. For HTTP tools, restrict destination hosts, methods, headers, body size, redirects, DNS behavior, and response size. For code tools, use a sandbox with a read-only base image, limited CPU and memory, no ambient credentials, controlled filesystem access, and an explicit network policy. Treat tool output as untrusted input even when it comes from a service your company operates. The output may contain secrets, prompt injection, enormous payloads, or instructions aimed at the next model turn.

Egress controls are as important as ingress validation. A tool should not be able to call every address on the internet because its input schema contains a URL. Resolve hostnames under policy, block private and link-local ranges where appropriate, limit redirects, and re-check the destination after each redirect. Separate control-plane endpoints from data-plane destinations. Give a tool a narrow allowlist or a brokered service interface whenever possible. Network policy should be evaluated against the normalized destination, not merely the original string.

Secrets must be injected just in time and withheld from model-visible output. The executor can receive a credential through a short-lived secret broker scoped to one call. The tool adapter should redact authorization headers, cookies, connection strings, and known secret patterns before logging or returning output. A downstream error that echoes a secret is still sensitive. Apply size limits and content inspection before tool results enter the conversation. If the model needs a status or a customer name, return only those fields, not the complete raw response.

Tool output needs a schema and trust label. Distinguish data returned from an external system, data derived by the executor, policy metadata, and free-form diagnostic text. A model should not be allowed to interpret an untrusted error message as a gateway instruction. Wrap results in a canonical envelope with tool call ID, result status, typed data, truncation information, and provenance. If a result is partial or stale, say so. If the executor could not verify the side effect, return an unknown outcome instead of a confident success sentence.

Timeouts are multidimensional. Set a queue deadline, authorization deadline, connection deadline, time to first downstream response, total execution deadline, and reconciliation deadline. A tool that waits for a long-running job should not occupy a gateway worker indefinitely. Convert long work into an asynchronous operation with a status handle, subject to authorization on every poll. The model can continue planning while a job runs, but the gateway must prevent it from starting a second conflicting action unless the workflow explicitly permits that concurrency.

Retries must be classified by failure evidence. A connection failure before dispatch may be safely retriable. A response indicating rate limiting may be retriable after the server’s delay. A timeout after dispatch is usually outcome-unknown. A validation error is not retriable without a changed proposal. A permission error should not be retried with a different credential. Encode this matrix in the tool contract and adapter. Exponential backoff is not a safety policy; it merely spaces out attempts.

Circuit breakers and budgets protect the rest of the platform. Track tool calls by tenant, workflow, resource, provider, and side-effect class. Limit concurrent writes, total spend, fan-out, recursion depth, and calls per model turn. A model that is asked to “research this” should not be able to call a search tool thousands of times because each individual call is cheap. When a budget is exhausted, return a structured policy outcome that the model can understand. Do not let the model recover from a denied action by inventing a new tool name or changing an argument casing.

Concurrency control matters when tools touch shared state. Use resource versions, conditional requests, locks, or transactional operations where available. A model may issue “read account balance” and “transfer funds” in sequence, but another actor can change the account between them. Bind a write to the version or facts that were authorized. If the downstream API cannot provide conditions, reduce the allowed scope or require a fresh confirmation. The gateway should not claim atomicity across services that do not support it.

Compensation is not rollback. If an order is created and shipment booking fails, a compensating cancellation may be possible, but it is another side effect with its own authorization and failure modes. Model workflows should declare whether steps are reversible, compensatable, or irreversible. For irreversible actions, put the approval and commit boundary as close to dispatch as possible. After dispatch, the ledger should expose the state honestly: completed, compensation pending, compensation failed, or outcome unknown. A neat “transaction failed” label can hide a real-world shipment or charge.

Human review can be inserted at the right boundary. Asking for approval before the model has resolved a target creates vague consent. Asking after dispatch is too late. The best checkpoint is after deterministic validation and normalization but before the irreversible external call. Show the user the exact high-level action and any important uncertainty. For sensitive workflows, require two-person approval, a change ticket, or a policy-controlled maintenance window. Make review decisions durable and replayable without exposing private payloads to operators who do not need them.

Streaming tool calls follow the protocol rules from the previous episode. Emit a tool-proposed event only after the gateway has parsed and validated the model’s call enough to identify it. Emit an execution-started event only after authorization and dispatch actually begin. Do not send “tool completed” when the downstream response merely arrived; completion may require a side-effect confirmation. If the caller disconnects, execution does not automatically stop. The operation status endpoint must tell the truth about work that continues after the stream is gone.

A tool call can race with cancellation. Define the linearization point: before dispatch, cancellation can prevent the call; after dispatch, cancellation becomes a request to stop or a status inquiry, not a rollback. The gateway should record which side won the race and use fencing or a dispatch token so a cancelled worker cannot start late. If the external provider supports cancellation, propagate it and record acknowledgment. If not, mark the action as in flight or unknown and continue reconciliation. “The browser closed” is not evidence that the payment did not happen.

Model loops require containment. After a tool result, the model may request another tool, return an answer, or repeat a call. Set maximum turns, maximum tool calls, total wall-clock time, and cumulative cost. Detect repeated equivalent calls and contradictory actions. Require the model to receive a structured denial rather than an empty result, so it can explain a blocked step without trying infinite variations. For high-risk domains, use a workflow state machine instead of allowing the model to choose any next tool from a flat list.

The state machine should distinguish plan, validate, approve, execute, observe, and close. A plan is not an execution request. A validated call is not dispatched. A downstream acknowledgment is not a confirmed side effect. A completed tool is not necessarily a completed business workflow. These distinctions make recovery possible. They also create useful metrics: how often models propose invalid arguments, how often approvals expire, how many calls end unknown, and which tools generate the most compensation work.

Observability must be privacy-aware and action-aware. Log tool identity, version, policy decision, durations, sizes, status classes, attempt counts, and downstream request IDs. Avoid raw prompts, complete arguments, and full tool output by default. Use structured redaction and access-controlled sampling for incident investigation. Trace spans should show the relationship between model attempt, policy evaluation, executor, and downstream service, but traces must not become a second ungoverned data lake. Record hashes and references when they are enough to prove continuity.

Testing must attack the seams. Feed malformed JSON, duplicate keys, huge arrays, Unicode confusables, invalid URLs, redirects to private addresses, stale approvals, expired credentials, and tool output containing injection text. Kill the worker before and after dispatch. Drop the downstream response. Replay the same idempotency key with changed arguments. Change authorization while a call waits in a queue. Disconnect the client as a charge commits. Return a success response with no side effect and an error response after a side effect. Verify that the ledger and status API preserve uncertainty instead of guessing.

Run contract tests against every adapter. Confirm that timeouts map to the right evidence class, provider request IDs are captured, cancellation is propagated where supported, sensitive fields are redacted, and retry behavior follows the declared policy. Use a fake downstream service that can pause between “received” and “committed,” because that is where many real incidents occur. Test schema evolution with old in-flight calls and new proposals. A tool contract is only real if the adapter, executor, policy engine, and audit record agree on its meaning.

The gateway’s public API should make outcomes easy to retrieve. Return a tool call ID, operation ID, status URL, retryability, and side-effect classification. When an action is denied, explain the category without leaking policy internals or sensitive data. When it is pending, provide a pollable state with authorization checks. When it is unknown, say what evidence is missing and what reconciliation path exists. Clients and agents can handle a constrained truth much better than a generic 500 error followed by a dangerous retry.

The implementation pipeline is now clear. Authenticate the principal and create an operation identity. Select a versioned capability from the policy-filtered tool registry. Parse and normalize the model proposal. Validate syntax, semantics, authorization, budgets, data boundaries, and approval requirements. Reserve execution capacity and create an idempotency record. Dispatch through an isolated adapter with scoped credentials and egress controls. Record provider evidence. Reconcile the external outcome. Return a typed result or uncertainty state to the model and caller. Close the ledger only when the public and operational completion conditions are satisfied.

The central design choice is whether a gateway is merely a convenient function router or an enforcement boundary. A function router can expose names and forward JSON. An enforcement boundary must preserve identity, version capabilities, reject ambiguity, limit authority, isolate execution, distinguish proposal from action, and retain durable evidence. The second design is more work, but once AI can touch production systems, the first design is not simplicity. It is unpriced risk.

Admission control reserves not just model tokens but executor slots, approval capacity, and reconciliation work. Streaming makes proposals and outcomes visible as typed events.
