Welcome to AI Dev Tools, the Crazyrouter Podcast. This is episode five hundred eighty-three. Today: cancellation propagation for AI gateways. Stop the work, not just the waiting. In our last episode, we made every timeout share one clock. But a deadline only describes when an answer stops being useful. It does not prove that the database query, model generation, or tool invocation has actually stopped. Today we will design the other half of that contract: how a cancelled operation travels through a gateway, what it can safely interrupt, and how to account for work that refuses to disappear.

Imagine a developer asks an assistant to investigate a failing build. The gateway starts a model request, launches a repository search, and schedules a second provider as a possible fallback. Four seconds later, the developer clicks stop. The browser closes its stream. The gateway handler returns. Everything looks quiet. Yet the provider keeps generating tokens, the search worker keeps scanning, and the fallback timer still fires. The developer sees zero additional output, while the system pays for three pieces of invisible work. That is the central distinction: cancelling delivery is not the same as cancelling execution. A reliable gateway must track both.

Start with an operation identity and an explicit lifetime. Give the user request one operation identifier, and give each model attempt or tool call its own child identifier. Store the relationship between parent and children. In a simple service, an in-memory cancellation scope may be sufficient. Across queues and worker processes, you also need durable operation state. Useful states include running, cancellation requested, and terminal. Terminal outcomes can include completed, failed, and cancelled. Avoid treating cancellation requested as proof of cancelled. It is an instruction in flight, not an execution receipt. Record who requested it, why, and when, without putting private prompts into your logs.

Several events can trigger that instruction. A user presses stop. The end-to-end deadline expires. A service begins graceful shutdown. An administrator revokes an operation because its authorization is no longer valid. Each event may have a different reason code, but it should enter the same cancellation pathway. A client disconnect needs more thought. For a short synchronous request, disconnect can reasonably cancel the work. For an explicitly asynchronous job, disconnect usually means only that the observer went away. Document that distinction in the API. Otherwise mobile network interruptions become accidental job deletion, while synchronous requests become accidental background jobs.

Inside one process, use structured task ownership. The handler owns a cancellation scope, and every child task must belong to it. When cancellation arrives, signal the scope, stop creating new children, and await child termination for a bounded cleanup interval. In Python, that can mean carefully managed task groups and cancellation-aware network clients. In JavaScript, that can mean propagating an abort signal into fetch calls and downstream libraries. Neither pattern is magic. A library may ignore the signal. A blocking computation may not yield. A broad exception handler may accidentally swallow cancellation. Test the actual adapters you deploy, not just the language primitive you selected.

At the provider boundary, distinguish three capabilities. Some providers expose an explicit cancellation operation for an asynchronous job. Some offer a streaming connection whose closure may interrupt generation. Others provide no reliable way to stop work already accepted. Even when a cancellation endpoint returns success, check what success means in that provider's contract. It may acknowledge the request rather than confirm termination. Do not promise that closing a socket stops billing. Track cancellation requested, provider acknowledgement, and confirmed terminal state separately. If confirmation is impossible, preserve an unknown outcome and reconcile later through supported status or usage interfaces.

Now consider queues. Removing a message from a queue is not enough, because a worker may already have leased it. Mark the operation as cancellation requested in an authoritative store, then make workers check that state before beginning expensive work. Recheck immediately before an irreversible side effect. Use a version or fencing token when competing workers can act on the same job. A stale worker should not be allowed to commit a result after a newer operation state has invalidated its authority. There is still a race between checking and acting, so combine the check with the state transition where your storage system allows it. For external effects, rely on idempotency and explicit recovery rather than pretending the race cannot happen.

This matters most for tools. Cancelling a model response and cancelling a payment are different operations. Before a tool crosses its commit point, cancellation may prevent it. After the effect commits, you cannot describe the operation as though nothing happened. Return or persist the known effect, suppress unnecessary subsequent steps, and decide whether a separate compensating action is appropriate. A refund is not an erased payment. A reverted deployment is not a deployment that never ran. Compensation needs its own authorization, audit trail, and failure handling. Never automatically reverse a real-world action merely because a browser tab disappeared.

Here is a concrete race. A deployment tool receives authorization, submits a release, and then the user cancels before the response arrives. The gateway knows the network call ended ambiguously. It should not resubmit with a fresh identifier, and it should not assert that the release was cancelled. Look up the release using the original idempotency key or operation reference. If it completed, report that outcome when the user reconnects. If it is still pending and supports cancellation, request cancellation and keep watching its state. If the state cannot be determined, expose that uncertainty and route it for reconciliation. Unknown is an operational state worth designing for.

Streaming creates another subtle boundary. Once you have delivered tokens, you cannot take them back. Stop forwarding new data after cancellation, close or abort the upstream stream where supported, and prevent buffered output from leaking through a separate writer task. Keep the result status honest: partial output followed by cancellation is not a completed answer. If the transport supports a final event, include a machine-readable reason and operation identifier, but do not rely on that event arriving after the client has disconnected. Your durable operation record should remain the source of truth for clients that reconnect and ask what happened.

Cancellation must also shut down the recovery machinery. A scheduled retry, a speculative second provider, or a delayed fallback can resurrect an operation after its owner has gone away. Before every new attempt, check both the remaining deadline and the cancellation state. Share those checks across routing and retry layers. Do not let each adapter invent its own meaning of active. When racing two providers, cancel the losing attempt after choosing a valid winner, while recording any residual work that cannot be stopped. Hedging is a latency technique, not permission to leave an unbounded trail of abandoned generations.

Measure the gap between intent and reality. Useful metrics include time from cancellation request to local task termination, time to provider terminal confirmation, active children remaining after a grace period, and usage attributed to cancelled operations. Keep confirmed post-cancellation usage separate from estimates. A delayed invoice does not tell you exactly when every token was generated. Segment by provider, adapter version, tool type, and cancellation reason, using bounded labels rather than raw operation identifiers. Set an alert on persistent orphan work, not on every normal cancellation. Users pressing stop is expected behavior; children running forever is not.

Build a test matrix around timing. Cancel before queue admission, while waiting in the queue, during connection setup, after the first token, and just before a tool commits. Cancel twice to prove that the pathway is idempotent. Deliver a late provider response and verify it cannot overwrite the terminal state incorrectly. Simulate a worker that ignores cancellation, then confirm your grace-period alert and reconciliation process activate. Disconnect an asynchronous client and prove its accepted job continues according to contract. Disconnect a synchronous client and prove retries cannot restart it. Finally, test shutdown under load so process termination does not turn cleanup into an unlimited wait.

Roll this out in stages. First, trace operation ownership and detect orphan work without changing behavior. Next, propagate local cancellation through safe read-only calls. Then add provider-specific cancellation and durable worker checks. Introduce side-effect handling only when commit points, idempotency keys, and reconciliation are explicit. Your acceptance criteria should be concrete: no new attempts after cancellation, bounded local cleanup, truthful terminal status, and observable residual provider work. Some upstream systems will remain imperfect. A good gateway makes that limitation visible rather than hiding it behind a successful abort call.

The takeaway is simple. Deadlines say when work is no longer useful. Cancellation communicates that decision. Confirmation tells you whether execution actually stopped. Keep those three concepts separate, and your system becomes easier to operate, easier to bill accurately, and safer around tools that change the world.
