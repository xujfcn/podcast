Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. Today we’re continuing our series on trustworthy AI API gateways with the problem that follows adaptive routing under uncertainty: multi-provider failover and graceful degradation. When the preferred provider is unavailable, how can a gateway recover without duplicating side effects, breaking a response contract, or quietly lowering quality? And when no fully equivalent route remains, how should it degrade in a way that users can understand and systems can safely handle?

Failover is often described as a simple sequence: try provider A, then provider B, then provider C. That description is attractive because it fits on a whiteboard. It is also incomplete. A failed request is not always safe to retry. A provider may have accepted the request even though the gateway saw a timeout. A streamed answer may already have reached the client. A tool call may have charged a card, created a ticket, or sent a message before the connection disappeared. In those cases, switching providers is not just a network recovery action. It is a decision about operation history, uncertainty, and user-visible meaning.

The central principle is this: failover must preserve the request’s contract, and degradation must be explicit. Availability is valuable, but an answer that arrives by violating authorization, duplicating a side effect, or pretending an incomplete result is complete is not a successful recovery. The gateway needs to know what was promised, what happened, what remains unknown, and what alternatives are still safe.

Start with a failure-aware operation envelope. At ingress, record the request identifier, tenant, capability class, data classification, residency requirements, model and contract versions, idempotency key, tool permissions, streaming mode, maximum attempts, and degradation policy. The envelope should also state whether the operation is read-only, repeatable, compensatable, or non-repeatable. These properties are more useful for failover than a generic HTTP method. A POST that asks for a draft may be safely repeatable, while a GET that triggers a billing action through an internal tool is not.

The gateway should classify an operation before it chooses a retry or fallback. A read-only completion with no external tools is usually replayable. A generation that uses deterministic seeds may be reproducible enough for a controlled retry, although token sampling and provider differences can still change the output. A tool-using request is conditionally replayable only if every tool invocation has an idempotency contract or can be reconciled. A request that asks the model to perform an irreversible action may require confirmation or a durable workflow rather than transparent failover.

This classification should be visible in policy, not inferred from the prompt. The prompt may say “send this email,” but the gateway must rely on an authorized tool declaration, an operation class, and a side-effect policy. Model text cannot grant itself permission to retry. A model-produced tool call is an untrusted proposal until the gateway’s authorization and execution layers accept it.

Next, distinguish failure detection from failure certainty. A connection refusal gives reasonably strong evidence that an attempt did not reach a provider. A timeout after headers were sent gives weaker evidence. A timeout after a tool request was accepted gives almost no evidence about whether the side effect occurred. The gateway should represent this as an attempt state, such as not-started, sent, acknowledged, streaming, completed, failed-before-execution, failed-after-unknown, or completed-with-uncertain-usage. “Error” is too coarse to drive safe recovery.

This is where idempotency keys become essential. Every operation that could be retried should carry a stable gateway-generated idempotency key, scoped to the tenant, operation, and intended effect. The key must survive provider failover, but it cannot magically make a provider idempotent. The adapter needs to know whether the provider honors the key, how long it retains it, and what response it returns for a duplicate. For tool calls, the key should flow into the tool executor or an idempotency ledger, not stop at the model API boundary.

An idempotency ledger can provide a durable answer to a crucial question: has this intended effect already been accepted? The ledger records the operation key, tool name, normalized arguments or a secure argument digest, authorization context, execution state, result reference, and timestamps. Before executing a side effect, the executor atomically claims the key. A repeat request sees the existing state rather than creating a second effect. If the first execution is still uncertain, the safe response may be “pending reconciliation,” not another attempt.

Do not treat a provider’s request identifier as a universal idempotency key. Provider identifiers often describe an attempt, not the user’s intended operation. On failover, the second provider may receive a new request ID while the gateway operation remains the same. Maintain both levels: one operation ID for the client-visible intent and one attempt ID for each provider interaction. Decision records should link them so operators can reconstruct the chain without guessing.

A failover plan should be constructed before the first attempt. It contains the primary route, eligible alternatives, capability equivalence, data movement rules, maximum fallback depth, per-attempt budget, total operation budget, and termination conditions. The plan should say whether a fallback can change model family, region, response mode, or quality class. It should also identify which changes require client notification or a new authorization check.

Equivalence is not binary. Two providers may both support JSON schema while differing in strictness. Two models may both support tool calling while emitting different argument conventions. Two streaming endpoints may use different event boundaries or omit usage until the end. Build a contract compatibility matrix. For each candidate, record guarantees for content type, schema validity, tool semantics, ordering, streaming, token usage, citations, safety behavior, and maximum context. A fallback is valid only for the dimensions the request requires.

If a requested guarantee is unavailable on every alternative, the gateway has to choose among honest options. It can reject before spending money. It can ask the client to relax the requirement. It can switch to a declared lower capability mode. Or it can return a partial result with an explicit status. The right answer depends on the contract and consequence. For an internal brainstorming request, buffered delivery instead of streaming may be acceptable. For a structured extraction pipeline, returning prose instead of valid JSON may poison downstream records and should usually be rejected.

Graceful degradation is therefore a product of capability and consequence. Define degradation tiers in advance. Tier zero is equivalent recovery: the same semantic guarantees on another eligible route. Tier one changes delivery characteristics, such as buffered output instead of streaming, while preserving the answer contract. Tier two reduces optional features, such as disabling citations or a nonessential tool, with client-visible metadata. Tier three returns a safe partial response or asks for human review. Tier four rejects with a useful explanation. Never allow the system to drift between tiers merely because a provider happens to be responding.

The client-facing protocol should expose the relevant transition. A gateway does not need to reveal every internal score or provider secret, but it should be able to say that the request was recovered on an alternate route, that streaming was unavailable and buffering was used, or that a result is partial and requires review. Use stable machine-readable fields such as operation status, recovery state, degradation tier, completion confidence, and retry-after guidance. Human-readable text can accompany them, but downstream systems need structured semantics.

Streaming makes failover especially difficult. Before the first byte reaches the client, the gateway may still have a clean opportunity to switch. After content has been emitted, a silent provider handoff can create a response that repeats, contradicts, or changes voice halfway through. If the stream ends unexpectedly, classify what the client received. An incomplete answer should not be labeled complete simply because a fallback generated a continuation.

One approach is buffered failover: hold a small prefix or the entire response until a commit point, then release it. This improves recovery but increases latency and memory use. Another is explicit stream segmentation. The gateway sends an interruption event, closes the first segment, and begins a clearly marked recovery segment if the contract permits continuation. A third is to stop and return a resumable operation token. Choose per capability class. There is no universal “transparent streaming retry.”

Define a commit point for each response mode. Before commit, the gateway may replace the route if no externally visible effect has occurred. After commit, it must honor what was already delivered and use only a continuation policy that preserves the client’s semantics. For structured output, commit may occur only after schema validation. For a human-facing chat stream, commit may occur when the first content token is sent, unless the protocol explicitly supports revisions. For a tool call, commit is tied to the side effect ledger, not to the model’s textual output.

Tool execution deserves its own state machine. A model can propose a tool call, the gateway can authorize it, the executor can send it, and the tool can complete while the model connection fails. On reconnect, the model may propose the same call again because it never saw the result. The gateway must consult the ledger before executing. If the result exists, return it to the new model context. If execution is pending, wait or reconcile. If execution failed before claim, a retry may be safe. If the outcome is unknown, require a tool-specific reconciliation method or escalate.

Compensation is not the same as rollback. If an email was sent, deleting a record does not unsend it. If a payment was captured, a refund is a new business action with its own authorization. Model the available compensation explicitly, with limits and approval requirements. A failover system should never invent compensation because a generic retry budget remains. It should either reconcile the original effect or report that the operation’s outcome is unknown.

Provider adapters should normalize failure classes without erasing evidence. Transport failures, authentication failures, quota exhaustion, invalid requests, safety refusals, context overflow, malformed responses, and usage disagreements need different recovery rules. A timeout may permit a new route for a read-only operation. An invalid request should normally stop and surface a gateway or client bug. A safety refusal is not proof of provider outage and should not be sprayed to every provider. A malformed tool response may permit fallback only if the tool has not executed and the alternate route meets the same contract.

The adapter should preserve raw evidence in a protected trace: timestamps, connection phase, headers that are safe to retain, provider request ID, bytes received, terminal events, and usage metadata. General logs should contain redacted summaries and references, not prompts, credentials, or sensitive tool arguments. This evidence is what lets an operator decide whether a retry was safe. Without it, the gateway is forced to guess, and guessing becomes a hidden source of duplicate actions.

Budgeting must cover the whole operation, not just each attempt. A primary timeout followed by two fallbacks can multiply input charges and evaluator costs. Reserve a total budget when the route plan is created. Reserve an attempt allowance before dispatch, reconcile actual usage after completion, and stop when the remaining budget cannot support an honest fallback. If the first provider may have charged despite a timeout, account for that uncertainty conservatively. A system that fails over successfully but exceeds a tenant’s spend policy has not respected the request contract.

Time budgets require the same treatment. Set a total deadline, an attempt deadline, and a recovery deadline. Do not give every fallback the full original timeout. Once time is consumed, the gateway may need to return a cached answer, a partial result, or a pending status rather than launch a final doomed attempt. For interactive clients, a quick honest failure may be better than a complete answer that arrives after the user has abandoned the session. For asynchronous jobs, the gateway can persist the operation and notify the client when reconciliation finishes.

Cascading failure is the enemy of naive failover. If many gateway replicas detect the same provider problem and immediately send all traffic to the same alternate, the alternate can fail next. Use admission control, per-provider concurrency limits, queue budgets, and load-shed rules. A fallback route should be reserved capacity, not an imaginary infinite resource. When capacity is exhausted, return a controlled overload status or lower a declared optional feature rather than create an unbounded retry storm.

Use a circuit breaker, but give it nuance. An open breaker can protect a provider from a known transport outage. It should be scoped by capability, region, and response mode where possible. A provider may be broken for long-context streaming but healthy for short buffered text. Half-open recovery should use small probes and gradual traffic, with hysteresis to prevent oscillation. Circuit state is an input to route planning, not an excuse to ignore policy or operation state.

Failover should also account for correlated dependencies. Two providers may depend on the same cloud region, identity service, content filter, DNS path, or upstream model family. Alternating between them does not provide real resilience if the failure domain is shared. Maintain a dependency map and diversity goals. For high-consequence traffic, a fallback plan may require a genuinely separate region or provider class. The plan should state what failure modes it is designed to survive and which ones remain shared.

Data residency and privacy rules follow the request across every attempt. An alternate provider is not eligible merely because it is online. Re-check region, encryption, retention, training-use, tenant isolation, and data classification constraints when a plan is activated. Do not copy a sensitive prompt into a diagnostic request to test a fallback. Redaction, tokenization, or a reduced-context mode may enable recovery, but only if the policy explicitly permits that transformation and the client contract can tolerate it.

Context transfer is another hidden source of semantic drift. A conversation state may include system instructions, prior tool results, hidden metadata, attachments, and provider-specific reasoning artifacts. On failover, reconstruct only from a canonical gateway representation. Do not assume that a provider’s internal conversation ID can be imported elsewhere. Validate context size, ordering, roles, attachment permissions, and tool result integrity. If some state cannot be transferred, the gateway must select a degradation tier or stop rather than silently omit it.

Quality continuity matters even when the protocol succeeds. A fallback model may answer more briefly, refuse a borderline request, use different citation conventions, or interpret a tool schema differently. Add a quality envelope to the route plan: minimum factuality or evaluation threshold where measurable, required schema fields, citation policy, language, tone, and domain restrictions. If the alternate cannot meet the envelope, return a declared lower-quality mode or ask for review. HTTP 200 is not semantic success.

Observability must follow the operation across providers. Emit one trace for the client intent, child spans for route decisions and provider attempts, and linked spans for tool executions. Metrics should distinguish primary success, equivalent failover, degraded success, partial completion, safe rejection, unknown side-effect outcome, and infrastructure failure. Track time to recovery, fallback depth, duplicate-prevention hits, reconciliation latency, budget consumed, and contract violations. A single success-rate number hides the most important differences.

Decision records should answer five questions: what did the client ask for, what did the gateway promise, what attempts occurred, what is known about each outcome, and why was the final status selected? Include policy and contract versions, idempotency state, degradation tier, capability compatibility, deadlines, and termination reason. Avoid raw sensitive content. A compact record with durable references is better than a huge log that no one can safely inspect.

Test failover with fault injection that reflects real ambiguity. Drop connections before dispatch, after dispatch, after headers, during a stream, after a tool claim, and after a tool completes. Return duplicate terminal events, corrupt JSON, stale usage, delayed errors, rate-limit storms, and provider responses that contradict their status codes. Make the alternate route slower, cheaper, regionally ineligible, or semantically weaker. Verify not only that traffic moves, but that it moves only when the operation state and policy allow it.

Replay is valuable for recovery design. Take recorded envelopes with redacted or synthetic content and run them through the failover planner under different fault points. Compare the planned status, fallback choice, budget, and client-visible events. For side-effecting workflows, replay the state machine against a simulator that models accepted, pending, completed, and unknown outcomes. The goal is not to prove that every failure can be hidden. The goal is to prove that every failure ends in a defined, honest state.

Canary new failover behavior in observation mode first. Let the gateway calculate a recovery plan while the existing behavior remains authoritative. Compare whether the proposed fallback preserves the required capability, how much budget it would consume, and whether it would have changed a client-visible status. Then enable it for read-only, low-consequence traffic with strict limits. Expand to streaming and tool paths only after their state transitions and duplicate-prevention controls have been exercised in realistic tests.

A practical first implementation can be intentionally small. Support one read-only text capability across three providers. Define a canonical operation envelope and attempt state machine. Add stable idempotency keys even though the first capability has no tools. Use a precomputed compatibility matrix, a total time and cost budget, and one equivalent fallback plus one explicit rejection path. Buffer responses until validation, emit recovery metadata, and test connection failures at each phase. Only after those basics work should the system add streaming continuation, tool reconciliation, or automated quality-based degradation.

Measure graceful recovery by the quality of its decisions, not by the number of errors concealed. Track equivalent recovery rate, safe rejection rate, partial-result rate, unknown-outcome rate, duplicate side effects prevented, contract-compliant success, cost per usable outcome, time to client-visible resolution, and percentage of operations with complete evidence. Also track how often clients understand the final status and how often operators can reconcile an ambiguous attempt from one record. These are reliability and trust metrics together.

The deeper lesson is that a multi-provider gateway is not a proxy with extra destinations. It is an operation coordinator. It carries an intent through changing providers while preserving authorization, budget, data boundaries, protocol meaning, and side-effect history. Adaptive routing chooses an eligible path under uncertainty. Failover continues that decision when the path breaks. Graceful degradation defines what the gateway is allowed to change when equivalence is no longer available.

The safest gateway does not promise that users will never see failure. It promises that failure will be classified, bounded, and represented honestly. Before the first byte, it can often recover transparently. After a commit point, it must preserve what was delivered. Around side effects, it must reconcile instead of guessing. When no safe equivalent remains, it should reduce capability visibly, create a pending workflow, or reject with a reason. That is not weakness. It is dependable engineering.
