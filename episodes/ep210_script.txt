EP210: AI API Gateway Retry Contracts - Make Backoff Safe for Developers

Welcome back to AI Dev Tools, the Crazyrouter podcast. Today we are talking about retry contracts for AI APIs: the small but important set of rules that tells a developer when to try again, how long to wait, and when another attempt could make things worse. This is not another general discussion of retries. It is about making retry behavior a dependable part of an API gateway contract, especially when one logical request can cross several providers with different rate limits, timeouts, and failure semantics.

The first principle is simple: a status code alone is not a recovery plan. A five hundred response, a five hundred three response, a stream disconnect, and a client-side timeout do not carry the same retry risk. The gateway should return a stable error code, a retryability classification, and a bounded wait hint when it has enough evidence. Clients should be able to make a decision without reverse engineering provider messages or guessing from punctuation in an error string.

Start by defining retry classes at the gateway boundary. Some failures are safe to retry, such as a connection failure before the provider accepted a request, provided the operation is read-only or protected by idempotency. Some are conditionally retryable, such as a provider timeout where acceptance is unknown. Others should not be retried automatically: invalid credentials, policy denial, invalid request parameters, an exhausted deadline, or a tool call whose side effect may already have happened. Keep the classes stable even when the internal provider adapters change.

Retry-After deserves special attention. For a temporary overload or rate limit, the gateway can return a delay in seconds or an absolute HTTP date. The value should represent the earliest sensible retry time, not an invitation to create a synchronized stampede. Add bounded jitter instructions or document that clients must apply jitter locally. Always cap the hint with the caller's remaining deadline. A response saying retry in sixty seconds is not useful to a request with a ten-second budget. The contract should make that mismatch explicit.

Provider hints and gateway policy are different signals. A provider may say to wait five seconds, while the gateway knows that the selected route is unhealthy and the next eligible provider is available now. The gateway must decide whether to preserve, shorten, or replace the hint, and expose a safe reason category rather than leaking credentials or internal topology. Record the original provider signal internally for diagnosis, but give the client one coherent instruction. Two contradictory backoff headers are an operational bug.

Retries also need a budget, and that budget is more than a maximum attempt count. Track remaining wall-clock time, estimated token cost, concurrency reservation, and the number of attempts already spent. A retry that fits under an attempt limit can still violate the user's deadline or double the expected spend. For streaming, reserve a separate policy: after tokens have been delivered, a blind replay may duplicate visible output. In many cases the honest response is an incomplete stream with a resume or reconciliation path, not an automatic restart.

Idempotency is the boundary between inconvenience and damage. A client retrying a pure completion may pay twice or receive different text. A client retrying a tool call may create two tickets, charge a card twice, or send duplicate messages. The gateway should bind an idempotency key to the logical request and a request fingerprint. The same key with the same relevant content can return the recorded result or an in-progress state. The same key with different content must be a conflict. Do not make clients discover this rule through an accidental duplicate side effect.

Backoff must account for caller populations. If every SDK retries after the same fixed delay, a provider recovery becomes a second outage. Use exponential backoff with a clear maximum, full jitter, and a small initial delay only for failures that are likely to recover quickly. For rate limits, honor a server-provided window when it is trustworthy. For overload, prefer admission control and a useful retry hint over allowing thousands of requests to sleep in memory. A gateway should not turn its clients into a distributed queue it cannot observe.

The SDK is where this contract becomes real. Provide a default retry policy that is conservative, deadline-aware, and disabled for unsafe operations unless the caller opts in with idempotency. Expose hooks for logging the decision, but do not require every application team to implement its own classifier. Make cancellation stop the backoff timer and any outstanding provider work. When the policy gives up, return the original stable error code together with attempt count and a safe retry recommendation. Hiding all of this behind a generic exception encourages accidental loops.

Test the contract as behavior, not as a list of headers. Create fixtures for a connection failure before acceptance, a timeout after acceptance is unknown, a rate limit with a retry window, an overload response with no capacity, a deadline that expires during backoff, and a stream that disconnects after partial output. Assert the client-visible code, delay bounds, attempt count, idempotency behavior, and cancellation. Add a test where two clients receive the same provider hint and verify that their actual retry times are still spread by jitter.

Observability should answer whether retries are helping. Measure retry rate by error class, success after retry, time spent waiting, added tokens and cost, deadline exhaustion, and duplicate suppression. Separate gateway-generated retries from SDK retries so an application does not see one request while the infrastructure performs four attempts. Alert on retry amplification: a modest increase in provider errors should not produce a much larger increase in total traffic. That ratio is often the earliest sign that a recovery policy is unstable.

There is also a product decision: how much retry behavior should be visible to users? For interactive requests, a short transparent retry may improve experience. For batch jobs, a durable queue and explicit state may be better. For agents, the gateway should return enough metadata for the orchestrator to distinguish a temporary provider problem from a failed business action. A single universal retry policy is attractive in documentation and wrong in production. Workload class belongs in the contract.

Keep the public surface small. Define stable error codes, a retryable field, a bounded Retry-After value when appropriate, an attempt or route summary that does not expose secrets, and an idempotency rule. Version the policy when semantics change. Document that hints are upper bounds or earliest times precisely, because ambiguous words like “backoff” create incompatible implementations. Then publish examples for synchronous completions, streaming responses, tool calls, and asynchronous jobs.

The practical checklist is direct. Classify failures by safety and ownership. Make Retry-After coherent with deadlines and gateway policy. Bound attempts by time, cost, and concurrency, not only by count. Add jitter and prevent retry storms. Make idempotency mandatory for risky side effects. Put conservative defaults in the SDK. Test accepted, unknown, partial, cancelled, and expired outcomes. Measure whether retries recover useful work or merely multiply traffic.

The larger lesson is that retry behavior is part of the API, even when nobody writes it down. Developers will retry because networks fail and providers vary. A gateway that gives them precise, bounded guidance can turn that instinct into resilient behavior. A gateway that returns vague errors leaves every client to invent a different policy, and the ecosystem eventually pays for those differences in latency, cost, and duplicate work.
