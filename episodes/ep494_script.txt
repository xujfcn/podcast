Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we examined policy dependency freshness. A policy decision is only as trustworthy as the capability catalog, provider facts, tenant configuration, keys, clocks, and other inputs behind it. When those inputs expire or diverge, two healthy workers can reach different conclusions from the same rule. Today we focus on recovery. What should a gateway do after a dependency becomes stale, a region splits, a provider fact is corrected, or a clock and key set fall out of alignment? The answer is not to refresh everything and replay every old decision. Our topic is policy dependency freshness recovery: restore trusted inputs, identify decisions made under stale assumptions, and recover without enlarging authority or repeating unsafe effects.

Start with a realistic incident. A provider capability catalog says that a model supports structured tool calls in Tokyo. The fact expires while the catalog service is unreachable. One region continues using the last-known value inside its continuity window. Another region blocks the capability because it cannot refresh. A third region receives a corrected provider report saying that tool calling was disabled for the model version. The gateway now has completed requests, queued work, cached authorization decisions, and in-flight plans that relied on different dependency states. Recovery must restore a common basis for decisions, but it must not assume that old authority becomes valid again merely because the dependency is healthy now.

Separate recovery of inputs from recovery of work. Input recovery means obtaining, validating, and activating current dependency facts. Work recovery means deciding what to do with requests, sessions, queues, tools, charges, and effects that were paused or executed while the inputs were stale. These are related but not identical. A fresh capability catalog can tell the gateway what the provider supports now. It cannot prove that a request made yesterday was safe, that a tool call was authorized at the time, or that an old plan should be resumed. Every recovered work item needs its own decision.

Define dependency states precisely. A dependency can be fresh, aging, expired, unavailable, disputed, revoked, quarantined, restored-pending-verification, or trusted. The state should include source, version, digest, valid interval, observed time, expiry time, region, tenant or scope, verification method, and owner. “The service returned 200” is not enough. A response can be syntactically valid but signed by an old authority, missing a required field, outside its valid interval, or inconsistent with another source. Dependency recovery begins by making the state honest.

Use a dependency health record rather than a boolean. Record freshness age, source sequence, schema version, signature status, consistency with peers, completeness, revocation status, and downstream consumers. A provider fact may be current but incomplete. A tenant configuration may be fresh but not yet distributed to every worker. A key set may be available but missing the certificate needed for a particular region. These distinctions determine whether a dependency can support a low-risk status lookup, a new model request, a tool action, a charge, or a deletion decision.

Classify dependencies by safety impact. A stale recommendation label may affect route preference but not authorization. A stale residency map can send sensitive data to the wrong region. A stale credential scope can authorize an action that is no longer permitted. A stale pricing table can create a billing discrepancy without changing execution. A stale tool schema can cause an external side effect. Assign recovery requirements to the dependency’s consequences: maximum age, acceptable uncertainty, quorum, source authority, verification steps, and allowed degraded behavior. One global freshness threshold is almost always either too strict for harmless work or too weak for dangerous work.

Freeze only what must be frozen. When a dependency expires, stop new operations that rely on it if the policy requires fresh evidence. Do not automatically stop unrelated traffic that uses independent inputs. Mark affected queues, routes, tools, tenants, regions, and policy classes. A provider capability outage should not block a request that uses a verified text-only route if the capability is irrelevant. Conversely, a route that appears healthy should not continue accepting sensitive tool work if its residency or tool-contract facts are stale. Dependency-aware isolation is safer than platform-wide panic.

Preserve the last trusted snapshot with a bounded continuity window. A previously verified dependency can support limited work while recovery runs, but only under explicit conditions. Bind the snapshot to policy epoch, region, tenant scope, provider account, data class, and operation type. Do not extend the window merely because requests keep arriving. Do not refresh the expiry on every read. If the snapshot is usable for status lookup but not for new authorization, encode that difference. Continuity is a controlled risk budget, not a silent promise that stale data is current.

Recovery should begin with source authentication. Verify the source identity, signing chain, key status, schema, sequence, valid interval, and scope before accepting a new fact. Reject responses that are validly formatted but outside the expected authority. Protect against replayed dependency documents by requiring monotonic sequence numbers, freshness proofs, or server-side issuance records. A stale signed artifact is still stale. Authenticity proves who issued a fact; freshness proves whether it is safe to use now.

Then validate semantic completeness. Check required capabilities, region fields, retention terms, cancellation behavior, usage semantics, model version, tool schema, and any obligations the policy depends on. A partial provider catalog can be worse than no catalog if missing values are interpreted as permissive defaults. Define fail-safe defaults for absent fields. If a capability is unknown, treat it as unavailable for high-risk operations. If a residency value is missing, do not select the route for data that requires regional proof. Recovery must close the gap between “we received something” and “we can safely decide.”

Cross-check important inputs independently. Compare provider facts with gateway probes, contract snapshots, signed account metadata, or a second approved source. A capability report that says tools are enabled should be tested with a non-side-effecting request. A region claim should be checked against provider attestation where available. A pricing update should be compared with a known fixture before billing is reopened. Independent evidence should be proportional to impact. A high-risk dependency may require two sources or a live probe; a low-risk preference may require only authenticated version validation.

Recovery must be region-aware. A global dependency may be available in the control plane while one execution region cannot verify it. Do not mark the dependency globally trusted until the scope required by policy has converged. Publish a recovery manifest listing the dependency digest, target regions, worker classes, evaluator versions, validity interval, and verification obligations. Workers should acknowledge not only receipt but activation and successful use in a decision probe. Regions that remain stale should be isolated from operations requiring the recovered input.

Use dependency epochs and watermarks. Assign a new epoch when a dependency is refreshed, corrected, revoked, or restored after an outage. Carry the epoch into policy decisions and work envelopes. A watermark can state the newest source sequence incorporated into the regional snapshot. If a worker evaluates under an old epoch, the decision receipt should say so. If a queued operation requires at least epoch 18, a worker with epoch 17 must not silently process it. Epochs make recovery progress measurable and prevent hidden mixing of old and new inputs.

Do not replay stale authorization. Suppose a request was admitted when the provider capability was believed to be valid, then paused after the capability expired. Once the catalog is fresh again, the gateway should re-evaluate the request under current context, not automatically reuse the old allow. Compare the original decision with the new dependency state. If the required guarantees remain equivalent, issue a continuation decision with a new receipt. If the operation’s data, actor, provider, region, or side-effect scope changed, require fresh authorization. Recovery restores the ability to decide; it does not restore a previous decision by default.

Distinguish read-only recovery from side-effect recovery. A stale dependency may have affected a model response that can be safely revalidated, but it may also have affected a tool plan that could send money, change a record, or contact a third party. Recompute read-only projections freely when evidence permits. Quarantine external actions until the tool contract, identity, arguments, authority, and idempotency state are checked again. A new provider capability fact cannot justify executing an old tool plan without validating the plan against current policy and current target state.

Queued work needs a recovery classification. For each item, record admission epoch, dependency versions, operation state, provider attempt state, side-effect state, customer deadline, and data classification. Classify it as safe to continue, requires reauthorization, requires transformation, retryable, permanently invalid, side-effect-unknown, or manual review. Do not classify solely by queue age. A recently queued request can be unsafe if its dependency was revoked; an older read-only request may be safe if its guarantees remain stable. Recovery should produce explicit outcomes, not merely drain the queue.

Long-running sessions require checkpoint validation. A workflow may have a model plan, a tool selection, a provider session, and a pending callback. At resume time, compare every checkpoint’s dependency watermark and contract digest with the current trusted snapshot. Revalidate the next transition rather than rerunning the entire conversation. If an old plan contains a tool argument built under an obsolete schema, translate and validate it or discard it. If a session token belongs to a retired provider account, do not refresh it into a new account without an explicit migration decision. Resume verified state, not stale authority.

Provider recovery facts can be late or contradictory. A provider may report that a feature was disabled during the period when the gateway believed it was available. Preserve the original fact, the corrected fact, valid intervals, receipt times, and affected operations. Recompute current eligibility and identify work that may require remediation. Do not retroactively pretend that every earlier decision was made with the corrected fact. The recovery process should distinguish decisions that were reasonable under then-current evidence from decisions that must be compensated because a contractual guarantee was not actually met.

If a dependency is revoked, recovery may require negative authority. A revoked key, region, provider account, or capability should produce a deny or quarantine artifact that propagates faster than ordinary positive updates. Workers should block affected operations even if the last positive snapshot has not expired. Cache invalidation, credential revocation, queue marking, and adapter restrictions should use the revocation epoch. When the dependency later returns, the revoke record must still be checked. Restoration never cancels a revocation automatically.

Clock recovery deserves special care. Dependency freshness often depends on time. A worker with a skewed clock may accept expired facts or reject valid ones. Record clock source, offset, monotonic health, and maximum uncertainty. During recovery, use server-issued validity intervals or monotonic leases where possible. If clock uncertainty exceeds the policy threshold, isolate high-risk decisions. Do not “fix” time by changing the system clock while operations are in flight without recording the event. A time correction can alter expiry, credential validity, retention, and replay decisions at once.

Key recovery is not just key distribution. A region may receive the new trust root but still run an old certificate bundle, or it may activate a key without confirming revocation status. Verify trust-root epoch, certificate chain, effective time, revocation source, and worker activation. Keep old and new keys during an intentional overlap, but define which artifacts each key may authenticate. Do not accept a dependency document signed by a key that is valid cryptographically but retired for policy purposes. Trust recovery must be scoped to the exact authority needed.

Tenant configuration recovery can expose cross-tenant mistakes. A stale shared cache may serve one tenant’s region restriction or provider allowance to another tenant. Bind configuration snapshots to tenant, version, scope, and policy epoch. Invalidate shared caches on tenant-specific changes and test that an unavailable tenant configuration fails closed only for that tenant’s affected work. During recovery, compare control-plane configuration with worker snapshots and audit any decision made under a mismatched tenant epoch. Tenant isolation is part of dependency freshness.

Provider catalog recovery should account for account and model identity. A capability fact for one provider account may not apply to another account, region, or model alias. Include native model ID, account, region, contract digest, and service version in the dependency key. If an alias resolves differently after recovery, invalidate route decisions that used the old resolution. A friendly model name is not a stable capability identity. Recovery should prevent a new catalog fact from being attached to the wrong route merely because the display name matches.

Pricing and usage dependencies need financial containment. If pricing data is stale, the gateway can continue execution while placing charges in a pending state, or it can stop routes where the contract requires known pricing. When fresh pricing arrives, compare the effective time with operation admission and provider attempt time. Reconcile estimates and final usage without changing historical prices silently. Do not release all pending charges immediately after a pricing refresh; validate the mapping, currency, units, discounts, and tenant agreement first. Financial recovery is a controlled publication, not a database refresh.

Recovery should be staged. First isolate affected work. Then authenticate sources and load candidate facts. Validate schemas and semantics. Cross-check high-risk inputs. Activate a regional snapshot. Run decision probes. Re-evaluate queued and in-flight work. Open only the lowest-risk class. Observe outcomes. Expand gradually. Keep unresolved operations quarantined. Each stage should have entry criteria, exit evidence, owner, timeout, and rollback or containment action. A single “dependency healthy” signal cannot substitute for staged recovery.

Use recovery leases. A recovered dependency can be trusted for a bounded period while longer-term reconciliation continues. The lease should identify scope, epoch, evidence, issuer, start time, expiry, and permitted operations. A lease for text routing should not authorize tool execution or sensitive document processing. If the source becomes disputed before lease expiry, revoke the lease. Leases make temporary trust explicit and prevent a successful refresh from becoming an unbounded authority grant.

Observe the recovery itself. Track stale dependency age, affected operation count, candidate facts rejected, validation failures, peer disagreement, region convergence, decision re-evaluation count, work resumed, work quarantined, side effects prevented, billing adjustments, and unresolved evidence gaps. Track how many old decisions were reused versus replaced with fresh decisions. A recovery that resumes traffic quickly but reuses stale authority is not successful. Measure whether the system restored trustworthy decision inputs, not merely whether queues became shorter.

Test failure during recovery. Deliver a fresh dependency to only half the regions. Send an older update after the new epoch. Revoke a key while a recovery lease is active. Correct a provider capability after queues reopen. Resume a workflow with an obsolete tool schema. Let a worker’s clock jump forward. Restore a backup containing a stale snapshot. Make a shared cache return one tenant’s configuration to another. Trigger a tool action just as a dependency is disputed. Verify that the system fails safely, preserves evidence, avoids duplicate effects, and keeps old decisions distinguishable from new recovery decisions.

Incident review needs a dependency timeline. Reconstruct when the input was fresh, when it aged, when it expired, when each region observed the change, what policies were active, which operations relied on the input, and when recovery became trusted. Link decision receipts, queue classifications, provider events, credential changes, and compensating actions. The timeline should answer both “why did this worker allow the operation?” and “why did recovery later block or reauthorize it?” A dependency incident is not explained by a single freshness timestamp.

The deeper lesson is that recovery is a new trust decision. A fresh dependency does not erase stale decisions, reverse external effects, or prove that prior work was safe. The gateway must restore inputs, verify scope and freshness, publish epochs, re-evaluate affected work, and reopen capacity progressively. It must preserve revocations, quarantine uncertainty, and keep read-only recovery separate from side-effect recovery. The goal is not to make every operation continue. The goal is to resume only the work that current evidence and current authority can support.

Classify dependencies by consequence, preserve bounded continuity, authenticate and validate every refreshed fact, and use epochs, watermarks, leases, and regional acknowledgments. Never replay stale authorization merely because a service is healthy again. Re-evaluate queued and long-running work, keep revocations active, quarantine side effects, and reopen capacity in stages. A trustworthy gateway does not recover by forgetting uncertainty; it recovers by earning fresh authority one dependency, region, and operation at a time.
