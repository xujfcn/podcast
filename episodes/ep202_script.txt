EP202: AI API Gateway Failure Semantics - Make Partial Failure Predictable

Welcome back to AI Dev Tools - The Crazyrouter Podcast. An AI request rarely fails in one clean way. A provider can accept the prompt and then time out. A stream can deliver useful tokens and lose the connection before its finish marker. A retry can succeed while the first attempt is still running. A fallback can return an answer that looks valid but does not support the same tools or context. Today we are talking about failure semantics for AI API gateways: how to define what each failure means, what the gateway may do next, and what the client can safely rely on.

The goal is not to make failures invisible. That is impossible, and hiding them usually makes recovery less safe. The goal is to make partial failure explicit and bounded. Developers should be able to tell whether work was never accepted, may still be running, produced a complete result, or produced only a partial result. Operators should be able to tell which layer made the decision and whether a second attempt could duplicate work or charges.

Start with an outcome vocabulary. A request can be rejected before dispatch because of authentication, policy, quota, or capability. It can be dispatched and fail before any useful response. It can produce a complete response with a normal terminal signal. It can produce a partial response and then disconnect. It can time out while the upstream may still be processing. Or it can have an unknown outcome because the gateway lost contact after sending the request. These are different states, even when the client receives a five hundred status code.

Write the outcome model down as a contract. For every state, define whether the client may retry, whether the gateway may retry, whether an idempotency key is required, and whether billing reconciliation is pending. Include a stable error code, a retry hint, a request identity, and a trace identity. Do not make clients infer semantics from provider-specific messages. A useful gateway error is not just “upstream error.” It says, for example, “dispatch outcome unknown; retry only with the same idempotency key,” or, “stream incomplete after output; do not automatically replay.”

Deadlines are the first boundary. There should be one end-to-end deadline owned by the user-visible request, and smaller budgets for queueing, connection setup, provider time, normalization, and response delivery. A gateway timeout should leave enough time for the client to receive a meaningful error and for telemetry to record the final state. Avoid stacking independent timeouts that turn a thirty-second request into a minute of silence. Propagate the remaining deadline to each upstream attempt, and refuse a retry when the remaining budget cannot support it.

Separate cancellation from timeout. A client cancellation means the caller no longer wants the result, but the provider may still be working. A gateway timeout means the gateway could not finish within its contract. A provider timeout means an upstream attempt exceeded its own allowance. These events can lead to similar user experiences, but their operational consequences differ. Record who initiated cancellation, when it happened, whether the upstream cancellation was acknowledged, and whether the work might continue in the background.

Before retrying, ask whether the first attempt is known to be safe to abandon. Connection failure before request transmission is usually different from a disconnect after the provider has accepted the body. A response status may be definitive, while a transport reset is ambiguous. Classify failures by transmission phase: not sent, sent but not acknowledged, accepted with no output, output started, and terminal output received. This phase is more useful for retry decisions than a generic network error label.

Idempotency is the bridge across ambiguity. Give retryable operations a client-supplied idempotency key, or have the gateway create one and return it immediately. Store the key with the request fingerprint, workload contract, and final outcome. If a duplicate arrives, return the existing result or its current state instead of dispatching the same operation again. Scope keys to the tenant and endpoint, enforce an expiration policy, and reject reuse with a materially different request. For generation jobs and tool actions, idempotency should be durable enough to outlive a process restart.

Text generation and external actions need different rules. Repeating a pure completion may cost more and produce a different answer, but it normally does not change the outside world. Repeating a tool call that sends an email, charges a card, or mutates a database can create a real duplicate side effect. The gateway should know whether a route is read-only, replayable, or side-effecting. For side effects, require an idempotency contract at the tool boundary, or stop and surface an unknown outcome for human or application reconciliation.

Streaming adds a second dimension: how much output has already become visible. A stream is not complete merely because some tokens arrived. Define an event contract with a start event, ordered content or tool events, usage where available, and an explicit terminal event. If the connection ends without a terminal event, mark the result incomplete. Preserve the last delivered event identifier if the protocol supports resumption. If it does not, tell the client that a new request is a new generation, not a continuation, and do not pretend otherwise.

The gateway must also handle slow consumers. Bound buffers and propagate cancellation when the client disappears. Otherwise, a disconnected browser can keep a provider connection and its token spend alive. Make the distinction visible in telemetry: provider finished but delivery failed, provider was cancelled by backpressure, or the gateway dropped output after a buffer limit. These are different capacity and product problems, and they need different fixes.

Fallback is a semantic decision, not just a network decision. A second provider is eligible only if it supports the request's capability contract: input type, context size, structured output, tool schema, safety policy, residency, latency budget, and output protocol. If the first attempt already emitted content, silently starting a different model can confuse the client and mix two generations. For non-streaming requests, a fallback may be reasonable after a classified pre-output failure. For streaming, default to an explicit incomplete result unless the client has opted into a restart with clear labeling.

Do not let retries multiply at every layer. The client, gateway, SDK, queue, and provider adapter may each have a retry loop. Set one owner for cross-provider retry decisions, and make other layers respect the remaining attempt budget. Carry an attempt number, a retry reason, and an absolute deadline through the call chain. Apply exponential backoff with jitter only where waiting can still improve the outcome. A retry after a policy rejection, invalid request, or unsupported capability is not resilience; it is noise.

Use error classes that map to actions. A client-correctable request error should be stable and non-retryable. A temporary capacity error may be retried after a delay or routed elsewhere. An authentication or quota error needs an owner and a clear remediation path. A provider protocol error should quarantine the affected capability and preserve enough evidence for an adapter fix. An unknown dispatch outcome should trigger reconciliation, not blind replay. Keep provider details in structured metadata while exposing a smaller, stable surface to application developers.

Billing must follow the outcome model. A request that timed out at the gateway may still have consumed provider tokens. A hedge or retry may create two billable attempts even when the user receives one answer. Record estimated and provider-reported usage separately, link every attempt to one logical request, and reconcile late usage after the user-visible response. The gateway should be able to explain whether a charge belongs to the winning attempt, a failed attempt, or duplicated work caused by an ambiguous outcome. Cost observability is part of reliability because surprise charges change retry and fallback policy.

Observability should make the state transition reconstructable without storing sensitive prompts. Capture a request fingerprint, tenant and workload class, route policy version, attempt sequence, transmission phase, first-byte and first-token times, event counts, terminal reason, cancellation source, and usage reconciliation state. Use the same logical request identifier across client, gateway, provider, and asynchronous worker logs. Redact content, but retain safe hashes and schema versions so an operator can compare attempts without exposing user data.

Test failure semantics as scenarios, not isolated status codes. Simulate a timeout before transmission, a reset after transmission, a provider response after the gateway deadline, a stream that ends after a tool request, a slow client, a duplicate idempotency key, and a fallback with an incompatible context limit. Add a provider that returns a valid-looking error body with the wrong schema. Verify the final client contract, the number of upstream attempts, the idempotency record, and the billing state for each case.

Chaos tests should include delayed knowledge. Let the provider complete after the gateway has told the client that the outcome is unknown. Then verify that reconciliation updates the durable request record without sending a second side effect. Disconnect the gateway after dispatch and restart it. The right result is not merely that the process comes back; it is that the system can answer whether the original work completed and what a safe next action is.

There is a useful design review question for every new gateway feature: what happens if the connection disappears at this exact line? Ask it around queue admission, request transmission, first output, tool execution, stream finalization, usage reporting, and billing. For each boundary, name the durable state, the retry owner, the client-visible outcome, and the evidence needed to reconcile later. This turns vague resilience language into an implementable contract.

The practical lesson is simple. Reliable AI APIs do not promise that providers never fail. They promise that failure has a meaning. Model outcomes by transmission phase, enforce one end-to-end deadline, distinguish cancellation from timeout, preserve idempotency, mark streams incomplete without a terminal event, make fallbacks capability-aware, assign one retry owner, reconcile billing, and test ambiguous outcomes deliberately. When partial failure is explicit, developers can build safer clients and operators can recover without guessing.
