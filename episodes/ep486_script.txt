Welcome to the Crazyrouter Podcast, where we make AI infrastructure practical. In the last episode, we designed exception reconciliation: block new admission, revoke derived authority, quarantine queued work, follow child credentials, ask providers what happened, and keep unknown outcomes visible before declaring temporary authority closed. Today we widen the lens. A single logical AI operation may cross several gateways, routers, model providers, tool adapters, regions, and billing systems. Each system assigns its own request ID, status, timestamp, token count, cost, and interpretation of success. If we reconcile only one layer, the operation can look complete in one dashboard and still be running, duplicated, mischarged, or unauthorized somewhere else. Our topic is multi-provider operation reconciliation: building a common control plane without erasing the provider-specific facts needed for safety, reliability, and accountability.

Start with the problem that every team eventually meets. A user asks an agent to summarize a document and save the result. The client creates one operation. The gateway routes the prompt to a reasoning model, sends a tool call to a document service, retries a timed-out inference through a second provider, and streams partial output back to the application. The first provider says request accepted. The gateway sees a timeout. The second provider returns a result. The billing system records two attempts. The tool service reports one successful read. The client receives a response but disconnects before the final event. If an operator asks whether the operation succeeded, there is no single honest answer until these observations are connected.

The first design decision is to define the logical operation separately from its attempts. A logical operation represents the user or workflow intent. An attempt represents one execution against one provider or internal subsystem. A provider request is a further external identity attached to an attempt. Keep these levels distinct. The logical operation should have a stable operation ID, tenant, actor, purpose, policy context, and intended side effects. Each attempt should carry the parent operation ID, attempt number, route, provider account, model, region, and authority digest. The provider request ID belongs to the provider, but it must be recorded as an observed identifier rather than treated as the universal identity.

Use a canonical operation envelope at every boundary. It should include operation ID, workflow ID, step ID, tenant, principal, client request ID, parent operation ID, attempt ID, provider request ID when known, semantic operation type, data classification, policy version, authority version, idempotency key, deadline, and trace context. Do not place raw prompts or documents in the envelope. Carry references, hashes, and classifications instead. The envelope gives systems enough lineage to reconcile decisions and effects without turning every queue and log into a copy of customer data.

Canonicalization is essential. Different providers call the same concept by different names. One says queued, another says processing, another says in progress. One reports input tokens, another reports prompt units. One returns a refusal, another returns a safety finish reason. Normalize these observations into a small internal vocabulary, but preserve the native value alongside it. A canonical state might be created, admitted, dispatched, accepted, running, streaming, succeeded, failed, canceled, rejected, expired, unknown, or superseded. The normalized state supports control-plane decisions. The native state supports investigation and provider-specific handling. Never discard the original evidence merely because a mapper produced a convenient label.

Separate observed state from derived state. Observed state is what a provider or subsystem explicitly reported at a point in time. Derived state is what the control plane infers from several observations. For example, an HTTP timeout is an observation that the gateway did not receive a response in time. It is not proof that the provider did not execute the request. “Effect unknown” is a derived state that correctly preserves uncertainty. Store the source, timestamp, confidence, and rule that produced every derived conclusion. This prevents a dashboard label such as failed from quietly becoming the basis for an unsafe retry.

Build reconciliation around an append-only operation ledger. Each material event should record operation ID, attempt ID, source system, event type, provider, native status, canonical status, event time, received time, sequence or version, evidence reference, and integrity metadata. Events might include admitted, policy checked, dispatched, provider accepted, first token received, tool requested, tool completed, usage reported, charge posted, client disconnected, cancellation sent, or result delivered. The ledger is not necessarily every debug log. It is the smallest durable set of facts needed to reconstruct authority, execution, outcome, cost, and delivery.

Event time and receipt time answer different questions. A provider may tell us at 12:01 that a job completed at 11:59. A webhook may arrive after a retry has already started. Store both. Account for clock skew and delayed delivery. Do not order events solely by local arrival time. Use provider sequence numbers when available, otherwise use a monotonic gateway sequence and retain uncertainty about cross-system ordering. A reconciliation engine should be able to say that two facts are concurrent or that their order is unknown instead of inventing a precise timeline from unreliable clocks.

Correlation is not enough; define causality. A trace ID can connect spans, but it does not explain which attempt was a replacement, which provider call was a retry, or which tool side effect was authorized by which decision. Model causal links explicitly: spawned-by, retried-from, fallback-for, canceled-by, compensates, reports-usage-for, delivers-result-for, and depends-on. A fallback attempt should never be mistaken for an independent user request. A compensation should not be counted as a second business operation. Causal edges make graphs useful for both incident analysis and billing reconciliation.

Provider routing must preserve the contract, not just select an endpoint. Before creating an attempt, record the route decision: required capability, policy constraints, data residency, model family, provider account, price class, deadline budget, and fallback eligibility. When a fallback happens, compare the actual provider capability with the original contract. A cheaper or available endpoint may still be incompatible with structured output, tool calling, context length, region, or safety requirements. Reconciliation should verify not only that some provider answered, but that the answer came from a route allowed to answer this operation.

The control plane needs a state machine for the logical operation and a separate state machine for each attempt. The logical operation may be partially succeeded even when no single attempt has a clean success. A streaming response can be delivered to the client while the provider remains uncertain about final completion. A tool step can succeed while the overall workflow fails later. Avoid forcing every complex lifecycle into one terminal boolean. Use dimensions such as execution status, delivery status, side-effect status, usage status, and authority status. An operation may be execution-complete, delivery-partial, side-effect-confirmed, usage-pending, and authority-valid at the same time.

This multidimensional model is more accurate than a single status, but it needs clear terminal rules. Define what “done” means for each dimension. Execution may be terminal when the provider reports completion or the gateway has a sufficient failure proof. Delivery may be terminal when the client acknowledges the final response or the delivery deadline expires. Side effects may be terminal only when the tool or provider confirms commit, cancellation, or a bounded unknown. Usage may remain open until a final usage event or a reconciliation window closes. Authority may be closed immediately after expiry even if other dimensions remain unresolved. A single operation-level status should summarize these dimensions and link to the unresolved facts.

Retries are where reconciliation most often fails. A transport timeout creates ambiguity. The provider may have completed the request, or it may never have received it. Before creating a retry, consult the original attempt’s idempotency key, provider guarantees, and current policy. If the operation is read-only and the result can be compared safely, a retry may be acceptable. If the operation can trigger a tool call or billable generation, require stronger evidence or route the retry through an idempotent adapter. Record the decision that allowed the retry and link the new attempt to the uncertain original. Never hide duplicate attempts behind a friendly operation ID.

Idempotency needs provider-aware scope. A gateway-wide key may not be recognized by a provider. A provider-specific key may not survive a fallback. Derive a stable logical idempotency key from operation, step, and canonical arguments, then derive provider-specific keys without losing the parent relationship. If a provider cannot support idempotency, the gateway must decide whether to prohibit retries, use a deduplication layer, or classify the operation as at-risk. The control plane should expose this limitation to operators instead of reporting a clean retry success that may have duplicated an external effect.

Reconcile usage and cost independently from execution. Providers may emit estimated usage, final usage, delayed usage, or no usage at all. One provider may count cached input tokens; another may not. Some bill by image, second, character, or tool execution. Store raw provider usage, the pricing version used, currency, discounts, account, and whether the amount is estimated or final. Convert to a canonical usage view only with a versioned mapping. A zero-cost record can mean free service, missing usage, failed billing ingestion, or a provider that reports later. Do not use missing cost as proof that no provider work happened.

Create a reconciliation window for late facts. An operation can be delivered to the client while usage, provider status, and tool evidence are still pending. Mark the operation operationally complete if appropriate, but leave the accounting and evidence dimensions open. Schedule follow-up reconciliation with a deadline and owner. When a late event arrives, update the derived view without rewriting history. If a late provider completion conflicts with a fallback success, preserve both attempts and determine whether the client-visible result, bill, or side effect needs correction.

Billing reconciliation requires invariants. The sum of provider charges should be explainable by attempts and pricing versions. Gateway markup or discounts should be derived from explicit rules. A customer should not be charged twice because a timeout caused a fallback, unless both attempts were actually billable and the contract permits it. Conversely, a provider charge should not disappear because the client disconnected. Track charge state as estimated, posted, disputed, adjusted, waived, or unknown. Link every adjustment to evidence and an accountable rule. Finance needs a stable ledger, not a dashboard that changes when a provider finally sends a webhook.

Privacy and data residency must travel through the operation graph. A fallback provider in another region is not merely a reliability choice; it may change whether the request is allowed. The route decision must bind tenant residency, data class, consent, and provider contract to every attempt. During reconciliation, check that actual provider and region match the approved constraints. If a provider reports a different region than expected, treat it as a policy incident even if the model result is excellent. Keep content access metadata-first and reveal payloads only under a separate, purpose-bound authorization.

Provider identity can be surprisingly complex. One vendor may expose multiple accounts, projects, regions, and quota pools under one model name. Record the provider account and contract selected before dispatch. This matters for data processing terms, rate limits, pricing, and incident response. If the provider silently routes internally, capture the most specific identity it exposes and label the remaining part unknown. “GPT-like model” is not an adequate attestation for a security or billing investigation. Reconciliation should answer which contract and account accepted the work.

Security policy must be reconciled at every attempt, not just at the logical operation. An operation that was authorized for provider A may not be authorized for provider B. A fallback may need a fresh data-classification check. A tool result may cause a later write that needs a new decision. Carry the authority digest into the ledger and compare it when attempts are created. If policy changes during a long-running operation, decide whether continuation is allowed, whether the next attempt requires reauthorization, and whether already-produced output may still be delivered. Reconciliation should expose policy drift rather than assuming the first allow governs the entire graph.

Cancellation is another multidimensional fact. The gateway may send a cancel request, the provider may acknowledge it, the worker may stop polling, and the client may still receive buffered tokens. Record cancellation intent, dispatch, provider acknowledgment, observed termination, and delivery behavior separately. A canceled request is not necessarily a deleted request. If the provider cannot cancel, classify the attempt as cancellation-unsupported and continue tracking its outcome. For sensitive operations, compensate or quarantine downstream effects rather than trusting a cancellation button that controls only the local worker.

Tool calls need operation-level reconciliation with strict boundary semantics. A model may propose a tool call, the gateway may approve it, the adapter may dispatch it, and the tool may return an uncertain result. The tool call must have its own step and idempotency identity, linked to the model attempt but not hidden inside its text. A provider retry should not automatically repeat the tool side effect. The final model answer should state when it relied on an unknown tool outcome. This keeps the logical conversation useful without pretending that an unverified external action completed.

Make the reconciler deterministic and repeatable. It should consume the same ledger and produce the same derived state, subject to explicitly versioned provider facts and policy rules. Use compare-and-set updates, monotonic sequence numbers, and idempotent event ingestion. Duplicate webhooks should not create duplicate charges or state transitions. Out-of-order events should be stored first and interpreted when prerequisites arrive. If a mapping rule changes, do not silently rewrite prior conclusions; run a new reconciliation version and retain the old result for audit.

Distributed control planes need convergence safeguards. Multiple regions may receive the same provider webhook. A billing service may reconcile an attempt before the gateway region that created it is reachable. Use a globally unique event ID, source sequence, and conflict policy. Prefer the stricter safety outcome when facts conflict about authorization or cancellation. For cost, preserve both values and mark the discrepancy. For provider status, retain native observations and derive a conservative state. A green regional dashboard must not hide a red fact that another region has already received.

Design explicit conflict classes. Some conflicts are harmless duplicates. Some are semantic differences that can be normalized. Some indicate provider inconsistency, clock skew, compromised telemetry, or a real policy violation. The reconciler should classify conflicts, assign severity, and create an investigation record for high-impact cases. Do not resolve every conflict by “last write wins.” Last arrival is a transport property, not a truth property. When evidence cannot establish the answer, keep the answer unknown and assign an owner.

Observability should serve reconciliation rather than overwhelm it. Provide an operation view with a compact timeline, attempt graph, provider identities, authority facts, delivery status, side effects, usage, cost, and unresolved items. Let operators expand into native provider details without losing the canonical view. Offer queries such as “show all attempts that may have executed after revocation,” “find charges without final usage,” “find tool effects with unknown outcomes,” and “find fallbacks that crossed a residency boundary.” These are control questions, not merely performance questions.

Measure reconciliation quality. Track time from provider event to ingestion, percentage of operations with complete attempt lineage, unknown attempts older than the threshold, duplicate side effects prevented, late usage events, unexplainable charges, fallback contract violations, cancellation confirmation rate, and cross-region convergence time. Break down by provider and operation type. A system can have excellent latency and terrible truthfulness. If operators cannot tell what happened after a timeout, the gateway is not reliable in the operational sense.

Test adversarial sequences. Send a provider success after the gateway starts a fallback. Deliver duplicate and out-of-order webhooks. Drop the final streaming event. Change policy between attempts. Return usage for an unknown request ID. Report a provider region that does not match the route. Crash the reconciler after recording a charge but before updating the operation. Run two regions against the same event. Make a tool call complete after the parent model attempt is canceled. Verify that the system preserves lineage, avoids duplicate billing, blocks unauthorized continuation, and labels uncertainty rather than guessing.

Run synthetic end-to-end operations through every important provider route. Use harmless data and low-cost models. Exercise normal completion, timeout, fallback, cancellation, tool use, streaming disconnect, delayed usage, and provider outage. Compare the client-visible result, provider records, gateway ledger, billing ledger, and policy events. The goal is not just to confirm that requests work. It is to prove that the organization can reconstruct one operation across all systems and take the right action when those systems disagree.

There is a temptation to build a universal provider abstraction that makes every backend look identical. Resist that temptation. Common semantics are useful for routing, policy, dashboards, and reconciliation, but provider differences are evidence. Preserve native statuses, limits, error codes, usage fields, cancellation behavior, and contract identifiers. The control plane should make differences legible, not flatten them into a misleading lowest common denominator. A provider that cannot cancel, cannot guarantee idempotency, or reports usage late is still usable in some contexts, but the route policy must know the cost of that limitation.

The deeper lesson is that a multi-provider gateway is not merely a proxy. It is a distributed accounting and authority system. It must reconcile intent with attempts, attempts with provider facts, provider facts with side effects, side effects with delivery, and all of them with usage, cost, and policy. The common control plane is valuable because it creates one place to reason about the operation. It is trustworthy only when it keeps enough detail to explain where its conclusions came from and what remains uncertain.
